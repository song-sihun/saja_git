## 1. 지난 학습 내용 복습: 웹 요청 처리의 흐름과 Filter 기술

*   **Spring Security와 필터(Filter):** 스프링 시큐리티는 서블릿 API에서 제공하는 '필터' 기술을 사용하여 인증/인가 처리를 수행합니다.
*   **요청 처리 과정:** 웹 애플리케이션이 요청을 받으면 (Servlet API 사용), 요청이 도착하기 전에 여러 개의 필터를 순차적으로 거치게 됩니다.
    1.  **서블릿 API의 구성 요소:** 서블릿 API는 크게 Servlet, Filter, Listener 세 가지 기술로 나뉩니다.
    2.  **필터의 역할:** 필터는 실제 요청이 들어올 때(요청 전) 해당 필터들을 거쳐 수행되며, 처리가 끝난 후에도 작동할 수 있습니다.
    3.  **핵심 동작 원리:** 필터 체인(Filter Chain)을 통해 여러 필터가 일련의 과정을 형성하며 순차적으로 요청을 가로채고 처리합니다.
*   **필터 등록 방식 (Annotation vs. Bean):**
    *   `@WebFilter`와 같은 어노테이션을 사용해 등록할 수 있으며, 이 경우 웹 애플리케이션 서버가 필터를 동작시킵니다.
    *   하지만 설정이 복잡하거나 여러 패키지에 분산된 필터들을 관리할 때는, `@Autowired` 등으로 **빈(Bean) 자체를 직접 등록**하는 방식(DI/IoC 원리)이 기본적이고 유연합니다.
    *   필터를 설정할 때 필요한 정보로는 URL 패턴 매칭(`urlPatterns`)과 실행 순서 지정 등이 있습니다.

## 2. 스레드 로컬(ThreadLocal) 이해 및 필요성

*   **필요성의 배경 (스레드의 특성):** 웹 서버는 요청이 들어올 때마다 별도의 스레드(Thread)를 할당하여 요청을 처리합니다. 하나의 요청 전체가 시작부터 끝까지 이 단일 스레드를 이용해 동작합니다.
*   **문제 제기:** 필터나 기타 과정에서 특정 사용자 정보(예: 로그인한 유저 ID)와 같은 값들을 저장할 때, 여러 단계의 호출(Filter $\rightarrow$ Controller $\rightarrow$ Service)을 거치면서도 이 정보를 유지해야 합니다.
*   **ThreadLocal의 해결책:** `ThreadLocal`은 **특정 스레드 영역에만 값을 저장**할 수 있도록 제공하는 메커니즘입니다.
    *   이 덕분에 여러 컴포넌트(필터, 서비스 등)가 동일한 메모리 공간을 참조하더라도, 각 요청(즉, 각 스레드)별로 격리된 데이터를 안전하게 사용할 수 있습니다.
*   **안전성 문제 (Thread Pool):** 실제 웹 애플리케이션은 스레드 풀(ThreadPool)을 사용하여 스레드를 재사용합니다. 따라서 `ThreadLocal`에 저장한 데이터는 **요청 처리가 끝날 때 반드시 명시적으로 제거(Clear)**해주어야 합니다.
    *   만약 이 클리어 과정이 생략되면, 다음 사용자가 다른 요청으로 접근할 때 이전 요청의 데이터가 남아 충돌을 일으키는 보안 문제가 발생합니다 (정보 누수).

## 3. Spring Security의 원리와 동작 방식 (인증/인가 포함)

*   **Spring Security의 역할:** 외부에서 들어오는 모든 사용자 요청에 대해, 이 사용자가 **'누구인지(인증)'**와 **'무엇을 할 권한이 있는지(인가)'**를 확인하는 보안 계층 역할을 합니다.
    *   **(비유):** 인증은 출입문에서 "당신이 사원입니까?"를 묻는 것이고, 인가는 "사원이라도 이 방에 들어갈 수 있습니까?"를 체크하는 과정입니다.
*   **동작 구조:** Spring Security 모듈을 추가하기만 해도 기본 설정(Default Configuration)이 작동합니다.
    *   이는 내부적으로 **Security Filter Chain**이라는 필터 체인 객체를 구성하여 모든 요청이 이 보안 장치들을 거쳐가게 만듭니다.
    *   개발자는 `HttpSecurity` 등의 설정을 통해 어떤 URL에 인증을 적용할지, 기본 사용자 정보(ID/PW)는 무엇으로 할지 등을 세부적으로 설정합니다.

## 4. 결론 및 학습 태도 조언

*   **학습 방법론의 중요성:** 기술적인 내용 자체보다, **이러한 기초 지식들(자바 문법, 필터 구조, 스레드 개념 등)이 웹 프레임워크 내부에서 어떻게 사용되고 있는지 그 '흐름'을 이해하는 것**이 가장 중요합니다.
*   **회고 활동의 적극적 활용:** 강의 내용을 단순히 듣는 것으로 끝내지 않고, "내가 이 개념(예: ThreadLocal)을 다른 코드로 구현해 본다"와 같이 **스스로 설명하고 재현해보는 '회고 활동'**이 지식을 내재화하는 데 필수적입니다.
*   **복습의 중요성:** 기초가 튼튼하지 않으면 어려운 최신 기술도 어려워지므로, 현재 배우는 내용을 이해하기 위해 필요하다고 느껴지는 자바 기본기를 반복적으로 복습하고 활용해보는 과정이 권장됩니다.

## 1. Spring Boot와 WAS 환경 이해 및 스레드 관리
*   **WAS 내장 방식의 변화:** 과거에는 WAR 파일을 외부 WAS(Web Application Server)에 직접 배포했지만, 현재 Spring Boot는 WAS를 내장하고 있어 스프링처럼 설정과 관리가 편리해졌다.
*   **요청 처리와 쓰레드:** WAS는 들어오는 요청 하나하나를 처리하기 위해 스레드를 사용한다. 따라서 서버가 시작될 때 스레드를 충분히 미리 확보(Pool)하는 것이 중요하다.
*   **성능 최적화:** 애플리케이션의 예상 성능과 용량에 맞춰 최소(Min)와 최대(Max) 스레드 수를 적절하게 설정해야 한다. 요청이 들어올 때마다 스레드를 새로 생성하면 자원 소모가 크고, 이로 인해 사용자 체감이 느려질 수 있다.
*   **스레드 로컬 (ThreadLocal):** 웹 애플리케이션 서버는 사용자가 요청할 때마다 독립적인 하나의 스레드를 할당하여 처리한다. 이는 메인 메서드가 끝날 때까지 동작하는 단일 흐름과 유사하며, 각 요청은 자체 쓰레드 내에서 모든 처리가 이루어지게 된다.

## 2. Spring Security의 개요 및 핵심 기능
*   **정의 및 역할:** 스프링 시큐리티는 Java 기반 웹 애플리케이션의 인증(Authentication)과 권한 부여(Authorization)를 담당하는 강력하고 포괄적인 보안 프레임워크다.
*   **핵심 원칙:** 모듈화, 확장성, 선언적 보안 설정에 기반을 두고 개발자에게 유연성을 제공한다.
*   **주요 기능:**
    *   **인증 (Authentication):** 사용자의 신원을 확인하는 과정이다. (예: ID/Password를 통한 로그인) 다양한 인증 메커니즘(폼, HTTP Basic 등)을 지원한다.
    *   **권한 부여 (Authorization):** 사용자에게 특정 자원 또는 기능에 접근할 권한이 있는지 확인하는 과정이다. 역할 기반 접근 제어(RBAC) 등을 포함한다.
    *   **세션 관리:** 사용자의 세션을 생성하고 유지하며 보안성을 높인다.
    *   **로깅 및 감사 (Logging):** 로그인 시도 실패/성공 등 중요한 이벤트에 대한 로그를 남겨 보안 감사를 돕는다.

## 3. Spring Security의 동작 원리: 필터 체인(Filter Chain) 메커니즘
*   **서블릿 컨테이너와 WAS:** 웹 요청은 서블릿 API 기반으로 처리되며, WAS는 필터 체인(Filter Chain)을 통해 여러 단계의 처리를 수행한다.
*   **필터란?** 필터는 클라이언트가 애플리케이션에 요청을 보낼 때, 서버가 실제로 내부 로직을 실행하기 전에 중간에서 개입하여 특정 작업을 처리할 수 있게 해주는 객체다 (예: 인코딩 처리, 보안 검증 등).
*   **Spring의 구현 방식 (핵심):**
    *   스프링은 일반 서블릿 컨테이너와 연동되는 과정이 매우 복잡하지만, 이를 **`DelegatingFilterProxy`**라는 특별한 필터를 이용해 간소화한다.
    *   이 프록시 패턴 덕분에 Spring의 애플리케이션 빈(Bean)으로 정의된 보안 로직들이 마치 WAS 레벨에서 동작하는 것처럼 쉽게 통합되어 작동할 수 있다.
    *   이렇게 되면 개발자는 서버 컨테이너에 직접 필터를 등록할 필요 없이, 스프링 설정만 통해 강력한 보안 기능을 활용할 수 있게 된다.

## 4. 주요 보안 위협 방어 기법: CSRF (Cross-Site Request Forgery)
*   **CSRF 공격의 개념:** 인증된 사용자가 웹사이트에 로그인한 상태일 때, 악의적인 제3자가 가짜 요청(예: 출금 페이지 링크)을 만들어 사용자 브라우저의 쿠키를 이용해 서버로 전송하여 원치 않는 작업을 수행하도록 유도하는 공격이다.
*   **CSRF 방어 방법:** 웹사이트가 **Anti-CSRF 토큰**을 사용한다. 이 토큰은 서버(웹페이지 폼)가 생성하여 사용자 브라우저에 숨겨진 필드 값으로 전달하며, 요청이 들어올 때마다 클라이언트가 반드시 해당 토큰 값을 포함해야 한다.
*   **작동 원리:** 서버는 요청에 담긴 토큰 값이 자신이 원래 제공한 토큰과 일치하는지 비교 검증한다. 악의적인 사용자는 이 토큰 값(랜덤 문자열)을 알 수 없기 때문에, CSRF 공격은 차단된다.

## 5. 실제 구현 흐름: 인증, 실패 처리, 성공 핸들러
*   **폼 기반 로그인 설정:** 스프링 시큐리티에서 폼 기반 로그인을 설정하면, 필요한 기본 필터(CSRF 토큰 등)가 자동으로 동작하며 보안 검증을 수행한다.
*   **로그인 실패 처리:** 사용자가 비밀번호 등을 잘못 입력하여 로그인이 실패할 경우, 개발자는 `failureUrl` 설정을 통해 기본 페이지로 돌아가지 않고 커스텀 오류 페이지나 로직으로 이동하도록 지정할 수 있다.
*   **성공 핸들러 활용 (SuccessHandler):** 로그인에 성공한 후 (`Authentication` 객체 획득), 단순히 리다이렉트(Redirect)만 하는 것이 아니라, `SuccessHandler`를 구현하여 **로그 기록, 알림 전송 등 성공했을 때 추가적으로 수행해야 할 비즈니스 로직**을 실행할 수 있다.
*   **보안의 중요성:** 개발자는 CSRF 토큰 사용은 필수적이며, 운영 환경에서는 보안이 취약한 설정을 절대 기본값으로 남겨두어서는 안 된다.

## 1. CSRF 토큰 처리 및 보안 설정 관리
- **문제 발생 배경:** 로그인 요청 시 CSRF(Cross-Site Request Forgery) 토큰을 사용해야 하지만, `Security` 설정에서 이 기능을 `disabled`로 설정했기 때문에 토큰 생성이 불가능하여 오류가 발생함.
- **해결 방안:** 보안 설정을 하거나 (CSRF 활성화) 또는 해당 설정을 제거/주석 처리하여 서비스 로직에 맞게 동작을 재정의해야 함.

## 2. 인증 핸들러(Success/Failure Handler) 활용
- **목적:** 로그인 성공 및 실패 시 추가적인 비즈니스 로직 (예: 로깅, 데이터 취합 등)을 구현하기 위해 제공되는 기능임.
- **`SuccessHandler` (로그인 성공 처리):**
    - 사용자가 인증에 성공했을 때 실행되는 핸들러를 지정할 수 있음.
    - 이 핸들러 내에서 요청(`Request`)과 응답(`Response`) 객체에 접근하여 다양한 작업을 수행 가능함 (예: 커스텀 리다이렉트, 알림 메시지 전송).
    - 인증된 사용자 정보(Authentication)는 `SecurityContext`를 통해 얻을 수 있으며, 이 정보를 이용해 사용자 ID 등 필요한 값을 추출할 수 있음.
- **`FailureHandler` (로그인 실패 처리):**
    - 로그인이 실패했을 때 실행되는 핸들러가 존재함.
    - 요청 예외(`Exception`) 객체를 받아 처리할 수 있으므로, "특정 시점에 로그인에 실패했다"는 기록을 남기는 등 커스텀 로깅 처리가 가능함.

## 3. 로그아웃 메커니즘과 세션 정리
- **로그아웃 핸들러 (Logout Handler):** 로그아웃 과정에서 필요한 추가적인 작업을 수행할 수 있도록 지원하는 기능임.
    - `logout` URL에 대한 별도의 설정이 필요하며, Spring Security가 기본적인 설정을 제공함.
    - `SuccessHandler`와 유사하게, `Authentication` 객체, `HttpServletRequest`, `HttpServletResponse` 등을 인자로 받아 로직을 구현할 수 있음.
- **세션 및 쿠키 정리 (Cleanup):** 로그아웃 시 단순히 인증만 무효화하는 것을 넘어, 사용자 경험(UX) 측면에서 추가적인 데이터 정리가 필요함.
    - **권한 정책 정의:** 세션에 남아있는 장바구니 정보 등 사용자가 쇼핑을 했거나 저장해둔 정보들을 완전히 지울지 여부에 대한 정책을 결정해야 함.
    - **실제 구현:** `Session` 객체나 특정 쿠키(예: J-SessionID)를 직접 무효화하거나 삭제하는 코드를 추가하여 필요한 데이터를 깨끗하게 정리할 수 있음.

## 4. 고급 보안 기능 (Remember Me) 설정
- **기능 설명:** 사용자에게 '로그인 상태 유지' 기능을 제공하며, 웹 애플리케이션에서 자주 사용하는 기능이므로 반드시 이해해야 함.
- **구현 방식:** `Security` 설정 클래스에 해당 기능을 활성화하고 토큰 검증 기간 등을 지정할 수 있음.
- **작동 원리:** 클라이언트가 'Remember Me' 체크박스를 통해 동의하면, 보안 필터가 내부적으로 이 기능을 처리하며 CSRF 같은 기본적인 보안 설정을 함께 동작시킴.

## 3. 사용자 인증 시스템 구축: UserDetailsService와 비밀번호 암호화
- **UserDetailsService 구현 필요성:** Spring Security는 사용자를 인증하기 위해 특정 객체 형태(UserDetails)를 기대한다. 따라서 자체적으로 `UserDetailsService` 인터페이스를 구현해야 한다. (실제로는 이 서비스를 통해 DB에서 가져온 사용자 정보를 해당 형태로 가공하여 반환).
- **비밀번호 암호화의 중요성:** 비밀번호는 절대 평문으로 저장되어서는 안 되며, 반드시 해시(Hashing) 알고리즘을 사용하여 암호화되어야 한다. (가장 안전한 보안은 관리자도 알 수 없는 형태임.)
- **PasswordEncoder 사용 필수:** 로그인을 시도하거나 UserDetails를 생성할 때, 비밀번호는 반드시 `PasswordEncoder` 인터페이스 구현체(예: `BCryptPasswordEncoder`)를 사용하여 인코딩해야 한다. 이렇게 해야 암호화된 값끼리 일치 여부를 비교할 수 있다.
- **임시 사용자 데이터 등록:** 개발 단계에서는 `InMemoryUserDetailsManager`를 이용하여 임의의 유저, 비밀번호, 권한을 설정하여 테스트한다. (실제 운영 시에는 이를 DB와 연동하는 로직으로 교체해야 한다.)

## 4. 권한 기반 접근 제어(Authorization) 설정 및 테스트
- **URL 패턴 매칭 및 역할 부여:** `WebSecurityConfigurerAdapter` 설정을 통해 특정 URL에 접근할 때 필요한 최소 권한(Role)을 지정한다.
    *   **권한의 명시적 사용:** 예를 들어, `/user/abc` 경로에는 'USER'와 'ADMIN' 권한이 모두 필요하다고 설정하여 제어할 수 있다.
- **URL 패턴 규칙 이해:**
    *   `/**`: 모든 하위 URL에 접근 가능함을 의미한다. (예: Admin의 모든 페이지 접근 허용)
    *   `/*`: 한 단계 아래의 디렉토리까지를 포함하는 더 구체적인 매칭이다.
- **세분화된 권한 제어:** 특정 경로(예: `/admin/**`)에 대해서는 'ADMIN' 권한이 있어야만 접근할 수 있도록 제한할 수 있다.
- **접근 테스트와 오류 코드 이해:**
    *   **403 Forbidden (권한 없음):** 해당 페이지가 존재하지만, 현재 사용자가 접근할 권한(Role)이 없을 때 발생하는 오류이다.
    *   **404 Not Found (페이지 없음):** 요청된 URL 자체가 애플리케이션에 정의되어 있지 않을 때 발생하는 오류이다.

## 1. 로그인 성공 시 페이지 이동 설정 및 디버깅 (14:01 ~ 14:06)
- **로그인 오류의 원인 파악:** 실제로 로그인이 안 된 것이 아니라, 인증 과정은 완료되었으나 지정된 다음 요청 URL(Success Page)이 없어서 발생한 문제일 수 있습니다.
- **`success url` 설정:** 로그인 폼 처리 시 성공했을 때 이동할 기본 페이지를 `success url`을 통해 명확히 지정해야 합니다. (예: 홈 컨트롤러의 `/hello`)
- **설정 확인 및 테스트:** 이 설정을 변경하고 재로그인 과정을 반복하며, 각 유형의 유저(슈퍼유저 등)가 정확하게 지정된 성공 경로로 이동하는지 테스트해야 합니다.

## 2. Spring Security 작동 원리 이해 (14:07 ~ 14:32)
- **권한 관리와 접근 제어:** `Permit All` 설정은 이미지나 정적(Static) 리소스처럼 권한 검사 없이 모든 사용자에게 접근을 허용하는 용도로 사용됩니다.
- **보안 필터 체인 (Filter Chain):** 요청이 들어오면 여러 보안 컴포넌트가 순차적으로 동작합니다. (예: `SecurityContextHolder Filter`, `UsernamePasswordAuthentication Filter`). 이 과정에서 요청에 대한 인증 및 권한 검사가 이루어집니다.
- **`SecurityContextHolder`의 역할:** 사용자 관련 정보는 최종적으로 `SecurityContextHolder`라는 곳에 저장됩니다. 이는 현재 스레드(ThreadLocal)를 기반으로 하기 때문에, 웹 애플리케이션의 어느 지점에서든 (Controller, Service, Repository 등) 접근하여 사용자 정보를 가져올 수 있습니다.
- **주요 인증 객체:** 보안 과정에서 사용되는 핵심 용어들을 이해해야 합니다:
    *   **`UserDetails`**: 데이터베이스에 저장된 유저의 상세 정보(이름, 비밀번호 해시값, 활성화 여부 등)를 담고 있는 객체의 추상화된 형태입니다.
    *   **`Authentication`**: 인증이 완료된 사용자 정보를 감싸는 역할을 합니다. 이 내부에는 `UserDetails`가 포함됩니다.

## 3. 보안 정보를 코드에서 활용하는 방법 (14:23 ~ 14:31)
- **정보 추출의 위치 불문:** 로그인 정보는 어디서든 접근할 수 있도록 저장되므로, Controller는 물론 Service 레이어나 다른 비즈니스 로직에서도 사용자 정보를 가져와 사용할 수 있습니다.
- **Annotation 활용 (가장 간편한 방법):** `@AuthenticationPrincipal` 같은 Annotation을 이용하면 해당 요청을 처리하는 메서드 매개변수에서 인증된 사용자(`UserDetails`) 객체를 가장 쉽고 명확하게 추출할 수 있습니다.
    *   *(예시: `Authentication @AuthenticationPrincipal userDetails`)*
- **직접 접근 (ContextHolder 사용):** 반드시 Annotation이 아닌 순수한 Java 코드로 정보에 접근해야 할 경우, `SecurityContextHolder.getContext().getAuthentication()`을 사용하여 저장된 객체에 직접 접근할 수 있습니다.

## 4. Thymeleaf를 이용한 프론트엔드 정보 연동 (14:35 ~ 14:47)
- **기술 스택 통합:** Spring Security가 관리하는 인증 정보를 View 레이어(Thymeleaf/JSP 등)에서도 출력하고 사용하려면 별도의 작업이 필요합니다.
- **의존성 추가 필수:** Thymeleaf에서 보안 네임스페이스를 사용하기 위해서는 반드시 관련 라이브러리 의존성을 프로젝트에 추가해야 합니다. (예: Gradle 빌드 파일 수정)
- **`sec:` Namespace 활용:** Thymeleaf 템플릿 내부에서는 `th:with sec:`와 같은 전용 네임스페이스(`Namespace`)을 사용하여 인증 정보를 가져옵니다.
    *   **활용 예시:** `${sec:authentication.name}`과 같이 사용하면 현재 로그인한 사용자의 이름이나 권한 목록(Authorities) 등을 출력할 수 있습니다.

## 5. 핵심 용어 정리 및 다음 학습 과제 (14:48 ~ )
- **핵심 개념 복습:** `Authentication`, `UserDetails`, `SecurityContextHolder` 등의 추상적인 객체와 그들의 역할을 이해하는 것이 중요합니다.
- **로그인되지 않은 사용자 처리 (`AnonymousUser`):** 보안 시스템은 요청이 들어올 때 기본적으로 '익명 사용자(Anonymous User)'를 생성하고 컨텍스트에 넣어두는 경우가 많습니다. 따라서 실제 유저가 익명 사용자인지 여부를 확인하는 로직을 추가하여, 적절한 예외 처리나 안내가 가능해야 합니다.
- **다음 학습 목표:** 현재까지 배운 개념들을 기반으로, 사용자 정보를 데이터베이스에서 불러와 인증시키는 커스텀 구현(예: `UserDetailsService` 직접 구현) 단계로 나아가야 합니다.

## 1. 고급 인증 및 권한 관리 이해 (Authorization)
*   **권한 기반 접근 제어 (ACL):** 단순 사용자 여부를 넘어, 사용자가 특정 페이지나 리소스에 접근할 수 있는 권한을 매우 상세하게 설정하고 제어할 수 있습니다.
*   **사용자 관리 서비스:** 사용자 정보 관리를 담당하는 `UserDetailsService`와 같은 개념의 서비스를 구현하여 데이터베이스의 실제 사용자 정보를 이용합니다.
*   **핵심 객체 흐름 이해:**
    *   인증된 사용자의 정보는 `Security Context Holder`를 통해 저장됩니다.
    *   이 정보를 꺼낼 때는 추상화된 `Authentication` 객체를 얻게 되며, 여기서 최종적으로 사용자의 상세 정보(`Principal`)를 추출합니다.
    *   직접 데이터를 가져오는 것이 번거로울 경우 `@AuthenticationPrincipal` 등의 어노테이션을 사용하여 편리하게 구현할 수 있습니다.
*   **프론트엔드 연동:** Thymeleaf 같은 템플릿 엔진의 네임스페이스 기능을 활용하여 인증된 사용자 정보(예: 사용자 이름)를 화면단에서 쉽게 가져와 사용할 수 있습니다.

## 2. 데이터 모델 설계: User와 Role의 관계 설정
*   **테이블 구조 정의:** 사용자는 `User` 엔티티로, 권한은 `Role` 엔티티로 분리하여 설계합니다. (엔티티 이름: `User`, `Role`)
*   **관계 매핑 전략 (Many-to-Many):** 하나의 사용자가 여러 개의 역할을 가질 수 있으므로(다 대 다), 관계형 데이터베이스에서는 중간을 값으로 저장하는 **조인 테이블**이 필요합니다.
*   **필수 제약 조건 설정:**
    *   **`Role` 엔티티:** `roleName`은 `Null` 불가하며, 테이블 내에서 중복될 수 없도록 **Unique 제약조건**이 필수입니다.
    *   **`User` 엔티티:** `userEmail`과 같은 식별 정보는 고유해야 하므로 **Unique 제약조건**을 적용합니다.
    *   **필드 타입 및 옵션:** 비밀번호(Password) 필드는 암호화된 값을 담기 위해 충분히 큰 크기를 확보하고, 생성일/수정일(`@CreationTimestamp`, `@UpdateTimestamp`) 등의 시간 정보를 관리하는 것이 좋습니다.
*   **관계 설정 유의사항 (양방향 매핑):** 사용자 정보 조회 시 사용자의 모든 권한을 한 번에 가져오는(eager loading) 패턴이 일반적입니다. 이때, 두 엔티티 중 어느 쪽에서 반대편 정보를 가져오는 것이 더 합리적인지 신중하게 고려해야 합니다.

## 3. Repository 구현 및 커스텀 조회 방법 정의
*   **Repository 생성:** `UserRepository`와 `RoleRepository`를 각각 생성하여 JPA의 데이터 접근 계층을 분리합니다.
*   **커스텀 메서드 추가의 중요성:** 단순히 기본 키(ID)로 조회를 하는 것을 넘어, 실제 서비스 로직에서 자주 사용될 검색 기준(예: 사용자 이름(`findByUsername`), 이메일(`findByEmail`))에 맞는 메소드를 직접 정의해주는 것이 효율적입니다.
*   **Layer 분리:** Repository는 순수하게 데이터 접근만을 담당하고, 복잡한 비즈니스 규칙이나 로직은 Service 계층에서 처리합니다.

## 4. 서비스 레이어 구축 및 회원 가입 로직 구현 계획
*   **서비스/컨트롤러 구조 정의:** `UserService`를 생성하여 비즈니스 로직을 전담하도록 합니다. 컨트롤러는 필요한 데이터를 받아와 서비스를 호출하는 역할에 집중합니다.
*   **필수 구현 기능 구상:** 당장 구현할 핵심적인 기능은 다음과 같습니다.
    1.  회원가입 폼 요청 (`GET /register`)
    2.  실제 회원 가입 처리 (`POST /register` 또는 `POST /signup`)
    3.  사용자 존재 여부 확인 (중복 체크)
*   **핵심 보안 로직: 비밀번호 인코딩:** 회원가입 과정에서 사용자가 입력한 평문 비밀번호는 **반드시 서비스 계층에서 암호화(Encoding/Hashing)**하여 데이터베이스에 저장해야 합니다. 이 과정을 생략하면 나중에 로그인이 불가능합니다.
*   **향후 권한 관리 계획 (Next Step):** 현재 로직에서는 초기 가입 시 권한 설정 부분이 누락되어 있으므로, 다음 단계에서는 사용자 생성과 함께 **초기 권한(Role)**을 지정하는 로직 추가가 필요합니다.
