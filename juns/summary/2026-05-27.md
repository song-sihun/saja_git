# 강의 요약

## 목차
1. 스프링 코어 원리 복습: IOC와 DI
2. 웹 계층 이해: Spring MVC와 아키텍처
3. 상태 관리 및 요청 흐름 제어 (Session, Scope, Forward/Redirect)
4. 데이터 접근 방식 심화: JDBC부터 Spring Data까지

---

## 1. 스프링 코어 원리 복습: IOC와 DI
*   **IOC 컨테이너 (Inversion of Control):** 객체를 프로그래머가 직접 생성/소멸하는 대신, 컨테이너가 라이프사이클 전반을 관리해주는 원리입니다.
*   **DI (Dependency Injection):** 컨테이너가 객체 간의 의존성(Dependency)을 직접 주입해주는 기법입니다.
*   **빈 등록 방법:** 스프링 컨테이너에게 빈을 알려주는 방법에는 주로 세 가지가 있습니다.
    *   XML 파일을 이용한 등록.
    *   Java Config 클래스를 이용한 등록.
    *   애노테이션(Annotation)을 이용한 등록.
*   **의존성 주입 방식:** 필요한 시점에 빈을 얻어오는 방법은 크게 두 가지입니다.
    *   **Dependency Lookup:** 개발자가 직접 빈을 컨테이너에서 조회(Lookup)하여 가져오는 방식.
    *   **Dependency Injection:** 컨테이너가 필요한 빈을 자동으로 주입(Injection)해주는 방식.
*   **주입 방법 3가지:**
    *   **생성자(Constructor):** 객체 생성 시 주입.
    *   **Setter:** Setter 메서드를 통해 주입.
    *   **필드(Field):** 필드에 직접 주입 (가장 간결).

## 2. 웹 계층 이해: Spring MVC와 아키텍처
*   **Spring MVC의 역할:** 클라이언트(Client)와 서버(Server) 간의 요청(Request)과 응답(Response) 흐름을 처리하는 웹 애플리케이션의 프레임워크입니다.
*   **MVC 패턴의 도입 배경:** 웹 애플리케이션 개발이 복잡해지면서, 코드의 유지보수와 개발 분담을 위해 Model, View, Controller 세 영역을 분리하는 것이 필요했습니다.
*   **프론트 컨트롤러 (Front Controller):** 요청 처리를 중앙 집중화하여 체계적으로 관리하는 디자인 패턴으로, Spring MVC가 이 역할을 수행합니다.
*   **L-C(View) 3-T(Model) 이해:** 요청이 들어왔을 때, 흐름을 따라 요청이 처리되는 과정을 이해하는 것이 중요합니다.
*   **HTTP 상태 유지 문제 해결 (쿠키 vs. 세션):**
    *   **HTTP 프로토콜의 특징:** 기본적으로 상태를 유지하지 않는(Stateless) 프로토콜입니다.
    *   **쿠키 (Cookie):** 클라이언트(브라우저) 쪽에 저장되는 Key-Value 형태의 문자열 쌍입니다. 저장할 정보가 제한적이며, 보안에 취약하여 민감 정보(비밀번호 등)를 담는 것은 위험합니다.
    *   **세션 (Session):** 서버 쪽에 정보를 저장합니다. 서버가 사용자별 상태를 유지할 수 있어 쿠키보다 보안성이 높고, 자바 객체 등 모든 형태의 데이터를 저장할 수 있습니다.
*   **Scope (스코프) 관리:** 애플리케이션에서 데이터가 유지되는 범위를 관리하는 개념입니다.
    *   **Application Scope:** 애플리케이션 전체에 전역으로 유지되는 영역 (보통 자주 사용되지는 않음).
    *   **Request Scope:** 하나의 요청(Request)이 처리되는 동안만 유지되는 범위.
    *   **Session Scope:** 사용자가 로그인하는 동안 세션 단위로 유지되는 범위.

## 3. 요청 흐름 제어 (Forward/Redirect)
*   **Forward (포워딩):**
    *   요청이 서버 내에서 다른 내부 자원(뷰, 컨트롤러)으로 **전달**되는 방식입니다.
    *   요청이 서버 내부에서 일어나므로, 원래의 요청 객체(Request Object)를 그대로 사용할 수 있습니다.
    *   (예: 컨트롤러 → 뷰)
*   **Redirect (리다이렉트):**
    *   서버가 클라이언트에게 새로운 요청을 보내라고 **응답**하는 방식입니다.
    *   클라이언트가 완전히 새로운 요청을 보내게 되므로, 요청 객체가 완전히 새로 생성됩니다.
    *   **PRG (Post/Redirect/Get) 패턴:** POST 방식으로 데이터를 처리한 후에는 반드시 리디렉트(Redirect)를 사용하여 GET 요청으로 마무리하는 것이 좋습니다. 이는 새로고침 시 데이터 중복 전송 오류를 방지합니다.
*   **데이터 전달의 특징:**
    *   **Forwarding:** 내부적으로 흐름이 변경되므로, 요청 객체(Request)를 통해 데이터 전달이 자유롭습니다.
    *   **Redirecting:** 요청 객체가 교체되므로, 일반적인 방식으로 데이터를 유지하기 어렵습니다. 이럴 경우 **`RedirectAttributes`** 같은 객체를 사용하여 데이터를 임시로 저장하고 다음 요청에서 사용할 수 있습니다.

## 4. 데이터 접근 방식 심화: JDBC부터 Spring Data까지
*   **JDBC (Java Database Connectivity):** 자바 코드에서 데이터베이스에 접속하여 데이터를 읽고 쓰는 가장 기본적인 원시 기술입니다.
    *   **특징:** 코드량이 매우 많습니다. (커넥션 획득/해제, SQL 실행, 결과 처리, 예외 처리 등의 반복적인 **보일러플레이트 코드**가 필수적).
*   **ORM (Object-Relational Mapping)의 필요성:** 자바 객체와 관계형 데이터베이스의 테이블 구조 사이의 데이터 형식 불일치를 해결하는 개념입니다.
*   **데이터 접근 프레임워크의 등장:** JDBC의 반복적인 보일러플레이트 코드를 줄여주기 위해 다양한 프레임워크가 등장했습니다.
    *   **Spring JDBC / MyBatis:**
        *   사용자가 SQL 구문(Query)을 명시적으로 작성해주면, 이 반복되는 코드들을 프레임워크가 자동으로 생성해줍니다. (SQL 기반 접근)
    *   **JPA (Java Persistence API):**
        *   **개념:** 객체와 관계형 DB 테이블 간의 매핑 정보만 알려주면(어떤 객체가 어떤 테이블에 대응되는지), 나머지 CRUD 작업(SQL 쿼리 작성, 데이터 삽입/수정 로직 등)을 프레임워크가 알아서 처리합니다.
        *   **특징:** SQL 쿼리를 직접 작성할 필요가 없어 코드가 간결해지지만, 그만큼 높은 개념 이해(학습 곡선)가 필요합니다.
*   **Spring Data 프로젝트:**
    *   Spring이 제공하는 상위 추상화 계층입니다. Spring JDBC나 JPA 같은 저수준 기술 위에 한 겹 더 감싸는 역할을 합니다.
    *   **장점:** 개발자가 사용할 때의 사용 방법(API)을 일관되게 유지하고, 내부적으로는 각 기술(JDBC, JPA 등)의 장점을 활용하여 개발 편의성을 극대화합니다.
    *   **최종 목표:** 데이터 연동의 가장 반복적이고 지루한 코드들(연결 관리, 트랜잭션, 예외 처리, 객체 매핑 등)을 모두 프레임워크가 대신 처리하게 하여, 개발자가 비즈니스 로직에만 집중할 수 있게 합니다.

## 1. 데이터베이스 접속 및 구조 이해
- **데이터베이스 접속 방법:**
    - 가장 간단하게는 '워크벤치(Workbench)'를 열어서 사용하는 것이 편리합니다.
    - 워크벤치를 통해 접속 시, 루트 유저, 데이터베이스 목록, 유저 목록 등을 조회할 수 있습니다.
- **데이터베이스 권한 사용 원칙:**
    - 모든 기능을 통일된 유저/데이터베이스/패스워드로 관리하는 것이 좋습니다.
    - **경고:** `root` 유저는 권한이 너무 광범위하여 함부로 사용해서는 안 되며, 오히려 일반 유저를 생성하고 해당 유저에 맞게 최소한의 권한만 부여하여 사용하는 것이 보안 및 학습 관점에서 바람직합니다.
- **테이블 생성 및 구조화:**
    - 실습을 위해 `users` 테이블을 생성하는 과정을 진행했습니다.
    - **주요 컬럼 및 제약 조건 학습:**
        - **`id`**: `BIGINT` 타입으로, `AUTO_INCREMENT`를 적용하여 기본 키(Primary Key)로 사용하고, 값이 자동 증가하도록 설정합니다.
        - **`name`**: `VARCHAR` 타입의 문자열 컬럼입니다.
        - **`email`**: `VARCHAR` 타입의 문자열 컬럼으로, `UNIQUE` 제약 조건을 부여하여 중복 등록을 방지합니다.
        - **`created_at`**: `TIMESTAMP` 타입으로, 기본값(`DEFAULT`)을 `CURRENT_TIMESTAMP`로 설정하여 별도 입력 없이 시스템 시간이 자동으로 기록되도록 합니다.
    - **캐릭터셋 설정:**
        - 이모지 등의 특수 문자를 저장하려면, 테이블 생성 시 `utf-8mb4`와 같은 적절한 캐릭터셋을 지정해 주는 것이 중요합니다.

## 2. Spring JDBC를 이용한 데이터베이스 설정 (DataSource Config)
- **Spring Boot와 DB 연결의 핵심:**
    - Spring Framework는 내부적으로 JDBC를 동작하며, **데이터 소스(DataSource)**라는 객체를 이용해 **커넥션 풀(Connection Pool)**을 관리합니다.
    - 커넥션 풀을 사용하려면 `DB URL`, `Username`, `Password` 등의 연결 정보(빈 값)를 설정 파일(application.properties)에 정확히 제공해야 합니다.
- **JDBC URL 규칙 및 확장성:**
    - DB URL은 `[호스트]:[포트]:[데이터베이스 이름]` 형식의 정해진 규칙을 따릅니다.
    - **확장성 고려:** 로컬 환경이 아닌 클라우드 환경(AWS 등)이나 네트워크에 연결된 DB에 접속할 때는 실제 IP 주소를 사용해야 합니다.
    - 포트 번호가 충돌할 경우 (예: 3306 사용 불가), 포트 번호를 변경하여(`3307` 등) 설정해야 합니다.
- **로깅 레벨 설정의 중요성:**
    - 애플리케이션의 디버깅 과정에서 `logging.level` 설정을 통해 JDBC 관련 동작을 상세하게 확인(`DEBUG` 레벨)할 수 있습니다. (실제 운영 환경에서는 과도한 로깅은 지양해야 합니다.)
- **다양한 DB 유형:**
    - MySQL 외에도 H2DB 같은 데이터베이스가 존재합니다. H2DB는 메모리 DB로, 테스트용이나 간단한 개발 환경에서 매우 간편하게 사용할 수 있어 유용합니다.

## 3. 테이블 구조화 및 JPA/Entity 개념 학습
- **데이터 타입 사용 권장 사항:**
    - 기존에는 기본적인 자바 타입(Int, Long 등)을 사용했지만, JPA 엔티티 클래스를 정의할 때는 **객체 타입(예: `Long`, `Integer`)**으로 사용하는 것을 권장합니다.
    - 이는 초기값 처리나 데이터 매핑의 안정성을 높여주기 위함입니다.
- **확장성을 고려한 설계:**
    - 데이터베이스 테이블을 설계할 때, 현재 예상되는 데이터 양보다 **충분히 크게 (혹은 넓게)** 설계하는 것이 장기적인 관점에서 유리합니다.
    - 과거처럼 저장 공간 비용을 최소화하기 위해 작게 설계했다가 확장 단계에서 발생하는 비용(수정 비용)이 더 클 수 있습니다.
- **Lombok 사용법:**
    - `@Getter`, `@Setter` 같은 어노테이션을 사용하면 Getter/Setter 코드를 간편하게 생성할 수 있습니다. 다만, 단순히 추상적으로 사용하는 것보다 구체적인 구조(예: 생성자, 타입 지정)를 나타내도록 구현하는 것이 좋습니다.

## 4. Spring JDBC Template을 활용한 CRUD 구현 및 핵심 원리 정리
- **JDBC Template의 역할 (프레임워크의 가치):**
    - Spring JDBC Template은 데이터베이스 작업을 할 때 발생하는 반복적이고 번거로운 코드들(커넥션 획득, Statement 생성, 결과 맵핑, 트랜잭션 관리 등)을 **대신 처리**해 줍니다.
    - 개발자는 기본적인 SQL 쿼리와 필요한 값(Parameter)만 알려주면 됩니다.
- **Spring의 동작 원리 (핵심 개념):**
    - **Spring Framework의 가치:** 개발자는 핵심적인 비즈니스 로직에만 집중하고, 반복적인 인프라 작업은 프레임워크에 맡기는 것이 중요합니다.
    - **빈(Bean) 등록의 중요성:** 스프링 컨테이너가 기능을 수행하려면, `DataSource`와 `JdbcTemplate` 같은 필수 객체들이 반드시 **빈(Bean)**으로 등록되어야 합니다.
    - **흐름 이해:** Spring Boot가 이 복잡한 빈 등록 과정을 자동으로 처리해 주기 때문에, 개발자는 핵심 기능 구현에만 집중할 수 있게 됩니다.
- **CRUD 구현의 핵심 (질의/수정/삭제):**
    - **`INSERT` (추가):** 쿼리문에서 값을 바꿀 위치를 물음표(`?`)로 표시하고, 필요한 값들을 배열 형태로 전달하면 JDBC Template이 알아서 처리합니다.
    - **`UPDATE` (수정):** 마찬가지로 쿼리문을 정의하고 필요한 값들을 전달합니다.
    - **`DELETE` (삭제):** 삭제할 대상을 식별하는 조건을 명시하고 실행합니다.
    - **`SELECT` (조회):** 조회 시 핵심은 **"결과값을 꺼내서 어디에 담을 것인가"**를 결정하는 것입니다. (Spring JDBC는 이 결과를 자동으로 객체로 매핑해 줍니다.)
- **결론적 이해:**
    - 실제 코드를 외워 쓰는 것보다, **"이러한 상황에서 어떤 개념(DataSource, JdbcTemplate 등)이, 어떤 원리(커넥션 풀, 빈 주입)로 동작하는지"**라는 개념과 흐름을 이해하는 것이 훨씬 중요합니다. 이 개념적 이해가 개발자로서의 경쟁력입니다.

## 1. 데이터 매핑의 이해: RowMapper의 필요성과 작동 원리

**핵심 내용:** 데이터베이스에서 조회한 결과를 자바 객체(Domain Object)로 변환(매핑)하는 과정에 대한 이해를 다룹니다.

*   **매핑의 필요성:** 데이터를 가져올 때 단순히 필드명과 컬럼명이 일치하면 `BeanPropertyRowMapper` 같은 편의 기능으로 처리할 수 있지만, 컬럼명과 필드명이 다를 경우 자동으로 매핑할 수 없습니다.
*   **RowMapper의 역할:** 개발자가 직접 `RowMapper` 인터페이스를 구현하여, SQL의 결과 셋(ResultSet)에서 어떤 컬럼의 값을 가져와서 (예: `ResultSet.get...()`) 최종 자바 객체의 어느 필드에 담을지 명시적으로 지정해야 합니다.
*   **매핑 방법 비교:**
    *   **`BeanPropertyRowMapper`:** 데이터베이스 컬럼명과 자바 엔티티의 필드명이 일치하는 경우에 간편하게 사용 가능합니다. (자동 매핑).
    *   **커스텀 `RowMapper`:** 컬럼명과 필드명이 불일치하거나, 매핑 규칙이 복잡할 때 필수적으로 사용해야 하며, 개발자가 직접 구현해야 합니다.

## 2. Spring JDBC와 데이터 접근 구조 이해

**핵심 내용:** JDBC의 복잡성을 추상화하고 개발 편의성을 높인 `JdbcTemplate` 사용법과 데이터를 조회/수정하는 방법론을 학습합니다.

*   **Spring JDBC의 역할:** JDBC는 복잡한 연결 및 실행 과정이 따르는데, Spring JDBC는 이러한 과정을 단순화하고 간편한 프레임워크를 제공합니다.
*   **`JdbcTemplate`의 기본 사용법:**
    *   **핵심 원칙:** 데이터 접근 시 **어떤 SQL 쿼리(Query)**를 사용할 것인지, **바인딩할 값(Parameter)**은 무엇인지 명확하게 알려줘야 합니다.
    *   **CRUD 작업별 접근:**
        *   **업데이트/삽입/삭제 (Update/Insert/Delete):** 주로 쿼리문과 바인딩된 값(파라미터)만 필요합니다.
        *   **조회 (Select):** 쿼리문과 바인딩된 값 외에, **결과를 담아줄 대상(매퍼)**을 지정해 주어야 합니다.
*   **조회 시 활용 도구:**
    *   **`RowMapper`:** 기본적인 결과 셋 매핑을 담당합니다.
    *   **`QueryForObject`:** 쿼리 결과가 단일 객체(Single Object)일 경우에 효율적으로 사용할 수 있는 객체입니다.
    *   **`JdbcTemplate`의 추상화:** Spring JDBC는 이러한 매핑 과정(RowMapper 사용 등)을 내부적으로 처리하여 개발자가 복잡한 JDBC 코드를 직접 작성할 필요가 없게 만듭니다.

## 3. DAO/Repository 구현과 의존성 주입(DI) 원칙

**핵심 내용:** 아키텍처 관점에서 계층 구조를 설계하고, 객체 간의 의존성을 효율적으로 관리하는 방법을 학습합니다.

*   **계층형 아키텍처 설계 (Layered Architecture):** 애플리케이션은 일반적으로 **Service Layer (비즈니스 로직)** $\rightarrow$ **DAO/Repository Layer (데이터 접근)** $\rightarrow$ **Infrastructure (JDBC)**의 구조를 따르는 것이 일반적입니다.
*   **DAO의 역할 정의:** DAO (Data Access Object)는 데이터베이스와 관련된 모든 작업을 담당하는 인터페이스 역할을 정의하고, 그 구현체(Implementation)가 실제 DB 접근 로직을 포함합니다.
*   **의존성 관리 원칙:** 상위 계층(예: `UserDAO` 인터페이스를 구현하는 `UserDAOImpl`)은 하위 계층(예: `JdbcTemplate`)에 의존해야 합니다.
*   **의존성 주입 (Dependency Injection, DI) 활용:**
    *   `UserDAOImpl` 같은 구현체 클래스가 `JdbcTemplate`을 사용하려면, 이 객체를 생성자(Constructor)를 통해 주입받아야 합니다.
    *   **편의성 증진:** Java의 Lombok 라이브러리에서 `@RequiredArgsConstructor` 어노테이션을 사용하면, 생성자에 반드시 포함되어야 할(필수적인) 필드들만 자동으로 찾아 생성자를 만들어주어 코드를 간결하게 유지할 수 있습니다.

*(강의 종료까지의 내용은 전체적인 구조를 정리하고 실습 및 테스트 환경(CommandLineRunner) 구성의 중요성을 강조하며 마무리되었습니다.)*

## 1. 웹 애플리케이션 아키텍처 이해 및 계층 구조
- 웹 애플리케이션은 클라이언트와 서버로 구성되며, 이 구조는 변하지 않습니다.
- **레이어드 아키텍처**를 기반으로 개발이 진행되며, 전체 시스템은 최소 3가지 부분으로 나뉩니다.
    - **프레젠테이션 레이어 (Presentation Layer):** 클라이언트의 요청을 받아 처리하고 결과를 사용자에게 보여주는 부분입니다.
    - **서비스 레이어 (Service/Business Layer):** 실제 비즈니스 로직을 담당하며, 애플리케이션의 핵심 규칙을 정의합니다.
    - **데이터 레이어 (Data/Persistence Layer):** 데이터베이스와의 연동을 담당합니다. 데이터베이스에서 데이터를 읽어오거나(CRUD), 프로그래밍된 데이터를 데이터베이스에 저장하는 등의 모든 데이터 조작이 일어나는 곳입니다.
- **기술 스택 변화:** 과거에는 웹 요청 처리 과정에서 Spring MVC(Model View Controller) 모듈을 이용했지만, 이번 시간에는 데이터 접근 계층에 초점을 맞춰 Spring JDBC를 학습합니다.

## 2. Spring JDBC 프레임워크의 필요성과 구조
- **JDBC의 역할과 한계:** 웹 애플리케이션이 데이터베이스와 통신하기 위해서는 Java Database Connectivity(JDBC) 기술을 이용해 직접 구현해야 합니다.
- **Spring JDBC의 역할:** JDBC를 직접 구현하는 것이 복잡하고 번거롭기 때문에, Spring JDBC와 같은 프레임워크를 사용합니다.
    - Spring JDBC는 개발자가 JDBC 프로그래밍을 더 쉽고 간편하게 사용할 수 있도록 구조를 제공합니다.
- **작동 원리:** 실제 데이터베이스 드라이버가 동작하는 중간층에 Spring JDBC 모듈이 끼어들어 개발 과정을 단순화하고 사용성을 높여줍니다.
- **핵심 학습 목표:** 개발자는 데이터 접근 계층 코드를 작성할 때 JDBC 기술이 필요하며, 이를 효율적으로 사용하도록 돕는 것이 바로 '프레임워크'입니다.

## 3. Spring JDBC의 핵심 요소: JDBC Template과 RowMapper
- **JDBC Template:**
    - Spring JDBC에서 가장 핵심이 되는 객체입니다.
    - **역할:** JDBC와 개발자 코드 사이에 '중간다리' 역할을 수행하여 데이터 접근 과정을 간편하게 처리해 줍니다.
    - **사용 방식:** 개발자가 SQL 문과 파라미터만 제공하면, JDBC Template이 내부적으로 복잡한 JDBC 연결 및 리소스 관리를 알아서 처리합니다.
    - **기능:** 기본적인 INSERT, UPDATE, DELETE 외에도 SELECT 쿼리 실행이 가능합니다.
- **RowMapper:**
    - **필요성:** SQL로 조회한 결과값(ResultSet)을 Java 객체(DTO)의 형태로 가져와야 하는데, 이를 위한 '그릇' 역할을 표준으로 정해준 것이 RowMapper입니다.
    - **기본 원리:** JDBC Template은 두 번째 인자로 RowMapper를 받으며, 이 RowMapper는 DB 컬럼을 Java 객체 필드에 매핑하는 역할을 합니다.
- **자동 매핑의 원리:**
    - 스프링 JDBC는 개발자가 명시적으로 RowMapper를 구현하지 않아도, 일반적으로 **Java 필드명**과 **DB 컬럼명**을 일치시켜서 자동으로 데이터를 매핑해 줍니다.
    - **규칙 (Convention):** Java는 대소문자를 구분하지만, 데이터베이스는 구분을 못하기 때문에 주로 언더바(\_)를 사용합니다. 따라서 개발 시 컬럼명은 `snake_case` (소문자와 언더바)를 사용하는 것이 일반적인 컨벤션입니다.
- **예외 처리 (RowMapper 수동 구현):**
    - 만약 Java 필드명과 DB 컬럼명이 완전히 다르거나 매핑 규칙이 일반적이지 않을 때는, 직접 `RowMapper` 인터페이스를 구현하여 개발자가 원하는 대로 데이터 매핑 로직을 작성해야 합니다.
    - 이 경우 익명 객체, 람다식, 또는 상속을 통해 구현할 수 있습니다.

## 4. 데이터 접근 객체(DAO) 구현 및 테스트 과정
- **DAO 구현 및 주입:**
    - 실제 프로젝트에서는 `UserDao`와 같은 데이터 접근 인터페이스를 만들고, 이 구현체 내부에서 `JdbcTemplate`을 이용해 로직을 구현합니다.
    - **빈 주입(DI) 방식:** `JdbcTemplate`을 DAO 클래스에 주입받을 때, 생성자, 필드, Setter 등 여러 방법이 있지만, `lombok`의 `@RequiredArgsConstructor` 같은 어노테이션을 사용하면 필수 의존성 필드에 대한 생성자를 간편하게 자동 생성할 수 있습니다.
- **CRUD 구현의 간편화:**
    - `JdbcTemplate`을 사용하면 DAO 계층에서 SQL 실행(INSERT, UPDATE, SELECT 등)을 간단한 메서드 호출로 구현할 수 있습니다.
    - **SELECT 쿼리 시 고려 사항:**
        - **결과가 여러 개일 때 (List):** `jdbcTemplate.query(...)`를 사용하며, 결과 타입을 `List<T>`로 지정합니다.
        - **결과가 한 개일 때 (Object):** `jdbcTemplate.queryForObject(...)`를 사용하며, 결과 타입을 단일 객체(T)로 지정합니다.
- **테스트의 중요성:**
    - 개발 과정에서 모든 메서드(INSERT, SELECT, UPDATE, DELETE)에 대해 테스트 케이스를 작성하고 실행하는 것이 매우 중요합니다.
    - 테스트는 단순히 코드를 작동시켜 보는 것을 넘어, "이 메서드가 내가 원하는 대로의 결과값을 반환하는가?"를 검증하는 과정입니다.
- **JUnit과 테스트 환경 설정:**
    - 프로젝트에서는 JUnit 같은 단위 테스트(Unit Test) 도구를 사용하여 각 메서드를 독립적으로 검증합니다.
    - **LifeCycle Annotation:** 테스트 메서드 전후에 공통 로직(예: 리소스 초기화 또는 정리)을 실행할 때 `@BeforeEach` 또는 `@AfterEach` 등의 어노테이션을 사용하여 개발 편의성을 높일 수 있습니다.

## 1. 테스트 메서드의 라이프사이클 관리
- **테스트 메서드 생명주기:** 테스트 메서드가 실행되기 전(Before), 실행된 후(After)에 공통적으로 수행해야 할 초기화나 정리 작업이 필요합니다.
- **`@BeforeEach`와 `@AfterEach` 활용:** 특정 테스트 메서드가 동작하기 직전에 초기화가 필요하거나, 테스트가 완료된 후 반드시 정리(cleanup)해야 하는 코드를 여기에 작성할 수 있습니다.
- **이점:** 테스트가 일관성 있는 환경에서 반복적으로 실행될 수 있도록 보장합니다.

## 2. Spring 환경에서의 테스트 설정 (애노테이션 사용)
- **DI(의존성 주입)의 중요성:** 실제 애플리케이션이 동작하려면 Spring 컨텍스트를 통해 객체(예: `UserDaoImpl`)가 생성되어 주입되어야 합니다. 개발자가 직접 `new UserDaoImpl()` 방식으로 객체를 생성할 수는 없습니다.
- **특정 테스트 어노테이션 사용:** 테스트의 목적(예: 데이터베이스 레이어 테스트)에 맞게 `@JdbcTest` 같은 어노테이션을 사용하면, Spring이 해당 테스트에 필요한 빈(Bean)들을 자동으로 주입하고 구성해 줍니다.
- **테스트 격리:** Spring 컨테이너의 복잡성 때문에 테스트 전용 어노테이션을 사용하면 테스트 범위를 최소화하고 안정성을 높일 수 있습니다.

## 3. 테스트 검증(Assertion) 및 트랜잭션 관리
- **Assertion의 역할:** 테스트가 기대하는 결과(성공 조건)가 실제로 일치하는지 검증하는 과정입니다. 단순히 코드가 돌아가는지 확인하는 것을 넘어, "이 값이 5와 같으면 성공이다"와 같은 구체적인 조건을 명시해야 합니다.
- **Assertion의 활용:**
    - 컬렉션의 크기 검증: `list.hasSize()`를 사용하여 데이터 목록의 개수를 검증합니다.
    - 특정 값 검증: 가져온 객체의 속성 값이 예상했던 값과 일치하는지 검증합니다.
- **데이터베이스 트랜잭션 관리:**
    - **기본 동작 (테스트):** 테스트 코드 내에서 DB에 데이터를 입력하더라도, 테스트가 종료되면 데이터베이스는 기본적으로 **롤백(Rollback)**됩니다. (테스트 데이터는 영구 저장되지 않음)
    - **`@Transactional`:** 특정 테스트 메서드에 이 어노테이션을 붙이면, 명시적으로 트랜잭션을 관리하며 테스트 종료 후 롤백을 시킬 수 있습니다.
    - **`@SpringBootTest`:** 이 어노테이션을 사용할 경우, JDBC 테스트와 달리 전체 애플리케이션의 트랜잭션을 수행하며, 기본적으로 데이터가 유지되는 특성이 있어 주의가 필요합니다.

## 4. 테스트 범위에 따른 어노테이션 선택 및 동작 이해
- **`@JdbcTest`의 특징:**
    - 목적: 데이터베이스 계층(JDBC)에 초점을 맞춘 테스트를 수행할 때 사용합니다.
    - 동작: 데이터베이스와 관련된 빈만 로드하여 테스트를 진행하며, 기본적으로 테스트 데이터는 롤백됩니다.
- **`@SpringBootTest`의 특징:**
    - 목적: 애플리케이션 전체(Controller, Service, Repository 등 모든 레이어)의 설정과 동작을 아우르는 통합 테스트를 수행할 때 사용합니다.
    - 동작: 모든 애플리케이션 설정을 로드하고 테스트를 진행합니다.
- **롤백 제어:**
    - 테스트에 입력된 데이터는 롤백되는 것이 기본 원칙이지만, 때로는 테스트 후에도 데이터가 남아있어야 할 때가 있어 트랜잭션 관리 전략을 명확히 이해하고 적용해야 합니다.

## 5. 효과적인 테스트 설계 및 학습 전략
- **테스트의 중요성 (핵심):** 기능 개발 단계뿐만 아니라, 시간이 지나 요구사항이 변경되거나 코드를 수정할 때도 테스트는 필수적입니다. 이는 시스템이 오작동하는 것을 방지하는 안전장치 역할을 합니다.
- **비즈니스 로직 테스트:** 개발자가 원하는 "조건"과 "예외 상황"을 테스트 케이스로 명시하는 것이 중요합니다. (예: 이메일 중복 조건, 사용자 권한 조건 등)
- **학습 전략:**
    - **너무 어려운 것부터 시도하지 않기:** JUnit 5나 Spring Boot Test와 같이 복잡한 테스트 환경 구성이 어려울 수 있습니다.
    - **점진적 접근:** 일단 자신이 가장 쉽게 이해하고 구현할 수 있는 간단한 기능 단위부터 테스트를 작성하는 습관을 들이는 것이 중요합니다.
    - **습관화:** 개발한 모든 객체와 기능은 반드시 테스트 코드를 통해 검증하는 것을 기본 습관으로 가져가는 것이 좋습니다.

## 1. 고급 테스트 시나리오 설계 및 검증
*   **테스트 범위 확장:** 단순한 성공/실패 테스트를 넘어, 엑셉션 발생 상황 등 다양한 시나리오를 테스트 코드로 구현하는 것이 중요합니다.
*   **업데이트(Update) 테스트:**
    *   `findById` 등을 통해 데이터를 조회한 후, 실제 업데이트 로직을 수행합니다.
    *   업데이트된 후 다시 조회하여 (예: Name 필드 비교) 원하는 값이 성공적으로 변경되었는지 비교(Assertion)하는 방식으로 테스트를 진행합니다.
*   **삭제(Delete) 테스트:**
    *   데이터를 삭제(Delete)한 후, 해당 ID로 다시 조회했을 때 데이터가 `null`이거나 조회에 실패하는지 확인하는 것이 성공 조건이 됩니다.
    *   Spring의 AssertJ와 같은 라이브러리는 `null`이 아닐 때와 같을 때 등 강력하고 다양한 조건을 제공하여 테스트의 정확도를 높일 수 있습니다.
*   **예외(Exception) 처리 테스트:**
    *   데이터가 없는 경우 등 특정 조건에서 의도적으로 오류를 발생시키고, 테스트 코드에서 이 예외가 올바르게 발생하는지 검증하는 것도 중요한 테스트 시나리오입니다.

## 2. 비즈니스 로직 단계에서의 예외 처리 기법
*   **예외 처리의 필요성:** 구현체(Service Layer)에서도 단순히 기능을 수행하는 것 외에, 비즈니스 규칙 위반이나 예외 상황(예: ID가 없는 경우 삭제 요청)이 발생할 수 있습니다.
*   **try-catch 구문 활용:** 오류가 발생할 수 있는 부분에 `try-catch` 구문을 사용하여 예외를 처리하고, 프로그램이 비정상적으로 종료되는 것을 방지하며 안전한 로직 흐름을 만듭니다.
*   **사용자 정의 예외(Custom Exception) 생성:**
    *   일반적인 런타임 예외(RuntimeException)를 상속받아, 비즈니스 영역 특성에 맞는 예외 클래스(예: `UserNotFoundException`, `InvalidEmailException`)를 정의하는 것이 가장 좋습니다.
    *   예외 객체를 생성할 때 메시지(Message)나 특정 값을 포함하여, **"무엇 때문에"** 오류가 발생했는지 명확히 알려줄 수 있습니다.
*   **핵심 원칙:** 예외가 발생했을 때도 시스템이 안정적으로 동작할 수 있도록, 비즈니스 로직의 오류 발생 지점마다 명확한 예외 처리 로직을 추가해야 합니다.

## 3. 데이터 접근 계층 이해: Spring JDBC와 레파지토리 패턴
### 🔗 데이터 접근 아키텍처 흐름
*   **JDBC의 역할:** 데이터베이스와 통신하는 핵심 기술이며, 기본적인 데이터베이스 작업을 수행할 수 있게 합니다.
*   **프레임워크의 필요성:** JDBC만 사용할 경우 반복적이고 지루한 **보일러 플레이트 코드** (boilerplate code, 매번 똑같이 반복되는 코드)를 직접 작성해야 합니다.
*   **Spring JDBC의 역할:** 이러한 반복적인 코드를 **JDBC 템플릿(JdbcTemplate)**이라는 객체를 통해 자동화하고 추상화하여 개발자가 핵심 로직에만 집중할 수 있게 돕습니다.
*   **핵심 구성 요소 및 관계:**
    *   **DataSource:** 데이터베이스 연결(Connection) 객체를 관리하는 역할을 합니다. (주요 업무: Connection Pool 관리).
    *   **JdbcTemplate:** JDBC 템플릿이 실제 DB 작업(Insert, Update, Delete, Query 등)을 수행하는 핵심 도구입니다.
    *   **DataSource $\to$ JdbcTemplate:** JdbcTemplate은 내부적으로 DataSource가 제공하는 Connection 객체를 이용해 데이터베이스 작업을 수행합니다.
    *   **RowMapper:** `SELECT` 쿼리 결과 값을 자바 객체에 매핑(Mapping)해주는 인터페이스입니다. (Spring의 `BeanPropertyRowMapper`를 사용하거나 직접 구현할 수 있습니다.)
*   **Spring Data JDBC Repository:**
    *   가장 상위 레벨의 추상화 계층입니다. 개발자가 직접 JDBC Template을 사용하지 않아도, 간단한 선언만으로 (약속만 지키면) 필요한 데이터 접근 구현체까지 **자동으로 생성**해주는 기능을 제공합니다.

### 🚀 결론 및 학습 방향
*   데이터를 다루는 계층 구조(Data Layer)를 이해하는 것이 중요하며, 가장 추상적이고 개발 편의성이 높은 Spring Data Repository를 목표로 학습하는 것이 좋습니다.
*   직접 작성한 예제들(DPT 테이블 등)에 위에서 배운 **예외 처리 로직**과 **테스트 시나리오**를 적용해보는 실습이 중요합니다.
