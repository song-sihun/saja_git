## 1. 기술을 바라보는 관점: 왜 기술의 원리를 알아야 하는가?
- **배경지식 습득의 중요성:** 단순히 기술 사용법만 익히는 것을 넘어, 해당 기술이 '왜(Why)' 만들어졌는지 배경과 동작 원리(Principle)를 이해하는 것이 중요하다.
- **난이도 증가에 대한 대비:** 수업에서 다루는 내용들은 비교적 간단한 예제들 위주이지만, 실제 프로젝트에서는 복잡하고 어려운 문제가 발생한다. 기술의 근본적인 작동 방식을 이해해야 예상치 못한 문제 발생 시 해결할 수 있다.

## 2. 객체 지향과 관계형 데이터베이스의 구조적 충돌 배경 (OR-Mapping)
- **객체지향 프로그래밍(OOP)의 특징:** 개발자는 데이터를 객체 형태로 설계하고, 이 과정에서 '객체스럽게' 만듦에 집중한다.
- **DBMS의 제약:** 그러나 데이터를 저장하는 시스템은 여전히 관계형 데이터베이스(RDB)이며, RDB는 테이블 구조를 따른다.
- **불일치성 문제 (Impedance Mismatch):** 객체의 설계 방식과 RDB가 요구하는 표 형식 사이에서 발생하는 괴리(불일치성)이 발생한다. 이 간극을 해소하기 위한 기술이 필요하게 되었다.
- **ORM의 탄생:** 이 불일치성을 해결하고, 개발자가 객체 중심의 사고방식으로 데이터 처리를 할 수 있도록 돕는 것이 바로 ORM(Object Relational Mapping)이다.

## 3. JPA 및 ORM 기술의 표준화 과정과 중요성
- **기술 발전사:** 초기에는 JPA와 같은 개념을 구현하려는 시도가 있었으나 성능 문제 등으로 한계가 있었다. 이후 하이버네이트 등의 라이브러리가 등장하며 시장을 선도했다.
- **표준화의 필요성:** 자바 진영에서 JPA라는 표준 API를 제시함으로써, 어떤 개발자가 기술을 개발하더라도 이 표준을 맞추어 구현하도록 강제하는 생태계를 만들었다 (마치 JDBC API처럼).
- **장점 (Interoperability):** 특정 기술에 종속되지 않고, 여러 기능을 표준 인터페이스(예: JPA)를 통해 사용하는 것이 가능해져 높은 호환성과 유연성을 갖게 되었다.

## 4. JPA 핵심 동작 원리 이해하기 (Persistence Context, Entity 생명주기 관리)
- **JPA의 목적:** ORM을 이용해 객체와 관계형 DB 사이의 매핑 과정을 자동화하고 단순화하는 것이 주된 역할이다.
- **핵심 용어 및 개념 정리:**
    *   **Entity (엔티티):** 데이터베이스 레코드 하나의 정보를 담고 있는 '객체'.
    *   **Persistence Context (영속성 컨텍스트):** 애플리케이션 실행 과정에서 일시적으로 엔티티를 관리하는 저장소(메모리 영역). DB에 직접 접근하기 전에 데이터를 임시로 모아 처리한다.
    *   **EntityManager:** 영속성 컨텍스트에 엔티티를 저장하거나 검색하고 관리하는 주체.
- **엔티티의 생명 주기 (Life Cycle):**
    1.  **비영속 상태 (Transient):** 엔티티 객체를 단순히 생성한 상태 (아직 JPA가 관리하지 않음).
    2.  **관리 상태 (Managed):** `em.persist()` 메서드를 호출하여 영속성 컨텍스트에 올라와 JPA의 관리를 받기 시작하는 상태.
    3.  **DB 저장/수정:** 트랜잭션이 커밋되는 시점에, JPA가 영속성 컨텍스트 내부에서 변경된 데이터를 분석하고 데이터베이스에 한 번에 처리(Batch)한다. 이로 인해 성능이 향상된다.
- **핵심 기능의 원리:**
    *   **`@Id` (Primary Key):** 모든 엔티티는 반드시 고유 식별자(`id`)가 필요하다.
    *   **Generated Value:** ID 값이 DB에 의해 자동으로 생성되는 경우, JPA가 이 값을 미리 얻어와서 영속성 컨텍스트에서 사용할 수 있도록 하는 전략을 사용한다 (예: 인크리먼트).
    *   **Snapshot (스냅샷):** 트랜잭션 시작 시점에 엔티티의 초기 상태를 메모리에 기록해 둔 사본이다. JPA는 커밋 직전에 이 스냅샷과 현재 엔티티 값을 비교하여, **실제로 변경된 필드만** DB에 업데이트하는 데 사용한다.
- **트랜잭션의 중요성:** 모든 영속적인 작업은 트랜잭션(`@Transactional`) 내에서 이루어져야 한다. 액션이 종료되는 시점(커밋)에 비로소 데이터베이스 관련 처리가 일어난다.

## 5. 실전 프로젝트를 위한 개발 철학과 학습 조언
- **개발의 우선순위:** 무조건 "가장 완벽한 구조"를 고집하는 것보다, 일단 **빠르게 동작하게 만드는 것(Working prototype)**이 중요하다. 시장 요구에 맞춰 빠르게 출시하고 피드백을 받는 것이 중요하다.
- **기술 선택 원칙:** 오래된 기술이라도 특정 환경이나 목적에 맞게 잘 사용되고 있다면 무조건 나쁘다고 판단할 수 없다. 중요한 것은 '필요성'과 '적합성'이다.
- **깊이 있는 이해의 필요성:** 강의 내용을 단순히 따라 코딩하는 것에 그치지 않고, JPA가 내부적으로 어떻게 동작하고 이 핵심 개념들이 어떤 역할을 하는지(원리)를 깊이 있게 이해해야 실제 프로젝트에서 발생하는 복잡한 문제에 대처할 수 있다.

## 1. JPA 개요 및 핵심 원리 이해
- **정의:** JPA (Java Persistence API)는 자바 객체(Object)와 관계형 데이터베이스를 매핑하는 ORM 표준 기술입니다.
- **목적:** JDBC 사용 시 발생하는 복잡성을 줄이고, 객체지향적인 방식으로 데이터를 처리할 수 있게 합니다.
- **핵심 구성 요소:**
    *   **엔티티 (Entity):** 객체 자체를 나타내는 클래스입니다. 데이터베이스의 테이블 구조와 매핑됩니다.
    *   **영속성 컨텍스트 (Persistence Context, PC):** 트랜잭션이 시작되고 끝나는 동안 발생하거나 관리되는 엔티티들만 일시적으로 관리하는 공간입니다. *(주의: DB 전체 데이터를 보유하는 것이 아니라, 현재 트랜잭션 범위 내의 데이터만 임시로 관리합니다.)*
    *   **엔티티 매니저 (EntityManager):** 영속성 컨텍스트에 접근하고 엔티티의 생명주기를 관리해 주는 인터페이스입니다.

## 2. 영속성 컨텍스트와 엔티티 매니저의 동작 범위
- **PC와 EM의 관계:** `EntityManager` 하나당 `Persistence Context`가 1:1로 존재하며, 이를 통해 데이터 관리가 이루어집니다.
- **관리 범위 제한:** PC는 해당 트랜잭션이 진행되는 동안 생성되거나 수정된 엔티티들만 관리합니다. 트랜잭션이 커밋/롤백 되면 이 정보들은 소멸됩니다.
- **다중 컨텍스트 지원:** 하나의 애플리케이션 내에서도 여러 개의 다른 영속성 컨텍스트(다른 데이터베이스 접속 정보, 트랜잭션 등)를 독립적으로 관리할 수 있습니다.

## 3. JPA 환경 설정 필수 요소 및 권장사항
- **JPA의 이점 - DB 종속성 해소:** JPA는 다양한 데이터베이스 특성에 대응하는 구현체(Hibernate 등)와 다이얼랙트(Dialect) 역할을 합니다. 이를 통해 코드 수정 없이 여러 종류의 데이터베이스를 사용할 수 있습니다.
- **주요 설정 항목 이해 (예시):**
    *   `spring.jpa.*`: JPA 전반의 설정을 담당합니다. (예: DDL 생성을 자동으로 할지 여부 등)
    *   `hibernate.*`: 주로 내부적으로 사용되는 하이버네이트 관련 설정을 담고 있습니다.
- **DDL 전략 (`ddl-auto`):** 데이터베이스 테이블 생성/수정 자동화 옵션입니다.
    *   `create`, `update`: 개발 환경에서 편하지만, 실제 운영(Production) 환경에서는 스키마가 손실될 위험이 있어 사용에 매우 주의해야 합니다.
    *   운영 환경에서는 보통 **`validate`** 또는 **`none`**을 사용하는 것이 권장됩니다.

## 4. 엔티티 객체 설계 시 주의사항: `equals()`와 `hashCode()`
- **필수 구현의 이유:** JPA가 영속성 컨텍스트 내부에서 데이터를 비교하거나, 컬렉션(Set 등)에 넣을 때, 단순히 메모리 주소값만을 비교하는 기본 Java 동작 방식을 넘어 '논리적인 동등성' 비교가 필요합니다.
- **핵심 원칙 (엔티티 기준):** 엔티티 클래스에는 반드시 `equals()`와 `hashCode()` 메서드를 오버라이드(Overriding) 해야 합니다.
- **비교 기준:** 엔티티 간의 논리적 동등성 판단은 **ID 값**을 기준으로 하는 것이 가장 안전하고 표준적인 방법입니다. (모든 필드를 비교할 경우, ID가 없는 Transient 상태에서 발생하는 오류에 취약해질 수 있습니다.)
- **복합 키 사용 시:** 기본키(Primary Key)로 여러 컬럼을 사용하는 복합 키 엔티티의 경우, 모든 구성 필드(컬럼)를 `equals()`와 `hashCode()` 구현 시 반드시 포함해야 합니다.
- **비즈니스 키 (Business Key):** ID가 임시적이거나 신뢰하기 어려운 상황일 때 (예: 회원 가입 시 이메일), 데이터 일관성을 유지하고 중복을 방지하기 위해 해당 비즈니스 속성(이메일 등)을 기준으로 동등성을 부여할 수 있습니다.

## 5. 데이터 접근 계층(DAO) 설계 및 트랜잭션 관리
- **권장 패턴:** JPA를 사용할 때는 서비스 레이어에서 JPA의 기능을 직접 호출하는 것보다는, **'DAO (Data Access Object)'** 또는 **레포지토리(Repository)** 패턴을 사용하여 데이터를 처리하는 것이 일반적입니다.
- **트랜잭션 범위:** 핵심 원칙은 **"하나의 비즈니스 기능 단위당 하나의 트랜잭션(Transaction)과 영속성 컨텍스트를 사용해야 한다."** 입니다.
- **`@Transactional` 활용:** 서비스 메소드에 `@Transactional` 어노테이션을 붙여 해당 비즈니스 로직이 실행되는 동안 데이터베이스 접속 및 변경 사항이 관리되도록 보장하고, 예외 발생 시 롤백(Rollback)을 처리해야 합니다.
- **DAO 역할의 핵심:** DAO 내에서 필요한 로직이 수행될 때마다 트랜잭션을 명확하게 시작하고 끝내어 (커밋 또는 롤백) 데이터 일관성을 지키는 것이 중요합니다.

## 1. JPA의 핵심 동작 원리 및 엔티티 생명 주기 관리
*   **스프링 Data와 JPA 사용의 변화:**
    *   기존에는 `EntityManagerFactory`, `EntityManager` 등을 직접 설정해야 했으나, Spring Boot를 사용할 경우 프레임워크가 내부적으로 필요한 설정을 자동으로 처리해 줍니다.
    *   이러한 과정을 이해하는 것이 실제 개발에 도움이 되며, `EntityManager`의 주요 메서드를 정리할 필요가 있습니다.

*   **자동 변경 감지 (Dirty Checking):**
    *   JPA는 엔티티를 수정할 때 개발자가 별도의 "수정(update)" 명령을 실행하지 않아도 자동으로 변경을 감지합니다.
    *   이 기능은 트랜잭션 커밋(`COMMIT`) 시점에 데이터베이스에 반영됩니다. (명시적으로 `merge` 등의 명령이 필요 없음)

*   **변경 감지 원리:**
    *   JPA는 엔티티를 조회할 때(Read), 처음 가져온 데이터의 상태를 내부적으로 스냅샷(Snapshot)으로 저장합니다.
    *   트랜잭션 종료 시, 현재 값과 이 스냅샷을 비교하여 변경 여부를 판단하고 필요하다면 업데이트를 수행합니다.

*   **엔티티 4가지 상태 (Entity Life Cycle):**
    *   **비영속 상태(Transient):** 클래스 인스턴스를 새로 생성했을 때의 순수 객체 상태입니다. (DB와 무관)
    *   **영속 상태(Persistent):** `em.persist()` 메서드를 실행하여 영속성 컨텍스트가 관리하는 상태입니다. DB에 실제로 저장되지 않은 데이터일 수 있습니다.
    *   **준영속 상태(Semi-Persistent / Detached):** 엔티티 매니저(`EntityManager`)가 종료될 때, 컨텍스트에서 분리된 상태입니다. 이 상태에서는 변경 내용이 자동으로 감지되거나 반영되지 않습니다.
    *   **삭제된 상태(Removed):** 삭제 명령을 받은 상태입니다.

*   **트랜잭션과 영속성:**
    *   엔티티의 수정 사항은 트랜잭션이 커밋될 때만 실제로 DB에 반영됩니다. (COMMIT 전에는 반영되지 않음)
    *   **쓰기 지연(Write-Behind):** `persist()` 등의 명령을 사용해도 즉시 INSERT가 이루어지는 것이 아니라, 배치(Batch) 또는 트랜잭션이 마무리되는 시점에 한꺼번에 데이터베이스에 기록됩니다.

## 2. 트랜잭션 제어 및 고급 패턴 이해
*   **JPA 캐싱 효과:**
    *   같은 트랜잭션 내에서 동일한 엔티티를 여러 번 조회할 경우, DB 접근 없이 영속성 컨텍스트의 1차 캐시에서 데이터를 가져오기 때문에 성능상의 이점이 있습니다.
    *   만약 같은 데이터가 이미 캐시에 존재한다면(JPA 동작 원리 이해), 재조회 시에는 커밋 전까지 변화 감지 메커니즘이 작동하는 것을 확인해볼 수 있습니다.

*   **효율적인 리소스 관리 (Singleton Pattern):**
    *   `EntityManagerFactory`와 같은 리소스는 생성 비용이 크기 때문에, 여러 DAO(Data Access Object)에서 공유하여 사용하도록 싱글턴 패턴으로 구현하는 것이 효율적입니다.
    *   싱글톤 패턴 구현 시에는 **Private 생성자**를 사용하여 외부 생성을 막고, **Static 메서드/필드**를 통해 단일 인스턴스를 제공해야 합니다.

*   **애플리케이션 종료 처리 (`@PreDestroy` / JVM Shutdown Hook):**
    *   애플리케이션이 정상적으로 종료될 때(JVM Shutdown), 등록된 리소스 정리 로직을 실행할 수 있습니다. 이를 통해 JPA 컨텍스트가 가진 엔티티들이 안전하게 청소되고 메모리가 해제되도록 처리해야 합니다.

## 3. 객체 지향 모델과 데이터베이스 관계 매핑 전략
*   **객체와 테이블의 연관관계 차이:**
    *   **테이블(DB):** 물리적인 **외래키(Foreign Key)**를 통해 관계를 맺습니다. (예: `사원` 테이블에 `부서ID`라는 외래키 컬럼을 가짐)
    *   **객체(OOP):** 객체 간의 **참조(Reference)** 필드를 사용하여 관계를 표현합니다. 이는 한 방향 참조가 일반적입니다.

*   **주요 연관관계 유형:**
    *   **1:1 (One-to-One):** 사용자 ↔ 프로필처럼, 한쪽 엔티티가 하나만 대응되는 경우. (예: `User`와 `UserProfile`)
    *   **1:N (One-to-Many):** 학교 ➡️ 학생처럼, 한 쪽이 여러 개의 항목을 가질 수 있는 경우. (예: `Department`에 여러 `Employee` 정보)
    *   **N:M (Many-to-Many):** 사용자 ↔ 역할(Role)처럼, 서로 다수의 관계를 가지는 가장 복잡한 형태의 관계입니다.

*   **관계형 DB와 객체 매핑 방식 비교:**
    *   **DB (N:M 표현):** 직접 N:M 관계는 불가능하며, 반드시 **연결 테이블(Join Table)**을 중간에 두어 `(User ID, Role ID)` 쌍의 형태로 데이터를 저장해야 합니다.
    *   **객체 (OOP N:M 표현):** 엔티티 클래스 자체 내부에 관련된 객체의 리스트 또는 셋(`List<Role>`, `Set<Role>`) 필드를 정의하여 관계를 표현하는 것이 자연스럽습니다.

## 1. JPA와 연관 관계 매핑의 이해
- **연관관계 개념:** 객체 간 또는 테이블 간에 존재하는 논리적인 연결(Relationship)을 정의하는 방법입니다.
- **주요 관계 유형:** 크게 1:1 (일대일), 1:N (일대다), N:M (다대다)의 세 가지 방식으로 표현됩니다.
- **DB vs 객체 매핑 차이점:**
    - 데이터베이스(RDBMS)는 다대다 관계를 처리하기 위해 중간 테이블을 사용해야 합니다.
    - 하지만 자바 객체의 관점에서 볼 때는 별도의 '중간 엔티티'가 필요하지 않을 수 있으며, 단순 리스트(`List<T>`) 형태로 연관성을 가질 수 있습니다 (예: `User`가 여러 개의 `Role` 목록을 갖는 경우).

## 2. One-to-Many 관계 모델링 및 엔티티 정의 실습
- **예제 설정:** 학교(School)와 학생(Student) 두 테이블을 사용하여 일대다(One-to-Many) 관계를 매핑하는 과정을 진행합니다.
- **엔티티 설계 원칙:**
    *   테이블 구조를 보고 스쿨 엔티티와 스튜던트 엔티티 등 필요한 개별 엔티티로 정의할 수 있습니다.
    *   엔티티 이름은 복수형보다는 단수로 사용하는 것이 좋습니다 (예: `School`, `Student`).
- **기본 구현 요소:** 모든 엔티티는 기본 키(ID)를 가지며, 기본적인 Getter/Setter와 생성자 등을 추가하는 것이 효율적입니다.

## 3. 객체와 테이블 간의 관계 매핑 심화 학습
- **관계 방향성 고려 (학생 → 학교):** 학생(Student) 개체가 스쿨에 대한 정보를 가질 때, 단순히 외래 키 값(`school_id`)만 가지는 것과 스쿨 엔티티 자체를 갖는 것 사이에서 설계적 고민이 필요합니다.
- **객체 매핑의 역할:** JPA와 같은 ORM을 사용하면 학생 객체는 단지 `School` 타입의 객체를 참조하게 됩니다. 이때 실제 데이터베이스와의 관계를 맺어주기 위해 `@ManyToOne`과 `@JoinColumn` 어노테이션이 필수적으로 사용됩니다.
- **매핑 핵심 요소:**
    *   **관계 정의 (`@ManyToOne`):** 현재 엔티티(Student)가 어떤 타입의 다른 엔티티(School)와 관계를 맺는지 알려줍니다 (다수 -> 하나).
    *   **조인 컬럼 지정 (`@JoinColumn`):** JPA에게 객체 참조가 실제 데이터베이스에서 어느 **컬럼 이름(필드명이 아닌)**을 사용하여 조인을 진행해야 하는지 명시적으로 알려주는 것이 중요합니다.

## 4. 영속성 컨텍스트 기반의 데이터 조작 (CRUD) 및 트랜잭션 관리
- **데이터 조회(Read):**
    *   `EntityManager.find()`를 사용하여 엔티티를 조회하면, JPA는 연관된 엔티티들까지 찾아와서 자동으로 객체 그래프 형태로 채워줍니다. 이 과정에서 필요한 테이블 조인 쿼리가 실행됩니다 (예: 학생을 가져올 때 학교 이름이 자동 로딩됨).
- **데이터 생성 및 수정(Create/Update):**
    *   새로 생성된 엔티티는 초기에는 '비영속 상태(Transient)'입니다. 이 객체를 영속성 컨텍스트에 넣어주기 위해 반드시 `entityManager.persist()`를 호출해야 합니다.
    *   ID가 자동으로 증가하는 경우, `@GeneratedValue` 옵션을 반드시 설정해야 오류를 방지할 수 있습니다.
- **트랜잭션 관리 (Transaction):**
    *   엔티티의 상태 변경(생성, 수정, 삭제) 작업은 데이터 일관성을 위해 트랜잭션 범위 내에서 이루어져야 합니다. `entityManager.getEntityManagerFactory().getEntityManager()`를 통해 트랜잭션을 시작하고 커밋하는 과정이 필수적입니다. (트랜잭션 종료 시 영속성 컨텍스트가 정리됨).
- **실전 적용:** 실제 데이터를 생성(Create)하거나, 객체를 로드하여 값을 수정(Update)하는 모든 작업에는 엔티티 매니저를 통한 트랜잭션 관리가 필요합니다.

## 1. 기본 CRUD 작업 복습: 생성, 수정, 삭제 구현
- **생성(Create):** 새로운 학생 또는 학교 정보를 추가하는 기본적인 방법부터 살펴본다.
- **수정(Update) 시 핵심:**
    - 데이터 업데이트를 위해서는 반드시 트랜잭션(Transaction)을 사용해야 한다.
    - 데이터를 수정할 때는 먼저 엔티티 매니저(`EntityManager`)를 통해 ID로 해당 객체(학교 또는 학생)를 불러와야 한다.
    - 영속성 컨텍스트에 로드된 엔티티의 경우, 단순히 필드를 변경하고 트랜잭션을 커밋하기만 하면 JPA가 자동으로 이를 감지하여 DB를 수정한다.
- **삭제(Delete):**
    - 특정 ID의 데이터를 삭제할 때는 `EntityManager`를 사용하여 해당 엔티티를 불러온 후 리무브(`remove`) 메서드를 사용한다.

## 2. 관계 매핑과 영속성 제어: CascadeType 및 연관관계 주인 이해
- **데이터 무결성 문제 (Foreign Key):** 부모 엔티티(학교)가 삭제될 때, 자식 엔티티(학생)와의 연결 고리 때문에 오류가 발생할 수 있다. 이는 데이터베이스의 제약 조건 때문이다.
- **`CascadeType` 사용 목적:** 관계된 여러 엔티티 간에 하나의 변화가 생겼을 때, 해당 변화를 연쇄적으로 전파하기 위해 사용한다. (예: 부모가 삭제되면 자식도 같이 삭제)
    - **주요 옵션:** `ALL` (전체 작업에 적용), `PERSIST` (저장 시 함께 저장), `REMOVE` (삭제 시 함께 삭제) 등 필요에 따라 선택하여 부여한다.
    - 이 옵션들은 JPA가 객체를 처리하는 방식(생성, 수정, 삭제)을 자동화하고 데이터 일관성을 유지하는 데 도움을 준다.

## 3. 엔티티 간의 객체지향적 설계 원칙
- **연관관계 매핑 (OneToMany/ManyToOne):**
    - 물리적으로는 테이블과 외래 키(Foreign Key) 관계를 통해 연결되지만, 객체 모델에서는 연관성을 파악하고 관리해야 한다.
    - **`@mappedBy` 사용:** 양방향 연관관계가 있을 때, 실제로 외래 키를 가진 쪽이 '연관관계의 주인'이 된다. 주인(실제 외래 키 필드를 가진 엔티티)이 아닌 쪽에 `@mappedBy`를 사용하여 이 사실을 JPA에 알려줘야 한다.
- **객체 설계 시 주의 사항:**
    - 무조건 모든 객체가 서로 관련된 정보를 가져야 하는 것은 아니다. 필요에 따라 로딩할 정보만 갖도록 설계하는 것이 좋다.
    - 양방향 참조(예: 학교 $\rightarrow$ 학생 리스트, 학생 $\rightarrow$ 학교)를 할 경우, 데이터베이스 구조와 달리 JPA가 영속성 컨텍스트 내에서 끝없는 무한 루프 조회(Circular Dependency)를 일으킬 수 있으므로 주의해야 한다.

## 4. 데이터 조회 최적화: Lazy와 Eager 로딩 전략
- **N+1 문제 예방 및 성능 최적화:** 연관 관계의 데이터를 어떻게 가져올지 결정하는 것이 중요하다.
- **로딩 전략 (FetchType):** JPA는 엔티티 간의 관계를 로드할 때 기본적으로 두 가지 전략을 사용한다.
    - **`EAGER` (즉시 로딩 - Fetch Join):** 객체를 조회하는 시점에 연관된 모든 데이터를 함께 가져온다. 성능상 비용이 클 수 있다.
    - **`LAZY` (지연 로딩):** 실제로 해당 데이터가 필요할 때(시스템이 참조하는 시점)가 되어서야 DB에 쿼리가 날아간다. 대용량 환경에서 성능을 최적화하는 데 유리하다.
- **기본값:**
    - `@ManyToOne`, `@OneToOne` 같이 '원'으로 끝나는 관계는 기본적으로 `EAGER`인 경우가 많다.
    - `@OneToMany` 같이 리스트 형태로 여러 개를 가질 수 있는 관계는 기본적으로 `LAZY`이다. (실제 사용하지 않을 수도 있기 때문에)

## 1. JPA 로딩 전략과 FetchType 이해하기

*   **Fetch Strategy의 개요:** JPA에서 엔티티 데이터를 언제 가져올지(Loading 시점) 결정하는 전략입니다. 주요 전략으로는 **Lazy (느긋하게)**와 **Eager (즉시)**가 있습니다.
*   **기본 동작 원리 (Default):**
    *   `@ManyToOne`: 기본적으로 `LAZY`입니다. 데이터 목록을 가져오는 과정에서 모든 관련 데이터를 채우는 것은 비용이 크기 때문에, 필요할 때 로딩하는 것이 일반적이기 때문입니다.
    *   `@OneToOne`: 일반적으로 즉시 가져오기(Eager)가 권장됩니다 (단, 명확한 필요에 따라 조정 가능).
    *   *(참고)* `list`로 끝나는 엔티티는 리스트를 채우는 비용이 크므로 Lazy 설정을 따르는 것이 효율적입니다.
*   **FetchType 수동 설정:** 기본값을 무시하고 특정 필드를 즉시 로딩(`EAGER`)하거나 지연 로딩(`LAZY`)하도록 강제할 수 있습니다.

## 2. 트랜잭션 및 영속성 관련 핵심 문제점 (Detached Entity)

*   **문제 발생 상황:** JPA의 가장 중요한 함정 중 하나는 **트랜잭션(Transaction) 경계**를 벗어나는 것입니다.
    *   예: 비즈니스 로직에서 엔티티 리스트를 조회하고 처리한 후, 이 객체를 Presentation Layer(컨트롤러 등)로 넘겨주는 경우.
*   **Lazy Loading의 위험성:** 만약 엔티티가 Lazy 로딩으로 설정되어 있고, 트랜잭션이 종료된 이후에 외부 레이어에서 해당 필드에 접근하려 하면 **`LazyInitializationException`** 오류가 발생합니다.
*   **해결 방안:** 객체 데이터를 활용하는 모든 과정은 반드시 하나의 **긴 트랜잭션(Long Transaction)** 내부에서 이루어져야 합니다.

## 3. 엔티티 간의 연관 관계 매핑: 다대다, 일대일

### A. 다대다 관계 (@ManyToMany)
*   **DB 원리:** 관계형 데이터베이스는 두 엔티티가 직접적으로 여러 개씩 연결되는 것을 표현할 수 없기 때문에, **중간 테이블(Joining Table)**을 반드시 생성해야 합니다. (예: 사원 ↔ 프로젝트 매핑 테이블).
*   **JPA 구현:** `@ManyToMany`를 사용할 경우, JPA가 자동으로 이 중간 테이블 구조를 인식하고 관리합니다.
    *   이때 사용되는 별도의 중간 테이블은 엔티티로 명시적으로 정의하지 않아도 자동 생성됩니다. (다만, 중간 테이블에 추가적인 정보(예: 참여 일자)를 저장하려면 이를 엔티티로 승격시켜야 합니다.)

### B. 일대일 관계 (@OneToOne)
*   **연관관계의 주인(Owning Side) 개념:** 두 엔티티 사이에 주인을 지정하는 것이 핵심입니다. **실제 외래 키(Foreign Key) 컬럼을 가지고 있는 쪽**이 연관관계의 주인이며, 이 엔티티에서만 관계를 설정할 수 있습니다.
*   **주인이 아닌 쪽 처리 (`@MappedBy`):** 주인이 아닌 쪽에서는 `@MappedBy` 어노테이션을 사용하여 "나는 저쪽 엔티티에 의해 관련되어 있다"라고 참조 관계만을 알려줍니다. (데이터베이스 테이블 구조에는 영향을 미치지 않습니다.)

## 4. 객체 생명주기 관리와 개발 방향

*   **CascadeType (영속성 전파):** 관련된 개체(Associated Object)의 생명 주기(Life Cycle)가 변경될 때, 다른 엔티티까지 함께 처리할지 결정합니다.
    *   `ALL`: 모든 작업(Persist, Merge, Remove 등)을 전파합니다.
    *   `PERSIST`: 저장 시에만 전파합니다.
    *   `MERGE`/`REMOVE`: 각 특정 상황에 맞게 사용됩니다.
*   **고아 객체 처리:** 부모 엔티티가 삭제될 때 자식 엔티티들을 어떻게 할지(전부 함께 삭제할지 등)도 캐스케이드 옵션으로 지정해 주어야 합니다.
*   **추가 학습 권장 사항:**
    *   위에서 다룬 모든 복잡한 주제(FetchType, 관계 매핑 전략, Cascade옵션)는 개념적 이해와 함께 **직접 코드로 구현하고 값을 바꿔가며 테스트**를 반복하는 것이 가장 효과적인 학습 방법입니다.
    *   JPA는 나중에 실제 프로젝트에 투입될 환경을 가정하여, 문제 발생 및 해결 과정 자체를 중심으로 깊이 있게 공부하는 것을 추천합니다.
