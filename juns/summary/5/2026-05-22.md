## 1. 웹 애플리케이션의 계층형 아키텍처 복습
*   **최종 목표:** Spring Framework를 이용하여 웹 애플리케이션을 구축하는 것.
*   **계층 구조:** 애플리케이션은 여러 계층(레이어)으로 구성됩니다.
    *   **데이터 레이어 (Data Layer):** 데이터베이스와의 통신을 담당하며, 주로 DAO(Data Access Object) 패턴을 사용합니다. (예: `UserDaoImpl`이 `UserDao` 인터페이스 구현)
    *   **서비스 레이어 (Service Layer):** 비즈니스 로직(핵심 코드)을 담당합니다. 데이터 레이어에 의존하며, 트랜잭션 관리 등 복잡한 로직이 수행됩니다.
    *   **프레젠테이션 레이어 (Presentation Layer):** 사용자에게 보여지는 화면(View)과 인터페이스를 담당합니다. 웹 애플리케이션의 경우 **컨트롤러(Controller)**가 이 역할을 수행하며, 서비스 레이어에 의존성을 가집니다.
*   **스프링 역할:** Spring Framework는 IOC(Inversion of Control)라는 핵심 기술을 제공하여, 이러한 각 계층 간의 의존성 주입(Dependency Injection)을 관리해 줍니다.
*   **주요 모듈:** 현재 배우고 있는 **Spring MVC**는 웹 요청 처리(프레젠테이션 레이어)를 담당하는 모듈이며, 데이터 접근 방식에 따라 Spring JDBC, JPA 등의 모듈과 함께 사용될 수 있습니다.

## 2. 웹 통신과 HTTP 프로토콜의 기본 원리
*   **통신 방식의 근간:** 웹 애플리케이션은 결국 네트워크를 통해 클라이언트와 서버가 데이터를 주고받는 통신 과정에 기반합니다.
*   **프로토콜의 필요성:** 네트워크 상에서 데이터가 원활하게 주고받으려면 반드시 통신에 대한 '규약(프로토콜)'이 필요하며, HTTP가 대표적인 프로토콜입니다.
*   **요청-응답 모델:**
    *   **클라이언트가 먼저 요청(Request)**을 보내야만 서버가 동작합니다. 서버가 능동적으로 정보를 보내주는 것이 아닙니다.
    *   **통신 과정:** 클라이언트가 요청 $\rightarrow$ 서버가 요청 처리 $\rightarrow$ 서버가 응답(Response)합니다.
    *   **HTTP의 특성 (Stateless):** HTTP는 기본적으로 **'무상태(Stateless)'** 프로토콜입니다. 즉, 요청과 응답 처리가 끝나면 해당 연결은 종료되며, 서버는 클라이언트가 이전 요청을 했는지 여부를 알 수 없습니다.

## 3. 상태 유지와 세션 관리 (Session & Cookie)
*   **문제점:** HTTP의 Stateless 특성 때문에 서버는 사용자가 누구인지, 이전에 어떤 작업을 했는지 기억할 수 없습니다.
*   **해결책 (상태 유지):** 상태 정보를 유지하기 위해 다음과 같은 객체들을 사용합니다.
    *   **세션(Session):** 세션 객체는 특정 사용자가 로그인하거나 특정 작업을 시작한 시점에 생성되어, **세션이 종료될 때까지** 상태 정보를 유지합니다. 요청이 여러 번 들어와도 세션 정보는 지속적으로 유지됩니다.
    *   **쿠키(Cookie):** 서버가 클라이언트의 브라우저에 보관하는 키-값(key-value) 형태의 작은 데이터 조각입니다. 쿠키는 요청을 보낼 때마다 클라이언트가 서버에게 함께 전송하여 서버가 사용자를 식별할 수 있게 돕습니다.
*   **사용 흐름:** 서버는 세션 객체를 생성하고, 이 세션을 브라우저가 보관할 수 있도록 쿠키를 발행하여 클라이언트에게 전달합니다. 클라이언트는 이후의 모든 요청에서 이 쿠키를 첨부하여 전송합니다.

## 4. 웹 프레임워크의 발전 과정과 Spring MVC 이해
*   **초기 형태:** 초기 웹 애플리케이션은 `main()` 메서드처럼 전체 흐름을 순차적으로 처리하는 형태였습니다.
*   **웹 애플리케이션의 변화:** 웹 환경은 클라이언트와 서버의 상호작용(요청-응답)이 필수적이게 되었습니다.
*   **Servlet의 등장:** 자바 진영에서 요청을 받아내고 일련의 작업을 처리할 수 있는 기술이 필요했고, 이것이 **서블릿(Servlet)**입니다. (서블릿은 모든 웹 요청을 받을 수 있는 핵심 메커니즘을 제공합니다.)
*   **페이지 기술의 한계 (JSP):** 서블릿 내에서 HTML 코드를 직접 출력해야 하는 구조는 복잡하고 비효율적이었습니다.
*   **MVC 패턴의 등장:** 이러한 복잡성을 해결하기 위해 역할을 분리한 MVC(Model-View-Controller) 패턴이 필요했습니다.
*   **Spring MVC의 역할:** Spring MVC는 요청을 효율적으로 처리하기 위해 **DispatcherServlet**이라는 '프론트 컨트롤러(Front Controller)' 역할을 수행합니다. 모든 요청은 이 디스패처 서블릿을 거치게 됩니다.
    *   **핵심 기능:** 디스패처 서블릿이 요청을 받아 어떤 로직(Controller)이 처리해야 할지 빠르고 효율적으로 분배(핸들링)해주는 역할을 합니다.

## 5. Spring MVC의 핵심 원리 및 고급 개념
*   **요청 매핑 (Mapping):**
    *   `@RequestMapping`, `@GetMapping`, `@PostMapping` 등의 애너테이션은 개발자가 "특정 URL과 HTTP 메서드가 들어왔을 때 이 메서드를 실행해라"라는 약속(규칙)을 부여하는 방식입니다.
    *   **메서드 분리:** 같은 URL 경로라도 요청 방식(GET/POST 등)에 따라 다른 로직을 수행하도록 구현할 수 있습니다.
*   **요청 처리의 메커니즘:**
    *   실제 구현은 Spring이 제공하는 Servlet의 내부 메서드(`doGet()`, `doPost()`, 등)를 오버라이딩(Overriding)하는 방식으로 동작합니다.
    *   Spring은 이 서블릿을 감싸서(Wrapper) 개발자가 애너테이션만으로 간편하게 요청-응답 처리를 할 수 있도록 합니다.
*   **요청의 흐름 제어 (Redirect vs. Forward):**
    *   **Forward (포워딩):** 요청 자체가 하나이며, 디스패처 서블릿이 내부적으로 다른 자원(View)으로 **제어권**을 넘겨 처리하게 합니다. (요청 자체가 동일함)
    *   **Redirect (리디렉트):** 클라이언트에게 "새로운 주소로 재접속하라"고 응답하는 방식입니다. 서버가 응답을 보낸 후, 클라이언트는 완전히 새로운 요청(새로운 리퀘스트 객체)을 보내게 됩니다.
    *   **핵심 차이:** 포워딩은 '하나의 요청'을 가지고 처리하는 것이며, 리다이렉트는 '두 개의 요청'으로 처리됩니다.
*   **뷰 기술과 데이터 전달:**
    *   **Thymeleaf:** HTML과 유사하게 작성되지만, 서버에서 동적으로 HTML 결과를 만들어 반환하는 View 기술입니다.
    *   **모델 (Model) / 모델 속성(@ModelAttribute):** 요청 파라미터(사용자가 보낸 데이터)를 단순 변수에 담는 것이 아니라, **특정 객체(DTO)에 구조적으로 담아** Spring 컨테이너에게 전달하는 역할을 합니다.
        *   **주의사항:** 모델에 데이터를 채우려면, 요청 파라미터의 이름(Name)과 DTO 객체의 필드 이름(Field)이 일치해야 합니다.
*   **Scope (스코프):** 데이터를 저장하고 공유하는 생명 주기(Life Cycle) 영역을 의미합니다.
    *   **Scope 종류:**
        1.  **Page Scope:** 특정 페이지 내에서만 사용 (가장 제한적)
        2.  **Request Scope:** 요청(Request)이 처리되는 동안만 생존 (하나의 요청 단위)
        3.  **Session Scope:** 세션이 생성되어 사라질 때까지 생존 (사용자 단위)
        4.  **Application Scope:** 애플리케이션이 구동되는 동안 항상 유지 (전역 단위)

## 1. 폼 데이터 유효성 검증의 필요성 및 어려움
- **배경:** 사용자가 폼(Form)을 통해 입력한 데이터(이름, 이메일, 비밀번호 등)가 서버에 도달했을 때, 이 데이터가 유효한지 검증하는 과정이 필수적이다.
- **기존 방식의 문제:** 수동으로 `if/else` 문을 사용하여 데이터의 유효성(값이 비어 있는지, 형식에 맞는지 등)을 검사하려면 매우 복잡하고 많은 코드를 작성해야 한다.
- **목표:** 반복적이고 복잡한 검증 로직을 프레임워크 레벨에서 처리하여 코드를 간소화하는 것이 목표이다.

## 2. 스프링 Validation 모듈의 이해와 사용 방법
- **도입된 모듈:** `validation` 의존성을 추가하여 자동으로 유효성 검증을 수행할 수 있는 모듈을 사용한다.
- **기본 동작 원리:** 스프링이 개발자가 직접 작성하는 복잡한 `if-else` 로직을 대신 처리해준다.
- **핵심 3단계 약속:**
    1. **도메인 객체에 규칙 정의:** 검증을 수행할 모델(DTO/Entity) 클래스의 필드에 유효성 검증 규칙(Constraint Annotation)을 붙여야 한다.
    2. **Controller에 `@Valid` 사용:** 컨트롤러 메서드의 파라미터에 `@Valid` 어노테이션을 사용하여 해당 객체의 유효성 검증을 트리거(trigger) 해야 한다.
    3. **`BindingResult` 주입 및 활용:** 검증 과정에서 발생한 오류 정보(에러 메시지, 오류 필드 등)를 담는 `BindingResult` 객체를 컨트롤러 메서드에 주입받는다.

### 💡 `BindingResult`의 역할
- **목적:** `@Valid` 검증이 성공했는지 실패했는지에 관계없이 오류 정보를 받을 수 있게 해준다.
- **흐름 제어:**
    - `BindingResult`를 통해 `hasErrors()`와 같은 메서드를 호출하여 오류 존재 여부를 체크한다.
    - **오류 발생 시:** 데이터를 처리하지 않고, 사용자가 오류를 확인할 수 있도록 폼 페이지로 다시 리다이렉션한다.
    - **오류 없음 시:** 정상적으로 서비스를 호출하여 비즈니스 로직을 처리한다.

## 3. 유효성 검증 규칙(Constraint) 정의하기
- **기본 필수 검증:**
    - **Null 체크:** 값이 존재하는지 확인 (`@NotNull`)
    - **공백/빈 문자열 체크:** 필드가 비어 있지 않은지 확인 (`@NotEmpty`)
- **형식 및 길이 검증:**
    - **사이즈 제한:** 최소/최대 길이를 지정 (`@Size(min=X, max=Y)`)
    - **이메일 형식:** 이메일 형식인지 체크 (`@Email`)
    - **패턴 검증:** 가장 까다로운 조건을 처리할 때 사용하며, 정규 표현식(`@Pattern`)을 이용해 복잡한 규칙(예: 비밀번호 조합, 특정 패턴)을 지정할 수 있다.
- **메시지 제공:** 각 검증 조건에 실패했을 때 사용자에게 보여줄 커스텀 오류 메시지를 `@Message` 등을 이용해 설정할 수 있다.

## 4. Controller 및 View에서의 처리 흐름
- **View (Thymeleaf)에서의 처리:**
    - **모델 전송:** 컨트롤러가 폼으로 요청을 보낼 때, 반드시 검증 규칙이 적용된 도메인 객체 모델을 함께 전달해야 한다.
    - **폼 바인딩:** 폼 태그 내에서 `th:field` 속성을 사용하여 HTML 입력 필드와 모델 객체의 필드를 연결한다.
    - **오류 메시지 출력:** `BindingResult`가 담고 있는 오류 정보를 View에 표시하기 위해 `th:if`와 필드별 에러 존재 여부를 확인하는 로직(예: `hasErrors()`)을 사용한다.
- **전체 흐름 요약 (강사 강조):**
    1. 클라이언트가 폼 제출.
    2. **Controller:** `BindingResult`와 `@Valid`가 붙은 객체를 받는다.
    3. **Validation:** `@Valid`이 동작하며 도메인 객체의 `@NotNull`, `@Size` 등의 규칙을 검사한다.
    4. **결과 처리:**
        - **에러 존재:** `BindingResult`에 오류 정보를 담고 컨트롤러가 폼으로 재진입(redirect)을 유도한다.
        - **에러 없음:** 값이 유효하다고 판단하여 비즈니스 로직을 정상적으로 수행한다.

> **핵심 정리:** Validation 모듈은 우리가 수동으로 처리해야 할 복잡한 데이터 검증 로직을 **자동화**해주며, 개발자는 이 과정을 위한 **약속(어노테이션 및 구조)**만 지켜주면 된다.

## 1. Spring MVC 동작 방식 이해 (Mapping & Data Flow)
이 섹션에서는 Spring MVC가 URL 요청을 받아 어떻게 페이지와 데이터 흐름을 처리하는지 구조적으로 파악합니다.

- **요청 처리 기본 원리:**
    - `@GetMapping`이나 `@RequestMapping`으로 정의된 URL에 따라 특정 페이지(View)가 동작하며 내용을 출력합니다.
    - **모델(Model) 사용:** 컨트롤러가 서비스 레이어에서 가져온 데이터(예: 유저 리스트)를 모델에 담으면, View(JSP/Thymeleaf 등)가 이 데이터를 꺼내와 화면에 뿌려줍니다.
- **URL 매핑과 파라미터:**
    - **Path Variable 사용:** URL 경로 자체에 변수(예: `/users/{id}`)를 포함하여 요청을 처리할 수 있으며, 이 값을 코드 내에서 특정 자료형(예: `Long`)으로 받아올 수 있습니다.
    - **데이터 타입 강제:** Path Variable의 타입이 기대하는 자료형과 다를 경우 (예: Long 타입에 문자 'A' 전달), Spring은 자동으로 형변환을 시도하다가 **오류(Type Conversion Error)**를 발생시킵니다.
- **HTTP 메서드에 따른 분기:**
    - URL 경로가 같더라도, 요청이 들어오는 **HTTP 메서드(GET, POST, PUT, DELETE)**에 따라 다른 컨트롤러 메서드가 실행됩니다.
    - `GET`은 조회, `POST`는 데이터 생성, `PUT`은 데이터 수정, `DELETE`는 데이터 삭제 등의 역할을 담당하며, 각각의 메서드 매핑을 이해하는 것이 중요합니다.
- **검색 및 페이지네이션 (Pagination):**
    - 검색 기능 구현 시 URL 파라미터(Query Parameter)를 통해 검색 값과 현재 페이지 번호를 받습니다.
    - 너무 많은 데이터를 한 번에 가져오는 부하를 막기 위해, 검색 결과는 페이지 단위로 처리하는 것이 필수적입니다.

## 2. Thymeleaf와 서버 폼 처리의 핵심 원리
폼 제출 및 서버 템플릿 엔진인 Thymeleaf를 사용하여 데이터를 동적으로 처리하는 방법을 학습합니다.

- **Thymeleaf의 역할:**
    - HTML은 정적인 문서이지만, Thymeleaf는 서버에서 데이터를 동적으로 가져와 채우고(동적 생성), 조건문(`th:if`)이나 반복문(`th:each`)을 사용해 콘텐츠를 만들어내는 **템플릿 엔진**입니다.
    - **동적 사용 문법:** `${}` 문법으로 모델에 담긴 값을 꺼내 쓰거나, `th:href` 등에서는 슬래시를 이용해 경로를 지정할 수 있습니다.
- **폼 데이터 바인딩 및 유효성 검사 (Validation):**
    - **폼 전송의 약속:** 클라이언트가 폼을 제출할 때, 데이터를 담을 객체를 모델(Model)에 담아 보내고, 컨트롤러 매개변수에 `@Valid` 애너테이션을 붙여 Spring에게 유효성 검사를 요청해야 합니다.
    - **Spring의 역할:** Spring 프레임워크가 객체에 붙은 제약 조건(Constraint)을 체크하고, 유효성 검사 결과(에러 메시지 등)를 다시 객체에 담아줍니다.
    - **에러 처리의 중요성 (Forward vs. Redirect):**
        - **Forwarding (포워딩):** 검증 오류가 발생했을 때, 데이터를 모델에 담아 **원래 페이지로 돌아가(Forwarding)** 에러 메시지를 표시하는 것이 적합합니다. (에러 값 유지가 가능)
        - **Redirecting (리다이렉팅):** 리다이렉트 후에는 에러 값을 유지하기 어려우므로, 별도의 방법을 사용해야 합니다.
- **Redirect Attribute (Flash Attributes):**
    - 리다이렉트(Redirect)가 발생했을 때, 세션(Session)을 사용하지 않고 **임시 값**을 한 번 저장해 두는 메커니즘입니다. (예: "회원가입 성공했습니다" 메시지 표시)

## 3. 고급 데이터 처리 및 상태 관리 기법 (Validation, Redirect, Session)
강화된 데이터 검증 기법과 웹 애플리케이션의 상태 관리 방식을 다룹니다.

- **고급 유효성 검사 (Validation Constraints):**
    - 기본적인 Null/Empty 체크 외에도 다양한 조건을 활용하여 데이터의 정확성을 높일 수 있습니다.
    - **주요 검증 규칙:** `@NotBlank` (공백 포함 공백 아님), `@Size` (길이 제한), `@Pattern` (정규식 패턴 검사), 날짜 형식 검증 등 복잡한 비즈니스 규칙에 맞게 검사할 수 있습니다.
- **클래스 설계 및 권장 사항:**
    - DTO(Data Transfer Object)나 Entity를 정의할 때, Lombok의 `@Data`는 편리하지만, 필드의 역할을 명확히 파악하기 어려우므로 너무 광범위하게 사용하기보다는 필요에 따라 `@Getter`, `@Setter` 등을 명확히 사용하는 것이 좋습니다.
    - **DI(Dependency Injection) 원칙 준수:** 서비스 객체 등은 직접 `new` 키워드를 사용하기보다 스프링 컨테이너가 주입(Injection)하도록 하는 것이 모범 사례입니다.
- **학습 요약 및 다음 내용:**
    - 강의 내용을 통해 Spring MVC의 요청 처리 흐름, 템플릿 엔진 사용법, 그리고 유효성 검사 기법까지 전반적인 Web 계층의 흐름을 익혔습니다.
    - **다음 학습 목표:** 이번 섹션에서 다룬 유효성 검사 및 요청 처리를 넘어, 애플리케이션 전반의 **상태 관리(State Management)** 기법(쿠키, 세션)에 대해 더 깊이 이해하는 것이 중요합니다.

## 1. Spring MVC의 동작 원리 및 요청 처리 과정
- **Spring MVC의 역할:** 웹 애플리케이션을 만들기 위해서는 클라이언트의 요청을 받아 서버가 이를 처리할 수 있어야 합니다. Spring MVC는 이 과정에서 프런트엔드(Front-end)의 역할을 전담하는 프레임워크입니다.
- **MVC의 핵심 철학:** 프레임워크(Spring) 자체는 사용자가 *무엇을* 원하는지 (예: 리스트 조회, 회원가입, 로그인) 알 수 없습니다. 사용자의 요청 의도는 개발자가 직접 정의해야 합니다.
- **컨트롤러 구현의 약속:** 개발자는 `Controller` 클래스를 통해 "나(컨트롤러)는 이런 URL 요청을 받으면, 이런 방식으로 처리할 거야"라는 약속을 남겨주어야 합니다.
- **요청 매핑 (Request Mapping):**
    - URL을 통해 요청을 처리하는 것을 의미합니다.
    - **메서드 방식(HTTP Method) 기반 매핑:** 요청 시 사용하는 HTTP 메서드(GET, POST, DELETE 등)를 기반으로 요청을 처리하는 것이 가능합니다.
    - **주요 메서드:** GET, POST는 전통적인 방식이었으나, API 발전과 함께 DELETE, PUT, PATCH 등 RESTful 아키텍처에서 사용되는 다양한 메서드가 추가되었습니다.

## 2. 데이터 유효성 검사 (Validation) 이해하기
- **목적:** 사용자가 전송한 데이터 값이 유효한지(예: 이메일 형식, 비밀번호 길이 등) 검증하는 과정입니다.
- **동작 원리:**
    - 개발자가 객체에 `@Valid` 등의 어노테이션(Annotation)을 붙여서 **"이 필드들은 이런 조건들을 만족해야 해"**라는 약속을 선언합니다.
    - Spring 프레임워크가 요청을 받으면 자동으로 이 검증 과정을 수행합니다.
    - **오류 처리:** 유효성 검사 조건에 맞지 않을 경우, `BindingResult`라는 객체에 오류 정보(어떤 필드에서, 어떤 메시지로)를 담아 전달받을 수 있습니다.
- **프레임워크의 역할:** 개발자는 비즈니스 로직이나 유효성 검사 *규칙*만 알려주면, 프레임워크가 번거로운 값의 읽기, 검사, 오류 처리 등 "귀찮은 일들"을 알아서 처리해 줍니다.

## 3. HTTP 프로토콜의 특성 및 상태 유지 문제
- **HTTP의 기본 특성: Stateless (무상태성):**
    - HTTP 프로토콜은 요청(Request)과 응답(Response)이 오가면 상태를 유지하지 않습니다. 서버는 클라이언트가 누가 접속했는지, 이전 요청에서 무엇을 했는지 알지 못합니다.
    - *원리적 이유:* 데이터베이스 연결처럼 접속 슬롯(연결 자원)의 개수가 유한하기 때문에, 상태 정보를 유지하는 프로토콜은 서버에 엄청난 부담을 주기 때문에 HTTP는 설계 단계부터 무상태성으로 만들어졌습니다.
- **상태 정보의 필요성:**
    - 웹 애플리케이션이 쇼핑몰, SNS 등 '나'라는 개인화된 경험을 제공하려면 **상태 정보를 유지**하는 것이 필수적입니다.
    - (예: 로그인 상태, 장바구니 내용 등)
- **문제점:** 무상태성으로 인해, 클라이언트가 요청을 해도 서버 입장에서는 매번 처음 접속한 사용자로 인식하게 되어 개인화된 서비스를 구현할 수 없습니다.

## 4. 상태 정보를 위한 기술: 쿠키(Cookie)와 세션(Session)
- **필요성:** HTTP가 가진 무상태성 문제를 해결하고 사용자 상태를 유지하기 위해 사용됩니다.
- **기술 분류:**
    - **쿠키 (Cookie):** 사용자에게 **클라이언트(브라우저)** 측에서 정보를 저장하게 하는 기술입니다.
        - **특징:** 저장된 정보는 브라우저에 물리적으로 저장되며, HTTP 헤더를 통해 서버에 다시 전송됩니다.
        - **한계:** 쿠키는 단순한 키(Key)와 값(Value) 형태로만 저장할 수 있습니다.
    - **세션 (Session):** 사용자가 정보를 **서버** 측에 저장하게 하는 기술입니다.
        - **원리:** 서버가 사용자의 상태 정보를 유지하고, 클라이언트에게는 이 세션 정보를 식별할 수 있는 작은 식별자(ID)를 쿠키 형태로 전송받아 사용합니다.
        - **장점:** 서버 측에 데이터를 저장하므로, 클라이언트가 악의적으로 정보를 조작하거나 탈취하기 어렵습니다.
- **보안 및 정보 저장 시 유의사항:**
    - **보안 취약점:** 쿠키에 아이디나 비밀번호 같은 민감 정보를 그대로 저장하는 것은 매우 위험합니다. (누구나 가로채서 사용할 수 있음)
    - **저장 방식 결정:**
        - **클라이언트 저장 (쿠키):** 노출되어도 영향이 적은 정보 (예: 테마 설정, 언어)를 저장합니다.
        - **서버 저장 (세션):** 노출되면 안 되는 중요한 정보 (예: 사용자 인증 정보)를 저장합니다.

## 5. 실습: 쿠키를 활용한 요청 처리
- **목표:** 쿠키가 실제로 HTTP 요청에 어떻게 포함되어 전송되는지 이해하기 위해 컨트롤러를 구현합니다.
- **구현 내용:**
    - GET 매핑을 사용하여 클라이언트가 요청할 때 포함된 쿠키 정보들을 읽어옵니다.
    - 실제 웹 애플리케이션에서는 이 과정에서 사용자로부터 데이터를 받아와 쿠키에 저장하는 방식으로 동작함을 확인합니다.
- **핵심 이해:** 웹 브라우저는 요청을 보낼 때, 이전에 서버로부터 받은 모든 쿠키 정보들을 함께 HTTP 요청 객체에 담아 서버로 전송합니다.

## 1. 쿠키 개체 생성 및 속성 이해
쿠키(Cookie)는 클라이언트(브라우저)가 서버와 주고받는 작은 텍스트 정보이며, 서버가 사용자의 브라우저에 저장하도록 요청하는 객체입니다.

*   **쿠키 생성 방법:**
    *   `jakarta.servlet.http.Cookie` 객체를 생성자를 통해 생성하며, **쿠키 이름(Name)**과 **쿠키 값(Value)**을 필수적으로 지정해야 합니다.
*   **쿠키 속성 설정 (SetAttribute):**
    *   쿠키가 브라우저에 성공적으로 전달되고 유지되기 위해서는 반드시 속성을 지정해 주는 것이 좋습니다.
    *   **Path (경로):** 쿠키를 사용하고자 하는 URL 경로를 지정합니다. 슬래시(`/`)로 지정하면 애플리케이션 전체에서 사용함을 의미합니다.
    *   **Domain (도메인):** 쿠키를 사용할 도메인을 지정합니다.
    *   **MaxAge (유지 시간):** 쿠키가 유효하게 유지될 시간(초 단위)을 설정합니다.
        *   지정하지 않을 경우, 브라우저가 닫힐 때까지 유지되는 세션 쿠키가 됩니다.
        *   최대 3년까지 유지 시간을 설정할 수 있습니다.

## 2. 쿠키 데이터의 전송 (쓰기/읽기)
쿠키를 사용하기 위해서는 서버가 클라이언트에게 데이터를 **전송(쓰기)**하고, 클라이언트가 그 데이터를 **요청(읽기)**해야 합니다.

*   **쿠키 쓰기 (서버 $\rightarrow$ 클라이언트):**
    *   서버는 클라이언트에게 응답(Response)을 보낼 때 쿠키를 추가해야 합니다.
    *   `HttpServletResponse` 객체의 `addCookie()` 메서드를 사용하여 생성된 쿠키 객체를 추가하여 브라우저에 전달합니다.
*   **쿠키 읽기 (클라이언트 $\rightarrow$ 서버):**
    *   클라이언트가 서버에 새로운 요청(Request)을 보낼 때, 브라우저가 저장된 쿠키 정보를 요청에 포함하여 서버로 전송합니다.
    *   서버는 `HttpServletRequest` 객체의 `getCookies()` 메서드를 사용해 요청에 담겨 온 모든 쿠키 정보(Cookie 배열)를 읽어올 수 있습니다.
    *   **확인 사항:** `getCookies()`는 쿠키가 여러 개일 수 있으므로 **배열(Cookie[])** 형태로 결과를 반환합니다.

## 3. 쿠키를 활용한 상태 정보 유지 (로그인 구현)
쿠키는 사용자의 상태 정보를 서버가 아닌 **클라이언트(브라우저)**에 저장하여, 사용자가 페이지를 이동해도 **"이전의 상태"**를 기억하게 해주는 데 사용됩니다.

*   **로그인 상태 유지 원리:**
    1.  사용자가 로그인에 성공하면 (서버 단에서 ID/PW 검증 완료), 서버는 **"로그인 성공"**을 나타내는 고유한 쿠키를 생성합니다.
    2.  이 쿠키의 이름(예: `loginOk`)은 서버 개발자가 임의로 정하며, 쿠키의 값(Value)에는 **사용자를 식별할 수 있는 정보** (예: 사용자 ID)를 저장합니다.
    3.  서버는 이 쿠키를 응답에 담아 브라우저에 전송합니다.
    4.  사용자가 이후 페이지를 요청할 때, 브라우저는 이 쿠키를 포함하여 서버에 전송합니다.
    5.  서버는 요청 객체에서 해당 쿠키를 읽어와 "이 사용자가 현재 로그인한 사용자이구나"라고 판단하고, 로그인 사용자에게만 보이는 콘텐츠를 제공할 수 있습니다.
*   **필수 원칙:** 쿠키의 이름은 사용자별로 다르게 지정하면 안 되며, 서버에서 **통일된 이름**으로 지정하여 모든 요청에서 동일하게 확인해야 합니다.

## 4. 쿠키와 세션의 관계 및 보안 고려 사항
쿠키는 상태 유지의 가장 기본적인 방법이지만, 웹 애플리케이션의 실제 인증 과정에서는 더욱 복잡하고 안전한 메커니즘을 사용합니다.

*   **세션(Session) 메커니즘:**
    *   세션은 사용자별로 서버 메모리에 생성되는 객체(상태 정보)를 의미합니다.
    *   **자동 쿠키 발급:** 서버가 세션 객체를 생성할 때, 서버는 이 세션 객체를 식별하기 위한 고유한 **세션 ID**를 발급하고, 이 ID를 쿠키 형태로 클라이언트에 자동으로 저장해 주는 역할을 합니다.
    *   클라이언트가 요청을 보낼 때 세션 ID 쿠키를 통해 서버는 메모리에 저장된 사용자별 세션 객체를 찾아 사용합니다.
*   **실제 시스템의 구현 방식:**
    *   단순히 쿠키나 세션만 가지고 로그인 기능을 구현하기에는 **보안상 취약점**이 많기 때문에, 실제 상용 웹 애플리케이션에서는 이러한 쿠키/세션 처리 과정에 **Spring Security**와 같은 전문적인 보안 프레임워크를 사용하여 복잡하고 디테일하게 처리합니다.
*   **핵심 정리:**
    *   **쿠키:** 클라이언트(브라우저)에 데이터를 저장하는 '저장소'의 역할.
    *   **세션:** 서버 메모리에서 사용자별 상태를 관리하는 '상태 객체'의 역할.
    *   쿠키는 세션을 식별하는 데 필수적이지만, 실제 로그인 인증 로직은 전용 보안 모듈을 활용하는 것이 안전합니다.

## 1. 쿠키 삭제 및 조작의 원리
*   **쿠키 삭제의 개념 이해:** 브라우저가 가지고 있는 쿠키를 직접 '삭제'하는 것은 기술적으로 불가능합니다.
*   **강제 삭제 방법 (덮어쓰기):** 특정 쿠키를 삭제하려면, 같은 이름의 새 쿠키를 생성하여 덮어쓰는 방식으로 삭제를 유도해야 합니다.
    *   **핵심 구현:** 새로 생성하는 쿠키의 **유지시간(Max-Age)**을 **0**으로 설정하여 전송합니다.
    *   **작동 원리:** 기존 쿠키가 이 새 쿠키와 교체되며, 유지시간 0인 쿠키는 브라우저가 즉시 만료 처리하여 사실상 삭제되는 효과를 얻습니다.
*   **구현 단계:**
    1.  새 쿠키를 생성하고 원하는 값(ID 등)을 담습니다.
    2.  이 새 쿠키에 `Max-Age`를 0으로 설정합니다.
    3.  응답(Response) 객체에 이 쿠키를 실어 클라이언트에게 전송합니다.
    4.  (선택적) 쿠키 삭제 후에는 명시적으로 리다이렉트(Redirect) 처리하는 것이 좋습니다.

## 2. 쿠키 활용을 통한 웹 기능 구현
*   **다양한 활용 예시:** 쿠키는 단순히 로그인 정보를 저장하는 것 외에도 다양한 방식으로 활용될 수 있습니다.
    *   **버튼 및 링크에 적용:** 웹페이지의 버튼이나 링크에 쿠키를 전달하는 방식으로 사용자가 특정 정보를 가지고 페이지 이동을 하도록 할 수 있습니다.
    *   **데이터 전송:** ID나 패스워드와 같이 구조화된 정보를 객체 형태로 만들거나, 단순히 ID만 추출하여 쿠키에 담아 다음 페이지로 전송할 수 있습니다.
*   **시스템 설계 관점:**
    *   쿠키 컨트롤러를 통해 어떤 정보를 가져와야 하는지(예: ID만, 전체 객체)를 명확히 정의하는 것이 중요합니다.
    *   페이지 로딩 시, 클라이언트가 전달해 온 쿠키 값을 받아와서 (예: `요청한 쿠키 밸류`) 이를 모델에 담아 화면에 보여주는 방식으로 활용할 수 있습니다.

## 3. 회원 인증 및 세션 관리 흐름 구현 (로그인/로그아웃)
강의에서 제시된 가장 핵심적인 구현 흐름은 다음과 같습니다.

*   **로그인 과정 (인증):**
    1.  **폼 요청:** 로그인 정보를 입력할 수 있는 폼(Form) 페이지를 요청합니다.
    2.  **로그인 처리:** 사용자가 ID와 비밀번호를 제출하면, 컨트롤러가 해당 값을 받아 처리합니다.
    3.  **인증 성공:** ID와 PW가 일치하면(로그인 성공), 시스템은 **사용자의 식별 정보를 쿠키로 클라이언트에게 전송**합니다.
    4.  **리다이렉트:** 로그인 처리가 완료된 후, 사용자를 메인 페이지(User List 등)로 리다이렉트합니다.
*   **페이지 접근 제어 (인가):**
    *   사용자가 `UserList` 등 내부 페이지를 요청할 때, 서버는 **쿠키에 유효한 로그인 정보가 있는지 확인**합니다.
    *   **로그인 상태:** 쿠키가 존재하면, 해당 페이지(User List)를 보여줍니다.
    *   **로그아웃 상태:** 쿠키가 없거나 만료되었다면, 유효성 검사(Validation)에 실패한 것으로 보고 **다시 로그인 폼으로 리다이렉트**합니다.
*   **로그아웃 구현:**
    *   로그아웃 기능을 구현하려면, 반드시 사용자 세션 정보를 담고 있는 쿠키를 **삭제(유효기간 0 설정)**해야 합니다.
    *   삭제 후에는 로그인 폼 페이지로 리다이렉트 시켜야 합니다.

## 4. 시스템 구현의 전반적인 설계와 학습 가이드
*   **필수 구현 컨트롤러:** 전체 기능을 구현하기 위해 최소한 네 가지 컨트롤러 메소드가 필요합니다.
    1.  로그인 폼 보여주기 (`Show Login`)
    2.  로그인 처리 (`Login Process`)
    3.  사용자 리스트 보여주기 (`Show User List`)
    4.  로그아웃 처리 (`Logout`)
*   **필수 HTML 페이지:** 최소 두 가지의 뷰(View)가 필요합니다. (로그인 폼 페이지, 사용자 리스트 페이지)
*   **학습 접근법 (조언):**
    *   전체 시스템을 한 번에 이해하려 하기보다, **가장 간단한 기능부터 단계적으로 구현**해 나가는 것이 중요합니다.
    *   **문제 분할:** "쿠키 삭제하기" → "로그인 폼 보여주기" → "로그인 처리 로직 구현"과 같이 작은 문제들로 나누어 접근하면 부담이 줄어듭니다.
    *   **발전 단계:** 여력이 되는 경우, 폼 유효성 검사(Validation)와 같은 고급 기능을 추가적으로 고려할 수 있습니다.




1. 계층형 아키텍처 복습

웹 애플리케이션은 보통 역할을 나눠서 만듦.

Controller → Service → DAO/Repository → DB

각 계층 역할은 이거임.

계층	역할
Presentation Layer	사용자 요청 처리, 화면 응답
Service Layer	비즈니스 로직 처리
Data Layer	DB 접근
View	사용자에게 보여지는 화면

Spring MVC는 주로 Presentation Layer, 즉 웹 요청을 받고 응답하는 쪽을 담당함.

중요한 구조는 이거임.

Controller는 Service에 의존
Service는 Repository/DAO에 의존
객체 생성과 주입은 Spring IoC/DI가 관리
2. HTTP 기본 원리

웹은 클라이언트와 서버가 요청/응답을 주고받는 구조임.

클라이언트 요청
→ 서버 처리
→ 서버 응답

중요한 건 클라이언트가 먼저 요청해야 서버가 응답한다는 점임.

서버가 아무 이유 없이 먼저 브라우저에 데이터를 보내는 구조가 아님.

3. HTTP는 Stateless

HTTP는 기본적으로 Stateless, 즉 무상태 프로토콜임.

뜻은 이거임.

요청과 응답이 끝나면 서버는 이전 요청 정보를 기억하지 않음.

예를 들어 사용자가 로그인했어도, 다음 요청에서 서버는 그냥 보면 “처음 온 사람인가?” 싶을 수 있음.

그래서 로그인 상태, 장바구니, 사용자 정보 같은 걸 유지하려면 별도 기술이 필요함.

그게 Cookie와 Session임.

4. Spring MVC 요청 흐름 복습

Spring MVC 요청 흐름은 계속 중요함.

브라우저 요청
→ DispatcherServlet
→ HandlerMapping
→ Controller
→ Service
→ Model
→ ViewResolver
→ Thymeleaf
→ HTML 응답

DispatcherServlet은 모든 요청의 입구임.

컨트롤러는 이런 식으로 요청을 받음.

@Controller
public class UserController {

    @GetMapping("/users")
    public String users() {
        return "users/list";
    }
}

여기서 "users/list"는 문자열 응답이 아니라 View 이름임.

5. 요청 매핑

URL과 HTTP 메서드에 따라 실행할 컨트롤러 메서드를 정함.

어노테이션	의미
@RequestMapping	공통 요청 매핑
@GetMapping	조회, 화면 요청
@PostMapping	생성, 폼 제출
@PutMapping	전체 수정
@PatchMapping	일부 수정
@DeleteMapping	삭제

같은 URL이라도 GET/POST에 따라 다른 메서드 실행 가능함.

@GetMapping("/login")
public String loginForm() {
    return "login";
}

@PostMapping("/login")
public String loginProcess() {
    return "redirect:/users";
}
6. Validation

Validation은 사용자가 보낸 값이 올바른지 검증하는 것임.

예를 들면 이런 것들임.

이름이 비어있으면 안 됨
이메일 형식이어야 함
비밀번호는 8자 이상이어야 함
나이는 음수면 안 됨

예전 방식으로 하면 if문이 많아짐.

if (name == null || name.isBlank()) {
    // 에러 처리
}

이게 많아지면 코드가 지저분해짐.

그래서 Spring Validation을 씀.

7. Validation 사용 흐름

Validation 기본 흐름은 이거임.

DTO 필드에 검증 어노테이션 붙임
→ Controller에서 @Valid 사용
→ BindingResult로 에러 받음
→ 에러 있으면 다시 폼 화면
→ 에러 없으면 서비스 로직 실행

예시:

@Getter
@Setter
public class UserLoginRequest {

    @NotBlank(message = "아이디는 필수입니다.")
    private String username;

    @NotBlank(message = "비밀번호는 필수입니다.")
    private String password;
}

컨트롤러에서는 이렇게 씀.

@PostMapping("/login")
public String login(
        @Valid @ModelAttribute UserLoginRequest request,
        BindingResult bindingResult
) {
    if (bindingResult.hasErrors()) {
        return "login";
    }

    return "redirect:/users";
}

중요한 점은 BindingResult는 @Valid 바로 뒤에 와야 함.

8. 자주 쓰는 검증 어노테이션
어노테이션	의미
@NotNull	null 불가
@NotEmpty	빈 문자열 불가
@NotBlank	공백 문자열 불가
@Size	길이 제한
@Email	이메일 형식
@Pattern	정규식 검사
@Min	최소값
@Max	최대값

문자열 검증에서는 보통 @NotBlank가 자주 쓰임.

@NotBlank(message = "이름은 필수입니다.")
private String name;
9. BindingResult

BindingResult는 검증 실패 정보를 담는 객체임.

if (bindingResult.hasErrors()) {
    return "user/form";
}

에러가 있으면 데이터를 저장하면 안 됨.

폼으로 다시 보내서 사용자가 수정하게 해야 함.

중요한 점은 Validation 실패 시 보통 redirect가 아니라 forward 방식으로 원래 폼을 다시 보여주는 게 좋음.

왜냐하면 redirect를 하면 요청이 새로 만들어져서 에러 정보가 날아가기 쉬움.

10. Thymeleaf에서 에러 출력

폼 화면에서 에러 메시지를 보여줄 수 있음.

<input type="text" th:field="*{username}">
<p th:if="${#fields.hasErrors('username')}"
   th:errors="*{username}">
</p>

핵심은 th:field로 DTO 필드와 input을 연결하는 것임.

<form th:object="${userLoginRequest}">
    <input th:field="*{username}">
</form>
11. Forward와 Redirect 차이
Forward

서버 내부에서 같은 요청을 유지한 채 View로 넘김.

return "login";

특징:

요청 객체 유지됨
Model 데이터 유지 가능
Validation 에러 표시하기 좋음

검증 실패 시 사용하기 좋음.

Redirect

브라우저에게 새 주소로 다시 요청하라고 시키는 것임.

return "redirect:/users";

특징:

새 요청 발생
기존 Request 사라짐
URL 변경됨
POST 중복 제출 방지 가능

처리 성공 후 사용하기 좋음.

예시:

POST /login
→ 로그인 성공
→ redirect:/users
→ GET /users
12. Cookie

쿠키는 브라우저에 저장되는 작은 데이터임.

서버가 응답에 쿠키를 담아 보내면 브라우저가 저장함.

다음 요청부터 브라우저는 그 쿠키를 서버에 같이 보냄.

서버 → 쿠키 발급 → 브라우저 저장
브라우저 → 다음 요청 때 쿠키 같이 전송

쿠키 생성 예시:

Cookie cookie = new Cookie("loginId", userId);
cookie.setPath("/");
cookie.setMaxAge(60 * 60);
response.addCookie(cookie);
13. 쿠키 읽기

요청에 담긴 쿠키를 읽을 때는 request.getCookies() 사용함.

Cookie[] cookies = request.getCookies();

if (cookies != null) {
    for (Cookie cookie : cookies) {
        System.out.println(cookie.getName());
        System.out.println(cookie.getValue());
    }
}

getCookies()는 배열을 반환함.

왜냐하면 쿠키가 여러 개일 수 있기 때문임.

14. 쿠키 속성
속성	의미
name	쿠키 이름
value	쿠키 값
path	쿠키 적용 경로
domain	쿠키 적용 도메인
maxAge	쿠키 유지 시간

path를 /로 하면 전체 애플리케이션에서 쿠키 사용 가능함.

cookie.setPath("/");

maxAge를 설정하지 않으면 브라우저 종료 시 사라지는 세션 쿠키가 됨.

15. 쿠키 삭제

쿠키는 서버가 브라우저 저장소를 직접 지우는 게 아님.

같은 이름의 쿠키를 다시 보내면서 maxAge를 0으로 설정해서 삭제를 유도함.

Cookie cookie = new Cookie("loginId", null);
cookie.setPath("/");
cookie.setMaxAge(0);
response.addCookie(cookie);

핵심은 이거임.

같은 이름 + 같은 path + maxAge 0

이렇게 해야 기존 쿠키가 제대로 삭제됨.

16. Cookie로 로그인 상태 유지

단순 로그인 흐름은 이렇게 볼 수 있음.

GET /login
→ 로그인 폼 보여줌

POST /login
→ 아이디/비밀번호 확인
→ 성공하면 쿠키 생성
→ response.addCookie()
→ redirect:/users

GET /users
→ 요청 쿠키 확인
→ 쿠키 있으면 목록 보여줌
→ 쿠키 없으면 redirect:/login

컨트롤러 메서드는 최소 이렇게 필요함.

1. 로그인 폼 보여주기
2. 로그인 처리하기
3. 사용자 리스트 보여주기
4. 로그아웃 처리하기
17. 쿠키 보안 주의

쿠키는 브라우저에 저장됨.

그래서 민감한 정보를 넣으면 안 됨.

절대 넣으면 안 되는 것:

비밀번호
주민번호
카드번호
중요한 개인정보
권한 정보 원문

쿠키에는 노출돼도 큰 문제 없는 값만 넣어야 함.

예를 들면:

테마 설정
언어 설정
최근 본 상품 ID

로그인 인증은 단순 쿠키만으로 처리하면 위험함.

실무에서는 보통 Session이나 Spring Security를 씀.

18. Session

세션은 사용자 상태 정보를 서버에 저장하는 방식임.

브라우저에는 실제 사용자 정보를 저장하지 않고, 세션을 찾기 위한 ID만 쿠키로 보냄.

흐름은 이거임.

서버가 세션 생성
→ 세션 ID 발급
→ 세션 ID를 쿠키로 브라우저에 보냄
→ 브라우저가 다음 요청 때 세션 ID 쿠키 전송
→ 서버가 세션 ID로 서버 메모리의 세션 찾음

즉, 세션은 서버 저장소고, 쿠키는 세션 ID 전달 수단임.

19. Cookie와 Session 차이
구분	Cookie	Session
저장 위치	클라이언트 브라우저	서버
보안	상대적으로 취약	상대적으로 안전
저장 형태	문자열 key-value	객체 저장 가능
사용 예시	테마, 언어, 최근 본 상품	로그인 정보
서버 부담	적음	있음

한 줄로 보면 이거임.

Cookie = 브라우저에 저장
Session = 서버에 저장, 브라우저에는 세션 ID만 저장
20. 오늘 제일 중요한 흐름

오늘 내용은 이렇게 연결됨.

HTTP는 Stateless라서 요청이 끝나면 상태를 기억 못 함
→ 로그인 상태 유지가 필요함
→ Cookie/Session 사용
→ 쿠키는 브라우저 저장
→ 세션은 서버 저장
→ 로그인 같은 중요한 정보는 세션 방식이 더 적합

Validation 흐름은 이렇게 기억하면 됨.

폼 제출
→ DTO에 바인딩
→ @Valid로 검증
→ BindingResult에 에러 저장
→ 에러 있으면 폼으로 forward
→ 에러 없으면 처리 후 redirect
최종 요약

오늘 공부 핵심은 이거임.

1. Spring MVC는 DispatcherServlet 중심으로 요청을 처리함
2. Controller는 URL과 HTTP 메서드에 따라 실행됨
3. Validation은 DTO에 규칙을 붙이고 @Valid로 실행함
4. BindingResult로 검증 에러를 처리함
5. 검증 실패는 forward, 처리 성공은 redirect가 적합함
6. HTTP는 Stateless라서 상태 유지가 안 됨
7. 상태 유지를 위해 Cookie와 Session을 사용함
8. Cookie는 브라우저 저장, Session은 서버 저장임
9. 쿠키 삭제는 maxAge 0으로 덮어쓰는 방식임
10. 로그인 인증은 단순 쿠키보다 세션/Spring Security 쪽이 안전함

한 줄 요약하면 이거임.

오늘은 Spring MVC 요청 처리 흐름 위에 Validation으로 입력값을 검증하고, HTTP의 Stateless 문제를 Cookie와 Session으로 해결하는 방법을 배움.
