## 1. 과정의 목표 및 장기 학습 과정의 중요성
- **장기 과정의 특성:** 6개월 과정과 같이 긴 학습 과정은 과정 중간에 지치거나 포기하고 싶은 마음이 들기 쉽다.
- **협력과 동기 부여:** 개인의 열정은 유지하기 어렵기 때문에, 동료들 간의 긍정적인 상호작용(회고 활동, 친밀감 형성)이 큰 동기 부여가 된다.
- **선한 영향력의 중요성:** 긍정적이고 열정적인 동료의 존재가 지쳐가는 사람에게 힘을 주고, 반대로 부정적인 태도(불평, 어려움 토로)는 주변에 쉽게 전파되므로 적극적인 태도가 필요하다.
- **학습의 목표 재확인:** 현재 배우고 있는 모든 과정(Java, 데이터베이스, JDBC, API, 웹 기술 등)은 궁극적으로 **스프링 프레임워크**를 활용하여 웹 애플리케이션을 완성하는 것을 목표로 한다.

## 2. 스프링 프레임워크의 개념 이해 (비유 설명)
- **프레임워크의 정의:** 프레임워크는 무(無)에서 시작하는 것이 아니라, 어떤 구조가 이미 준비된 '뼈대' 또는 '반제품'을 의미한다.
- **밀키트 비유:** 스프링 프레임워크는 요리 과정의 '밀키트'와 같다.
    - 밀키트가 있으면 (프레임워크 활용) → 체계적인 과정(설명서)을 따라 최선의 맛을 내기 쉽다.
    - 밀키트가 없으면 (맨땅부터 시작) → 모든 재료 준비부터 배합까지의 과정이 매우 복잡하고 어려워 최악의 결과가 나올 수도 있다.
- **스프링의 장점:** 스프링은 이미 잘 갖춰진 기반 위에서 개발을 할 수 있게 해주며, 개발자는 이 기본 구조를 기반으로도 자유롭게 필요한 설정이나 재료를 변경하거나 교체하여 사용 목적에 맞게 응용할 수 있다.
- **Spring Boot의 역할:** Spring Boot는 복잡했던 설정 과정(설정 및 의존성 관리)을 간편하게 만들어주는 도구이다. 이는 내부적으로 스프링 프레임워크가 동작하며 필요한 설정을 대신 처리해주는 역할을 한다.

## 3. 스프링 프로젝트의 구조 및 핵심 원리 학습
- **프로젝트 환경 구성:** 실제 강의에서는 `Core/IOC`을 학습하기 위해 웹 기능을 제외한 기본 스프링 부트 프로젝트를 생성하는 실습을 진행했다.
- **라이브러리 관리:** 프로젝트의 필요한 라이브러리(의존성)는 Maven Repository나 Gradle Repository 같은 외부 저장소에서 가져오지만, 로컬에는 `.m2` 디렉터리에 저장되어 있다.
- **기본 구조 이해:**
    - **`src/main/java`:** 사용자가 직접 코드를 작성하는 소스 코드가 들어가는 공간이다.
    - **`@SpringBootApplication`:** 이 어노테이션은 해당 클래스가 스프링 부트 애플리케이션의 시작점임을 나타내는 데 가장 중요한 역할을 한다.
    - **설정 파일 (Properties):** 스프링 애플리케이션의 속성 값은 보통 `application.properties` 또는 `application.yml` 파일에 정의하며, 이를 통해 애플리케이션의 구동 환경을 설정한다.
- **필수 의존성 이해:** 특정 기능을 사용하기 위해서는 반드시 관련된 라이브러리(의존성)가 추가되어야 한다. (예: `@RestController` 같은 웹 관련 기능을 쓰려면 `spring-boot-starter-web` 라이브러리가 필수로 추가되어야 함).

## 4. 핵심 개념 복습: 의존성 주입과 결합도(Coupling)
- **IoC/DI (제어의 역전/의존성 주입):** 스프링 프레임워크의 핵심 개념이다. 객체(Object)를 직접 생성하는 코드가 아닌, 스프링 컨테이너가 필요로 하는 객체를 대신 찾아서 연결(주입)해주는 원리이다.
- **결합도(Coupling) 감소의 목표:** 소프트웨어 개발 시, 모듈 간의 결합도(의존성)를 낮추는 것이 중요하다.
    - 인터페이스(Interface)를 도입하면 결합도를 낮출 수 있지만, 실제로 객체를 생성하는 부분(예: `TV` 객체를 생성하는 코드)이 여전히 특정 클래스에 의존하게 되면 결합도가 낮아지지 않는다.
    - **해결책:** **팩토리(Factory)** 패턴이나 IoC 컨테이너 같은 기술을 이용해 객체 생성 책임을 분리해야, 독립적인 방식으로 객체를 관리하고 필요에 따라 교체할 수 있게 되어 결합도가 완전히 낮아진다.

## 1. 결합도(Coupling)의 문제점과 인터페이스를 통한 해결
**핵심 내용:**
*   **높은 결합도(Tight Coupling)의 문제:** 시스템의 한 부분이 다른 부분과 너무 밀접하게 연결되어 있을 때 발생합니다. (예: `TVUser`가 `CaramiTV`라는 특정 객체를 직접 사용함).
*   **결합도의 영향:** 만약 핵심 객체(예: `CaramiTV`)를 새로운 기술(예: `Stv`)로 교체하려면, 해당 객체에 의존하는 사용자의 코드 전체를 대폭 수정해야 하는 문제가 발생합니다.
*   **해결책: 인터페이스(Interface) 활용:** 사용자가 구체적인 구현체(Concrete Class)가 아닌 **인터페이스 타입**에 의존하도록 코드를 작성해야 합니다.
*   **효과:** 인터페이스만 기준으로 코드를 작성하면, 실제 구현체(빈)가 바뀌더라도 사용자 코드(클라이언트 코드)는 수정할 필요가 없어집니다. (예: `List` 인터페이스를 사용하면 `ArrayList`가 되든 `LinkedList`가 되든 코드가 변하지 않음).

## 2. 객체 생성 의존성 문제와 TV 팩토리 패턴
**핵심 내용:**
*   **새로운 문제점:** 인터페이스를 사용해 결합도는 낮췄지만, 만약 사용자 코드 내에서 여전히 `new` 키워드를 사용하여 객체를 직접 생성한다면 (`TVUser`가 `new CaramiTV()`를 호출하는 경우), 여전히 높은 결합도가 남아있게 됩니다.
*   **TV 팩토리(Factory) 패턴의 등장:** 객체 생성의 책임을 사용자 코드에서 분리하기 위해 '공장(Factory)' 같은 별도의 객체(예: `TVFactory`)를 도입합니다.
*   **작동 방식:** 사용자 코드는 더 이상 `new`를 사용하지 않고, 대신 팩토리에게 "어떤 종류의 TV가 필요한지" 요청(예: `createTV("s")`)하고, 팩토리가 실제 객체를 생성하여 돌려주는 구조를 만듭니다.
*   **결과:** 팩토리 패턴을 사용하면 객체 생성에 대한 의존성도 낮아져, 객체가 교체되더라도 사용자 코드를 수정할 필요가 없어집니다.

## 3. IoC 컨테이너 개념 이해: 제어의 역전(Inversion of Control)
**핵심 내용:**
*   **핵심 개념:** IoC(Inversion of Control, 제어의 역전)는 **'제어권을 역전시킨다'**는 의미입니다.
*   **변화 전 (기존 방식):** 개발자(프로그래머)가 객체의 생성 및 라이프사이클 관리(어떻게 만들고, 언제 사용하고, 언제 파괴할지)를 직접 책임졌습니다.
*   **변화 후 (IoC 적용):** 객체의 생성과 생명주기 관리라는 책임을 개발자 본인이 아닌 **프레임워크나 컨테이너(Container)**에게 넘기는 것입니다. (책임의 전가)
*   **비유:**
    *   **TV 팩토리:** 단순하게 객체를 생성하는 역할을 수행합니다.
    *   **IoC 컨테이너:** 팩토리보다 더 큰 역할을 합니다. 객체의 생성뿐만 아니라, 객체가 생성된 후 초기화되는 과정(초기화 메서드 호출 등)이나 소멸 과정(종료 로직)까지 **전체 생명주기**를 관리합니다.
*   **실생활 비유:** 스마트폰이나 가전제품들이 표준화된 리모컨이나 인터페이스를 사용하는 것과 같이, 소프트웨어의 핵심 기능도 컨테이너가 통일된 관리 체계를 제공하는 것과 같습니다.

## 4. IoC 컨테이너의 작동 원리 및 장점
**핵심 내용:**
*   **컨테이너 역할:** IoC 컨테이너는 애플리케이션의 구성 요소들(객체)을 담고 관리하는 저장소 역할을 하며, 이 구성 요소들을 **빈(Bean)**이라고 부릅니다.
*   **빈 컨테이너(Bean Container):** 빈(Bean)의 생성과 라이프사이클을 관리하는 컨테이너를 의미합니다. (예: 웹 애플리케이션 서버가 서블릿 컨테이너나 JSP 컨테이너를 포함하는 것과 동일한 원리).
*   **IoC의 궁극적인 이점:**
    *   **결합도 하락:** 객체 간의 의존성을 낮추어, 한 부분을 수정해도 전체 시스템에 미치는 영향(파급효과)을 최소화합니다.
    *   **테스트 용이성 증가:** 객체들이 느슨하게 연결되어 있기 때문에, 특정 기능을 테스트할 때 전체 시스템을 띄우지 않고 독립적으로 테스트할 수 있어 개발 및 테스트가 용이합니다.
    *   **코드 재사용성 및 유지보수성 향상:** 모듈 단위로 개발과 수정이 가능해져 시스템의 전반적인 품질이 높아집니다.

## 5. 빈(Bean) 등록 방식: 설정 방법 학습
**핵심 내용:**
*   **빈(Bean) 등록의 정의:** IoC 컨테이너에게 "내가 관리하고 싶은 객체(빈)가 여기 있다"라고 알려주는(설정하는) 과정입니다.
*   **주요 등록 방식 3가지:**
    1.  **XML 방식 (XML Configuration):** 과거 가장 많이 사용되던 방식으로, XML 파일에 빈의 ID와 클래스를 명시적으로 정의합니다. (장점: 명확성 / 단점: 문자로 값을 전달하므로 오타 발생 시 런타임 오류 발생 가능).
    2.  **Java Config 방식 (Java Code):** 자바 코드를 이용하여 `@Configuration` 등의 어노테이션을 붙이고 `@Bean` 메서드를 통해 빈을 정의하는 방식입니다. (장점: 개발 언어 기반이므로 컴파일 시 오류를 확인할 수 있어 안정적임. 현재 표준적으로 사용됨).
    3.  **컴포넌트 스캔 방식 (Component Scan/Annotation):** `@Component` 같은 어노테이션을 클래스에 붙이면, 스프링 컨테이너가 해당 클래스를 자동으로 찾아 빈으로 등록하는 가장 간편한 방식입니다.

***

**💡 핵심 요약 포인트:**
*   **결합도가 높다** $\rightarrow$ **변경에 취약하다.**
*   **인터페이스를 사용한다** $\rightarrow$ **결합도를 낮춘다.**
*   **IoC 컨테이너를 사용한다** $\rightarrow$ **객체 생성 책임을 프레임워크에 맡겨서** (제어의 역전) **유지보수성과 안정성을 극대화한다.**

## 1. 스프링 공장 이용의 필요성 및 빈 등록 방식
- **스프링 공장(Factory)의 역할:** 애플리케이션의 구조를 크게 개선하며, 객체 간의 결합도를 낮추는 핵심 역할을 수행한다.
- **빈 등록 방식의 변화 (XML $\to$ Java Config):**
    - XML 파일 방식은 오류를 주로 **런타임(Runtime)**에 감지하는 한계가 있었다.
    - Java 기반 설정(Annotation Config)을 사용하면, 컴파일 시점(**Compile Time**)에 타입 오류를 미리 잡아낼 수 있어 안정성이 높고 선호된다.
- **빈 등록 방법:**
    - 클래스 레벨에 `@Configuration`을 사용하여 설정 클래스를 정의한다.
    - `@Bean` 어노테이션을 사용해 해당 메서드가 반환하는 객체를 스프링 컨테이너가 관리하는 빈(Bean)으로 등록한다.

## 2. ApplicationContext를 이용한 빈 생성 및 생명주기 관리
- **컨테이너의 선택:** 스프링은 `BeanFactory`와 `ApplicationContext`라는 공장(Container)을 제공한다. 그 중 기능이 확장된 **`ApplicationContext`**를 주로 사용한다.
- **빈 생성 원리:**
    - `ApplicationContext`가 초기화되면서 설정 파일에 정의된 모든 빈(Bean)을 자동으로 생성한다.
    - **스코프(Scope) 기본값 - Singleton:** 특별히 스코프를 지정하지 않은 빈은 기본적으로 **싱글턴(Singleton)** 형태로 동작한다. 즉, 애플리케이션이 동작하는 동안 메모리상에 오직 하나의 인스턴스만 존재하며 공유된다.
    - **스코프 - Prototype:** 빈을 등록할 때 `@Scope("prototype")`을 지정하면, 해당 빈은 공장 초기화 시점이 아닌, **사용(요청)할 때마다 새로운 인스턴스**를 생성한다.
- **빈 생성 시 유의 사항:**
    - 컨테이너가 빈을 생성할 때, 등록된 모든 빈은 설정된 스코프에 따라 미리 생성되거나 사용 시점에 생성된다.
    - 빈을 등록하는 빈(Outer Bean)의 생성 과정에서도 내부적으로 의존하는 빈들이 순차적으로 생성됨을 이해해야 한다.

## 3. 빈 사용 방법 및 의존성 주입 (DI) 이해
- **빈 획득 (Dependency Lookup):**
    - **`getBean(String id)`:** ID를 사용하여 빈을 얻는 방법. 모든 빈이 `Object` 타입으로 반환되므로, 사용 시 반드시 형 변환이 필요하다.
    - **`getBean(Class<T> type)`:** 타입을 사용하여 빈을 얻는 방법. 타입 안전성이 높다.
    - **다중 빈 처리:**
        - 여러 빈이 동일한 타입을 가질 경우, 타입만으로는 어떤 빈을 가져와야 할지 컨테이너가 알 수 없어 오류가 발생한다.
        - 따라서 이 경우 반드시 **ID를 명시**하여 컨테이너가 어떤 빈을 반환할지 지정해주어야 한다.
- **의존성 주입 (DI, Dependency Injection):**
    - **핵심 개념:** 객체가 자신이 필요로 하는 객체(의존성)를 직접 생성하는 것이 아니라, 외부 컨테이너(스프링)에게 "필요한 빈이 무엇이다"라고 선언만 하면, 스프링이 알아서 해당 빈을 찾아서 필요한 위치에 넣어주는(주입해주는) 방식이다.
    - **구현:** `@Autowired`와 같은 어노테이션을 사용하여 주입을 요청한다.
    - **이점:** 코드를 간결하게 유지하며, 객체 간의 결합도를 극도로 낮출 수 있다. (개발자는 빈의 생성 과정에 신경 쓸 필요 없이 사용에만 집중할 수 있음)

## 1. 스프링 프레임워크의 구조 이해 (IoC 컨테이너)
- 스프링 프레임워크는 가장 하단에 **코어 컨테이너**라는 기반 위에 동작합니다. 모든 상위 모듈은 이 코어 컨테이너를 기반으로 작동합니다.
- 강의 목표는 스프링 프레임워크의 핵심인 **IoC 컨테이너**를 이해하고, 그 동작 원리를 파악하는 것입니다.

## 2. 제어의 역전(IoC) 개념과 중요성
- **IoC (Inversion of Control, 제어의 역전):** 프로그래머가 객체(빈)를 생성하고 관리하던 제어권을, 외부의 컨테이너(스프링 컨테이너)에게 넘기는 원리입니다.
- **기존 방식의 문제점:** 프로그램의 핵심 로직(빈의 생성, 라이프사이클 관리 등)이 코드 내에 직접 구현되어 결합도가 높아집니다.
- **IoC를 통한 장점 (결합도 완화):**
    - 객체를 직접 생성하지 않고 컨테이너가 대신 관리하게 함으로써, 구현체가 변경되어도 사용자(Client) 코드는 전혀 수정할 필요가 없어집니다.
    - 코드가 유연하고 재사용성이 높아지는 등 높은 수준의 아키텍처를 설계할 수 있습니다.
- **예시 (TV 공장):** TV를 직접 만드는 것이 아니라 'TV 공장'을 이용하면, 내부적으로 TV의 종류가 바뀌어도(예: 일반 TV $\rightarrow$ 스마트 TV) 사용자의 코드는 영향을 받지 않아도 됩니다. 스프링 프레임워크는 이 '공장' 역할을 수행합니다.

## 3. 스프링을 활용한 빈(Bean) 관리 원리
- 스프링 프레임워크는 모든 객체(자바 객체)를 **빈(Bean)**이라고 부르며, 이 빈들을 생성하고 관리하는 역할을 컨테이너가 맡습니다.
- **빈 등록 방식의 발전:**
    - 초기에는 XML과 같은 설정 파일을 사용했지만, 오타 등 실시간 에러를 잡기 어렵다는 단점이 있었습니다.
    - 현재는 `@Bean`과 같은 **애너테이션(Annotation)**을 사용하여 빈을 정의합니다. 이 애너테이션을 붙이는 것만으로 해당 클래스가 빈 역할을 하도록 스프링 컨테이너에 알려줄 수 있습니다.
- **빈 생성 방식:**
    - **생성자 주입:** 객체를 생성할 때 필요한 값을 생성자를 통해 직접 전달합니다.
    - **Setter 주입:** 객체 생성 후, Setter 메서드를 통해 값을 설정해 줍니다.
- **빈 컨테이너 비교:**
    - `BeanFactory`: 빈을 요청할 때마다 생성(Lazy Loading)하는 방식입니다.
    - `ApplicationContext`: 공장(컨텍스트)이 활성화될 때 필요한 빈들을 미리 생성(Eager Loading)하여 메모리에 올려두므로, 사용 시점에서 접근 속도가 빠릅니다.

## 4. 빈의 범위(Scope) 및 의존성 주입(DI)
- **빈의 범위 (Scope):** 빈 객체가 몇 개의 인스턴스를 가질지 정의하는 것입니다.
    - **Singleton (기본값):** 가장 일반적인 형태로, 컨테이너가 단 하나의 인스턴스만 생성하여 모든 곳에서 공유합니다.
    - **Prototype:** 요청할 때마다(사용할 때마다) 새로운 독립적인 객체를 생성합니다.
- **의존성 주입 (DI, Dependency Injection):**
    - 가장 이상적인 방식입니다. 프로그래머가 직접 "빈을 얻어와라"($`get<Bean>()`$)라고 요청할 필요 없이, 단순히 **사용할 것이라는 위치에 선언만 해 놓으면** 스프링 프레임워크가 알아서 적절한 시점에 빈을 찾아 필요한 곳에 주입(Injection)해 줍니다.
    - 이는 코드를 더욱 간결하고 깔끔하게 만드는 핵심 메커니즘입니다.

## 5. 외부 설정 파일 관리 (PropertySource)
- 객체에 필요한 값(예: 주사위의 페이스 수)을 코드에 하드코딩하는 대신, 외부 설정 파일(예: `dice.properties`)을 통해 관리하는 것이 모범 사례입니다.
- **활용 방법:**
    - `@PropertySource` 애너테이션을 사용하여 스프링 컨테이너에게 해당 설정 파일을 사용하겠다고 알려줍니다.
    - `@Value` 애너테이션을 사용하여 설정 파일의 특정 키-값 쌍을 가져옵니다.
- **작동 원리:** 이 과정을 통해 프로그램은 설정 파일을 읽어온 값을 활용하여 빈을 초기화할 수 있게 되며, 개발자는 코드 수정 없이 외부 파일만 수정하여 기능을 변경할 수 있습니다.

## 1. 외부 의존성 주입의 원리 이해
- **외부 라이브러리 객체 사용:** 외부 파일이나 다른 라이브러리에서 제공하는 객체를 사용할 때, 해당 객체의 속성(Property)을 통해 값을 지정하여 새로운 객체를 생성할 수 있습니다.
- **데이터 소스 예시:** 커넥션 풀(Connection Pool) 같은 객체를 생성하는 과정에서, DB URL, 사용자 이름, 패스워드 등의 정보(값)가 필요하며, 이러한 값들을 프로퍼티(Properties)에 넣어주면 라이브러리들이 해당 값을 읽어와 실제 데이터 소스 객체를 생성합니다.
- **주입(Injection)의 목적:** 클래스나 객체가 생성될 때 필요한 값이나 다른 객체를 외부에 정의된 방식으로 넣어주는 것이 핵심입니다.

## 2. 스프링의 의존성 주입(DI) 방식 심화 학습
- **DI 방식의 종류:** Spring 프레임워크에서 객체(Bean)가 의존하는 다른 객체를 주입받는 방식은 크게 세 가지가 있습니다.
    *   **생성자 주입 (Constructor Injection):** 객체 생성 시 생성자를 통해 필수 값을 전달받아 주입하는 방식입니다. (가장 확실하고 권장되는 방식)
    *   **설정자 주입 (Setter Injection):** 객체 생성 이후에 setter 메서드를 통해 값을 설정해주며 주입받는 방식입니다. (유연성이 높으나, 필수 속성이 아닐 때 사용 권장)
    *   **필드 주입 (Field Injection):** (강의 텍스트에서는 직접 다루지 않으나 언급된 방식) 필드에 직접 주입받는 방식입니다.
- **DI의 구성 요소:**
    *   **의존성 (Dependency):** 특정 객체가 작동하는 데 필요한 다른 객체. (예: 플레이어는 다이스 객체에 의존)
    *   **IoC 컨테이너 (Spring Container):** 객체 간의 의존성 관계를 파악하고, 객체들을 자동으로 생성하여 주입해주는 '공장' 역할을 합니다.

## 3. 실제 비즈니스 로직 객체 구조화 및 DI 적용
- **객체 간의 관계 설정:** 주사위(Dice) 객체와 이를 사용하는 플레이어(Player) 객체, 그리고 전체 게임(Game)이라는 비즈니스 로직 객체를 설계합니다.
- **순환 의존성 및 주입의 흐름:**
    *   **다이스 → 플레이어:** `Player`는 주사위(Dice) 객체에 의존합니다.
    *   **플레이어 → 게임:** `Game`은 플레이어 리스트(`List<Player>`)에 의존합니다.
    *   **게임 → 플레이어 → 다이스:** 시스템은 '게임' 객체를 생성할 때, 이 게임이 여러 '플레이어'를 관리하고, 각 '플레이어'가 '다이스'에 의존하는 복잡한 의존성 구조를 형성합니다.
- **DI 적용 (세터 방식):**
    *   **`Player` 객체:** 생성자 방식 대신 세터 메서드를 사용하여 이름(`setName`)과 주사위(`setDice`)를 주입받도록 설정했습니다.
    *   **`Game` 객체:** `List<Player>`를 세터 메서드를 통해 주입받도록 설정했습니다.
    *   **장점:** 클래스 간의 의존성 관계를 명확히 파악하고, 스프링 컨테이너가 이 복잡한 의존 관계(Dice $\rightarrow$ Player $\rightarrow$ Game)를 순차적으로 해결하고 객체를 생성(주입)해 줍니다.

## 4. DI 방식 전환 및 구조화 패턴 이해
- **DI 방식의 변경:** 세터 주입 방식을 사용하던 `Player` 클래스를 **생성자 방식**으로 변경할 수 있습니다.
    *   **이점:** 생성자 방식은 해당 객체가 작동하는 데 **필수적인(required)** 의존성을 강제하여 객체의 안정성이 높아지고, 코드가 더 명확해집니다.
- **주입 방식에 따른 변경 사항:**
    *   주입 방식을 바꿀 때, 해당 클래스에 적절한 생성자 메서드(예: `Player(String name, Dice dice)`)를 직접 정의해주어야 합니다.
    *   이러한 방식의 전환은 클래스에 **생성자를 추가**하는 것으로 구현됩니다.

## 5. 계층형 아키텍처 관점에서의 객체 의존성 관리
- **전통적인 웹 애플리케이션 구조:** 실제 대규모 애플리케이션을 구성할 때도 이 객체 의존성 관리 원리가 적용됩니다.
    *   **Controller (Presentation Layer):** 사용자 요청을 받습니다.
    *   **Service (Business Logic Layer):** 비즈니스 로직을 처리하며, Controller로부터 의존성을 주입받습니다.
    *   **DAO/Repository (Data Access Layer):** 데이터베이스와의 통신을 담당하며, Service로부터 의존성을 주입받습니다.
- **핵심 원칙:** 각 계층은 자신의 역할을 수행하는 데 필요한 객체에 의존하고, 이 의존성은 IoC 컨테이너를 통해 외부에서 주입받는 것이 가장 효율적이고 확장성이 높은 방법입니다.

## 1. IoC와 제어의 역전 (Inversion of Control)의 이해
- **핵심 개념:** 스프링 프레임워크의 핵심 원리인 IoC(Inversion of Control)는 객체의 생성부터 라이프사이클 관리를 개발자가 직접 하는 것이 아니라, 스프링 프레임워크(IoC 컨테이너)에게 제어권을 넘겨주는 개념입니다.
- **작동 원리:** 스프링 컨테이너가 객체 생성에 필요한 정보를 미리 제공받으면, 이 정보를 바탕으로 객체를 관리하고 의존성 관계를 해결하여 객체들이 자동으로 생성되도록 합니다.
- **빈(Bean) 등록의 필요성:** 스프링 컨테이너가 어떤 빈을 관리해야 하는지 알 수 없으므로, 개발자는 애플리케이션에 사용될 빈들의 정보를 컨테이너에게 명시적으로 알려주어야 합니다.

## 2. 의존성 주입 (Dependency Injection, DI)의 개념 및 방식
- **DI의 정의:** 객체 간의 의존 관계를 처리하는 방식입니다. 개발자가 직접 필요한 객체를 찾아 가져오는 방식(Dependency Lookup) 대신, 시스템(스프링 컨테이너)이 필요한 시점에 의존 객체(Dependency)를 자동으로 주입해 주는 방식입니다.
- **DI의 주입 방식 3가지:**
    1. **Setter 메서드 방식:** Setter를 통해 주입받는 방식.
    2. **생성자(Constructor) 방식:** 생성자를 통해 주입받는 방식.
    3. **애노테이션(Annotation) 방식:** `@Autowired` 등의 어노테이션을 사용하여 주입받는 방식.
- **가장 바람직한 방식 (원칙):**
    *   애노테이션 방식이 가장 간편해 보이지만, 이 방식은 스프링 컨테이너에 대한 의존성이 매우 높습니다.
    *   반면, 생성자나 Setter를 통한 주입 방식은 스프링을 제외한 다른 컨테이너나 개발자가 직접 객체를 관리하는 환경에서도 적용 가능하므로, 구조적으로 더 독립적이고 유연합니다.
    *   **결론:** 구현의 유연성과 높은 결합도 해소 측면에서 생성자 주입이나 Setter 주입을 지향하는 것이 좋습니다.

## 3. 레이어드 아키텍처에서의 DI 적용 (실습 흐름)
- **계층 구조 구축 (Llayered Architecture):** 실제 애플리케이션은 일반적으로 [도메인 객체] $\rightarrow$ [DAO (데이터 접근)] $\rightarrow$ [Service (비즈니스 로직)] $\rightarrow$ [Controller (프레젠테이션)]의 계층 구조를 갖습니다.
- **의존성 흐름:** 각 계층은 자신이 필요한 아래 계층의 기능을 사용해야 합니다. (예: `Service`는 반드시 `DAO`에 의존합니다. `Controller`는 `Service`에 의존합니다.)
- **DI 적용 과정:**
    1. **빈 등록:** `UserConfig`와 같은 설정 클래스에서 빈을 등록합니다.
    2. **의존성 결정 및 주입:** 가장 의존성이 낮은 빈(예: `UserDAO`)부터 순서대로 빈을 등록하고, 각 빈이 자신이 의존하는 객체(예: `UserService`는 `UserDAO`에 의존)를 생성자나 Setter를 통해 명시적으로 주입받도록 설정합니다.
    3. **결과 검증:** 설정된 의존성 흐름에 따라 `Controller`를 통해 요청이 들어오면, `Service`를 거쳐 `DAO`가 호출되고, 최종적으로 비즈니스 로직이 정상적으로 실행되는지 확인합니다.

## 4. 빈 등록 방식의 확장 및 결론
- **ComponentScan (컴포넌트 스캔):**
    *   수동으로 `@Configuration` 클래스를 이용해 빈을 등록하는 방식(명시적 설정) 외에도, `@ComponentScan`을 이용해 특정 패키지 내의 클래스들을 스캔하여 자동으로 빈으로 등록할 수 있습니다.
    *   이는 빈 설정 과정을 훨씬 간편하게 만듭니다.
- **AOP 및 Lombok:**
    *   **AOP (Aspect-Oriented Programming):** 특정 기능(예: 로깅, 트랜잭션 관리)을 핵심 비즈니스 로직과 분리하여 처리할 수 있게 도와주는 도구입니다.
    *   **Lombok:** Getter, Setter 등 반복적이고 정형화된 코드를 직접 작성하지 않아도 컴파일 시 자동으로 코드를 생성해주는 도구입니다.
- **학습의 핵심 원칙:**
    *   단순히 사용법(Syntax)을 외우는 것보다, "왜 이런 구조와 방식을 사용하는지?"라는 근본적인 원리(Concept)를 이해하는 것이 가장 중요합니다.
    *   스프링이나 프레임워크 사용법 자체는 일종의 '약속(Convention)'이며, 이러한 약속들이 동작하는 원리를 이해하면 응용할 수 있습니다.
