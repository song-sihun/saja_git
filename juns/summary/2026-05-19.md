## 1. 스프링 프레임워크의 이해 및 학습 목표
*   **목표:** 이 과정은 Java 언어를 사용하여 웹 애플리케이션을 개발하는 것을 목표로 하며, 그 핵심 도구로 스프링 프레임워크를 사용하게 됩니다.
*   **학습 준비:** 스프링 프레임워크가 무엇인지, '프레임워크'라는 용어가 무엇을 의미하는지 등 기본적인 용어 정의를 명확히 이해하는 것이 중요합니다.
*   **중요성:** 스프링 프레임워크는 자바 어플리케이션을 개발하는 데 있어 업계에서 매우 높은 비율로 사용되는 핵심 기술입니다.

## 2. 좋은 소프트웨어의 핵심 원리: 결합도와 인터페이스
*   **객체지향 프로그래밍의 본질:** 객체지향은 여러 개체들이 독자적으로 기능하며, 서로 상호 작용(협동)하면서 문제를 해결해 나가는 방식입니다.
*   **결합도(Coupling)의 중요성:** 좋은 소프트웨어의 조건 중 가장 중요한 것은 '결합도를 낮추는 것'입니다.
    *   **높은 결합도의 문제점:** 개체 A가 개체 B에 강하게 의존하면, B가 교체되거나 변경될 때 A를 포함하여 시스템 전체의 코드를 대거 수정해야 하는 문제가 발생합니다. (예: TV 모델 교체 시, 사용자 객체 코드까지 수정 필요)
    *   **결합도를 낮춰야 하는 이유:** 외부 요소(데이터베이스, 라이브러리, 다른 컴포넌트)가 교체 가능성이 높기 때문에, 이를 어느 정도 추상화하여 수정의 영향을 최소화해야 합니다.
*   **해결책: 인터페이스(Interface) 사용:**
    *   객체와 객체 사이에 인터페이스를 두어 공통의 약속(규격)만 맞춘다면, 내부 구현체(구현체)가 누구로 바뀌어도 인터페이스를 사용하는 사용자 코드(클라이언트 코드)는 영향을 받지 않습니다.
    *   이는 마치 TV 사용자(클라이언트)가 TV의 실제 모델(구현체)이 아닌, 통일된 리모컨(인터페이스)만 사용하도록 설계하는 것과 같습니다.

## 3. 제어의 역전 (IoC) 및 컨테이너의 역할
*   **제어의 역전 (Inversion of Control, IoC):**
    *   일반적으로는 프로그래머(개발자)가 필요한 개체(객체)를 직접 생성하고 관리합니다. (제어 주체가 개발자)
    *   IoC 원칙은 개체 생성과 소멸까지의 관리를 직접 하는 대신, 외부 컨테이너(Container)에게 맡기는 것입니다. (제어 주체가 컨테이너)
*   **IoC 컨테이너 (IOC Container):**
    *   스프링 프레임워크에서 이 '컨테이너'의 역할을 담당합니다.
    *   **역할:** 애플리케이션 내에서 필요한 다양한 객체(빈, Bean)를 개발자가 직접 생성하는 것이 아니라, **스프링 컨테이너가 자동으로 생성하고 관리**합니다. (객체의 생명주기 관리)

## 4. Spring의 구조화와 빈(Bean) 관리
*   **빈(Bean):** 스프링 컨테이너가 관리하는 객체를 '빈'이라고 부릅니다.
*   **스프링의 장점 (뼈대/프레임워크 역할):**
    *   **구조화:** 애플리케이션의 기본 뼈대와 표준 구조를 제공합니다. (좋은 구조를 유지하게 도움)
    *   **유지보수 용이성:** 표준화된 구조 덕분에 누가 개발하더라도 일정한 품질과 높은 유지보수성을 가진 애플리케이션을 만들 수 있습니다.
    *   **연결성:** 스프링은 기본 베이스를 깔아주는 역할을 하며, 필요에 따라 다른 프레임워크(예: JPA, MyBatis)들을 연결하여 사용할 수 있게 합니다.

## 5. 빈 생성 및 주입 과정: DI와 구성 방법
*   **빈(Bean) 등록 및 관리:** 스프링 컨테이너가 어떤 빈들을 관리해야 하는지 알아야 합니다. 이를 '빈 등록'이라고 합니다.
    *   **@Component 애노테이션:** 클래스에 이 애노테이션을 붙여 '이것을 빈으로 관리해라'라고 명시적으로 선언합니다.
    *   **XML 설정 (레거시):** 과거에는 `xml` 파일을 이용해 `<bean>` 태그를 사용하여 빈의 이름, 클래스, 스코프 등의 속성을 지정했습니다. (최신 트렌드에서는 점차 사용 빈도가 줄고 있음)
    *   **Java Config (현대적 방식):** Java 클래스 파일 자체에 `@Configuration` 같은 애노테이션을 사용해 빈을 등록하는 방식입니다. (가장 많이 사용됨)
    *   **컴포넌트 스캔 (Component Scan):** 별도의 설정 파일 없이, 지정된 패키지 내의 모든 컴포넌트(@Component가 붙은 클래스)를 컨테이너가 자동으로 찾아서 빈으로 등록하는 기능입니다.
*   **의존성 주입 (DI, Dependency Injection):**
    *   빈을 **생성**하고 **관리**하는 것 외에도, 스프링은 빈들이 **실제로 사용되는 시점**에 필요한 객체들을 찾아 연결해주는 역할까지 해줍니다.
    *   **원리:** 개발자는 "나 이거 쓸 거야"라고 빈을 사용하겠다는 것만 선언(선언적 코드)하면, 스프링이 해당 빈을 찾아서 자동으로 연결(주입)합니다.
    *   **주입 방식:**
        *   생성자(Constructor)를 통한 주입
        *   Setter 메서드를 통한 주입
        *   애노테이션(`@Autowired` 등)을 이용한 주입 방식 (가장 일반적으로 사용됨)

3. 빈 등록 및 객체 관리 방법 (컴포넌트 스캔, 프로퍼티)

---

## 1. 스프링 프레임워크의 필요성 및 장점

*   **학습의 목표 설정:** IOC/DI 같은 개념을 배우는 근본적인 이유를 명확히 인식해야 한다. 즉, 직접 애플리케이션의 뼈대를 만드는 것보다, 이미 튼튼한 뼈대(프레임워크)를 활용하여 높은 품질의 애플리케이션을 더 쉽고 효과적으로 만들 수 있기 때문이다.
*   **프레임워크 소개:** 자바에서 가장 많이 사용되는 프레임워크 중 하나가 '스프링 프레임워크'이며, 이는 **IoC(Inversion of Control)**와 **DI(Dependency Injection)** 같은 핵심 원리를 기반으로 작동한다.
*   **모듈화와 확장성 (EJB 대비):**
    *   과거 기술인 EJB는 전체 구조를 완성하기 위해 모든 부분을 강제적으로 사용해야 하는 경직성이 있었다.
    *   스프링은 레고 블록처럼 설계되어 있어, **필요한 모듈만 가져다 쓸 수 있는 뛰어난 모듈화 장점**을 가진다.
    *   따라서 전체 책을 다 외우지 못하더라도, 핵심 코어만 이해하고 필요한 모듈(예: 스프링 JDBC, 스프링 MVC)만 추가하여 사용하면 된다.

## 2. 스프링의 핵심 원리 (IOC, DI, Bean)

*   **IoC (제어의 역전, Inversion of Control):**
    *   '제어'를 직접 하는 주체(프로그래머)가 아니라, 프레임워크(컨테이너)가 객체의 생명 주기(Life Cycle)와 관리 방식을 대신 담당하게 하는 원리다.
    *   이 개념 자체는 스프링보다 먼저 존재했던 일반적인 자바 디자인 패턴(예: 팩토리 패턴)에서 발전했으나, 스프링이 체계적으로 구현하고 널리 사용하게 만들었다.
*   **Bean (빈):**
    *   스프링 컨테이너에 의해 관리되는 자바 객체 그 자체를 '빈(Bean)'이라고 한다.
    *   우리가 개발하는 DAO, Service, Controller 등 모든 핵심 로직을 가진 클래스가 빈이 될 수 있다.
*   **DI (의존성 주입, Dependency Injection):**
    *   객체 A가 작동하기 위해 필요한 객체 B를 **A가 직접 `new` 키워드로 생성하지 않고**, 프레임워크(스프링 컨테이너)가 알아서 생성하여 A에게 *주입(Injection)*해 주는 행위이다.
    *   이 덕분에 객체 간의 결합도가 낮아지고, 테스트 및 유지보수가 용이해진다.
*   **빈의 라이프 사이클 관리:**
    *   핵심은 프로그래머가 직접 객체를 생성하고 소멸시키는 것이 아니라, **프레임워크(컨테이너)가 이 모든 과정을 관리(IoC)** 해주는 것이다.
*   **객체의 범위 (Scope):**
    *   빈을 등록할 때 객체가 생성되고 사용되는 범위를 지정할 수 있다.
    *   **싱글톤(Singleton):** 애플리케이션 전체에서 단 하나의 인스턴스만 존재한다. (기본값)
    *   **프로토타입(Prototype):** 요청할 때마다 항상 새로운 인스턴스를 생성한다.
    *   (추가 Scope: RequestScope, SessionScope 등)

## 3. 빈 등록 및 객체 관리 방법 (컴포넌트 스캔, 프로퍼티)

*   **설정(Config)의 중요성:** 빈들이 생성되고 의존성이 주입되려면, 컨테이너에게 어떤 빈을 사용할 것인지 알려주는 과정이 필수적이다.
*   **외부 의존성 주입 (DI의 확장):**
    *   객체는 자신이 만든 객체만 사용하는 것이 아니다. 데이터베이스 연결 객체(DataSource)처럼 **외부 라이브러리가 제공하는 객체**를 사용해야 하는 경우가 많다.
    *   이런 외부 자원(데이터베이스 접속 정보 등)을 빈 생성 시에 사용하려면, 해당 설정 정보를 명확하게 주입받아야 한다.
*   **설정 정보 관리 (Properties):**
    *   애플리케이션의 다양한 설정값(예: 서버 포트, DB 비밀번호 등)은 코드에 하드코딩하지 않고, **`application.yml` (또는 `.properties`)** 같은 설정 파일을 통해 관리한다.
    *   이를 통해 환경(개발, 운영)에 따라 설정을 쉽게 변경할 수 있다.
*   **빈 등록 방식의 진화: `@Component`와 컴포넌트 스캔:**
    *   과거에는 빈을 등록할 때 XML이나 `@Configuration` 클래스에 명시적으로 빈 이름을 하나하나 등록해 주어야 했다.
    *   **컴포넌트 스캔(Component Scan)**을 사용하면, 클래스 위에 `@Component`와 같은 애너테이션만 붙여 놓으면, 스프링 컨테이너가 실행 시 **해당 애너테이션을 가진 모든 클래스를 자동으로 찾아내어 빈으로 등록**해 준다.
    *   이는 개발자가 수동으로 빈 등록 코드를 작성하는 수고를 덜어주는 혁신적인 방식이다.
    *   **잠재적 문제:** 여러 빈이 동일한 타입이거나, 동일한 ID를 가질 경우 빈 충돌(Bean Collision) 또는 모호성 오류를 일으킬 수 있으므로 주의 깊게 처리해야 한다.

## 1. 컴포넌트 스캔 (Component Scan) 이해
*   **개념:** `@ComponentScan`은 지정된 베이스 패키지(Base Package) 아래에 있는 클래스들을 스캔하여 Spring IoC 컨테이너가 관리할 빈(Bean)으로 자동으로 등록하는 기능입니다.
*   **동작 범위:** 스캔은 기본적으로 `@ComponentScan`이 위치한 클래스의 패키지(즉, 베이스 패키지)를 기준으로 하위 패키지에 있는 빈들만 인식합니다.
*   **활용 예시:** 만약 `BasePackage` 안에 있지 않은 클래스(예: `Dice`)의 빈을 등록하고 싶다면, `@ComponentScan`의 속성을 이용하여 해당 클래스가 위치한 패키지를 명시적으로 지정해 주어야 합니다.

## 2. 설정 클래스 지정: @Configuration의 역할
*   **필요성:** 스프링 부트와 같이 프레임워크가 내부적으로 복잡하게 동작하는 환경에서는, 개발자가 "이 파일이 설정(설정 정보)을 담고 있는 클래스야"라고 명시적으로 알려주어야 할 때가 있습니다.
*   **@Configuration의 역할:** `@Configuration` 어노테이션은 Spring 컨테이너에게 해당 클래스가 빈을 정의하거나 설정을 관리하는 컨피그레이션 파일임을 알려줍니다.
*   **두 Annotation의 차이점:**
    *   `@ComponentScan`: "이 영역에서 빈들을 *찾아서* 등록해라." (Discovery)
    *   `@Configuration`: "이 파일 자체가 컨텍스트에게 *설정 정보를 제공*하는 파일이다." (Definition)
*   **함께 사용:** 일반적으로 빈을 찾고(ComponentScan) 그 빈들을 통해 서비스를 구성하는 설정 파일(Configuration) 역할을 하므로, 두 어노테이션이 함께 사용되어야 모든 설정이 정상적으로 동작합니다.

## 3. 빈의 역할 분리와 특수화된 Annotation
*   **계층적 특성 (Inheritance):** `@Service`, `@Repository`, `@Controller` 등은 근본적으로 `@Component`를 상속받은 특수화된 형태의 빈입니다. 따라서 이들 역시 `@Component`의 기능을 모두 수행합니다.
*   **특수화의 목적:** 단순한 빈 등록을 넘어, 해당 빈이 수행해야 하는 역할에 특화된 기능을 수행할 수 있도록 합니다.
    *   `@Controller`: 웹 애플리케이션의 요청 처리에 특화된 역할 수행.
    *   `@Service`: 비즈니스 로직 수행에 특화된 역할 수행.
    *   `@Repository`: 데이터 접근 계층(DB)에 특화된 역할 수행.
*   **결론:** 이 특수 어노테이션들은 빈 등록 기능 외에도, Spring 컨테이너가 해당 빈을 활용할 때 필요한 특정 라이프사이클 관리(예: 웹 요청 처리 로직) 등의 추가 기능을 제공합니다.

## 4. 빈 식별 및 의존성 주입 (Dependency Injection) 심화
*   **빈 ID 관리:**
    *   빈을 명시적으로 등록할 때는 ID를 자유롭게 지정할 수 있습니다.
    *   `@Component` 등의 어노테이션을 사용하여 등록할 경우, 기본적으로는 클래스 이름의 첫 글자를 소문자로 바꾼 것이 ID가 됩니다.
    *   만약 동일한 타입의 빈이 여러 개일 때, 의존성 주입 시 원하는 특정 빈을 지정해야 할 경우 `@Qualifier` 어노테이션을 사용해 명시적인 이름을 지정할 수 있습니다.
*   **주입 방식 (DI):** 빈을 가져와 사용하는 세 가지 주요 방법이 있습니다.
    1.  **생성자 주입 (Constructor Injection):** 가장 기본적이고 권장되는 방식. 객체 생성 시 필수 의존성을 전달받습니다. (기본 동작 방식)
    2.  **세터 주입 (Setter Injection):** 객체 생성 후 특정 Setter 메서드를 통해 의존성을 주입받는 방식.
    3.  **필드 주입 (Field Injection):** 필드 위에 `@Autowired`를 붙여서 주입받는 방식. (가장 간편하지만, 테스트 및 종속성 문제로 인해 **권장되지 않음**.)
*   **Best Practice (권장 사항):**
    *   **선호되는 주입 방식:** 생성자 주입을 사용하는 것이 가장 안정적입니다.
    *   **피해야 하는 방식:** 필드 주입은 Spring 컨테이너에 강하게 종속되므로, Spring 환경이 아닌 다른 환경으로 코드를 옮기기 어려워 유연성을 떨어뜨립니다.
*   **추상화 노력:**
    *   Spring Framework가 제공하는 어노테이션 대신, 자바 진영 표준(Jakarta EE)에서 제공하는 표준 어노테이션을 사용하려는 노력이 진행되고 있습니다. 이는 Spring에 대한 종속성을 낮추어 코드의 이식성을 높이기 위함입니다.

***
**✅ 핵심 요약: 자동화의 원리**
Spring이나 Spring Boot 같은 프레임워크의 모든 '자동으로 해주는 기능'은 개발자가 `@ComponentScan`이나 `@Configuration` 같은 어노테이션을 통해 **"여기서부터 시작해," "이것이 설정이야"**라고 명시적으로 약속(선언)해 주었기 때문에 동작하는 것입니다. 개발자가 명시적으로 알려주지 않은 부분은 시스템이 스스로 유추할 수 없습니다.

## 1. 프레임워크의 필요성과 Spring의 역할
- **프레임워크 사용의 이점:** 애플리케이션 개발 시 처음부터 직접 구현하는 것보다 프레임워크를 사용하면 생산성과 품질 면에서 큰 이점을 얻을 수 있다.
- **Spring의 역할:** Java 기반의 애플리케이션 개발에서 가장 많이 사용되는 프레임워크 중 하나이며, 마치 잘 만들어진 '반제품'과 같다.
- **사용 방법의 특징:** 프레임워크를 사용하려면 정해진 사용 방법(규칙)을 따라야 하며, 이 규칙을 이해하는 것이 중요하다.
 
## 2. IoC(제어의 역전)와 DI(의존성 주입)의 이해
- **IoC (Inversion of Control, 제어의 역전):** 프로그램의 동작 흐름 제어 권한을 개발자(코드)가 아닌 프레임워크(Spring Container)가 담당하도록 넘기는 개념이다.
- **IoC Container (Spring Container):** 애플리케이션 내부에서 객체(빈, Bean)를 직접 생성하고 관리하는 대신, 컨테이너에 맡긴다.
- **핵심 기능 (빈의 생명 주기 관리):**
    - 빈의 **생성(Creation)**: 컨테이너가 객체를 생성한다.
    - 빈의 **관리(Management)**: 빈이 살아있는 동안 필요한 작업을 처리한다.
    - 빈의 **소멸(Destruction)**: 객체가 사용을 마치고 메모리에서 해제될 때까지의 전 과정을 책임진다.
- **DI (Dependency Injection, 의존성 주입):** 객체들이 서로 필요로 하는 의존성(Dependency)을 직접 생성하거나 연결하지 않고, 외부(컨테이너)에서 주입받아 사용하는 패턴.
    - **효과:** 코드의 결합도(Coupling)를 낮추어 유지보수성과 테스트 용이성을 높인다.
- **DI 주입 방식 3가지:**
    1. **생성자 주입(Constructor Injection):** 객체를 생성할 때 필요한 의존성을 생성자 매개변수로 받아 주입한다. (가장 권장되는 방식)
    2. **세터 주입(Setter Injection):** 객체 생성 후, 세터 메서드를 통해 의존성을 주입받는다.
    3. **필드 주입(Field Injection):** `@Autowired` 등의 어노테이션을 사용하여 필드에 직접 주입한다. (가장 단순하나 권장되지 않음)

## 3. Spring Bean 등록 방법 (Bean Definition)
Spring 컨테이너가 빈을 관리하려면, 개발자가 "어떤 빈이 필요한지" 알려주어야 한다. 이를 빈 정의(Bean Definition)라고 한다.

- **1. XML 파일 방식 (구식):**
    - XML 태그와 네임스페이스를 사용하여 빈의 ID, 클래스, 스코프 등을 설정하는 방식이다. (현재는 사용 빈도가 낮음)
- **2. Java Config 방식 (Java @Bean):**
    - 자바 클래스 내부에 `@Configuration` 어노테이션을 붙인 클래스를 정의하고, `@Bean` 어노테이션을 사용해 특정 메서드에 반환되는 객체를 빈으로 등록한다. (수동 등록 방식)
- **3. Component Scan 방식 (자동 등록):**
    - 가장 현대적이고 효율적인 방법이다. 개발자가 빈으로 만들고자 하는 클래스에 `@Component` 어노테이션을 붙여준다.
    - Spring 컨테이너가 이 어노테이션이 붙은 모든 클래스들을 자동으로 찾아내어 빈으로 등록한다.
    - **특수 빈 어노테이션:** `@Service`, `@Repository`, `@Controller`, `@RestController` 등은 모두 `@Component`를 상속받은 형태로, 해당 계층의 역할을 명확히 구분하기 위해 사용한다.

## 4. Spring Boot을 활용한 간편화
- **Spring Boot의 특징:** 개발자가 빈을 직접 등록(Component Scan 또는 Java Config)할 필요성을 크게 줄여준다.
- **간편화의 원리:**
    1. **자동 구성 (Auto-Configuration):** 애플리케이션이 사용하는 라이브러리나 환경(예: 데이터베이스 종류)을 감지하고, 필요한 빈들을 자동으로 설정하여 제공한다.
    2. **설정 파일 기반 (Configuration Properties):** 사용자가 특정 빈을 직접 등록하기보다는, `application.properties` 또는 `application.yml`과 같은 설정 파일에 필요한 값(Key-Value)만 넣어주면, 스프링 부트가 이를 해석하여 적절한 빈을 생성한다.

## 5. 빈의 라이프사이클 관리 및 스코프
- **Bean Scope (빈의 범위):**
    - **Singleton (기본값):** 애플리케이션 전체에서 오직 하나의 인스턴스만 존재한다.
    - **Prototype:** 빈이 요청될 때마다 항상 새로운 인스턴스가 생성된다.
    - *(추가: Request, Session 등의 웹 환경 스코프가 있다.)*
- **라이프사이클 콜백 (Life Cycle Callback):**
    - **`@PostConstruct`:** 빈이 성공적으로 생성된 직후에 반드시 호출되는 메서드. (초기화 작업 수행)
    - **`@PreDestroy`:** 컨테이너가 해당 빈을 파괴(소멸)하기 직전에 호출되는 메서드. (리소스 정리, 정리 작업 수행)

## 1. 빈의 라이프사이클 관리
- **라이프사이클 관리의 중요성:** Spring 컨테이너는 빈(Bean)을 단순히 생성하는 것을 넘어, 해당 빈의 생명 주기(Lifecycle) 전체를 관리합니다.
- **주요 콜백 메서드:**
    - `@PostConstruct`: 빈이 완전히 초기화된 후(생성 완료 시점) 특정 작업을 수행하도록 지정합니다.
    - `@PreDestroy`: 컨테이너가 빈을 제거(소멸)하기 직전에 정리 작업을 수행하도록 지정합니다.
- **핵심 개념:** 이러한 어노테이션들을 사용하면, 개발자가 직접 코드로 특정 시점을 지정할 필요 없이 컨테이너가 적절한 시점에 메서드를 호출하여 라이프사이클을 관리해 줍니다.

## 2. Spring Profiles를 이용한 환경별 설정 관리
- **프로파일(Profile) 정의:** 애플리케이션이 어떤 환경(Development, Production 등)에서 동작하는지에 따라 설정을 다르게 분리하여 적용할 수 있는 기능입니다.
- **환경별 설정 예시:**
    - **데이터 소스:** 개발 환경에서는 가벼운 `H2DB`를 사용하고, 운영 환경에서는 `MySQL`과 같은 실제 데이터베이스를 연결하도록 설정할 수 있습니다.
    - **설정 파일 분리:** 환경별로 별도의 설정 파일(예: `dev-config.yml`, `prod-config.yml`)을 지정하고, 해당 파일을 통해 환경 설정을 로드할 수 있습니다.
- **목적:** 코드나 설정을 수정하지 않고도, 실행하는 시점의 환경에 맞춰 다양한 값(DB 접속 정보, API 엔드포인트, 플레이어 목록 등)을 동적으로 변경할 수 있습니다.

## 3. 프로파일 적용 및 우선순위 이해
- **프로파일 적용 방법:**
    1. **애플리케이션 클래스 레벨:** `@SpringBootApplication`에 `spring.profiles.active` 속성을 지정하여 기본 동작 프로파일을 설정할 수 있습니다.
    2. **실행 환경 설정 (가장 우선순위 높음):** 실제 애플리케이션을 실행할 때(CLI 또는 IDE의 Run Configuration) 아규먼트로 프로파일을 지정하는 것이 가장 높은 우선순위를 가집니다. (예: `java -Dspring.profiles.active=prod`)
- **프로파일의 작동 방식:** 스프링 컨테이너는 지정된 프로파일에 해당하는 설정만 로드하고 활성화합니다.
- **우선순위 (높은 순):**
    1. **실행 시점 명령어 (CLI/IDE Run Config)**
    2. **애플리케이션 코드 설정**
    3. **기본 설정**

## 4. 실습 정리 및 복습
- **종합 실습 목표:** 배운 개념들을 총망라하여 하나의 시스템(예: 도서관리 시스템)을 구축하는 것이 목표입니다.
- **핵심 학습 내용:**
    - **빈 등록 방법 비교:** 컴포넌트 스캔(`@ComponentScan`)을 이용하는 방법과 Java Config(`@Configuration`)를 이용하는 방법을 모두 익히고 활용할 수 있습니다.
    - **프로파일 적용 실습:** 시스템의 일부 기능(예: 데이터베이스 연결, 특정 비즈니스 로직)에 프로파일을 적용하여, 개발 환경과 운영 환경의 차이를 체감하며 동작시켜 봅니다.

## 1. 소프트웨어 설계 원칙: 레이어드 아키텍처와 SOLID 원칙
- **레이어드 아키텍처(Layered Architecture)의 이해:**
    - 시스템을 논리적으로 분리된 여러 계층(Layer)으로 나누어 설계하는 방식입니다.
    - 각 계층은 독립적인 책임을 갖고 상호 의존성을 관리해야 합니다.
- **객체지향 원칙 준수:**
    - 객체는 단일 책임의 원칙(Single Responsibility Principle)을 가져야 합니다. 하나의 객체가 너무 많은 기능을 담당하게 하는 것은 설계상 좋지 않습니다.
    - **목적별 분리:** 데이터를 다루는 역할(DAO), 핵심 비즈니스를 처리하는 역할(Service), 사용자 인터페이스를 담당하는 역할(Controller) 등 목적에 따라 객체를 분리하는 것이 핵심입니다.

## 2. 계층별 역할 분리와 객체 설계의 중요성
- **책임의 분리 원칙:** 시스템의 각 요소가 맡은 역할(책임)만 가지고 있도록 설계해야 합니다.
    - **Service Layer (핵심 비즈니스 로직):** 실제 비즈니스 규칙(예: 회원이 15세 이상인지 확인, 골드 회원 여부 판별 등)이 존재하는 가장 중요한 계층입니다.
    - **Data Access Object (DAO) Layer:** 오직 데이터베이스와의 통신(저장, 수정, 조회, 삭제 등) 기능만 담당해야 합니다. 비즈니스 로직을 포함해서는 안 됩니다.
    - **Presentation Layer (Controller):** 사용자 요청을 받고 결과를 사용자에게 보여주는 인터페이스를 담당합니다.
- **구조적 중요성:**
    - 프레임워크(Framework)의 목적은 개발자가 귀찮은 부분(반복적이고 기본적인 코드)을 처리할 수 있도록 도와주고, 개발자는 오직 비즈니스 로직에만 집중할 수 있게 하는 것입니다.
    - 복잡한 비즈니스를 처리하는 과정에서, 모든 로직을 한 곳에 모으기보다 목적에 따라 객체와 계층을 분리하여 설계하는 것이 효율적입니다.

## 3. Spring Boot 구현 실습: 클래스 구조 및 의존성 주입
- **계층적 구조 구현 실습 (Best Practice):**
    - `Controller` $\rightarrow$ `Service` $\rightarrow$ `DAO`의 순서로 의존성을 가지는 구조를 통해 계층을 분리합니다.
    - **의존성 주입(Dependency Injection):** 클래스 간의 의존성을 관리하기 위해 Spring의 주입(Injection) 방식을 사용합니다.
    - **생성자를 통한 주입:** 가장 명확하고 권장되는 방식으로, 생성자를 통해 필요한 의존성 객체를 받아와 초기화합니다.
- **테스트 용이성:**
    - 구조를 이렇게 분리하면 테스트가 용이해지며, 특정 계층(예: `DAO`)의 기능을 독립적으로 테스트할 수 있습니다.

## 4. 고급 설정 및 동작 원리: 프로파일링과 빈 등록
- **IoC(Inversion of Control)과 빈(Bean) 개념:**
    - Spring 컨테이너가 객체를 생성하고 관리하는 것이 핵심입니다. 우리가 개발자는 객체를 생성하는 과정을 Spring에게 위임합니다.
- **빈 등록 방식의 이해:**
    - `@Component`, `@Service`, `@Repository` 등의 어노테이션을 사용하여 어떤 클래스가 빈으로 인식되어야 하는지 Spring에게 알려줍니다.
    - `Config` 클래스 내에서 `@Bean` 어노테이션을 사용하여 빈을 명시적으로 등록할 수도 있습니다.
- **Spring Profile (프로파일링):**
    - 개발 환경(dev), 테스트 환경(test), 운영 환경(prod) 등 다양한 환경에 맞춰 설정값을 다르게 가져가야 할 때 사용합니다.
    - `application.yml` 같은 공통 설정 파일 외에, `application-dev.yml`처럼 환경별 파일을 추가하여 필요한 설정만 불러와 사용할 수 있습니다.
- **`@ComponentScan`과 동작 순서:**
    - `@ComponentScan`을 사용하면 지정된 패키지 하위의 모든 컴포넌트들을 자동으로 찾아 빈으로 등록하고 사용할 수 있습니다.

## 5. 마무리 및 학습 조언: 코어 원리 이해의 중요성
- **깊은 이해의 중요성:**
    - 단순히 프레임워크가 제시하는 코드를 '사용하는 방법'에 그쳐서는 안 되며, '왜 이 코드가 필요하고, 어떻게 작동하는지'라는 근본적인 원리를 이해하려 노력해야 합니다.
    - Spring 프레임워크는 가장 코어 기술이므로, 모든 기술을 배울 때 기본 원리(빈이 등록되고 의존성이 주입되는 과정)를 이해하는 것이 중요합니다.
- **개발자로서의 자세:**
    - **전체 구조 파악 능력:** 취업 후에도 맡은 코드의 일부만 수정하는 것이 아니라, 전체 서비스가 어떤 흐름(구조) 안에 작동하는지 큰 그림을 파악하는 능력이 중요합니다.
    - **지속적인 학습과 야망:** 기술 트렌드를 놓치지 않고 꾸준히 공부(스터디, 컨퍼런스 등)하는 노력을 게을리 해서는 안 됩니다.
