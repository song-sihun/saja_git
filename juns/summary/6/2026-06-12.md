## 1. 과정 복습 및 학습 자세 점검 (Warm-up & Review)
- **학습 격려:** 어려운 내용을 다루는 학문이므로 포기하지 않고 꾸준히, 매일 조금씩 학습하는 태도가 중요함.
- **완벽주의 경계:** 과제 제출 시 완벽하지 않더라도 과정을 중단하거나 포기하지 않는 것이 더 중요하며, 과정 자체를 경험으로 쌓아나가는 것이 핵심임.
- **기술 발전 트렌드:** 과거에는 특정 기술(예: 풀스택 개발)을 언급하는 것만으로도 어려웠지만, 현재는 기술들이 간편해지고 AI의 도움으로 구현이 쉬워졌음. 이로 인해 오히려 더 많이, 넓게 알아야 할 부분들이 생겼다는 점을 인지해야 함.
- **학습 방법:** 새로운 내용을 익히기보다는, 배운 지식을 여러 프로젝트(토이 프로젝트)에 응용하고 반복적으로 복습하며 심화하는 것이 가장 효과적임.

## 2. 핵심 디자인 패턴 심화 이해 (Builder, Response Entity)
- **빌더 패턴 (Builder Pattern):**
    - 객체 생성 시 생성자(Constructor)를 사용하는 대신, 불필요한 인자나 순서 배열 같은 불편함(Pain Point)을 해결하기 위해 사용됨.
    - 클래스 내에 빌더를 정의하여 단계적으로 개체를 만들 수 있게 하며, 이는 실제 개발 과정에서 매우 자주 활용되는 패턴임.
- **Response Entity:**
    - REST 컨트롤러에서 요청을 받은 후 응답을 할 때, 단순히 데이터(Data)만 보내는 것이 아니라 사용자에게 더 친절하고 상세한 정보를 제공하기 위한 객체입니다.
    - 요청이 성공했는지 실패했는지 여부, 그리고 **왜** 실패했는지 등의 상태 정보(Status Code 등)를 담아 클라이언트 측에 함께 전달할 수 있습니다.

## 3. 객체 설계 원칙: DTO와 엔티티의 분리
- **데이터 전송 관점 (DTO - Data Transfer Object):**
    - 애플리케이션의 계층(Controller $\to$ Service $\to$ Repository)을 거치며 데이터를 전달하는 목적으로 사용됩니다. 데이터 자체를 담는 '가방' 같은 역할을 합니다.
    - 프로젝트 규모가 커질수록, 요청(Request)이나 응답(Response)에 필요한 데이터 구조와 로직을 명확히 분리하기 위해 여러 개의 DTO/VO 클래스를 사용하는 것이 바람직합니다. (예: 요청용 가방과 응답용 가방 분리)
- **엔티티 (Entity):**
    - 데이터베이스(DB)의 테이블 구조를 반영하는 객체입니다. JPA와 깊은 연관성을 가지며, DB에 영속화되는 역할을 합니다.
    - 엔티티가 너무 많은 책임(데이터 저장 로직 + 비즈니스 로직 등)을 지니게 되면 설계 원칙(예: 단일 책임 원칙, SOLID)에 위배될 수 있습니다.

## 4. 고급 웹 개발 기능과 테스트 방법론
- **예외 처리 (Exception Handling):**
    - 일반적으로 화면 페이지에서는 예외 발생 시 '예쁜 에러 페이지'로 응답하지만, API(데이터 기반) 환경에서는 적절한 상태 코드와 함께 오류의 상세 원인을 데이터 형태로 담아 응답해야 합니다.
    - 이러한 전역적인 예외 처리 로직은 **`@RestControllerAdvice`**를 활용하여 구현하는 것이 효과적입니다.
- **테스트 및 모킹 (Mocking):**
    - 실제 단위 테스트(Unit Test)는 레이어별로 수행되어야 하므로, 특정 계층(예: 서비스)이 의존하는 다른 계층(예: Repository)의 동작을 가짜 객체(가짜 데이터나 로직만 제공하는 **목개체, Mock Object**)를 이용해 격리하고 테스트할 수 있습니다.

## 5. 보안 프레임워크 개요: 인증(Authentication)과 인가(Authorization)
- **스프링 시큐리티 (Spring Security):**
    - 스프링 기반 애플리케이션의 **인증 및 권한 부여(보안)**를 담당하는 필수적이고 강력한 모듈입니다.
- **핵심 개념 이해:**
    1. **인증 (Authentication): 누가 그 사용자임? (Who are you?)**
        - 사용자가 신분증이나 아이디/비밀번호 등을 제출하여 자신이 주장하는 존재가 맞는지 확인하는 절차입니다. (예: 출입증 발급 과정에서 사원임을 증명)
    2. **인가 (Authorization): 무엇을 할 수 있는 사용자임? (What can you do?)**
        - 사용자가 건물 안으로 진입한 후, 그 사람의 신분증(출입증/권한)에 따라 '강의실'만 갈 수 있고 '3층 사무실'은 접근할 수 없는 것처럼 **접근 권한을 제한**하는 절차입니다. (페이지 요청 시마다 이 과정이 발생함.)
- **요약:** 애플리케이션 개발 시 보안 기능을 구현할 때, 단순하게 코드를 짜는 것을 넘어 이러한 인증과 인가라는 개념적인 흐름을 이해하는 것이 가장 중요합니다.

## 1. 인증(Authentication)과 권한(Authorization)의 개념 이해
- **인증 (Authentication):** 사용자가 실제로 그 애플리케이션에 가입된 사용자 본인이 맞는지 신원을 확인하는 과정입니다. (Who are you?)
- **인가 (Authorization):** 인증을 마친 사용자가 특정 페이지나 기능에 접근할 수 있는 '권한'이 있는지 여부를 판단합니다. 모든 기능을 허용하는 것이 아니라, 접근 가능한 영역을 제한합니다.

## 2. Spring Security와 필터 기반 보안 메커니즘
- **Spring Security의 역할:** 인증 및 권한 부여 과정을 담당하는 프레임워크입니다. 개발자가 직접 구현할 필요 없이 시큐리티가 이 부분을 처리해줍니다.
- **주요 특징 및 기능:**
    *   필터(Filter) 기반의 강력한 보안 메커니즘을 이용합니다.
    *   폼 로그인 방식 등 다양한 인증 방식을 지원하며, 프로젝트에 맞게 세밀한 설정을 적용할 수 있습니다.
    *   사용자 정의 필터를 작성하여 요청/응답 처리를 커스터마이징 할 수 있습니다.

## 3. 웹 요청 처리 과정에서의 서블릿 기술 이해 (Filter, Listener)
- **웹 애플리케이션의 기본 흐름:** 클라이언트가 요청을 보내면, 이 요청은 내부적으로 서블릿 컨테이너를 거쳐 처리됩니다.
- **요청 핸들링 주체:** Spring MVC 환경에서는 모든 요청이 'DispatcherServlet'이라는 하나의 컨트롤러에 모여 들어옵니다.
- **필터(Filter)의 역할:** 웹 요청 파이프라인의 최**앞단 (윗단)**에서 요청을 가로채어 부가적인 작업을 수행합니다.
    *   **작동 시점:** 요청이 서버에 도달하기 전, 그리고 응답이 클라이언트로 돌아가기 직전(응답 과정) 모두 필터를 거칩니다.
    *   **사용 사례:** 보안 처리(인증/인가), 캐릭터 인코딩 변경 등 모든 요청에 걸쳐 동일하게 적용해야 하는 로직을 구현할 때 유용합니다.

## 4. Filter의 동작 원리와 구현 방법 심화 학습
### **A. 필터의 생명 주기 및 핵심 메서드**
- **필터 API:** Java Servlet API에서 제공하는 기술입니다. (Spring 프레임워크 자체의 기능이 아님을 이해해야 합니다.)
- **주요 라이프사이클 메서드:**
    *   `init()`: 객체가 생성될 때 한 번 초기화(초기 설정) 작업을 수행합니다.
    *   `doFilter()`: 요청 처리 흐름의 핵심입니다. 이 메서드를 통해 요청(`request`)과 응답(`response`) 객체를 받고, **필터 체인(Filter Chain)**을 이용해 다음 필터 또는 실제 서블릿으로 제어권을 넘겨줍니다.
    *   `destroy()`: 서버가 종료될 때 클린업 작업을 수행합니다.

### **B. 동작 흐름 (요청 및 응답 처리 과정)**
1.  **요청 전처리:** 요청이 들어오면 $\rightarrow$ 첫 번째 필터(`pre-process`) 실행 $\rightarrow$ 다음 필터(체인) 순서로 반복 $\rightarrow$ 최종적으로 실제 서블릿/컨트롤러에 전달됩니다.
2.  **응답 후처리:** 컨트롤러가 응답을 생성하고 돌려줄 때 $\rightarrow$ 마지막 필터부터 거꾸로 돌아가며(`post-process`) 실행됩니다.

### **C. 필터 등록 및 동작 원리**
- **실행 주체:** 웹 WAS(Web Application Server) 차원에서 필터를 실행시킵니다. (스프링이 직접 시작시키는 것이 아닙니다.)
- **등록 방법:** 필터가 WAS의 요청 처리 과정에 포함되도록 반드시 등록해야 합니다.
    *   `<filter>` 태그를 사용하는 `web.xml` 설정 (전통적 방식)
    *   `@WebFilter` 어노테이션 사용 (권장 방식)
- **URL 패턴:** 필터를 특정 URL 패턴에만 적용할지, 아니면 모든 요청(`/*`)에 적용할지를 정의합니다.

### **D. 심화 학습 포인트**
- **필터 체인(Filter Chain):** 여러 개의 필터가 순차적으로 동작하는 흐름을 관리하는 구조입니다.
- **AOP와의 유사성:** 필터는 AOP에서 어라운드 방식으로 동작하는 것과 유사합니다. (특정 메서드의 실행 전/후 등 특정 지점의 로직을 가로채어 처리할 수 있다는 공통점이 있습니다.)

***(추가 조언)***
*   필터의 작동 과정을 충분히 직접 코드로 구현하고, 다양한 컨트롤러를 추가하며 테스트해보는 것이 동작 원리를 이해하는 데 가장 효과적입니다.

## 1. 필터 체인(Filter Chain)의 이해 및 동작 원리
- **필터의 역할:** Spring Web 애플리케이션에서 요청이 들어올 때 요청과 응답 과정에 끼어들어 특정 로직을 수행하는 계층 구조입니다.
- **체인(Chain) 개념:** 여러 개의 필터가 연결되어 순차적으로 동작하며, 이전 필터가 처리한 데이터를 다음 필터에게 넘겨주면서 처리 흐름이 유지됩니다.
- **중단 현상 이해:** 체인에 필터가 빠지거나 연결이 끊기면(예: `FilterChain` 메서드 호출 누락), 요청은 정상적인 처리를 하지 못하고 멈추게 됩니다.
- **동작 순서 확인:** 모든 웹 요청(Request)은 필터들이 거치고 -> 서비스 레이어 -> 컨트롤러 등의 단계를 거쳐야 최종적으로 응답을 할 수 있습니다.

## 2. 필터 등록 방법: 컴포넌트 스캔과 수동 빈 설정
- **컴포넌트스캔 기반 자동 등록의 한계:** Spring은 일반적으로 컴포넌트를 자동으로 감지하여(Component Scan) 사용 가능한 필터를 등록합니다. 하지만 특정 설정이나 순서 제어가 필요할 때는 제한적일 수 있습니다.
- **명시적인 Bean 설정을 통한 등록 (권장):** `FilterRegistrationBean`과 같은 빈을 직접 생성하여 등록하면, 개별 필터에 대한 세밀한 제어와 구체적인 설정(URL 패턴 지정, 실행 순서 등)이 가능해집니다.
    - **순서 제어:** `@Order` 어노테이션이나 빈 레지스트레이션 자체를 통해 필터가 동작할 정확한 순서를 정의할 수 있습니다.
    - **패키징 충돌 방지:** 클래스 이름의 중복(예: `FilterConfig`)은 컴파일러 오류를 발생시킬 수 있으므로, 패키지 구조와 클래스명을 분리하여 사용해야 합니다.

## 3. Spring Web 아키텍처와 요청 처리 흐름
- **기저 기술 (Base Technology):** Spring의 웹 기능은 근본적으로 서블릿(Servlet API) 기반 위에서 동작합니다.
- **웹 서버 vs. 웹 애플리케이션 서버 (WAS):**
    - **웹 서버:** 정적인 자원(Static Resource)을 받아서 처리하는 역할만 수행합니다. 서블릿 요청 처리가 불가능합니다.
    - **WAS:** 서블릿 컨테이너를 포함하고 있어, 동적인 비즈니스 로직(서블릿 요청 처리)까지 완전히 구현하고 응답할 수 있습니다. (핵심: 서블릿 라이프사이클 관리 기능 보유)
- **요청 처리 메커니즘 (스레드):**
    - 하나의 HTTP 요청이 들어올 때마다 WAS의 스레드풀에서 **새로운 쓰레드(Thread)**가 할당됩니다.
    - 이 단일 쓰레드가 필터부터 컨트롤러, 서비스 레이어에 이르기까지요, 응답을 반환할 때까지 전체 요청 처리를 담당합니다.

## 4. 데이터 공유 메커니즘: ThreadLocal 활용 및 주의사항
- **데이터 전달의 필요성:** 필터를 거쳐 여러 계층(Service, Controller)으로 분산된 로직에서 이전 단계에서 처리한 값(예: 인증 정보)을 다음 단계가 사용해야 할 때, 이 데이터를 일관되게 전달하는 것이 중요합니다.
- **ThreadLocal의 역할:** `ThreadLocal`은 해당 스레드에만 국한된 저장 공간을 제공합니다. 따라서 여러 요청이 동시에 들어와도 서로 다른 쓰레드는 독립적인 데이터를 사용하므로, 데이터를 각 레이어 간에 안전하게 공유할 수 있습니다.
- **사용 시 핵심 주의사항 (가장 중요):**
    - WAS의 특성상 스레드가 풀(Pool)에서 재사용되기 때문에, 필터나 로직 수행이 끝난 후에는 **반드시 `ThreadLocal`에 저장한 값을 명시적으로 제거(`remove()`)** 해야 합니다.
    - 만약 데이터를 정리하지 않으면, 다음 요청을 처리하는 다른 사용자(다른 쓰레드)의 데이터가 이전 사용자의 값으로 잘못 인식되는 심각한 오류(데이터 누수/오염)를 초래할 수 있습니다.

## 1. 보안 모듈의 이해 및 Spring Security 소개
- **보안의 중요성:** 애플리케이션 개발 시, 인증되지 않은 사용자가 접근할 수 있는 페이지를 막는 등 강력한 보안 로직 구현이 필수적이다. (예: 비인가 사용자 접근 차단)
- **Spring Security 역할:** 과거에는 이러한 보안 기능을 모두 직접 구현해야 했으나, Spring Framework의 `Security` 모듈을 사용하면 안전하고 효율적으로 인증/인가 작업을 처리할 수 있도록 돕는다.
- **핵심 원리 이해 (필수 개념):**
    *   **인증(Authentication):** "이 사용자가 맞는지?" (아이디와 비밀번호 등 신원을 확인하는 과정).
    *   **인가(Authorization):** "이 사용자가 이 기능을 사용할 권한이 있는지?" (사용자에게 적절한 접근 권한을 부여하는 과정).
    *   인가는 반드시 인증이라는 전제 하에 의미가 있다.

## 2. 필터(Filter) 개념과 동작 원리 학습
- **필터의 정의 및 역할:** 요청(Request)이 웹 서비스(Servlet)까지 도달하기 *전*에 작업을 수행할 수 있게 해주는 메커니즘이다. (주로 보안 검증이나 인코딩 처리 등 공통 로직 적용 시 사용)
- **작동 방식:** 필터는 WAS 레벨에서 요청을 가로채서 정의된 여러 개의 필터들(Filter Chain)이 순차적으로 로직을 수행하게 한다.
- **필터의 생명주기 (Lifecycle):**
    *   `init()`: 필터 객체가 처음 생성될 때 한 번 실행되는 초기화 메서드.
    *   `doFilter()`: 실제 요청이 들어올 때마다 호출되며, 핵심 로직을 처리하는 메서드. 이 메서드를 통해 다음 필터와 최종 서비스(Servlet)로 요청 흐름을 넘겨주게 된다.
    *   `destroy()`: 필터 객체가 소멸될 때 실행되는 정리 작업.
- **필터 체인 (Filter Chain):** 여러 필터가 거치면서 순서대로 로직이 진행되도록 연결하고 관리하는 메커니즘이다. 다음 필터로 요청 흐름을 넘기는 역할을 수행한다.
- **활용 예시:** 캐릭터 인코딩 변경, 접근 권한 확인 등 서비스 코드 전체에 일일이 코드를 넣기 어려운 공통적인 작업을 처리할 때 매우 유용하다.

## 3. 웹 서버의 동시성 처리와 스레드(Thread) 관리
- **동시 요청 처리:** WAS는 단일 사용자의 요청을 하나씩 처리하는 것이 아니라, 여러 명의 사용자로부터 동시에 발생하는 수많은 요청들을 효율적으로 처리하기 위해 '쓰레드'를 이용한다.
- **스레드 풀 (Thread Pool):** 새로운 스레드를 생성하고 소멸시키는 과정은 자원 소모가 크고 시간이 걸린다. 따라서 WAS는 미리 일정 개수의 쓰레드를 준비해 놓은 *풀*을 사용하며, 요청이 올 때마다 이 풀에서 스레드를 할당받아 재사용한다.
- **WAS 설정 요소:** 서버의 용량을 고려하여 다음과 같은 파라미터를 설정해야 한다.
    *   **Minimum/Maximum Threads (최소/최대 쓰레드 수):** 동시에 처리할 수 있는 최대 동시 요청 수를 결정한다. 너무 적거나 많으면 성능 저하를 일으킨다.
    *   **Accept Count (수용 대기 요청 수):** 현재 사용 가능한 스레드가 부족하여 즉시 처리가 불가능할 때, 잠시 대기(Queue)할 수 있는 최대 요청 건수.

## 4. ThreadLocal을 이용한 데이터 공유 메커니즘
- **ThreadLocal의 개념:** 특정 쓰레드 내에서만 접근하고 사용하는 고유한 저장 공간이다. (Key Principle: 각 스레드는 자신만의 독립적인 데이터를 가짐)
- **필요성 및 동작 원리:**
    *   웹 요청이 들어올 때마다 여러 필터, 서비스, 컨트롤러를 거치게 되며(복잡한 호출 흐름), 이 과정에서 사용자 정보 같은 상태 정보를 매번 파라미터로 전달하는 것은 매우 번거롭고 복잡하다.
    *   `ThreadLocal`은 이러한 상태 값들을 쓰레드 자체에 바인딩하여 저장할 수 있게 해주므로, 개발자가 별도로 값을 전달하지 않아도 해당 요청을 처리하는 *쓰레드가 살아있는 동안* 어디서든 그 정보를 가져와 사용할 수 있다. (예: 사용자 인증 정보)
- **주의사항:** 스레드가 재사용될 경우(스레드 풀 사용), 이전 요청에서 저장했던 데이터가 남아있을 수 있으므로, 반드시 작업이 끝난 후에는 `remove()` 같은 클리어 과정을 통해 해당 쓰레드의 값을 비워줘야 한다.

## 1. ThreadLocal 패턴 이해 및 활용
- **개념:** `ThreadLocal`은 특정 스레드에만 데이터를 저장할 수 있게 해주는 저장 공간입니다. 이는 해당 스레드 내에서 동작하는 모든 로직이 동일한 데이터(예: 사용자 정보)를 공유하고 사용할 수 있도록 보장합니다.
- **작동 방식:** 요청이 들어올 때마다 새로운 쓰레드가 할당되거나, 기존 쓰레드가 재사용될 때 해당 스레드에 데이터를 *맡겨두는* 방식으로 값을 관리합니다. 이 값은 해당 스레드가 살아있는 동안(요청 처리 과정 전체)에서만 유효합니다.
- **장점:** 여러 레이어(Filter -> Service -> Controller 등)를 거치면서도 파라미터 전달 없이 한 요청의 상태 정보(사용자 ID, 인증 정보 등)를 일관되게 유지할 수 있습니다.
- **활용 예시:** Spring Security가 내부적으로 사용자 정보를 담는 `SecurityContextHolder`를 사용하여 이 패턴을 구현하는 것이 대표적입니다.

## 2. 사용자 컨텍스트 관리와 요청 흐름 제어
- **사용자 인증 정보 전달:** 일반적으로 사용자 객체(User)나 관련 데이터를 얻기 위해 전역적인 저장소(예: `ThreadLocal`)에 값을 할당합니다. 이 과정은 주로 웹 필터(`Filter`)에서 발생합니다.
- **요청의 일관성 확인:** 실제 요청이 들어와서부터 응답을 돌려줄 때까지, 해당 요청을 처리하는 모든 과정은 하나의 쓰레드(Thread) 내에서 동작합니다. 이는 `ThreadLocal` 패턴을 사용하는 근거가 됩니다.
- **핵심 개념: 데이터의 범위:** 사용자가 필터 단에서 저장한 값은 컨트롤러나 서비스 계층에서 직접 파라미터를 통해 전달받지 않아도, 같은 쓰레드 내부 로직에서는 `ThreadLocal`을 통해 값을 꺼내 쓸 수 있습니다.
- **데이터 정리(Cleanup)의 중요성:** 쓰레드가 요청 처리를 마치고 돌아올 때는 반드시 `ThreadLocal`에 저장된 데이터를 명시적으로 삭제(`clear()`)해야 합니다. 만약 이 과정이 생략되면 다음 사용자가 같은 쓰레드를 재사용할 때 이전 요청의 잔여 데이터가 남아 오작동을 유발합니다.
- **안전한 정리 로직:** 정리 과정은 예외 발생 여부와 관계없이 반드시 실행되어야 하므로, `try-finally` 블록을 사용하여 리소스 클리어(Clear) 로직을 구현하는 것이 가장 안전하고 바람직합니다.

## 3. Spring Security를 이용한 웹 애플리케이션 보안 구현
- **기본 문제점:** 별도의 설정 없이 만든 웹 페이지는 누구나 접근할 수 있어 보안에 매우 취약합니다. (모든 리소스가 `permitAll()` 상태)
- **Spring Security 모듈 추가의 효과:** `spring-boot-starter-security`와 같은 의존성을 추가하는 것만으로도, 애플리케이션은 기본적으로 강력한 인증(로그인) 로직을 요구하도록 설정됩니다.
- **보안 요청 제어 (`http.authorizeRequests()`):**
    - **기본 동작:** 기본 설정은 모든 페이지에 대해 인증이 필요하다고 가정합니다 (`anyRequest().authenticated()`).
    - **예외 처리:** 특정 페이지는 로그인을 거치지 않고도 접근 가능하도록 명시적으로 제외할 수 있습니다 (Ex: `/public/**` 경로는 누구나 접근 가능).
- **설정 주체와 구현 방법:**
    - Spring Security의 설정을 담당하는 클래스는 반드시 `@Configuration` 어노테이션을 붙여야 합니다.
    - 실제 보안 규칙 정의는 `HttpSecurity` 객체를 통해 빌드업(Build-up) 패턴으로 설정합니다.
- **사용자 및 비밀번호 등록:**
    - 기본 동작 시 서버가 임시로 생성한 사용자 이름과 비밀번호를 사용하여 초기 로그인을 수행할 수 있습니다.
    - 애플리케이션의 환경설정 파일(`application.yml` 또는 `application.properties`)에서 원하는 사용자 정보와 패스워드를 직접 지정하여 보안 설정을 오버라이드 할 수 있습니다.

## 1. Spring Security 개요 및 상태 관리 원리 이해
- **자동 인증 기능:** Spring Security 모듈만 의존성으로 추가하는 것만으로도 웹 애플리케이션에 자동으로 인증 화면이 제공된다. (사용자 입맛에 맞게 다양한 페이지 정보까지 커스터마이징 가능함.)
- **세션 및 쿠키의 역할:** 서버가 종료되어도 사용자의 로그인 상태(인증 정보)가 유지되는 것은 주로 **쿠키와 세션** 덕분이다.
    - 인증 과정에서 사용자 정보를 저장하고 상태를 유지하기 위해 쿠키나 세션을 활용한다.
    - 세션은 기본적으로 클라이언트(브라우저)의 요청이 들어올 때, 쿠키에 담긴 식별자(JSessionID 등)를 통해 서버가 사용자의 정보를 참조하여 상태를 알게 된다. (쿠키는 인증 작업 시 필요한 '증표'와 같은 역할을 한다.)
- **상태 유지 확인:** 실제 개발 환경에서 쿠키 에디터 등의 도구를 사용하여 특정 쿠키(예: JSession ID)를 삭제하고 요청을 재시도하면, 로그인 상태가 해제되어 다시 인증 과정을 거치게 됨을 확인할 수 있다.

## 2. 보안 위협 방어를 위한 주요 설정 (CSRF, 인증 방식)
- **다양한 인증 제공:** Spring Security는 기본적으로 HTTP Basic, Form 등 다양한 인증 방법을 지원하며, 기본적인 설정을 통해 웹 애플리케이션에 적용할 수 있다.
- **보안 취약점 방어:**
    - **CSRF(Cross-Site Request Forgery):** 사이트 간에 요청을 위조하여 사용자가 로그인된 상태에서 권한 없는 작업을 수행하게 막는 공격으로부터 보호하는 기능이다. (사용자와 함께 '표식' 등을 심어 전송함으로써 위변조 여부를 확인한다.)
    - **헤더 인증:** 레스트 컨트롤러 등 API 환경에서는 요청 헤더(Header)를 통해 인증 정보를 전달하고 처리할 수 있다.
- **인가 및 접근 제어 설정:**
    - `HttpSecurity` 객체를 이용하여 세부적인 보안 설정을 할 수 있다.
    - 모든 엔드포인트에 대한 인증 여부를 설정하거나, 특정 페이지(`permitAll()`)는 인증 없이 접근 가능하도록 예외 처리를 할 수 있다. (예: 로그인 폼 페이지, 기본 페이지)

## 3. Security 동작의 내부 메커니즘: 필터 체인 분석
- **필터 기반 인증/인가:** Spring Security가 인증 및 인가 작업을 수행할 때는 여러 개의 보안 필터(Filter)를 순차적으로 거치며 요청을 처리한다.
- **필터 체인의 흐름:** 요청이 들어오면 `FilterChainProxy`를 시작으로 다수의 필터들이 직렬로 동작하며 요청의 유효성 검사, 인증 정보 확인 등을 수행한다. (대표적인 예: `UsernamePasswordAuthenticationFilter`, `SecurityContextPersistenceFilter` 등)
- **인증 컨텍스트 저장:** 이러한 보안 과정에서 사용자 인증 정보를 안전하게 보관하고 관리하기 위해 **`ThreadLocal`**과 같은 영역을 이용한다.
    - 요청 처리 동안 인증된 사용자 정보가 시스템 전반에 걸쳐 유지되도록 값을 저장하는 역할을 한다.

## 4. 커스터마이징을 통한 로그인 플로우 구현
- **사용자 정의 경로 설정:** Spring Security의 기본 설정을 오버라이딩하여, 개발자가 원하는 페이지를 중심으로 인증 프로세스 흐름(Flow)을 정의할 수 있다.
    - **로그인 페이지 커스터마이징:** 초기 기본 설정된 로그인 페이지 대신 원하는 URL로 사용자 정의가 가능하다.
    - **프로세스 URI 지정:** 실제 로그인을 처리하는 로직의 경로(`loginProcessingUrl`)와 사용자가 인증 성공/실패 시 리다이렉트될 페이지(`successUrl`, `failureUrl`)를 명확히 설정할 수 있다.
    - **파라미터 정의:** 사용자 이름(Username)과 비밀번호(Password) 등의 파라미터가 클라이언트 측에서 어떤 이름을 가져야 하는지 명시적으로 지정해야 한다.
- **프런트엔드 연동 필수 사항:**
    - Security 설정으로 정한 로그인 경로와 액션, 메서드를 프론트엔드의 폼 태그(`form`)의 `action`과 `method`에 반드시 맞춰주어야 인증 요청이 정상적으로 처리된다.

## 5. 결론 및 심화 학습 주제
- **핵심 원리 정리:** Spring Security는 필터 체인(Filter Chain)을 이용하여요청마다 인증/인가 작업을 수행하며, 이 과정에서 세션과 스레드 로컬 등의 메커니즘을 통해 사용자 상태를 관리한다.
- **개발자의 역할:** Spring Boot의 스타터가 기본 모범 사례를 제공하지만, 실제 서비스 환경에서는 시스템의 특성에 맞게 보안 설정을 변경하고 커스터마이징할 수 있어야 한다.
- **심화 학습 분야:** 배운 개념을 바탕으로 향후 더욱 발전된 인증/인가 방식을 학습할 수 있다.
    - JWT(JSON Web Token)를 이용한 토큰 기반 인증
    - OAuth, 소셜 로그인 (카카오 등 외부 서비스 연동)
