## 1. 오리엔테이션 및 학습 태도 점검: 어려움을 극복하는 과정의 중요성
- **배경 지식의 중요성 강조:** 프로그래밍 초기에 변수 선언, JPA, JDBC 같은 개념들이 어렵게 느껴졌지만, 반복적인 경험을 통해 점차 익숙해지듯 보안(Security)과 같은 복잡한 주제도 꾸준히 학습하면 이해할 수 있습니다.
- **기술 습득의 관점:** 현재 배운 지식은 가장 기초적이고 핵심 로직을 사용법 중심으로 다루고 있으므로, 실제 운영되는 서비스에 대해서는 더 많은 고려 사항이 있음을 인지해야 합니다.
- **학습 자세 유지:** 너무 어려워하는 부분에 좌절하지 말고, ‘다음에 어떻게 적용해 볼 수 있을까?’라는 관점에서 생각하며 꾸준히 학습 동기를 부여하는 것이 중요합니다.

## 2. 인증/보안 시스템의 기본 원리와 문제점 이해
- **JWT의 필요성 도출 과정:** JWT(JSON Web Token)가 왜 필요한지를 기술적인 배경에서 이해할 필요가 있습니다. 웹 애플리케이션은 클라이언트에게 상태를 유지시켜주지 않는 **무상태(Stateless)** 프로토콜인 HTTP를 기반으로 하기 때문에, 사용자가 누구인지 지속적으로 인증하는 메커니즘이 필수적입니다.
- **세션(Session) 기반 방식의 한계:** 서버가 사용자 정보를 세션에 저장하여 관리할 경우, **서버 확장성 및 분산 환경 구축 시 문제**가 발생합니다. (여러 대의 서버에서 동일한 상태 정보에 접근하기 어려움).

## 3. 대규모 시스템 구축을 위한 아키텍처 개념 (확장성과 상태 관리)
- **시스템 규모와 확장성:** 서비스 사용자가 늘어나고 동시 접속자 수가 증가하면, 하나의 서버만으로는 요청 처리에 한계가 오기 때문에 여러 대의 서버를 두어 트래픽을 분산시켜야 합니다.
- **로드 밸런서(Load Balancer) 역할:** 여러 대의 서버로 요청을 고르게 배분하는 장치입니다. 이 로드 밸런서는 클라이언트의 요청을 받아 가장 효율적인 서버로 안내하며, 이를 통해 시스템의 부하를 분산시킵니다.
    - *기본 방식:* 라운드 로빈(Round Robin) 등 순차적 분배 방식이 대표적입니다.
- **상태 관리 문제 해결 (Redis 도입):** 여러 서버가 상태 정보(세션 데이터 등)를 공유해야 할 때, 개별 서버의 메모리 세션은 한계가 있습니다. 따라서 **데이터베이스(DB)**나 **캐시 시스템(예: Redis)**과 같이 모든 서버가 접근 가능한 외부 저장소를 이용해 사용자 상태 정보를 관리하게 됩니다. (이를 통해 서버 분산이 가능해짐).

## 4. JWT를 활용한 토큰 기반 인증 심화 및 보안 메커니즘 학습
- **JWT의 역할 재정립:** JWT는 그 자체로 '무언가를 하는 것'이 아니라, 정보를 담아 구조화된 **웹 토큰** 역할을 합니다.
    - *구조:* 헤더(Header), 페이로드(Payload), 시그니처(Signature) 세 부분으로 구성됩니다.
- **JWT의 장점 (서버 부하 감소):** 서버가 매번 사용자 정보를 조회할 필요 없이, 서명만 검증하면 토큰에 담긴 정보가 위변조되지 않았음을 신뢰할 수 있어 시스템 부하를 줄일 수 있습니다.
- **보안 강화를 위한 메커니즘:** Access Token과 Refresh Token을 분리하여 사용하며 보안을 강화해야 합니다.
    - *Refresh Token의 관리:* Refresh Token은 탈취될 위험에 대비해 반드시 서버가 데이터베이스에서 관리(저장)하고, 블랙리스트를 두어 사용자가 만료/분실 신고를 할 경우 시스템적으로 사용할 수 없게 만들 수 있습니다. (이를 통해 토큰 재발급 및 강제 로그아웃 관리가 가능해집니다.)

## 5. 개발자로서의 성장 방향과 최신 트렌드 탐색
- **통합적 사고 능력 함양:** 기술 학습 시 단순히 지식을 얻는 것을 넘어, "이 서비스는 왜 이런 방식으로 인증을 하고 있을까?", "이런 문제는 어떻게 해결할 수 있을까?"처럼 시스템 전체를 아우르는 관점에서 질문하고 생각하는 것이 중요합니다.
- **개방형 정보 활용의 중요성:** 최신 기술 트렌드나 다른 기업/서비스가 유사한 기능을 어떻게 구현했는지(예: 브랜치 전략, 인증 방식) 적극적으로 찾아보고 분석하는 과정 자체가 가장 좋은 공부가 됩니다.
- **협업과 지식 공유:** 개인적인 능력 향상만큼이나 팀원들과 함께 복잡한 기술적 고민을 논의하고 해결책을 찾는 '회고 활동' 또한 중요한 성장 동력이 되며, 이는 직장 생활에서도 큰 자산이 됩니다.

## 1. 소셜 로그인의 등장 배경과 개인 정보 문제 인식
- **편의성 이상의 이유:** 소셜 로그인은 단순히 간편한 회원가입을 넘어, 사용자가 자신의 민감 정보를 직접 서비스에 제공하는 위험성을 해결하기 위해 존재한다.
- **데이터 주권 및 보안 의식 강화:** 과거에는 주민번호 같은 과도한 정보 요구가 흔했지만, 현재는 개인정보 유출과 오용 가능성에 대한 사용자들의 경각심이 높아졌다.
- **신뢰 기반 인증의 필요성:** 사용자는 자신이 이용하는 서비스(Client)가 어떤 정보들을 모아 나쁜 목적으로 사용할지 확신할 수 없기 때문에, 공신력 있는 대형 플랫폼(Google, GitHub 등)을 통한 '간접적인 신원 인증'이 필수적이다.
- **OAuth 2.0의 등장 배경:** 이러한 개인정보 보호와 보안 요구 증대 때문에, 사용자의 비밀번호를 공유하지 않고도 제3자 서비스에 한정된 접근 권한만을 부여하는 개방형 표준 프로토콜(OAuth)이 필요해졌다.

## 2. OAuth 2.0의 개념 및 핵심 역할 정의
- **개념:** OAuth 2.0은 사용자가 자신의 자격 증명(Credential)을 직접 공유하지 않고도, 서비스에 특정 범위의 접근 권한만을 위임할 수 있게 하는 표준 프로토콜이다. (위임을 통한 인증)
- **핵심 참여 주체 및 역할:**
    *   **리소스 오너 (Resource Owner):** 정보(Resource)의 실제 소유자이자 주인은 항상 **최종 사용자** 본인이다. 이들은 자신의 정보가 누구에게 어떻게 사용될지 통제권을 가진다.
    *   **클라이언트 (Client):** 정보를 요청하고 서비스를 제공받으려는 *내가 만든 서비스(애플리케이션)*를 의미하며, 사용자가 아닌 애플리케이션이 주체가 되어 권한을 요청한다.
    *   **권한 부여 서버 (Authorization Server):** 리소스 오너가 본인임을 인증하고, 클라이언트에게 접근 권한을 증명하는 **접근 토큰(Access Token)**을 발급해주는 주체다.
    *   **리소스 서버 (Resource Server):** 실제 보호된 정보(예: 사용자 프로필, 이메일 등)를 저장하고 보유하며, Access Token의 유효성을 검증한 후 정보를 제공하는 역할을 한다.
- **주요 용어 정리:**
    *   **Access Token:** 리소스 서버에 접근하여 보호된 자원을 요청할 때 사용하는 일종의 '자격 증명' (비밀번호 대체).
    *   **Refresh Token:** Access Token이 만료되었을 때, 새로운 Access Token을 재발급받기 위해 사용되는 토큰.
    *   **(참고) 서버 분리 가능성:** Authorization Server와 Resource Server는 논리적으로 분리되지만(대형 서비스), 실제로는 하나의 서버가 두 기능을 모두 수행할 수도 있다.

## 3. OAuth 2.0 인증 절차 (Authorization Code Flow) 상세 이해
- **프로세스 흐름 요약:** 사용자가 애플리케이션에 로그인 시도 → 권한 부여 요청 (Client ➡️ Authorization Server) → 사용자 승인 및 코드를 얻음 → 토큰 교환 (Code ➡️ Client Access Token) → 정보 접근 (Access Token ➡️ Resource Server).
- **① 초기 인증 단계 (권한 부여):**
    *   사용자가 서비스에 로그인 시도를 하면, 사용자는 외부 플랫폼(GitHub 등)의 인증 페이지로 리디렉션된다.
    *   플랫폼은 사용자에게 "이 클라이언트가 당신의 어떤 정보를 사용할 수 있도록 허용할지"를 **명시적으로 물어본다.** (개인정보 동의 획득 과정).
    *   사용자가 동의하면, 권한 부여 서버는 인증 코드를 발급한다.
- **② 토큰 교환 및 정보 요청:**
    *   클라이언트는 받은 **인가 코드(Authorization Code)**를 이용하여 직접 접근하는 것이 아니라, 전용 엔드포인트에 이 코드를 제출하고 Access Token을 받는다. (보안성 확보).
    *   애플리케이션은 획득한 Access Token을 가지고 리소스 서버에 필요한 사용자 정보(예: 이름, 이메일 주소)를 요청한다.
- **③ 토큰 만료 및 재발급:**
    *   Access Token은 유효 기간이 매우 짧아 매번 API 호출 시 사용된다.
    *   만료된 경우, Refresh Token을 사용하여 Access Token의 갱신(Refresh) 절차를 거친 후 새로운 자격 증명으로 서비스에 계속 접근할 수 있다.

## 4. 실습 준비: GitHub Developer Settings 설정 과정
- **필수 전제:** 프로젝트에서 OAuth를 이용하려면 인증 정보를 관리해 줄 외부 플랫폼(GitHub)에 앱을 등록해야 한다.
- **등록 단계 (기술 가이드):**
    1.  [GitHub] 사이트에 접속 후, `Settings` 메뉴로 이동한다.
    2.  하단부의 `Developer Settings`에서 `New GitHub App`을 생성한다.
    3.  웹사이트 주소(Website URL)와 **콜백 URL (Callback URL)**을 반드시 등록해야 한다.
- **⚠️ 콜백 URL 중요성:** 애플리케이션이 인증 코드를 받아올 때 돌아오게 될 최종 엔드포인트 주소를 지정하는 곳이며, `http://localhost:8080/oauth/github`와 같이 정확하게 설정해야 한다.

## 1. GitHub OAuth 설정 및 기본 원리 이해
- **GitHub App 사용 목적:** 외부 서비스(클라이언트)가 GitHub의 핵심 기능에 접근해야 할 때 GitHub App을 등록하여 권한을 확보합니다. (단, 본 프로젝트는 앱 기능을 직접 사용할 필요 없이 인증(Authentication) 과정만 거칩니다.)
- **앱 등록 절차 및 필수 항목 설정:**
    - `GitHub Apps` 페이지에서 새로운 앱을 등록하고 다음 정보를 설정해야 합니다.
        - **Homepage URL:** 서비스가 배포될 기본 주소 (예: `localhost:8080`).
        - **Authorization Callback URL:** GitHub가 사용자 인증 후 토큰이나 데이터를 리디렉션(redirect)할 때 사용되는 고유한 엔드포인트입니다. 이 경로는 특정 규칙을 따라야 합니다.
    - **필수 획득 정보 (Credentials):** 앱 등록이 완료되면 다음 두 가지 값을 반드시 복사하여 안전하게 보관해야 합니다.
        - **Client ID:** 애플리케이션 식별자.
        - **Client Secret:** 앱의 보안 비밀키로, 토큰 발급 시 서명(Signature)을 생성하는 데 사용되는 민감한 값입니다.
- **권한 범위 (Scope):** 서비스가 GitHub 사용자로부터 접근하고자 하는 정보의 범위를 명확히 설정해야 합니다. (예: 사용자 정보 읽기, 이메일 주소 읽기 등).

## 2. 소셜 로그인을 위한 데이터 모델링 강화
- **데이터베이스 구조 개선 필요성:** 서비스가 '직접 회원 가입'과 '소셜 로그인'이라는 두 가지 인증 방식을 모두 지원해야 하므로, 기존 User 테이블의 컬럼을 확장해야 합니다.
- **User 테이블 컬럼 추가 (필수):** 소셜 로그인의 사용자를 구분하고 정보를 보존하기 위해 다음 컬럼들을 `User` 엔티티에 추가합니다.
    - `social_id` (String): 소셜 플랫폼에서 사용하는 고유 ID.
    - `provider` (String): 로그인에 사용된 소셜 서비스 이름 (예: 'GitHub', 'Google').
- **데이터 분리 및 목적:**
    - **User 테이블:** 기본적인 사용자 식별 정보와 함께 소셜 로그인 정보를 담는 메인 역할.
    - **SocialUser 엔티티/테이블:** 소셜 플랫폼이 제공하는 상세 정보(아바타 URL, 이름 등)를 별도로 보관합니다. 이는 일반적인 사용자 프로필과 분리하여 관리할 필요가 있습니다.
- **추가 정보 수집을 위한 임시 테이블 (Optional):**
    - **SocialLoginInfo 엔티티/테이블:** 소셜 로그인을 통해 가입한 사용자가 추가 정보를 입력하게 하는 시나리오를 구현하기 위해 도입됩니다.
    - 이 테이블의 목적은 특정 시간(예: 20분) 제한을 두어 악의적인 요청을 방지하고, 해당 과정에서 필요한 임시 정보들을 관리하는 것입니다.

## 3. 서비스 로직 구현: 소셜 사용자 정보 관리
- **엔티티 및 레파지토리 구성:** 소셜 로그인 관련 기능을 안정적으로 처리하기 위해 추가적인 엔티티(`SocialLoginInfo`)와 이에 맞는 레파지토리를 정의해야 합니다.
- **핵심 기능 구현 (Service Layer):** `UserService`에서는 소셜에서 전송된 데이터를 받아 사용자 정보를 저장하고 업데이트하는 핵심 로직을 구현합니다.
    - **메서드 목적:** 사용자가 소셜로 로그인을 시도할 때, 해당 정보(`social_id`, `provider`)를 기반으로 시스템에 이미 같은 유저가 존재하는지 먼저 확인(Find)하는 것이 중요합니다.
    - **흐름 제어 (Upsert 로직):**
        1. 주어진 소셜 ID와 프로바이더를 가지고 DB에서 기존 사용자를 조회합니다.
        2. **사용자가 존재할 경우:** 기존 사용자 정보를 최신 정보로 업데이트합니다(Update).
        3. **사용자가 없을 경우:** 새로운 유저 정보를 생성하여 저장합니다(Insert).
- **정책적 결정의 중요성:** 소셜 로그인 기능 구현 시, 서비스는 다음 세 가지 측면에서 정책적 결정을 할 수 있습니다.
    1. 사용자에게 자사 사이트 직접 가입을 받을지 여부 (선택 사항)
    2. 소셜 플랫폼에서 받은 정보를 얼마나 저장할지 여부 (필수/선택)
    3. 소셜 로그인 후 추가 정보를 필수로 받아야 하는지에 대한 정책 정의

## 1. OAuth의 필요성과 개념 정의
OAuth(Open Authorization)는 외부 서비스를 이용하여 사용자 인증을 처리하는 표준 프로토콜입니다.

*   **기존 문제점:**
    *   오래된 웹 애플리케이션에서 사용자의 정보가 분산 관리되어 부담이 커짐.
    *   사용자 입장에서는 서비스 제공자가 불분명하거나 신뢰도가 낮은 경우 개인 정보를 제공하기 꺼려짐.
    *   서비스 제공자(운영 주체)의 시스템 문제나 정보 관리 미흡으로 인한 보안 위험 존재.
*   **OAuth의 해결책:**
    *   기존 계정 기반 가입 대신, 사용자가 이미 사용하는 대형 서비스(Google, Kakao 등)를 통해 인증하게 하여 편리성과 신뢰성을 높임.
    *   표준화된 표준 프로토콜을 사용하여 정보를 제공받는 쪽과 제공하는 쪽 간의 약속을 명확히 함.

## 2. 핵심 용어 및 아키텍처 이해
OAuth 구조를 이해하기 위한 필수 개념들을 정의합니다.

*   **Resource Owner (리소스 소유자):** 정보(개인 데이터)의 실제 주인은 사용자 자신입니다. 서비스 제공자가 정보를 유출하더라도 법적 주권자는 사용자에게 있습니다.
*   **Client (클라이언트):** 실제로 사용자를 의미하는 것이 아니라, OAuth를 이용하는 우리가 개발할 '서비스 애플리케이션' 자체를 의미합니다.
*   **인증 서버(Authorization Server) 및 리소스 서버(Resource Server):**
    *   일반적으로 하나의 서비스가 두 역할을 모두 수행하지만, 논리적으로 분리하여 이해해야 합니다.
    *   **동작 흐름:** 사용자가 접속 $\rightarrow$ 인증 서버에서 사용자 인증 수행 $\rightarrow$ **액세스 토큰(Access Token)** 발급 (클라이언트에게) $\rightarrow$ 클라이언트는 이 액세스 토큰을 가지고 리소스 서버에 정보 요청 $\rightarrow$ 리소스 서버는 토큰의 유효성을 검증 후 정보를 제공.

## 3. 개발 학습 방법론 및 조언
*   **개념 이해가 최우선:** 코드를 못 만들까 봐 걱정할 필요 없이, 먼저 개념(아키텍처, 흐름)을 깊이 이해하는 것이 가장 중요합니다.
*   **실습 방식의 권장:** 코드는 처음부터 완벽하게 손으로 짜는 것이 아니므로, '복사-붙여넣기'에 의존하기보다 직접 하나씩 입력해보면서(타이핑하며) 개념과 코드를 연결하여 이해하는 학습 방법이 효과적입니다.
*   **정보의 흐름 파악:** 실제로 동작하는 시스템을 볼 때도, 적절한 문서나 다른 개발자의 코드를 참고하고 이를 내 프로젝트에 맞게 수정하여 적용하는 방식으로 작업합니다.

## 4. 소셜 로그인 구현 준비 및 데이터베이스 설계
소셜 로그인을 구현하기 위해 필요한 데이터베이스 스키마 변경과 로직을 설계합니다.

*   **소스 테이블 추가:**
    1.  `social_user`: 소셜 로그인 시 사용자의 정보(ID, 닉네임 등)를 저장하는 목적의 테이블.
    2.  `users` (유저스): 기존 가입 사용자 정보를 관리하며, 소셜 로그인 유무 관련 컬럼을 추가하여 구분합니다.
    3.  **별도 `login_info` 테이블 설계:** 회원가입 정보(추가 정보)를 받아올 때의 시간 제한 및 오류 처리를 위해 사용됩니다. (예: 값 입력 시 20분 이내에 응답해야 함).
*   **구현 결과:** 위의 요구사항을 충족하기 위해 각 엔티티(`Entity`)와 리포지토리(`Repository`), 그리고 서비스 레이어의 메서드를 추가합니다.

## 5. 웹 페이지/컨트롤러 구조 구현 (Front-end & Controller)
클라이언트가 접근하게 될 다양한 상태별 페이지와 이를 처리할 컨트롤러 로직을 구성합니다.

*   **페이지 생성:** 소셜 로그인 프로세스를 담는 `auth` 디렉토리를 만들고, `info`, `welcome`, `login_form` 등 필요한 템플릿 페이지들을 구성합니다.
*   **컨트롤러 구현 목표:** 사용자가 링크를 통해 접근하는 모든 경로(홈, 마이 인포, 웰컴)가 정상적으로 처리되도록 컨트롤러 메서드를 작성합니다.
*   **MyInfo 페이지 로직 심화:**
    *   `myinfo` (마이 정보) 페이지는 단순히 `info` 템플릿을 보여주는 것이 아니라, **현재 인증된 사용자(Principal)**의 정보를 활용하여 커스텀 유저 상세 객체(`CustomUserDetails`)를 만들어야 합니다.
    *   이를 위해 서비스 계층에서 인증된 사용자의 데이터를 조회하고 모델에 전달하는 과정을 거칩니다.

## 6. 핵심 서비스 로직 완성: 시간 검증 기능 추가
회원가입 시 필수 정보를 받아오는 과정의 안정성을 높이기 위한 비즈니스 로직을 구현합니다.

*   **`SocialLoginInfoService` 역할:** 소셜 로그인을 통해 사용자가 추가 정보를 제출할 때, 단순 저장 기능을 넘어 **시간 제한(Time Constraint) 검증**을 담당하는 서비스 계층입니다.
*   **주요 기능:**
    1.  사용자 데이터베이스에서 이전에 기록된 정보의 시간 값을 조회합니다.
    2.  현재 시간과 저장된 시간을 비교하여, 설정된 시간 차이(예: 20분)를 초과했는지 검증합니다.
    3.  시간 초과 시 오류를 발생시키고 정보를 저장하지 못하게 처리하는 로직을 포함해야 합니다.

## 1. 소셜 로그인 및 데이터 처리 로직 구축
*   **소셜 로그인 플로우 이해:** 사용자가 소셜 로그인을 할 경우, 필요한 값을 얻어와 자동 가입 페이지를 띄워주고 시간을 체크하는 프로세스가 필요합니다.
    *   (예시) 특정 시간(20분 이상) 동안 활동이 없거나 요청 지연이 발생하면 에러 처리를 하도록 로직을 구현해야 합니다.
*   **서비스 레이어 설계:** 소셜 로그인 정보를 관리하기 위해 서비스 계층(`SocialLoginService`)을 구성합니다.
    *   실제 저장(`save`)과 불러오기(조회, `find`)의 두 가지 핵심 메서드를 중심으로 간단히 구현하는 것이 좋습니다.
*   **데이터 모델 정의 및 트랜잭션 처리:** 소셜 로그인 정보 저장을 위해 `SocialEntity`를 별도로 선언해야 합니다.
    *   저장 시 데이터 무결성 유지를 위해 트랜잭션(Transaction) 처리가 필수적입니다.
*   **핵심 조회 로직 구현:** 데이터를 저장하고 조회할 때, `Provider`, `UUID`, `SocialID` 세 가지 키를 조합하여 정보를 찾도록 서비스 메서드를 구성합니다.

## 2. 사용자 상세 정보 및 서비스 레이어 커스텀 구현 (Spring Security 통합)
*   **CustomUserDetailsService의 역할:** Spring Security가 사용자를 인증할 때(인증 객체 생성 시), 어떤 사용자가 누구인지 식별하는 역할을 담당하는 핵심 컴포넌트입니다.
    *   이 클래스는 반드시 `UserDetailsService` 인터페이스를 구현해야 하며, 현재 시스템에 맞게 사용자 정보를 조회하도록 로직을 구성해야 합니다.
*   **데이터 흐름 이해:** Spring Security는 내부적으로 '사용자 정보'와 이를 얻어낼 수 있는 '서비스 객체'의 쌍(Pair)을 요구합니다. (커스텀 UserDetails + 커스텀 UserDetailsServiceService).
    *   따라서, `CustomUserDetailsService` 외에도 유사한 기능을 하는 서비스 객체를 구현해야 보안 흐름에 문제가 없습니다.
*   **안정적인 데이터 처리:** 사용자 정보 조회 메서드(`loadUserByUsername`)에서는 사용자를 찾지 못할 경우를 대비하여 결과를 **Optional** 타입으로 반환하는 것이 좋습니다. (NullPointerException 방지)
*   **OAuth 2.0 통합 관점 확장:** 소셜 로그인이 외부 인증 서버(OAuth2/OIDC)를 사용하는 방식과 비교하며, 내부적으로 사용자의 정보를 얻어내고 이를 Security Flow에 맞는 객체로 변환해주는 것이 핵심임을 이해해야 합니다.

## 3. 전반적인 보안 설정(SecurityConfig) 및 OAuth 2.0 연동
*   **SecurityConfig의 역할:** 애플리케이션 전체의 보안 규칙과 흐름을 한곳에서 정의하는 가장 중요한 설정 파일입니다.
    *   `@EnableWebSecurity`, `RequiredArgsConstructor` 등 필수 어노테이션 및 구조를 갖춰야 합니다.
*   **필수 설정 요소 점검 (Best Practices):**
    *   **CORS(Cross-Origin Resource Sharing) 설정:** 허용할 오리진(`addAllowedOrigin`)과 헤더, HTTP 메서드 등을 명시적으로 지정해야 합니다. (기본값 '모두 허용'으로 설정 후, 추후 보안 강화 시 수정 필요).
    *   **접근 권한 설정 (Authorization):** 특정 URL에 대한 접근을 `permitAll()`(전체 허용), 혹은 인증이 필요한 요청만 허용하도록 구역별로 명확하게 지정해야 합니다.
        *   *(Tip)* 소셜 로그인 및 회원가입 과정에서 사용되는 핵심 링크들(`auth/`, `signup` 등)은 예외적으로 모든 사용자에게 접근을 허용(Permit All)해야 합니다.
    *   **로그아웃 및 성공 URL 설정:** 로그아웃 시 정상적인 흐름으로 안내할 디폴트 성공 URL을 지정하여 보안성을 높입니다.
*   **OAuth 2.0 통합 구현:** 외부 인증 서버를 사용하기 위해 다음 단계를 수행합니다.
    1.  `SecurityConfig`에 OAuth 2.0 관련 설정을 추가하고 필요한 클라이언트 정보를 등록합니다.
    2.  Spring Security가 내부적으로 사용하는 인터페이스(예: `OAuth2UserService`, `OidcUserService`)의 동작 방식을 이해해야 합니다.
    3.  실제 구현 시, 외부에서 들어온 인증 정보(클레임)를 파싱하여 애플리케이션이 사용할 사용자 객체로 변환하는 로직을 추가해야 합니다.

*   **핵심 비교 대상 (Service Layer):** OAuth2 흐름의 핵심 객체인 `AwsOAuth2UserService`와 `UserDetailsService`를 이해하는 것이 중요합니다.

## 2. 소셜 인증 정보 추출 및 데이터 처리 전략

*   **로그인 시나리오 재확인:** 기본적인 소셜 로그인 흐름은 성공적인 인증 이후, 획득한 정보를 DB에 저장하고 사용자에게 회원가입 폼을 제공하는 과정을 포함합니다.
    *   저장해야 할 핵심 정보: 소셜 ID, 프로바이더 이름(Provider), 사용자 이름(Username), 이메일 주소, 아바타 URL 등입니다.
*   **인증 요청 객체 활용 (`OAuth2UserRequest`):** 오스를 통해 전달받은 요청 객체를 이용해 필요한 정보를 추출합니다.
    *   **프로바이더 식별:** `ClientRegistration`을 사용하여 제공자가 누구인지(`Get Registration ID`) 확인할 수 있습니다.
    *   **속성 추출의 중요성 (getAttributes):** 사용자 이름, 이메일 등 여러 속성은 일반적으로 `OAuth2User` 객체의 `getAttributes()` 메서드를 통해 맵(Map) 형태로 얻어옵니다.
*   **안전한 데이터 타입 변환:** `getAttributes()`가 반환하는 값은 기본적으로 `Object` 타입이므로, 사용하기 전에 반드시 적절한 타입으로 형 변환(Casting)을 거쳐야 합니다.
    *   **Null 안전성 확보 (권장):** 단순 캐스팅 방식으로는 값이 `null`일 때 런타임 예외(`ClassCastException`)가 발생할 수 있습니다. 따라서 `String.valueOf()`와 같이 **널 값도 오류를 유발하지 않고 안정적으로 변환해주는 메서드**를 사용하는 것이 가장 안전하고 효율적입니다.
    *   **필수 체크 로직 구현:** 외부에서 들어오는 URI를 파싱(Parsing)하여 프로바이더 이름을 얻어올 때는, 해당 값이 `null`인지 또는 빈 문자열(`blank`)인지 사전에 철저하게 검사하는 로직을 추가해야 합니다.

## 3. 인증 성공 후 보안 컨텍스트 핸들링: 커스텀 구현

*   **인증 성공의 의미:** OAuth2를 통한 로그인이 '성공'했다는 것은 단순히 외부(GitHub 등)에서 인증 토큰이 발급되었다는 것을 의미할 뿐, 우리 내부 서비스에 알맞은 상태로 처리되어야 합니다.
*   **Security Context 갱신 필요:** 다음 요청부터 우리 보안 시스템(`Security`)이 사용자의 상태를 인지하고 활용하려면, 단순히 외부 인증 정보만 전달받아서는 안 됩니다.
    *   로그인 성공 시점에 적절한 정보를 추출하여 `Authentication` 객체를 생성하고, 이 객체를 **`SecurityContextHolder`**에 넣어줘야 합니다.
*   **커스텀 핸들러 구현:** 이러한 전처리 과정은 시스템이 제공하는 특정 인터페이스를 구현하여 처리해야 합니다.
    *   `OAuth2LoginSuccessHandler`와 같은 `AuthenticationSuccessHandler`를 커스텀으로 구현합니다.
    *   이를 통해 인증 성공 시점(Success)에 실행될 로직을 직접 정의할 수 있습니다 (예: DB 사용자 정보 업데이트, 컨텍스트 설정).
*   **커스텀 UserDetails 매핑:** 외부 서비스의 유저 정보를 그대로 사용하기보다, 우리 서비스가 사용하는 `CustomUserDetails`와 같이 커스텀된 형태로 가공하여 인증 객체에 담아 `SecurityContextHolder`에 저장하는 것이 권장됩니다.

*   **유저 객체 조회:** `UserService`의 `findByProvider`, `socialId` 등의 메서드를 사용하여 사용자 정보를 조회할 수 있습니다.
*   **Authentication 객체 생성:** 찾아온 유저 정보와 서비스를 이용하여 Spring Security의 `Authentication` 객체를 구성해야 합니다. (주요 포함 요소: Principal(사용자 정보), Credentials(비밀번호 등), Authorities(권한/롤)).
*   **SecurityContext 저장:** 완성된 `Authentication` 객체를 `SecurityContextHolder`에 저장하여 현재 사용자의 인증 정보를 시스템 전반에서 이용할 수 있도록 설정합니다.

## 2. 최초 가입자(First-Time User) 온보딩 플로우 설계
*   **분기 처리의 필요성:** 로그인 시 사용자가 **기존 사용자일 경우**와 **최초 방문 사용자일 경우**에 따라 로직이 달라야 합니다.
    *   **기존 사용자:** 정상적으로 `SecurityContext`를 설정하고 로그인을 완료합니다. (추가 정보 수집 불필요)
    *   **최초 사용자:** 최소한의 필수 정보만 저장 처리한 후, **추가적인 개인 정보(프로필 등)**를 입력받을 수 있는 별도의 화면으로 이동시켜야 합니다.
*   **회원가입 페이지 이동 준비:** 최초 사용자의 추가 정보를 받는 '회원가입' 화면으로 이동하기 전, 관련 컨트롤러(`registrationSocialUser`)를 구성합니다.

## 3. 리디렉션 처리와 필수 데이터 인코딩 구현
*   **리디렉트 시 데이터 전달 방식 (필수 개념):** `redirect`는 요청 자체가 바뀌기 때문에(Request Change), 단순한 모델 속성으로는 데이터를 다음 페이지로 넘길 수 없습니다.
    *   따라서, 필요한 정보(예: 소셜 ID, 프로바이더)들은 **URL Query Parameter** 형태로 뒤에 붙여서 보내야 합니다. (매개변수 방식 활용)
*   **URL 인코딩의 중요성:** URL에 담는 데이터는 특수 문자(`&`, 공백 등)가 포함될 수 있으므로, 반드시 `UrlEncoder` 등을 이용해 데이터를 안전하게 인코딩해야 합니다. 그렇지 않으면 주소나 서버 처리에 오류가 발생할 수 있습니다.

## 4. 로그인 성공 핸들러 및 회원가입 로직 완성
*   **커스텀 SuccessHandler 등록:** Spring Security의 설정에 사용자 지정 `SuccessHandler`를 등록합니다.
    *   **동작 원리:** 인증(Authentication)이 성공적으로 완료되었을 때 이 커스텀 핸들러가 동작하여, 필요한 전처리(추가 정보 수집 여부 판단 및 Redirect 처리)를 담당하게 합니다.
*   **로그아웃 로직 구현 (SecurityConfig):** 로그아웃 시 다음 처리를 정의합니다.
    *   `SessionValidation`을 통해 기존 세션 삭제.
    *   클라이언트 측 쿠키(예: `JSESSIONID`)를 명시적으로 삭제하여 보안성을 높입니다.
*   **추가 정보 저장 컨트롤러 구현:** 별도의 컨트롤러(`saveSocialUser`)를 만들어 사용자로부터 입력받은 정보를 처리합니다.
*   **핵심 비즈니스 로직 및 유효성 검사:**

    2.  **권한 부여 및 초기화:** 신규 가입 시 기본 권한(Default Role)을 할당하며, 비밀번호가 없는 소셜 사용자에게는 암호화된 임시 비밀번호(UUID 기반의 랜덤 문자열 등)를 생성하여 저장하는 것이 관례입니다.
    3.  **시간 제한 검증 (Rate Limit):** 최초 가입 정보 입력 시 **최대 시간(예: 20분)**을 초과했는지 체크해야 합니다. 이를 위해 소셜 로그인 인포 객체의 `createdAt` 시간을 활용하고, 현재 시간과의 차이를 계산하여 유효성을 판단합니다.
    4.  **최종 처리:** 모든 검증과 저장 작업이 완료되면, 최종적으로 `SecurityContext`를 업데이트해주고 사용자를 서비스의 메인 화면으로 안내합니다.

## 1. 사용자 정보 저장 및 Security Context 설정

-   **권한(Authority) 부여:** 저장된 사용자 역할(`Role`)들을 추출하여 권한 리스트로 만들고, 이를 `SecurityContextHolder`에 담아 현재 시스템 세션에 주입합니다.
-   **예외 처리 구현:** 인증 과정이나 컨텍스트 갱신 중 오류가 발생할 수 있으므로, 전체 로직을 `try-catch` 블록으로 감싸 예외 발생 시 로그를 남기도록 합니다.

## 2. 프로젝트 초기 환경 문제 해결 및 의존성 관리
-   **애플리케이션 구동 오류 진단:** 처음 코드를 실행했을 때 애플리케이션이 정상적으로 동작하지 않는 주된 원인은 해당 패키지에 `@SpringBootApplication` 어노테이션이 누락되었기 때문입니다. (Spring Boot의 컴포넌트 스캔 영역 지정 필요).
-   **순환 참조(Circular Dependency) 문제:** 빈(Bean)을 등록하는 과정에서 여러 서비스(`SecurityConfig`, `UserService`, `PasswordEncoder`)가 서로를 의존적으로 호출하며 생겨나면서 순환 참조 오류가 발생합니다.
-   **해결 방안 제시:** 이러한 복잡한 의존성 문제를 해결하기 위해, 특정 빈들을 별도의 `@Configuration` 클래스에 분리하거나 `@Order` 등을 사용하여 초기화 순서를 명시함으로써 시스템을 안정적으로 구동할 수 있습니다.

## 3. 핵심 기능 테스트 및 데이터 무결성 확보
-   **인증 흐름 검증:** GitHub와 같은 소셜 로그인을 통해 로그인하는 과정과, 로그인 되어 있는 상태/로그아웃 된 상태에서 재요청했을 때의 화면 차이를 확인하며 인증 플로우를 검증합니다.
-   **회원가입(Registration) 테스트 및 오류 수정:** 새로운 아이디로 가입을 시도할 때 에러 페이지로 이동하는 문제를 발견했습니다. 이는 필수 필드 값(예: 등록일자, `registrationDate`)이 데이터베이스에 저장되는 과정에서 `null` 값이 전송되어 발생한 문제입니다.
-   **데이터 무결성 확보:** 이러한 DB 저장을 방지하고 값을 채워 넣기 위해, JPA의 생명 주기 관련 어노테이션인 `@PrePersist`를 활용하여 엔티티가 영속화(persist) 되기 직전에 누락된 기본값을 자동적으로 설정하도록 로직을 추가했습니다.

## 4. 개발 마무리 및 테스트 시 고려 사항
-   **DB 테이블 초기화의 중요성:** 소셜 로그인이나 회원가입 기능을 반복적으로 테스트할 경우, 기존에 저장된 데이터 때문에 동일한 프로바이더 ID 또는 소셜 ID로 인해 오류(중복 키 제약 조건 위반)가 발생할 수 있습니다. 따라서 테스트를 시작하기 전에는 관련 DB 테이블(`soci_user`, `user` 등)의 데이터를 반드시 초기화하는 것이 중요합니다.
-   **서비스 구조 이해:** 복잡한 기능이 많은 만큼, 당장 모든 것을 완벽하게 구현하려고 하기보다는 핵심 로직 위주로 개발을 진행하며 전체적인 흐름을 파악하는 데 집중할 필요가 있습니다. (지나치게 기술적 내용에 압도되지 않도록 유의).
