---

## 1. 웹 애플리케이션의 진화와 React가 필요한 이유 (배경 지식)
*   **초기 웹 페이지 구조:** HTML/CSS를 이용한 정적 웹페이지는 응답을 받은 후 내용이 고정되어 값이 변하기 어려웠다.
*   **JavaScript의 등장:** JavaScript는 클라이언트(사용자 브라우저)에서 HTML 요소를 찾아 조작하고 이벤트를 처리할 수 있게 하여 상호작용성을 부여했다.
*   **SPA (Single Page Application) 개념:** 초기 웹 앱은 서버로부터 페이지 전체를 받는 방식이 아닌, 하나의 페이지 내에서 JavaScript를 이용해 동적으로 내용을 계속 변경하는 방식으로 동작하기 시작했다.
*   **React가 필요한 이유:** SPA 환경이 복잡해지고 자바스크립트의 역할이 커지면서, 브라우저의 성능과 효율적인 관리가 필요해졌고, 이 필요성 때문에 React와 같은 기술이 등장하게 되었다.

## 2. React의 핵심 원리: 가상 DOM (Virtual DOM) 이해
*   **문제 인식:** JavaScript가 브라우저 메모리에만 동작하기 때문에, 화면에 변화를 줄 때마다 실제 DOM(문서 객체 모델)을 직접 조작하는 것은 비효율적이고 성능 부하를 일으킬 수 있었다.
*   **해결책: 가상 DOM (Virtual DOM):** React는 실제 브라우저의 DOM과 똑같은 구조를 메모리 상에 가진 **가상 DOM**이라는 개념을 이용한다.
    *   데이터가 변경될 때마다 직접 화면을 바꾸는 것이 아니라, 가상 DOM 상태만 먼저 업데이트하고(추가/삭제), **이전 가상 DOM과 새 가상 DOM을 비교**한다.
    *   변화된 부분(차이점)만을 빠르고 효율적으로 찾아내어 실제 브라우저의 DOM에 반영(재그리기)함으로써 성능 저하를 최소화한다.

## 3. 컴포넌트 기반 구조 및 데이터 흐름 관리
*   **컴포넌트 단위:** 웹 애플리케이션을 작은 기능 단위의 독립된 모듈인 '컴포넌트'들로 분해하여 조립하는 방식으로 개발된다. (예: `Parent` 컴포넌트 안에 여러 개의 `Child` 컴포넌트를 포함시키는 방식)
*   **Hooks (훅):** React에서 기능을 사용할 때 필요한 함수들입니다. 핵심적으로 다음 3가지 훅을 알고 있어야 한다.
    *   `useState`: 컴포넌트가 가진 '상태(State)'를 관리합니다. 상태 값이 변경되면 해당 컴포넌트를 재렌더링하여 화면에 반영할 수 있습니다. (React가 상태 변화 관리를 담당)
    *   `useEffect`, `useLayoutEffect`: (자세한 설명 생략되었으나, 기능 구현 시 사용됨)
*   **Props (속성):** 부모 컴포넌트가 자식 컴포넌트로 데이터를 전달하는 방식입니다.
    *   데이터는 **단방향(One-way)**으로 흐릅니다. (부모 $\rightarrow$ 자식)
    *   자식이 부모의 값을 직접 변경할 수 없습니다.
*   **Key:** 리스트를 렌더링(반복하여 목록을 표시) 할 때, React가 각 항목들을 식별하고 관리하기 위해 반드시 **고유한 `key` 값**을 부여해야 합니다. (삭제나 수정 시 정확한 관리를 위함)
*   **Children:** 컴포넌트 자체를 감싸는 형태로, 부모와 자식의 관계에 관계없이 내부의 콘텐츠(여러 컴포넌트 조각들)를 전달받아 렌더링할 때 사용됩니다.

## 4. 실습 환경 구성 및 JSX 문법 정리
*   **React 개발 환경 구축:** 프로젝트 생성 시, Vite 또는 Create React App 같은 도구를 이용하는 것이 효율적입니다. (수동 설정보다 훨씬 간편함)
*   **개발 과정 요약:** 프로젝트 생성 $\rightarrow$ 필요한 의존성(`npm install`) 설치 $\rightarrow$ 서버 실행(`npm run dev`)을 통해 개발이 가능합니다.
    *   React 코드를 수정하면 브라우저 새로고침 없이 자동으로 변경 사항이 반영됩니다.
*   **JSX 문법:** HTML처럼 생겼지만, 실제로는 자바스크립트 코드와 같이 동작하여 **정적인 HTML 조각(Snippet)**으로 변환되는 확장된 문법입니다.
    *   HTML 태그가 아닌 JavaScript 코드(변수나 함수 등)도 `{ }` 중괄호를 사용하여 삽입할 수 있습니다.
    *   **필수 규칙:** JSX는 반드시 시작 태그와 끝 태그를 쌍으로 갖춰야 합니다. (예: `<Component>...</Component>`)
    *   **Fragment 사용:** 하나의 컴포넌트가 여러 개의 HTML 요소를 묶어야 할 때, 불필요한 `<div>` 태그 추가 없이 구조적으로 묶어주기 위해 `<></>`와 같은 프래그먼트를 사용할 수 있습니다.

***

### ✨ 핵심 정리
React는 **컴포넌트**를 기반으로 하며, **가상 DOM(Virtual DOM)**을 통해 성능 최적화를 달성합니다. 데이터 흐름은 **단방향 (Props)**이며, 개발의 효율성을 극대화하기 위해 JSX와 Hooks 같은 기능을 사용합니다.

# 강의 요약: React 고급 기능 및 컴포넌트 설계 원칙

## 목차
1. 조건부 렌더링과 상태 기반 로직 구현
2. JavaScript 이벤트 핸들러 처리의 핵심 이해 (함수 참조 vs. 실행)
3. 리스트 렌더링 심화와 키(Key) 사용 규칙
4. 대규모 컴포넌트 구조 설계: To-Do 리스트 모델링

---

## 1. 조건부 렌더링과 상태 기반 로직 구현
*   **조건부 렌더링 이해:** 컴포넌트는 특정 **상태(State)**의 참/거짓 여부(`true`/`false`)에 따라 다르게 렌더링되어야 한다. (예: 로그인 여부에 따라 '환영합니다' 또는 '로그인이 필요합니다' 출력)
*   **조건문 활용:** JSX 내에서 조건에 따른 분기를 처리하는 방법은 다음과 같다.
    *   **삼항 연산자 (Ternary Operator):** `condition ? true일 때 값 : false일 때 값` 형태로 사용한다.
    *   **논리 AND 연산자 (`&&`):** 특정 값이 `true`일 때만 해당 요소를 출력(렌더링)하고, `false` 또는 `null`일 때는 아무것도 렌더링하지 않게 하는 데 효과적으로 사용된다. (단축 연산자 활용)
*   **데이터 구조 활용:** 컴포넌트가 부모로부터 전달받는 데이터(Props)에 기반하여 출력할 콘텐츠를 다변화할 수 있다. 예를 들어, 서버 응답 메시지 목록을 받아와 '메시지가 있습니다', '메시지 카운트 N개' 등으로 세분화하여 출력을 구성할 수 있다.
*   **상태 변화의 반영:** 상태가 변경되면 컴포넌트는 자동으로 다시 렌더링되어(Re-render), 새로운 조건에 맞는 UI를 보여주게 된다. (예: 증가/감소 버튼 클릭 시 카운터 값의 변화)

## 2. JavaScript 이벤트 핸들러 처리의 핵심 이해
*   **함수 참조 전달과 즉시 실행의 차이:** React에서 이벤트를 처리하는 함수는 **함수의 이름(참조)**을 넘겨주어야 하며, 코드를 작성할 때 해당 함수를 바로 호출하여 값을 넣으면 안 된다.
    *   ✅ **정확한 방식 (함수 참조):** `onClick={myFunction}` 형태로 등록한다. 이벤트가 발생했을 때 React가 이 함수를 호출한다.
    *   ❌ **잘못된 방식 (즉시 실행):** `onClick={myFunction()}` 형태로 작성하면, 컴포넌트가 처음 렌더링될 때 해당 코드가 즉시 실행되고 그 결과 값만 등록된다. 따라서 이벤트 발생 시점에 원하는 로직이 작동하지 않는다.
*   **핵심 원리:** 이벤트 핸들러는 '무언가를 할 수 있는 함수' 자체를 등록하는 것이지, '즉시 계산된 값'을 등록하는 것이 아님을 이해해야 한다.

## 3. 리스트 렌더링 심화와 키(Key) 사용 규칙
*   **리스트 렌더링 개요:** 배열 형태의 데이터를 받아 각 항목별로 동일한 컴포넌트를 반복하여 출력하는 방법이다. (예: 투두 목록, 상품 목록)
*   **`key` 속성의 중요성:** 리스트를 렌더링할 때 반드시 고유하고 안정적인 `key` Prop을 사용해야 한다.
    *   **키가 필요한 이유:** React는 `key`를 사용하여 각 리스트 항목의 식별자 역할을 수행하며, 데이터의 추가/삭제 시 어떤 항목이 변경되었는지 효율적으로 추적하여 성능 최적화를 돕는다.
    *   **권장 방식:** 데이터베이스에서 조회한 데이터에는 보통 **Primary Key (PK)**와 같이 고유성을 보장하는 값이 있으므로, 이 값을 `key`로 사용하는 것이 가장 좋다.
    *   **주의 사항:** 단순히 배열의 인덱스(`index`)를 `key`로 사용하는 것은 항목이 추가되거나 삭제될 때 순서가 바뀌면서 오류를 유발할 가능성이 크므로 가급적 피하는 것이 권장된다.

## 4. 대규모 컴포넌트 구조 설계: To-Do 리스트 모델링
*   **컴포넌트 분리 원칙:** 애플리케이션의 규모가 커질수록, 역할을 분담하여 여러 개의 작은 컴포넌트로 나누는(Componentization) 것이 필수적이다. (예: 전체 컨테이너 $\rightarrow$ 입력 영역 컴포넌트 + 리스트 출력 컴포넌트 $\rightarrow$ 개별 아이템 컴포넌트)
*   **상태 관리의 흐름 (State Lifting):** 데이터(State)는 가장 상위 레벨에서 관리하는 것이 바람직하며, 이 상태를 필요로 하는 하위 컴포넌트로 Props 형태로 전달한다.
    *   **최적화된 구조:** To-Do 리스트의 전체 데이터 배열(`toDos`)과 이를 수정/추가하는 핵심 로직(함수)은 **전체를 감싸는 상위 컨테이너 컴포넌트 (Container Component)** 가 보유하고 관리해야 한다.
    *   **데이터 흐름:** 데이터와 로직을 가진 최상위 컴포넌트 $\rightarrow$ Prop으로 데이터를 하위 리스트 컴포넌트에 전달 $\rightarrow$ 필요할 때 함수를 Props으로 내려주어 상태 업데이트 요청.

## 1. 리스트 렌더링 및 데이터 출력 기본 원리 (List Rendering)
- **데이터 배열 활용:** JavaScript의 `map()` 메서드를 사용하여 배열(리스트) 내의 데이터를 순회하며 JSX 요소로 반복 출력할 수 있습니다.
- **반복 출력의 이해:** 리스트를 표시할 때는 반드시 반복문(`map`)을 사용해야 하며, 데이터가 많아질 경우 성능이나 React 규칙상 각 요소를 고유한 `key` prop으로 지정하는 것이 필수적입니다.
- **활용 예시 (Props 전달):** 부모 컴포넌트에서 받은 데이터를 자식 컴포넌트에 속성(props) 형태로 내려보내서 재사용할 수 있습니다.

## 2. 컴포넌트 분리 원칙과 구현 방법 (Component Decomposition)
- **분리의 목적:** 하나의 거대한 컴포넌트를 여러 개의 작고 독립적인 기능 단위로 나누어 코드의 가독성과 관리 용이성을 높입니다. (재사용성 증대).
- **단계적 분리 과정:**
    1. 전체 구조를 가진 최상위 컴포넌트 (`Todo`)가 존재합니다.
    2. 이 컴포넌트 내부에서 리스트만 담당하는 별도의 컴포넌트 (`TodoList`)로 분리할 수 있습니다.
    3. 다시 `TodoList` 내에서 개별 항목 하나하나(`TodoItem`)를 독립된 컴포넌트로 분리하여 재사용합니다.
- **Props 전달 메커니즘:** 상위 컴포넌트는 하위 컴포넌트가 필요로 하는 데이터나 기능을 Props를 통해 명시적으로 전달해야 합니다. (데이터의 일방향 흐름).
- **분리의 적정성:** 모든 부분을 작게 쪼개기보다는, 기능적인 단위(예: 항목별 상태 관리, 삭제 버튼 등)가 생길 때 나누는 것이 효율적입니다.

## 3. 상태 관리와 이벤트 처리: CRUD 기능 구현하기 (State Management & Interactions)
- **상태의 소유권 확보:** 컴포넌트가 상호작용을 통해 데이터를 변경하려면, 해당 데이터(`todos` 배열)를 누가 '진정한 주인(Source of Truth)'으로 가지고 있는지 명확해야 합니다. 이 주인은 **가장 상위 부모 컴포넌트**여야 합니다.
- **삭제 기능 (Delete):**
    - 삭제 로직(메서드) 자체는 데이터를 소유한 가장 상위 컴포넌트에서 정의되어야 합니다.
    - 이 로직을 하위 컴포넌트까지 Props를 통해 내려보내고, 아이템 클릭 시 해당 함수가 실행되도록 등록합니다.

## 1. 리액트 상태 관리 Hook 비교 (`useState` vs `useRef`)
리액트의 핵심 상태 관리 방법인 세 가지 Hooks의 차이점(일반 변수, `useState`, `useRef`)을 심층적으로 학습합니다.

*   **`useState` (상태):**
    *   컴포넌트가 **새로 렌더링될 때마다 값이 초기화되지 않고** 상태를 유지하며 관리합니다.
    *   상태(State)가 변경되면 리액트는 해당 컴포넌트를 **자동으로 재렌더링**시킵니다. (값이 화면에 표시됨)
    *   값의 변화는 UI 업데이트와 직결됩니다.
*   **`useRef` (참조):**
    *   클래스 컴포넌트의 인스턴스 속성처럼 사용되어, **값을 저장하고 유지**할 수 있지만, 값이 변경되더라도 리액트는 해당 컴포넌트를 재렌더링하지 않습니다.
    *   주로 DOM 요소에 직접 접근하거나(Refs), 렌더링과 관계없이 값을 보존해야 할 때 사용합니다. (예: 타이머 ID, 이전 값 저장 등)
    *   일반 JavaScript 변수처럼 동작하여 컴포넌트가 새로 시작되어도 값이 초기화되지 않고 유지됩니다.

## 2. 컴포넌트 렌더링과 데이터 흐름 이해
*   **컴포넌트 라이프사이클:** 앱이 처음 구동될 때는 최상위 `App`부터 모든 하위 컴포넌트가 순차적으로 렌더링을 거칩니다. 이후에는 수정되거나 의존성이 바뀐 컴포넌트만 필요한 경우에 한정하여 재렌더링됩니다.
*   **Hook별 리렌더링 동작:**
    *   `useState` 값을 업데이트하면: 상태 변화로 인해 **컴포넌트 전체가 재렌더링**되며, 화면의 값이 변경된 것을 확인할 수 있습니다.
    *   `useRef` 값을 업데이트하면: 값은 유지되지만, **재렌더링이 발생하지 않기 때문에** 화면에 변화가 나타나지 않습니다.

    *   이 배열에 명시된 값이 변경될 때만 이펙트 내부의 로직이 다시 실행됩니다.

## 1. `useEffect`와 의존성 배열 활용
*   **`useEffect`의 역할:** 컴포넌트가 마운트되거나, 특정 상태(State)가 변경될 때 "부수 효과(Side Effect)"를 처리하는 데 사용됩니다. (예: 데이터 가져오기, 타이머 설정 등)
*   **첫 번째 인자 (Effect 함수):** 실제 부수 효과가 실행되는 코드를 작성합니다.
*   **두 번째 인자 (의존성 배열, Dependency Array):** `useEffect`가 재실행될 조건을 지정하는 핵심 부분입니다.

### 📌 의존성 배열 활용 규칙
| 설정 | 역할 및 실행 시점 | 사용 예시 | 주의 사항 |
| :--- | :--- | :--- | :--- |
| **배열 생략 (의존성 없음)** | 컴포넌트가 렌더링될 때마다 매번 실행됩니다. (대부분 비효율적) | - | 모든 상태 변화에 민감하게 반응합니다. |
| **특정 값 지정 (`[count]`)** | 해당 값이 변경될 때만 Effect 함수가 재실행됩니다. | `[count]` | 특정 의존성(state, prop 등)을 목록으로 나열해야 합니다. |
| **빈 배열 (`[]`)** | 컴포넌트가 최초로 화면에 표시될 때 (마운팅 시) *단 한 번만* 실행되며, 의존성 값이 변경될 일이 없어 안정적입니다. | `[]` | 데이터 페칭 등 초기화 작업에 주로 사용됩니다. |

## 2. 컴포넌트 라이프사이클과 정리 작업 (Cleanup)
*   **언마운팅(Unmounting) 개념:** 컴포넌트가 화면에서 사라질 때를 의미합니다. 이 과정에서 실행해야 하는 정리가 필요한 경우가 있습니다.
*   **클린업 함수 (Cleanup Function):** `useEffect`의 **반환 값**을 이용해 구현하며, 컴포넌트가 언마운트되거나 Effect가 재실행되기 직전에 정리 작업을 수행합니다.
*   **필요한 상황:** 인터벌 타이머(`setInterval`) 설정, 외부 이벤트 리스너 등록 등 시스템 자원을 차지하는 설정을 해제할 때 필수적입니다.
*   **구현 방법:** `useEffect` 내부에서 정리 코드를 가진 함수를 반환합니다 (`return () => { /* cleanup code */ }`).

## 3. 값이 바뀌어도 리렌더링되지 않게 값 유지하기 (`useRef`)
*   **문제 제기:** `useState`는 값이 바뀔 때마다 컴포넌트가 **재실행(Re-render)** 되며, 이를 원하지 않을 수 있습니다 (예: ID 값, 로직 계산 중간 변수).
*   **`useRef`의 역할:** 값은 저장하지만, 그 값을 변경한다고 해서 *컴포넌트를 리렌더링시키지 않습니다*. 즉, 값이 유지되지만 상태 변화를 일으키지 않는 "읽기 전용(Read-only) 컨테이너"처럼 작동합니다.
*   **활용 목적:** 화면에 표시할 필요는 없지만 컴포넌트 수명 주기 동안 계속 값으로 보존하고 싶은 데이터를 저장하는 데 사용됩니다.

## 4. 실제 DOM 요소에 접근하기 (`useRef`)
*   **접근 문제:** 일반적인 JavaScript 방식(예: `document.getElementById()`)으로 HTML 요소에 접근할 경우, 개발 과정에서 코드가 지저분해지거나 실수가 발생하기 쉽습니다.
*   **`useRef`의 확장된 용도:** 특정 DOM 요소에 `<input ref={myRef} />`와 같이 `ref` 속성을 직접 부여하면, React가 이 요소를 내부적으로 관리하고 접근할 수 있게 해줍니다.
*   **접근 방법:** `ref` 변수(예: `myRef`)를 사용하여 `.current` 속성으로 해당 DOM 요소에 쉽게 접근할 수 있으며, 이를 통해 값(`myRef.current.value`)이나 속성(`myRef.current.type`, `myRef.current.placeholder`)을 읽어올 수 있습니다.
*   **요약:** `useRef`는 **① 리렌더링 없이 값을 유지**하거나, **② DOM 요소에 쉽고 깔끔하게 접근**하는 두 가지 목적으로 사용됩니다.
