3. 스프링 시큐리티를 활용한 로그인 플로우 분석

---

## 1. 인증 및 권한 관리의 필요성 이해
- **인증(Authentication)과 인가(Authorization)의 중요성:** 개발하는 모든 서비스는 '사용자가 누구인지'를 확인하고, 이 사용자가 어떤 행동을 할 수 있는지(권한) 검사하는 과정이 필수적입니다.
- **HTTP 프로토콜의 한계:** HTTP 자체는 상태(State)를 유지하지 않는 Stateless 프로토콜이기 때문에, 지속적으로 클라이언트가 '나 자신'임을 증명하고 정보를 유지하기 위한 별도의 메커니즘 (예: 세션 관리)이 필요합니다.

## 2. 표준화된 인증 시스템 (OAuth/SSO) 개요
- **소셜 로그인의 등장 배경:** 초창기에는 사용자에게 아이디와 비밀번호 같은 민감한 정보(주민등록번호 등)를 직접 요구했으나, 앱의 증가와 보안 및 개인정보 보호에 대한 중요성 증대로 인해 사용자 경험과 데이터 보호 측면에서 어려움이 발생했습니다.
- **SSO(Single Sign-On)의 목적:** 사용자가 여러 애플리케이션마다 각기 다른 아이디/비밀번호를 기억하고 관리하는 불편함을 해소하기 위해, 이미 신뢰성이 검증된 외부 플랫폼(카카오, 네이버 등)을 통해 한 번 인증받고 이를 공유하는 표준화가 필요해졌습니다.
- **OAuth의 역할과 표준:** 이러한 복잡한 문제를 해결하고 공통의 기준을 만들기 위해 OAuth와 같은 표준 프로토콜이 등장했습니다. 개발자들은 이 표준에 맞춰 구현함으로써 시스템의 안정성과 확장성을 확보합니다.
- **주요 용어 정의 및 이해 (Architecture):**
    *   **리소스를 소유한 사용자(Resource Owner):** 실제 정보의 주체인 최종 사용자를 의미합니다.
    *   **클라이언트(Client):** 우리가 개발하는, 서비스를 이용하려는 애플리케이션입니다.
    *   **제공자 (Provider/Identity Provider):** 인증 정보를 보유하고 표준에 맞춰 인증을 수행해주는 외부 서비스(예: 구글, 네이버 등)를 의미합니다.

## 3. 스프링 시큐리티를 활용한 로그인 플로우 분석
- **보안 프레임워크의 필요성:** 보안은 매우 복잡한 분야로, 수동으로 모든 것을 구현할 경우 놓치기 쉬운 '구멍'이 생길 위험이 높습니다. 따라서 Spring Security와 같은 검증된 프레임워크를 사용해야 안정적으로 개발할 수 있습니다.
- **Security Context와 ThreadLocal의 활용:**
    *   요청이 들어올 때마다 독립적인 스레드(Thread)가 할당되며, 이 요청과 관련된 정보는 `ThreadLocal`이라는 메모리 영역에 보관됩니다.
    *   Spring Security는 인증 과정에서 사용자의 신원 정보를 가져와 이를 `SecurityContext`라는 객체에 담아 해당 스레드에 저장합니다.
    *   **Security Context Holder:** 개발자가 이처럼 중요한 사용자 정보(`Authentication` 객체)를 요청 처리의 여러 단계(필터, 컨트롤러, 뷰 등) 어디서든 일관성 있게 접근할 수 있도록 도와주는 핵심 메커니즘입니다.

## 4. 고급 보안 처리: 사용자 흐름 제어 및 세션 관리
- **인증 성공 후 커스텀 로직 처리 (Success Handler):**
    *   로그인이 성공적으로 완료된 직후에 추가적인 비즈니스 로직(예: 환영 메시지 표시, 초기 정보 요청 등)을 실행하고 싶다면 `AuthenticationSuccessHandler`를 구현해야 합니다.
    *   이 핸들러는 개발자가 직접 '추가적으로 할 일'을 정의하는 지점입니다.
- **신규/기존 사용자 분리 처리:**
    *   로그인 성공 후, 시스템은 사용자의 인증 정보(Provider와 Social ID)를 기반으로 데이터베이스에서 이 사용자가 **기존에 가입했던 사용자인지** 확인합니다.
    *   **재가입 방지 및 유저 관리:** 기존 사용자인 경우 해당 사용자에게 로그인 정보를 연결하고 세션을 유지하며, 처음 방문한 신규 사용자일 경우 새로운 계정 생성을 진행합니다.
- **보안 최적화 (세션 및 시간 체크):**
    *   사용자의 보안을 위해 특정 페이지에 진입했을 때 유효 기간(Time Limit)을 설정하여 비활동 시간을 감지하고, 일정 시간이 지나면 세션을 만료시키거나 재인증 절차를 요구하는 것이 필요합니다. 이는 시스템의 보안성을 높이는 핵심 요소입니다.

4. 소셜 로그인 인증 과정 분석 (OAuth/AS 2)
5. 인증 성공 후 추가 로직 구현 및 사용자 경험 개선

## 1. 디버깅을 통한 코드 실행 흐름 이해하기 (Debugging)
- **브레이크 포인트 사용:** 코드가 언제 특정 위치를 실행하는지 확인하고 싶을 때 브레이크 포인트를 설정하여 디버그 모드로 애플리케이션을 구동한다.
- **실행 과정 추적:** 브레이크 포인트를 통해 멈춘 후 '다음' 버튼 등으로 코드를 단계적으로 실행시키면서, 해당 시점에 변수 값들이 어떻게 변화하고 어떤 로직으로 이동하는지 자세히 확인한다.
- **목표:** 단순히 코드를 읽는 것 이상으로, 실제로 프로그램이 메모리상에서 데이터를 가지고 어떻게 흐르는지 눈으로 확인하며 이해도를 높일 수 있다.

## 2. 빈(Bean) 관리 및 의존성 문제 처리 방안
- **의존성 사이클 위험:** 여러 객체가 서로를 필요로 하면서 순환 참조(Circular Dependency)가 발생할 경우, 애플리케이션 구동 시 예외(`BeanDefinitionStoreException` 등)가 발생할 수 있다. (예: A는 B를 필요로 하고, B는 다시 A를 필요로 하는 상황).
- **해결 방안:** 특정 빈을 모듈의 핵심 로직에서 잠시 분리하거나 설정 파일(e.g., `AppConfig`)에 별도로 빼둠으로써, 초기화 단계에서의 순환 참조 문제를 예방할 수 있다.

## 3. 보안 설정(Security Config)의 핵심 요소
- **PermitAll 지정:** 일부 특정 링크(예: OAuth 관련 URL)는 권한이 없더라도 외부 연동이나 시스템 호출을 통해 접속이 필요하므로, 해당 경로들을 `permitAll()`로 명시적으로 허용해야 한다.
- **CSRF (Cross Site Request Forgery):** 사용자가 의도하지 않은 다른 페이지의 폼으로 위조 요청(데이터 전송)을 보내는 것을 방지한다. 이를 위해 타임리프(Thymeleaf) 등의 템플릿에서 CSRF 토큰을 `hidden` 필드로 포함시켜, 서버가 이 코드를 확인하고 유효성을 검증해야 한다.
- **CORS (Cross Origin Resource Sharing):** 서로 다른 서버나 도메리노티에서 API 요청이 들어올 때 발생할 수 있는 보안 문제를 막기 위해 모든 요청에 대해 허가(Relaxed 설정)하도록 설정을 추가한다.
- **HTTP Basic:** 인증 과정에서는 HTTP Basic Authentication을 비활성화(`disable()`)하는 것이 권장된다.

## 4. 소셜 로그인 인증 과정 분석 (OAuth/AS 2)
- **인증 플로우의 핵심:** OAuth나 AS 2와 같은 외부 시스템 연동 방식은 인증(Authentication) 과정을 거쳐 사용자의 정보를 받아오고, 이 정보를 내부 사용자 객체로 변환하는 단계를 포함한다.
- **커스터마이징 및 확장성:** 로그인 로직을 `WebFilter` 내에서 구현함으로써, 기본적인 인증 흐름 외에 필요한 커스텀 비즈니스 로직(예: 회원 여부 체크, 추가 정보 수집)을 쉽게 추가할 수 있다.
- **사용자 정보 매핑:** 소셜 로그인 과정에서는 외부 공급자가 제공하는 사용자 객체(User Object)를 받게 되는데, 이 정보를 서비스 계층에서 이용 가능한 자체 User Details Service (혹은 `OAuth2UserService`)를 통해 시스템의 사용자 객체로 변환하여 사용한다.

## 5. 인증 성공 후 추가 로직 구현 및 사용자 경험 개선
- **로그인 후 처리 필수:** 로그인이 성공적으로 완료되었을 때, 단순히 세션을 만드는 것 외에 필요한 비즈니스 로직이 있다.
    *   **신규 사용자 체크:** 해당 소셜 계정으로 처음 가입한 사용자(Initial Login)인지 확인하는 과정이 필요하다.
    *   **데이터 동기화/저장:** 신규 사용자로 판명되면, 추가 정보를 가져와서 시스템 데이터베이스에 저장하거나 업데이트한다.
- **보안 컨텍스트 유지 (Security Context Holder):** 로그인 프로세스에서 사용자 인증 정보(Authentication 객체)를 `SecurityContextHolder`에 넣어두는 작업은 매우 중요하다. 이 과정을 통해 다른 필터나 서비스 레이어에서도 현재 사용자가 누구인지 지속적으로 알 수 있게 되어 시스템의 보안 상태가 유지된다.

## 6. 비즈니스 로직 테스트 시 고려사항
- **오류 기반 학습:** 개발 과정에서 오류(Error)를 발생하는 경험을 하는 것이 이해도를 높이는 데 매우 효과적이다. 특정 기능이 왜 예상과 다르게 작동하는지 원인을 분석하면서 학습한다.
- **테스트 환경 관리:** 여러 사용자로 시스템을 테스트할 경우, 각 테스트 케이스 간의 영향을 방지하기 위해 사용자 데이터를 적절히 삭제하거나 초기화하여 테스트를 진행해야 한다.

## 7. 개발 모범 사례: 환경 변수 관리의 중요성 (Best Practices)
- **민감 정보 보호 원칙:** 비밀번호 키(Secret Key), 클라이언트 ID, 시크릿 값과 같은 민감하고 중요한 설정 값들은 Git에 코드 형태로 하드코딩해서는 안 된다.
- **환경 변수 사용 권장:** 이러한 값들은 운영 환경이나 로컬 개발 환경의 **운영체제 환경 변수(Environment Variables)** 또는 별도의 Secret Manager를 통해 주입받아 사용하는 것이 가장 안전하고 좋은 방법이다. (예: 시스템 변수 설정)

---

### 💡 기타 참고 사항
*   **인텔리J IDE 설정:** 실제 애플리케이션이 환경 변수를 읽지 못하는 문제가 발생할 경우, 프로그램 실행을 담당하는 IDE(IntelliJ 등)의 **런 구성(Run Configuration)**에 들어가서 해당 환경 변수들을 수동으로 추가해 주어야 할 때가 있다.
*   **프로바이더별 API 확인:** 소셜 로그인이나 서비스 연동 시 사용되는 프로바이더마다 아바타 URL이나 사용자 정보를 가져오는 방식이 다를 수 있으므로, 반드시 각 제공사의 문서를 참고하여 설정을 확인해야 한다.

## 1. 환경 변수 설정 및 관리의 중요성 (ENV Variable Configuration)
- **문제 인식:** 개발 환경(IntelliJ 등 IDE)에서 애플리케이션을 실행할 때, 운영체제에 정의된 환경 변수가 제대로 인식되지 않는 경우가 발생한다.
- **해결 방안:**
    *   `module-info` 설정이나 `modify options` 내의 'Environment Variables' 메뉴를 통해 필요한 환경 변수를 명시적으로 추가해야 한다.
    *   애플리케이션을 IDE 외부(예: 배포 서버)에서 실행할 때는, 필요한 환경 변수들만 제대로 설정되어 있는지 확인하는 것이 핵심이다.
- **핵심:** 코드가 의존하는 모든 민감 정보나 설정을 하드코딩하지 않고, 외부의 환경 변수를 통해 주입받아 운영하는 습관을 들여야 한다.

## 2. 보안 원칙과 아키텍처 디자인 고려 사항 (Security & Best Practices)
- **보안 위험 경고:** 데이터베이스 접속 정보(ID, 비밀번호 등)나 중요한 API 키와 같은 민감한 정보들을 코드에 하드코딩하여 소스코드 저장소(예: GitHub)에 올려두는 것은 매우 큰 보안 위험을 초래한다.
- **운영 환경에서의 관리:** 실제 서비스 운영 시에는 이들 중요한 정보를 네트워크에 연결된 전용 관리 시스템이나 서비스(예: AWS Secrets Manager 같은 중앙 집중식 비밀 값 저장 공간)를 이용하여 보관하고, 애플리케이션이 필요할 때만 값을 불러와 사용하도록 설계해야 한다.
- **적용 범위:** 개인 프로젝트에서도 나중에 실제 상업용 서비스를 구축하는 흐름을 염두에 두고 '보안' 관점에서 코드를 설계하는 것이 중요하다.

## 3. 전체 시스템 흐름 이해와 확장성을 위한 테스트 방법 (System Flow & Extensibility)
- **단순 실행 이상의 목표:** 단순히 기능이 돌아가게 만드는 것을 넘어, 전체적인 서비스의 동작 원리와 각 컴포넌트 간의 상호 작용(Flow)을 깊이 있게 이해하는 것이 중요하다.
- **종합적 테스트 필요:** 구현된 코드를 한 가지 경로(예: GitHub 로그인)로만 테스트하지 말고, 다양한 상황과 방법을 통해 실행해 봐야 한다 (예: 소셜 로그인을 사용했을 때의 처리 과정, 비로그인 상태에서 요청을 보냈을 때의 동작 등).
- **모듈화 설계 습관:** "이 기능을 추가하려면 어디에 어떤 코드를 삽입해야 할까?"를 미리 고민하며 바라보는 능력이 중요하다. 서비스 요구 사항이 변경되더라도 어느 부분을 수정하고 확장할지 시나리오를 구상해 보는 연습이 필요하다.

## 4. 향후 학습 방향: 문서화와 자기 주도 학습 능력 배양
- **다음 단계 (문서화):** 백엔드 코드를 구현하는 것만큼 중요한 과정은 해당 API를 외부에 명확하게 설명하고 문서화하는 것이다. 다음 시간에는 **Swagger**와 같은 도구를 이용한 API 문서화 방법을 학습한다.
- **학습의 핵심 목표:** 궁극적으로 지식을 수동적으로 받아들이는 것을 넘어, 새로운 기술이나 개념을 접했을 때 그것이 어떤 원리로 동작하는지 스스로 학습하고 문제를 해결하여 적용할 수 있는 '자기 주도 학습 능력'을 키우는 것이 가장 중요함을 강조한다.

## 목차

2. OpenAPI 표준과 Swagger 활용 방안
3. 백엔드 API 기능 개발 단계 (Repository, Service, Controller)
4. Swagger를 이용한 자동 문서 생성 설정

---

## 1. API의 개념과 문서화의 중요성
- **API 정의**: API(Application Programming Interface)는 소프트웨어 간에 원활하게 상호작용할 수 있도록 하는 필수적인 통신 규약입니다.
    - 웹/모바일 애플리케이션 환경에서는 백엔드 시스템과 프론트엔드 또는 서로 다른 웹 서비스 간의 데이터 통신을 위해 API가 광범위하게 사용됩니다.
- **API 문서화의 중요성**:
    - API를 효과적으로 사용하기 위해서는 구조, 요청 방식(어떤 데이터를 어떻게 보내야 하는지), 응답 형식, 인증 방법, 오류 코드 등을 명확히 설명하는 문서화가 필수적입니다.
    - 문서화가 부족하거나 불완전할 경우 개발자들이 코드를 분석하거나 담당자에게 문의해야 하는 비효율적인 상황이 발생합니다.
    - 따라서 API 문서화는 개발자의 경험(DX)을 개선하고 시스템 유지보수 효율성을 높이는 핵심 요소입니다.

## 2. OpenAPI 표준과 Swagger 활용 방안
- **API 명세의 역할**: 데이터 통신 시 URI를 통해 어떤 정보가 들어와야 하는지, 그리고 그에 대한 상세한 명세를 정의하는 것이 중요합니다.
    - 과거에는 이러한 명세가 문서 파일(Excel, Word 등)로 수동 제공되어 명세서와 실제 코드 간의 불일치 문제가 자주 발생했습니다.
- **Swagger 및 OpenAPI 도입**: 이러한 문제를 해결하기 위해 Swagger라는 프레임워크를 활용하여 API 문서를 자동 생성하고 관리합니다.
    - **OpenAPI Specification (OAS)**: API 기술을 표준화한 포맷입니다. 수많은 개발자가 이 표준을 기반으로 API 명세를 정의하며, Swagger는 이 표준을 따르는 대표적인 도구 중 하나입니다.
    - **작동 원리**: 개발자는 코드 레벨에서 `@Annotation` 등의 주석(어노테이션)만 적절하게 설정해주면, Swagger가 이를 읽어와 API의 기능과 구조를 자동으로 분석하고 상세한 문서를 생성해 줍니다. (개발자가 모든 것을 직접 구현할 필요 없음)

## 3. 백엔드 API 기능 개발 단계
*실습 과정에 맞춰 코드를 구성하는 순서입니다.*

- **Repository 계층 (데이터 접근)**: 데이터베이스와의 상호작용을 담당합니다.
    - **Entity 정의**: 사용자 정보를 담는 `User` 엔티티를 설계하고, DB 테이블(e.g., `swagger_user`)을 정의합니다.
    - **Email 기반 검색 구현**: 일반적으로 ID를 사용하지만, 이메일을 아이디로 사용하는 서비스 패턴에 맞춰 Repository 메서드에 `findByEmail()` 등을 추가하여 이메일 기반 유저 조회가 가능하도록 구현했습니다.
- **Service 계층 (비즈니스 로직)**: 실제 비즈니스 규칙과 로직을 처리합니다.
    - **회원가입(Registration) 로직 구현**: 회원가입 기능을 담당하는 `registerUser` 서비스를 구현했습니다.
        1. 유저 레파지토리를 사용하여 이메일이 이미 존재하는지 먼저 확인합니다 (Validation).
        2. 가입되지 않은 경우, 새로운 User 엔티티를 생성하고 암호화 등의 처리를 거쳐 DB에 저장(`save()`)합니다.
- **Controller 계층 (API 게이트웨이)**: 외부 요청을 받고 응답하는 인터페이스 역할을 합니다.
    - **요청 처리 구현**: 클라이언트가 전송한 데이터를 받는 `POST` 매핑(@PostMapping) 등을 구현하여 API를 외부에 노출했습니다.
    - **DTO(Data Transfer Object) 활용**: 요청 본문(Request Body)의 데이터는 엔티티 대신 별도의 DTO(`RegisterRequestDto`)로 받아서 사용하는 것이 좋습니다. (나중에 유효성 검사 등 확장 용이)

## 4. Swagger를 이용한 자동 문서 생성 설정
- **설정 파일 추가**: 프로젝트에 `SwaggerConfig`와 같은 설정을 하는 클래스를 추가하여 API 명세 정보를 정의합니다.
    - 이 설정 파일을 통해 해당 API가 어떤 내용을 포함하는지 (제목, 설명 등) OpenAPI의 표준을 따라 메타데이터를 제공할 수 있습니다.
- **버전 관리 및 정보 상세화**:
    - **OpenApiDefinition** 등을 사용하여 전체 API에 대한 제목(Title), 버전(Version), 설명(Description)과 같은 공통 정보를 부여합니다.
    - 이렇게 설정한 후 서버를 재시작하고 Swagger UI 경로로 접속하면, 코드를 직접 작성하지 않았음에도 불구하고 등록된 엔드포인트(`GET`, `POST` 등)의 명세와 사용 방법이 자동으로 표시되는 것을 확인할 수 있습니다.

## 1. Swagger와 OpenAPI의 이해: API 문서화 표준
- **개념:** Swagger는 API 문서를 자동으로 생성하고 관리할 수 있도록 하는 도구이며, Open API가 이 분야의 업계 표준입니다.
- **표준의 중요성:** 표준이 존재함에 따라 사용 방법이 통일되어 개발자들에게 일관된 방식으로 API를 사용할 수 있게 합니다. (이는 개발 과정에서 안정성을 높여줍니다.)
- **주요 구성 요소:**
    *   **Swagger UI Browser:** API 문서를 시각적으로 확인하고 실제로 API를 테스트할 수 있는 인터페이스를 제공합니다.
    *   **Swagger Editor:** API 정의 파일을 실시간으로 미리 보고 편집할 수 있게 합니다.
    *   **Swagger Codegen:** API 문서 기반으로 클라이언트 SDK나 서버 코드를 자동으로 생성해 줍니다.

## 2. Swagger의 주요 기능 및 개발적 장점
- **자동화된 문서 생성:** API 코드에 적절한 주석(Annotation)만 추가하면, 문서를 수동으로 작성할 필요 없이 구조화된 형태로 자동 생성됩니다.
- **테스트 용이성 제공:** 기존 HTTP 클라이언트 대신 Swagger UI를 통해 실제 값을 넣고 테스트가 가능합니다.
- **범용성 (Language/Framework Independence):** 특정 프로그래밍 언어, 프레임워크에 국한되지 않고 다양한 환경에서 사용 가능합니다.
- **핵심 장점: 협업 및 생산성 증대:**
    *   API 명세(Specification)를 제공하여 개발자 간의 원활한 의사소통이 가능하며, 백엔드와 프론트엔드 개발자의 역할 분담이 쉬워집니다.
    *   개발자가 문서 작성에 대한 부담을 덜고 코드 작성에 집중할 수 있도록 합니다.

## 3. 상세한 API 동작 규격 정의 (Annotation 활용)
- **요청 및 응답 명세:** 단순히 엔드포인트만 보여주는 것을 넘어, 요청 파라미터의 필수 여부, 데이터 타입, 예시 값 등을 `@Operation`과 같은 애너테이션을 이용해 디테일하게 지정할 수 있습니다.
- **응답 시나리오 정의:** 단 하나의 성공 응답(200 OK)만 정의하는 것이 아니라, 여러 가지 가능한 시나리오를 명확히 설명합니다. (예: 회원가입 실패 시 400 Bad Request, 리소스 부재 시 404 Not Found 등).
- **응답 구조의 세분화:**
    *   `@ApiResponse`: 특정 응답 코드(HTTP Status Code)에 대한 시나리오를 정의합니다.
    *   `content`, `schema`: 응답 본문(`Body`)이 어떤 데이터 타입(JSON, XML 등), 스키마를 따르는지 구체적으로 설명합니다.

## 4. DTO 및 데이터 모델 레벨의 명세 강화
- **데이터 검증 규칙 반영:** 단순히 필드의 이름과 타입을 정의하는 것을 넘어, 데이터 객체(DTO) 자체에 `@Schema`와 같은 어노테이션을 적용할 수 있습니다.
- **요구사항 지정:** 각 필드가 필수 값(`required`)인지, 어떤 형식의 예시 값을 가질 수 있는지 등을 명확하게 문서화합니다. (최신 버전에서는 `required` 속성 사용 권장)

## 5. 실제 인증/인가 로직 구현 (JWT 기반 보안 적용)
- **보안 문서화:** API 레벨에서 `@SecurityRequirement` 애너테이션을 사용하여, 해당 메서드를 호출하기 위해 특정 인증(Authentication)이나 인가(Authorization) 절차가 필요한지 문서에 명시할 수 있습니다.
- **실제 로직 구현 (JWT):** 실제 애플리케이션 단계에서는 보안 문서화 내용을 바탕으로 다음과 같은 기능을 추가적으로 구현합니다.
    *   **토큰 생성:** 로그인 요청 시, 사용자 정보를 기반으로 JWT(JSON Web Token)를 생성하여 반환합니다. (`@PreAuthorize` 등 권한 체크가 필요한 로직과 연결됨)
    *   **토큰 검증/파싱:** 클라이언트가 전송한 토큰을 받아 유효성을 확인하고 사용자 ID 등을 추출하는 메서드가 필요합니다.
    *   **토큰 무효화 (Logout):** 로그아웃 시, 사용된 토큰을 메모리 또는 저장소에 기록하여 더 이상 사용할 수 없도록 만듭니다.

*(강의는 결국 개발자가 자동 문서 생성 기능을 활용하며, 단계적으로 API 명세(규격 정의) → 로직 구현(보안 적용) 순서로 나아감을 보여주었습니다.)*

## 1. JWT 토큰 생성 및 파싱 과정
- **JWT 토큰의 이해:** 사용자 인증(Authentication)에 사용되는 표준 토큰 구조이며, 토큰을 생성하고 검증하는 것이 주요 목표입니다.
- **토큰 생성 (Creation):**
    *   `jwt` 라이브러리를 사용하여 토큰을 만듭니다. 주로 `create()` 메서드를 이용합니다.
    *   필수 정보: 서브젝트(Subject, 사용자 ID), 만료 시간(Expiration Time, 현재 시점으로부터 미래의 일시 지정), 비밀 키(Secret Key) 및 알고리즘(예: HMAC256).
- **토큰 파싱/검증 (Parsing):**
    *   수신된 토큰을 검증하고 내부 정보를 꺼내기 위해 `parse()` 메서드를 사용합니다. 이때 생성 시 사용했던 것과 동일한 알고리즘과 비밀 키를 이용해야 합니다.
    *   디코딩된 JWT 객체에서 `getSubject()` 등을 통해 사용자 ID를 추출할 수 있습니다.

## 2. 로그인 및 로그아웃 로직 구현 (인증 처리)
- **로그인(Login) 흐름:**
    *   사용자가 아이디와 비밀번호를 전송하면, 해당 정보를 받아 JWT 토큰을 발행하는 유틸리티 클래스(`JWTUtil`)를 사용합니다.
    *   토큰 생성 성공 시, 이 토큰 값을 응답 엔티티에 담아 클라이언트에게 반환합니다.
- **로그아웃(Logout) 흐름:**
    *   사용자가 로그아웃을 요청할 경우, 발행된 토큰을 블랙리스트(Blacklist) 처리하여 무효화해야 합니다. 이를 위해 `jwtUtil.invalidate()` 메서드를 사용합니다.
- **안정성 확보를 위한 자료구조 활용:**
    *   웹 애플리케이션은 멀티스레드 환경에서 동작하므로, 토큰을 관리하는 Map 구조로는 일반적인 `HashMap` 대신 **`ConcurrentHashMap`**을 사용해야 합니다.
    *   `ConcurrentHashMap`은 여러 스레드가 동시에 데이터에 접근하여 저장하거나 수정할 때 발생하는 동시성 문제(Concurrency Issue)를 해결해주는 자료구조입니다.

## 3. Spring Security를 이용한 접근 제어 설정
- **목적:** 특정 API 엔드포인트가 요청될 때 반드시 유효한 JWT 토큰이 포함되어 인증되었는지 확인하고 싶을 때 사용합니다.
- **글로벌 보안 설정 (Global Configuration):**
    *   `WebSecurityConfigurerAdapter`를 상속받아 전역적으로 Security 설정을 추가할 수 있습니다. 이 과정에서 어떤 인증 방식(예: Bearer JWT)을 사용할지 지정합니다.
    *   이렇게 설정하면 기본적으로 모든 API에 대한 보안 요구사항이 적용됩니다.
- **메서드 단위의 접근 제어:**
    *   특정 컨트롤러 메서드 레벨에서 `@RequireSecurity()`와 같은 애너테이션(Annotation)을 추가하여, 해당 기능만 인증이 필요함을 명시할 수 있습니다.
    *   이는 모든 API에 보안을 적용하면서도 예외적인 API (예: 사용자 목록 조회 등)는 예외 처리하거나 인증 없이 접근 가능하도록 세밀하게 설정하는 것이 중요합니다.

## 4. Swagger를 활용한 API 문서화 및 정리
- **개념:** Swagger(또는 OpenAPI)는 개발된 API에 대한 사용 설명서 역할을 하는 도구입니다. API의 요청 방식, 필요한 파라미터 등을 사용자에게 자동으로 제공하여 개발 과정을 효율적으로 만듭니다.
- **활용 방법:**
    *   **의존성 추가 및 설정:** 관련 의존성을 프로젝트에 추가하고, `@Configuration`을 통해 Swagger 설정을 해줍니다.
    *   **커스터마이징:** 기본 설정 외에도 필요에 따라 상세한 설계를 할 수 있으며, 코드를 기반으로 문서가 자동으로 생성됩니다.

## 1. 어노테이션을 활용한 API 상세 명세 정의 방법
- **자동 구조화 기능:** `@RestController` 등 컨테이너를 기준으로 필요한 기능을 알아서 생성해주어, 개발자가 코드 흐름을 쉽게 파악할 수 있도록 합니다.
- **API 설명 추가 (Description):** 제공되는 적절한 어노테이션(Annotation)에 상세한 설명값(설명서)을 넣어 API가 어떤 역할을 하는지 명확하게 기록할 수 있습니다.
- **파라미터 및 응답 설정:**
    - **요청 파라미터 설명:** 각 파라미터가 어떤 값이며, 기본적으로 어떤 값을 가져야 하는지 등을 상세히 정의할 수 있습니다. (예: 필수값 여부, 데이터 타입 등)
    - **응답 스키마(Schema) 정의:** DTO 같은 객체를 만들 때 해당 객체의 구조와 속성(스키마)을 명확하게 정의하여 API의 응답 형태를 문서화합니다.
- **목적:** 이러한 상세한 설명들은 개발 및 테스트 과정에서 사용자가 요청하는 파라미터나 기대되는 응답값을 정확히 이해할 수 있도록 돕습니다.

## 2. 보안 및 인증 관리 적용 실습
- **인증 기반 접근 제어:** API에 무조건적인 정보가 아니라, '로그인이 된 사용자에게만' 특정 정보가 제공되어야 할 경우 인증 관련 설정을 통해 접근을 제한할 수 있습니다.
- **세부 접근 권한 설정:** 전체 애플리케이션 레벨의 보안 설정 외에도, 개별 메서드(Method) 단위에 어노테이션을 붙여 해당 로직 실행 시에만 특정 인증 절차를 거치도록 지정할 수 있습니다.
- **테스트 용이성 확보:** API 테스트 과정에서 매번 복잡한 인증값을 직접 입력하는 것이 불편하므로, 미리 필요한 인증 값을 저장하고 이를 이용해 인증 과정을 진행하여 테스트의 효율성을 높일 수 있습니다.

## 3. 향후 개발 방향 및 전체 애플리케이션 구축 로드맵
- **백엔드 마무리 정리:** 강의를 통해 백엔드 애플리케이션 구조화와 Swagger 등을 활용한 API 명세서 작성 방법을 숙지합니다.
- **프론트엔드 학습 전환 (Next Step):** 다음 주부터는 프론트엔드(React 등)로의 학습 영역을 확장합니다.
- **종합 실습 목표:** 백엔드에서 구현된 API를 바탕으로, React와 같은 프런트엔드를 이용해 데이터를 가져오는 애플리케이션(예: 투두앱)을 직접 만들어보면서 전체적인 개발 프로세스(Full Stack)를 정리하는 것을 최종 목표로 합니다. 이 과정에서 Swagger 등을 활용하여 지속적으로 API 명세를 업데이트하며 실습을 마무리할 계획입니다.
