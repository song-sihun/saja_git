## 1. 주간 학습 내용 및 프로젝트 일정 안내
- **프로젝트 제출 기한 연장:** 지난주까지 진행된 레스트 컨트롤러 자켓 프로젝트 제출 마감일을 일부 조정하고, 학생들에게 재제출을 독려함.
- **학습 과정의 중요성 강조:** 실력 향상은 단순히 이론을 보는 것보다 실제로 코드를 작성하며 뭔가를 완성해보는 경험(프로젝트)을 통해 가장 빠르게 이루어진다는 점을 강조.

## 2. 개발자 관점의 시야 확장과 중요성
- **사용자(End-user)에서 설계자(Developer)로의 전환:** 사용자가 단순히 서비스를 이용하는 입장에서 벗어나, '어떻게 하면 더 좋을까?'라는 관점으로 서비스를 바라보는 것이 중요하다는 점을 설명함.
- **관찰력과 아이디어 발상:** 웹 애플리케이션을 많이 사용해 보고 분석할수록, 개발자가 미처 생각하지 못한 개선점이나 새로운 아이디어를 얻을 수 있다. 이는 제품 기획에 있어 매우 중요한 요소가 됨.
- **개발의 재미와 지속성:** 기술 학습은 어렵게 느껴지기 쉽지만, 본인이 깊이 이해하고 구현하는 과정에서 점진적으로 '아하!' 하는 재미를 느끼며 지식을 확장할 수 있음.

## 3. 프레임워크 기반 보안(Security) 설계의 필요성과 장점
- **보안 시스템 구축의 근본적 목적:** 웹 애플리케이션을 ‘나의 집’에 비유하여, 외부의 정상적인 방문객뿐만 아니라 악의적인 의도를 가진 방문객으로부터 내부 정보를 보호하는 것이 핵심 목표임을 설명함.
- **스프링 시큐리티 사용 이유 (표준화 및 효율성):**
    - 직접 보안 기능을 구현할 경우 매우 어렵고 방대하며, 기술과 비용이 많이 들기 때문에 전문가가 필요한 영역임.
    - 스프링 프레임워크 내의 `spring-security` 모듈을 사용하면 검증된 표준(Standard)을 따라 낮은 비용으로 안전한 수준 높은 보안 시스템을 구현할 수 있음.
    - **결론:** 복잡하고 광범위한 웹 개발 과정에서 핵심 비즈니스 로직에만 집중할 수 있도록, 프레임워크가 공통의 어려운 기술적 문제를 대신 처리해 주는 역할을 하기 때문에 필수적으로 사용됨.

## 4. 스프링 시큐리티 주요 컴포넌트 심화 정리 (필터, OAuth, CORS 등)
- **시큐리티 구조 이해:** 전체 보안 시스템은 수많은 '약속(Convention)'들로 이루어져 있으며, 개발자가 이 약속들을 따라 설정을 해주면 시큐리티 모듈이 동작함. 이러한 규칙을 이해하는 것이 가장 중요함.
- **주요 컴포넌트별 역할:**
    *   **`Filter` (필터):** 요청(Request)이 들어오고 응답(Response)이 나갈 때 중간에서 가로채어 처리하는 역할을 수행함. 단순한 필터가 아닌, `OncePerRequestFilter`를 상속받는 방식으로 구현되어 전체 요청 과정 중 **단 한 번만** 필터가 실행되도록 보장해야 함 (여러 번 실행 시 오작동 방지).
    *   **OAuth2:** 다른 서비스(예: 구글 로그인)의 인증 시스템을 빌려와서 사용자가 별도의 계정 정보를 제공하지 않아도 안전하게 인증을 처리할 수 있도록 하는 방식.
    *   **CORS (Cross-Origin Resource Sharing):** 서버가 외부 도메인/다른 출처(Origin)에서 들어오는 요청들을 차단하고 허용하는 통제 메커니즘. 신뢰할 수 있는 특정 서버의 요청만 받아들이도록 꼼꼼하게 설정 가능함.
    *   **Object Mapper / Exception Handling:** 복잡한 데이터 구조를 쉽게 주고받기 위한 객체 매핑 기능(Mapper)과, 예외가 발생했을 때 사용자 친화적이고 표준화된 방식으로 오류 메시지를 처리하도록 하는 메커니즘이 존재함.

## 5. 핵심 개념 이해: JWT와 인증/인가의 관계
- **JWT (JSON Web Token)의 본질:** JWT 자체는 아무런 '기능'을 수행하지 않는, 암호화 및 변조가 불가능하게 설계된 단순한 **문자열(String)**일 뿐임.
- **인증 vs. 인가 개념 구분:**
    *   **인증(Authentication):** "당신이 누구인지" 확인하는 과정 (예: 아이디와 비밀번호를 통해 사용자 본인임을 증명).
    *   **인가(Authorization):** "당신이 무엇을 할 수 있는지" 권한 범위를 결정하는 과정 (예: 이 사용자는 게시글 쓰기는 가능하지만, 관리자 페이지 접근은 불가능함).
- **JWT의 역할:** JWT는 사용자 인증/인가 과정을 수행해 주는 주체가 아니라, **인증과 인가에 필요한 정보를 담아 전달하기 위한 수단(Mechanism)**으로 사용됨. 이를 이용해 로그인을 구현하는 과정이 핵심임.
- **학습 방향성 제시 (개념 중심 학습):** 코드를 암기하거나 문법의 어려움 때문에 막히지 않도록, 항상 "로그인이란 무엇인가?", "상태 정보 유지란 무엇인가?" 등 **근본적인 개념과 전체 흐름(순서)**을 머릿속으로 그려보는 것이 가장 중요하다.
    *   *(궁극적인 목표):* 개발 과정에서 왜 이런 코드가 필요하며 (설계의 이유), 어떤 순서로 동작해야 하는지(흐름)를 이해하는 것에 집중해야 함.

## 1. 로그인 개념 이해 및 중요성: 왜 로그인이 필요한가?
- **일상과의 연관성:** 프로그래밍 개념은 우리의 일상생활의 개념과 완전히 동떨어진 것이 아니라, 인간의 삶의 역사와 맥락을 같이 한다. (예: 보안 시스템 등) 따라서 개념을 별개로 생각하기보다 일상적 관점에서 접근하는 것이 이해에 도움이 된다.
- **로그인의 본질적 목적:** 사용자가 로그인한다고 할 때 가장 먼저 질문해야 할 것은 "왜(Why)" 로그인이 필요한지, 그리고 "로그인을 하면 무엇이 달라지는지"이다.

## 2. 상태 정보 유지의 필요성과 HTTP 프로토콜의 한계
- **HTTP 프로토콜의 특징 (Stateless):** 웹 통신에 사용되는 기본 프로토콜인 HTTP는 요청(Request)과 응답(Response)을 주고받은 후, 클라이언트(Client)에 대한 정보를 스스로 기억하거나 유지하지 못한다. 즉, 매번의 요청이 독립적이다.
- **로그인의 핵심 역할:** 상태 정보(State Information)를 유지하는 것이 바로 로그인을 하는 주요 목적이다.
    *   클라이언트가 여러 페이지를 이동하며 요청하더라도, 서버는 사용자가 누구인지를 계속 인지할 수 있어야 한다.

## 3. 인증(Authentication) 과정과 기본 구현 원칙
- **로그인의 필수 단계:** 로그인 기능은 최소한 두 가지 단계를 거쳐야 완성된다.
    1.  **아이디/비밀번호 검증 (Verification):** 사용자가 입력한 ID와 비밀번호가 서비스에 저장된 정보와 일치하는지 확인한다. (기본적인 인증 절차)
    2.  **상태 정보 유지:** 검증이 성공했을 때, 이후의 모든 요청에서도 사용자의 상태를 기억할 수 있도록 메커니즘을 구축해야 한다.

## 4. 세션 관리 방식 비교 (Session Cookie vs. JWT)
- **세션 기반(Session/Cookie):**
    *   **동작 방식:** 서버는 웹 애플리케이션 서버 내부에 사용자별 '세션 저장 공간'을 마련하고, 로그인 시 고유한 `세션 ID`를 생성한다. 이 세션 ID가 쿠키 형태로 클라이언트 브라우저에 전달된다.
    *   **상태 유지 원리:** 클라이언트가 요청할 때마다 이 세션 ID(쿠키)를 서버로 보내면, 서버는 이 ID를 기반으로 저장된 사용자 객체를 찾아 인증을 수행한다. (세션과 쿠키의 결합 동작)
- **토큰 기반(JWT - JSON Web Token):**
    *   **동작 방식:** 사용자가 로그인하면 서버가 JWT 형태의 토큰을 발급하여 클라이언트에게 응답(Response) 또는 쿠키로 전송한다.
    *   **사용 이점 (분산 환경):** 서버가 여러 대일 경우 (Scale-out), 세션 기반은 모든 서버가 세션 정보를 공유해야 하는 어려움이 있다. JWT는 토큰 자체에 사용자 정보가 포함되어 있어, 어떤 서버에서도 이를 검증할 수 있으므로 분산된 환경에 유리하다.
    *   **JWT의 작동 원리:** 사용자는 이후 요청 시마다 이 토큰을 클라이언트에서 가지고 와서 서버에 전송하며 인증한다.

## 5. Spring Framework에서의 유효성 검사 및 토큰 발행 흐름
- **유효성 검사 (Validation):**
    *   `@Valid` 등을 통해 사용자가 보낸 요청 데이터(ID, 비밀번호 등)가 비어있는지(Null), 특정 형식에 맞는지 등의 기본적인 조건을 체크한다. 이 과정은 로그인 처리의 첫 번째 단계이다.
    *   만약 유효성 검사에 실패하면, 서버는 에러 객체와 함께 사용자에게 오류 메시지를 반환한다.
- **로그인 프로세스 흐름 (JWT 중심):**
    1.  클라이언트가 ID/PW를 전송한다.
    2.  서버는 **유효성 검사**를 수행하고, 데이터 유무 및 형식을 확인한다.
    3.  ID/PW 일치 여부를 DB에서 **인증**한다. (가장 기본적인 단계)
    4.  (성공 시) 서버는 사용자에게 식별된 상태 정보를 유지할 수 있는 JWT를 발급하여 응답해 주는 것이 최종 동작이다.

- **💡 토큰 구조의 이해:** 복잡하게 보이는 코드는 실제로는 '로그인 성공 $\rightarrow$ 토큰 생성 $\rightarrow$ 클라이언트에 전달'이라는 매우 간단한 약속 과정에 불과하다.
    *   **Access Token vs. Refresh Token:**
        *   **Access Token:** 짧은 유효기간을 가지며, 실제 API 요청 시 사용된다. 탈취 위험이 있으므로 짧게 설정한다.
        *   **Refresh Token:** 긴 유효기간을 가지며, Access Token이 만료되었을 때 새로운 Access Token을 발급받기 위해 사용된다. 이 토큰은 보안상 중요하기 때문에 서버가 별도로 관리(DB 저장)할 필요가 있다. (이 과정이 코드를 복잡하게 만드는 주된 이유이다.)

## 1. 로그인 과정 및 토큰 구조 이해 (Access Token, Refresh Token)
- **로그인 기본 흐름:** 사용자 이름(User Name), 비밀번호(Password)가 일치할 경우 서버는 클라이언트에게 `액세스 토큰(Access Token)`을 발급합니다.
- **토큰 역할 분리:** 기본적인 인증 과정 외에, 추가적으로 더 긴 기간 동안의 사용자 세션을 유지하기 위해 `리프레시 토큰(Refresh Token)`을 별도로 발급하여 제공하는 것이 핵심입니다.
- **클라이언트 이해:** Access Token과 Refresh Token 모두 서버가 생성한 후 클라이언트에 전달되는 형태임을 명확히 인지해야 합니다.

## 2. 클라이언트 테스트 시나리오 및 트러블슈팅
- **테스트 범위 확장:** API 테스트를 진행할 때 단순히 성공/실패 경우만을 구분하는 것을 넘어, 다음과 같은 다양한 시나리오를 구축하여야 합니다:
    *   **성공 케이스:** 정상적인 로그인 및 토큰 발급 과정.
    *   **실패 케이스:** 잘못된 아이디/비밀번호 입력 등 인증 실패 상황.
    *   **무효화 테스트 (Crucial):** 만료되었거나 변조된(변조 문자열, 다른 값이 들어간) 토큰을 사용하여 요청했을 때 오류가 정확히 발생하는지 확인합니다.
- **토큰 값 관리의 중요성:** 테스트 과정에서 얻은 토큰 값을 상수처럼 하드코딩하지 않고, 클라이언트 글로벌 세팅이나 환경 변수 등 적절한 곳에 저장하여 재사용하는 것이 효율적입니다.
- **인증 방식별 테스트:** HTTP 헤더를 이용할 때와 쿠키(Cookie)를 이용해 토큰을 전달하는 경우의 동작 차이점을 반드시 테스트해야 합니다.

## 3. 리프레시 토큰의 목적과 보안적 활용
- **주요 목적:** Access Token은 사용 기한이 짧아 주기적으로 만료되므로, 유효 기간이 지나도 사용자 경험을 유지하기 위해 `Refresh Token`이 있습니다. Refresh Token의 주 업무는 **만료된 Access Token을 갱신(Refresh)**하는 것입니다.
- **발급 조건 및 보안성:**
    *   리프레시 토큰은 필요할 때 무조건 발급해서는 안 됩니다.
    *   강력한 **보안 메커니즘**이 필요한데, 리프레시 토큰을 별도로 관리하는 주된 이유는 **토큰 탈취 여부를 확인**하고 이상 징후를 탐지하기 위함입니다.
    *   단순히 갱신 요청만 받은 것이 아니라, 해당 토큰이 정상적으로 사용되는지 '신고(또는 검증 작업)'가 필요합니다.

## 4. Refresh Token을 안전하게 추출하고 검증하는 방법
- **토큰 전송 방식:** 리프레시 토큰은 클라이언트 측에서 HTTP 요청의 `쿠키`를 통해 전달받아 사용하는 것이 가장 일반적이고 효율적인 방법입니다.
- **코드 구현 원칙 (Client Side):**
    *   HTTP 서블릿 리퀘스트(Request) 객체에서 쿠키 정보를 꺼내오는 메서드를 사용해야 합니다.
    *   반드시 `getCookies()`를 사용하여 쿠키 배열을 얻어오고, 코드가 널(Null)이 아닐 경우에만 처리를 진행합니다.
    *   쿠키 이름을 가져올 때 오타가 나지 않도록 주의하며, 문자열과 비교할 때는 **문자열 리터럴**이 앞에 오는 방식을 사용하는 것이 안전합니다 (방어적 코딩).
- **검증 로직 구현:** 토큰을 추출했다면, 단순히 값을 얻는 것으로 끝나지 않습니다. 다음과 같은 순서로 검증 파이프라인을 구축해야 합니다:
    1.  **토큰 추출 및 유효성 검사:** 쿠키 등에서 Refresh Token을 추출합니다.
    2.  **토큰 파싱 및 검증:** 전용 라이브러리(Tokenizer)를 사용하여 토큰의 형식이 맞는지, 만료되지는 않았는지 등을 확인합니다.
    3.  **일치 여부 확인 (서버와 동기화):** 추출된 Refresh Token이 서버에 저장되어 있는 기존 기록과 일치하는지 비교하고 유효성을 판단하여 Access Token 갱신을 진행합니다.

## 1. JWT 유효성 검사(Validation) 문제 해결
- **문제 진단:** 초기에 Jaccard의 Validation API만 추가하여 테스트했을 때, 실제 값이 비어 들어오는 경우에도 오류가 정상적으로 동작하지 않는 문제가 있었습니다.
- **원인 파악 및 해결:** Spring 프레임워크 환경에서 JWT를 사용하기 위해서는 단순히 Annotation을 추가하는 것 외에 적절한 의존성 설정과 구체적인 구현체가 필요합니다.
- **핵심 개선 사항:** `jakarta` 전용 라이브러리 대신, 스프링 프레임워크와 연동되도록 완전하게 구현된 스타터(예: Spring Security 관련)를 사용해야만 빌트인 기능들이 정상적으로 동작하며 유효성 검사가 제대로 이루어집니다.

## 2. 리프레시 토큰 개념 및 활용 시나리오
- **개념 정의:** 리프레시 토큰은 Access Token의 만료(Expiry)에 대비하여 세션을 연장하거나 새로운 Access Token을 발급받기 위해 사용되는 보안 메커니즘입니다.
- **사용 시나리오 (OAuth 2.0/JWT 기반):**
    1.  일반적으로 사용자에게 "로그인 연장할까요?"라고 명시적으로 물어보지 않아도, 시스템이 백그라운드에서 토큰 갱신을 처리하는 것이 일반적입니다.
    2.  시스템은 Access Token의 만료가 임박하거나 만료되었음을 감지하면, 리프레시 토큰을 호출하여 새로운 Access Token(X-S 토큰)을 자동으로 갱신합니다.
- **세션과의 차이점:** 세션을 이용할 경우, 단순히 세션 유지 시간을 늘리는 방식으로 처리하지만, JWT와 같은 토큰 기반 인증 방식에서는 리프레시 토큰을 활용한 재인증 과정(Token Refreshing)을 거쳐야 합니다.

## 3. 리프레시 토큰 기반 인증/인가 구현 과정
- **① 요청 접수 및 토큰 추출:** 클라이언트가 리프레시 토큰을 담아 요청할 경우, 요청에서 쿠키 등의 형태로 리프레시 토큰 값을 추출합니다.
- **② 토큰 검증 (Validation):**
    *   추출된 토큰이 유효한지 (변조되지 않았는지)부터 검증하며, 시그니처 및 시크릿 키를 이용해 무결성을 확인하는 절차가 선행되어야 합니다.
    *   (핵심) **데이터베이스 검증:** 이 리프레시 토큰은 반드시 데이터베이스에 저장된 토큰 값과 일치해야 합니다 (DB 저장/검사). 이는 만약 사용자가 신고를 하거나 관리자에 의해 강제로 해당 토큰을 비활성화(블록킹 또는 삭제) 했을 경우에도 시스템이 이를 감지할 수 있게 하는 중요한 보안 장치입니다.
- **③ 사용자 정보 추출 및 검증:** 유효한 리프레시 토큰으로부터 클레임 객체(Claim Object)를 얻어와서, 해당 토큰에 저장된 사용자 ID 등의 정보를 이용해 서비스 계층에서 실제 DB의 사용자 정보가 존재하는지 재확인합니다.
- **④ Access Token 갱신:** 모든 검증 과정(토큰 유효성 $\rightarrow$ DB 일치성 $\rightarrow$ 사용자 존재 여부)을 성공적으로 통과한 경우에만, 클레임으로부터 얻은 정보를 이용해 새로운 Access Token을 발급합니다.
- **⑤ 응답 처리 및 보안 예외 설계:**
    *   새로 생성된 Access Token은 쿠키와 HTTP Response Body 모두에 담아 응답하는 것이 안전하며 일반적입니다.
    *   **예외처리 (Exception Handling):** JWT 관련 오류는 종류별로 상세하게 처리해야 합니다.
        *   `SignatureExpiredException`: 토큰 형식이 잘못되거나 시그니처가 틀린 경우.
        *   `ExpiredException`: 토큰의 만료 시간(Expiry Time)이 지났을 경우 (가장 일반적인 케이스).
        *   `Unauthorized`: 인증 자체가 불가능한 경우.
    *   여러 종류의 예외를 `catch` 블록으로 분리하여 처리함으로써, 사용자에게 "어떤 오류"가 발생했는지에 따라 더 친절하고 구체적인 메시지를 전달할 수 있습니다.

## 4. 보안 예외 처리 및 테스트 계획 수립
- **예외처리 목적:** 단순히 에러 코드를 반환하는 것을 넘어, 사용자가 현재 상황(토큰 만료 등)을 명확히 인지하고 이해할 수 있도록 구체적인 정보를 제공하기 위함입니다. (Friendly Error Message 제공).
- **테스트 시나리오 설계:** 리프레시 토큰의 동작 여부를 확실하게 검증하기 위해, Access Token의 만료 시간을 의도적으로 짧게(예: 10초) 설정하여 테스트 계획을 수립합니다.
    *   **Step 1:** 로그인 요청 (정상 작동 확인).
    *   **Step 2:** 짧은 시간 대기 후 리소스 접근 시도 (만료 발생, 실패 예상).
    *   **Step 3:** 만료 발생 직후 Refresh Token 호출하여 재인증 시도 (성공 예상).
    *   **Step 4:** 토큰의 유효성을 깨뜨리거나 DB에서 삭제된 상황을 가정하고 테스트 진행.

# 강의 요약: JWT와 리프레시 토큰을 이용한 인증 시스템 구축

## 목차
1. 기존 인증 방식의 문제점과 웹 토큰의 필요성 (JWT 소개)
2. 액세스 토큰(Access Token) 및 리프레시 토큰(Refresh Token)의 역할
3. JWT 기반의 토큰 갱신 플로우 상세 과정

---

## 1. 기존 인증 방식의 문제점과 웹 토큰의 필요성 (JWT 소개)
*   **세션/쿠키 방식의 한계:**
    *   **세션(Session):** 서버가 모든 사용자 정보를 저장하고 관리해야 하므로, 사용자가 많아지면 서버 부하가 크고 복잡한 인프라 구축이 필요함 (확장성 문제).
    *   **쿠키(Cookie):** 정보가 외부에 노출되거나 위조될 위험(보안 취약점)이 있어 보안에 취약함. 또한, 쿠키 자체에는 자바 객체와 같은 복잡한 데이터를 저장할 수 없고 문자열 형태만 가능하다는 한계가 있음.
*   **JWT(JSON Web Token)의 등장 배경:**
    *   쿠키나 세션 방식의 단점인 보안 및 서버 부하 문제를 해결하기 위해 고안됨.
    *   클라이언트에게 정보를 전송하며, **서버에 상태 정보(State)를 저장할 필요가 없어** 여러 대의 서버 환경에서도 인증 관리가 용이함 (확장성 확보).
    *   JWT는 헤더-페이로드-시그니처 세 부분으로 구성되어 있으며, 시그니처 값을 통해 데이터의 위변조 여부를 검증하여 보안을 강화한 토큰 형태임.
    *   **중요:** JWT 자체는 인증 메커니즘이라기보다는 '토큰' 그 자체이며, 서버 측 필터 및 로직이 이 토큰의 유효성을 판단하여 인증을 수행함.

## 2. 액세스 토큰(Access Token) 및 리프레시 토큰(Refresh Token)의 역할
*   **액세스 토큰 (AT):**
    *   사용자가 서비스에 진입할 때 사용하는 주요 토큰으로, **실제 API 접근을 위한 인증 수단**입니다.
    *   보안상의 이유로 유효 시간(Life Time)이 매우 짧게 설정됩니다 (예: 10초~30분).
    *   장점은 보안성이 높지만, 단점이자 가장 큰 취약점으로 **토큰 탈취 시 만료되기 전까지 무효화하기 어렵다**는 점을 안고 있습니다.
*   **리프레시 토큰 (RT):**
    *   액세스 토큰의 짧은 수명으로 인한 접근 제한(Expired) 문제를 해결하기 위해 도입되었습니다.
    *   AT과 동일한 형태일 수 있으나, **서버가 RT를 관리하고 저장**합니다. 이 덕분에 서버는 사용자가 만료된 AT를 재발급받을 권한이 있는지 지속적으로 검사할 수 있습니다.
    *   주요 역할은 AT가 만료되었을 때, 새로운 AT를 안전하게 발급(갱신)해주는 것입니다.

## 3. JWT 기반의 토큰 갱신 플로우 상세 과정
*   **로그인 및 초기 인증:**
    1.  사용자가 아이디/비밀번호를 전송하며 로그인 요청을 합니다.
    2.  서버는 유효성을 검증한 후, **액세스 토큰(AT)과 리프레시 토큰(RT)** 두 가지를 모두 생성합니다.
    3.  이때 AT은 클라이언트가 API 요청 시 사용하도록 하고, RT는 보안을 위해 서버 측 저장소에 관리됩니다.
*   **API 접근 및 만료:**
    1.  클라이언트는 AT을 헤더나 쿠키 형태로 포함하여 보호된 페이지(인증 필요 리소스)를 요청합니다.
    2.  서버의 인증 필터가 토큰의 유효성을 검사하고, 통과하면 정상적인 API 접근이 이루어집니다.
    3.  시간이 지나 AT가 만료되면, 서버는 접근 권한을 거부하고 '토큰 만료'를 알립니다.
*   **토큰 갱신 (Refresh Flow):**
    1.  클라이언트는 API 요청 실패 후, **리프레시 토큰(RT)을 이용해 토큰 갱신 엔드포인트**를 호출합니다.
    2.  서버는 전송된 RT가 유효한지, 그리고 해당 사용자에 대해 블랙리스트 처리가 되어있지는 않은지 DB에서 확인합니다.
    3.  검증이 성공하면, 서버는 **새로운 액세스 토큰(AT)**을 클라이언트에게 발급하고 재접근할 수 있게 합니다.
    4.  만약 RT가 만료되었거나 탈취된 경우, 갱신에 실패하며 사용자에게 다시 로그인을 요청하게 됩니다.

**요약 결론:** 리프레시 토큰은 단순히 AT를 주기적으로 새로 받는 역할을 수행하여, 사용자가 별도의 로그인 과정 없이 오랫동안 인증 상태(로그인 유지)를 유지할 수 있도록 해주는 핵심 메커니즘입니다.

## 1. JWT의 기본 구조와 동작 원리
- **JWT (JSON Web Token):** 사용자 간에 정보를 안전하게 전송하기 위해 사용되는 문자열 기반 토큰 방식입니다.
- **구성 요소:** JWT는 일반적으로 세 부분(Header, Payload, Signature)으로 구성되며, 이 중 '시그니처(Signature)'를 생성할 때 **비밀 키(Secret Key)**가 필수적으로 사용됩니다.
    - 시크릿키는 랜덤하게 생성하거나 주어진 문자열을 이용해 만들 수 있습니다.
- **JWT 생성:** 라이브러리(예: JWTS)를 사용하면 JWT 문자열을 쉽게 생성할 수 있으며, 이때 표준 정보뿐만 아니라 원하는 정보를 담아 보관할 수 있습니다.
    - **클레임(Claims):** 토큰에 저장하고자 하는 핵심 정보들로, 키-밸류 형태로 자유롭게 추가할 수 있습니다.
- **JWT 사용 (검증 및 추출):**
    - **서명 검증:** JWT를 사용하여 정보를 꺼내올 때 가장 먼저 `JWS`의 `PASS(VerifyWith)` 메서드를 이용해 서명을 검증해야 합니다. 이 과정이 성공해야 토큰 정보에 접근할 수 있습니다.
    - **정보 추출:** 서명이 검증된 후, `Payload()` 메서드를 이용하면 담겨있던 클레임즈 객체(Claims)를 얻을 수 있으며, 이를 통해 필요한 모든 정보를 꺼내 쓸 수 있습니다.

## 2. 토큰 관리 및 보안 강화 방안 (Refresh Token, 쿠키 설정)
- **Refresh Token의 역할:** JWT는 탈취 시 무용화하기 어렵다는 특징이 있습니다. 이 문제를 해결하고 상태 정보 유지를 위해 Refresh Token을 사용하며, 이는 **데이터베이스에 저장하여 관리**해야 합니다.
    - 데이터베이스 관리를 통해 토큰이 탈취되었을 때 해당 토큰을 무효화(Revoke)할 수 있게 됩니다.
- **로그인 과정의 핵심:**
    1. 사용자 ID/PW 일치 여부 확인 (기본 인증).
    2. 상태 정보 유지를 위해 JWT를 발행하고 클라이언트에게 전달합니다.
    3. 권한(Role) 등 추가적인 정보를 토큰 내에 담아 관리 효율성을 높입니다.
- **토큰 저장 방식 및 보안:**
    - **Access Token & Refresh Token:** 두 종류의 토큰을 모두 사용하며, 일반적으로 둘 다 브라우저 쿠키에 저장하는 것이 일반적입니다.
    - **쿠키 보안 옵션 설정 (권장):**
        - **HttpOnly:** 자바스크립트(JavaScript) 접근 불가 플래그입니다. 클라이언트가 쿠키의 내부 값을 열어보거나 조작할 수 없게 하여 보안을 강화합니다. (전달만 가능하도록 제한)
        - **SameSite:** CSRF 공격 방지 목적으로 사용됩니다. `HttpOnly`와 함께 설정하여 안정성을 높입니다.

## 3. Spring Security 연동 과정: JWT 필터 구현 핵심 업무
- **필터의 역할:** 서버가 요청을 처리할 때, 인증된 사용자만이 리소스에 접근하도록 하기 위해 중간 단계(Filter)를 거칩니다. 이 JWT 필터가 그 중심 역할을 합니다.
- **JWT 필터의 핵심 임무:**
    1. 클라이언트가 요청과 함께 보낸 JWT 토큰을 추출합니다.
    2. 토큰을 검증하여 유효성을 확인하고, 내부 정보를 파싱합니다.
    3. 이 정보를 이용해 `Authentication` 객체(사용자 인증 정보)를 생성합니다.
    4. 생성된 `Authentication` 객체를 **SecurityContextHolder** (스레드 로컬)에 저장하여, 해당 요청이 처리되는 동안 모든 시스템 컴포넌트가 사용자 인증 상태 및 권한을 공유하고 접근할 수 있게 합니다.

## 4. 인증 흐름 제어 및 보안 설정 상세
- **Authentication 객체 구성 요소:** 필터에서 SecurityContextHolder에 저장하는 `Authentication` 객체는 다음 세 가지 핵심 정보를 포함합니다.
    1. **Principal (사용자 정보):** 사용자 식별 값입니다.
    2. **Credentials (비밀번호):** 비밀번호는 보안상 노출을 막기 위해 보통 `null`로 처리됩니다.
    3. **Authorities (권한):** 사용자의 역할을 담은 객체이며, 필요한 권한 정보들을 모두 여기에 추가합니다.
- **커스텀 UserDetails 활용:** Spring Security가 기본적으로 제공하는 `UserDetails` 인터페이스를 구현하여 커스텀 사용자 정보를 저장할 수 있습니다. 이는 기존의 Username/Password 외에 다른 사용자 정보를 함께 관리하기 위함입니다.
- **Refresh Token 재발급 (갱신):**
    - Access Token은 짧은 시간으로 설정하고, Refresh Token을 이용해 접근 토큰을 주기적으로 갱신(재발급)하는 패턴이 일반적입니다.
    - 만료 시간이 다가오면 클라이언트가 리프레시 요청(`/refresh`)을 통해 새로운 Access Token(만료 시간을 늘린 것)을 발급받습니다. 보안 강화를 위해 필요하다면 Refresh Token도 함께 갱신하는 것이 좋습니다.
- **Spring Security 설정 (Security Config):**
    - JWT 사용 시, 기본 세션 기반 인증 대신 **스테이트리스(Stateless)** 설정을 사용하도록 변경해야 합니다.
    - `OncePerRequestFilter`를 상속받아 구현하여 해당 필터가 요청마다 한 번만 실행되도록 제어합니다.
    - 사용자 정의 예외 처리기(`Custom AuthenticationEntryPoint`, Handler)를 등록하여 인증 실패 시 일관성 있게 오류를 반환하도록 설계하는 것이 좋습니다.


1. DisableEncodeUrlFilter
 - URL에 세션 ID를 붙이는 기능을 막는 필터
 - JWT API에서는 거의 신경 안 써도 됨

2. WebAsyncManagerIntegrationFilter
 - 비동기 요청에서도 SecurityContext를 유지하게 해주는 필터 
 - 일반 REST API에서는 그냥 지나가는 필터라고 보면 됨.

3. SecurityContextHolderFilter
 - 현재 요청에서 사용할 SecurityContext를 준비하는 필터
 - SecurityContext : 현재 요청의 인증 정보 저장소
 - JwtAuthenticationFilter가 SecurityContext에 인증 객체를 넣음.

4. HeaderWriterFilter
 - 보안 관련 HTTP 응답 헤더를 추가하는 필터
 - 브라우저 보안 강화

5. CorsFilter
 - CORS 처리 필터
 - React 프론트에서 Spring API 호출할 때 자주 걸리는 그거
 - 출처가 다르기 때문에 CORS 검사가 필요함
 - Origin, Access-Control-Allow-Origin, OPTIONS preflight 같은 걸 처리
 
6. LogoutFilter
 - 로그아웃 요청인지 확인하는 필터
 - 기본적으로 /logout 요청이면 로그아웃 처리를 함
 - Did not match request to /logout : 지금 요청은 /logout이 아니므로 아무것도 안 하고 다음 필터로 넘김
 - JWT 로그아웃을 직접 구현한다면 보통 /auth/logout 같은 컨트롤러를 만들고, refresh token 삭제/블랙리스트 처리를 직접 함.  기본 LogoutFilter는 크게 안 쓸 수도 있음.

7. JwtAuthenticationFilter
 - 요청 헤더에서 Authorization 꺼냄
 - Bearer accessToken인지 확인
 - JWT 검증
 - 토큰에서 userId, email, role 추출
 - DB에서 유저 조회 또는 UserDetails 생성
 - UsernamePasswordAuthenticationToken 생성
 - SecurityContextHolder에 저장

8. RequestCacheAwareFilter
 - 로그인 전에 접근하려던 URL을 저장해두는 필터
 - JWT REST API에서는 거의 필요 없음

9. SecurityContextHolderAwareRequestFilter
 - HttpServletRequest에서 보안 관련 메서드를 쓸 수 있게 감싸주는 필터
 - request.getUserPrincipal()
 - request.isUserInRole("USER")
 - 이런 메서드들이 Spring Security 인증 정보를 기반으로 동작하게 해줌

10. AnonymousAuthenticationFilter
 - 인증된 사용자가 없으면 익명 사용자 인증 객체를 넣는 필터
 - 로그인 안 한 사용자를 null이 아니라 anonymousUser, ROLE_ANONYMOUS 같은 형태로 넣어줌

11. SessionManagementFilter
 - 세션 관련 보안 처리를 하는 필터
 - already authenticated UsernamePasswordAuthenticationToken : JWT 필터에서 이미 인증 객체가 들어갔다
 - Preparing session with ChangeSessionIdAuthenticationStrategy : 세션 고정 공격 방지를 위한 세션 ID 변경 전략
 - JWT API 서버라면 보통 세션을 안 쓰는 구조가 많음, JWT 기반 REST API면 보통 Security 설정에 이게 들어감
 - .sessionManagement(session ->
        session.sessionCreationPolicy(SessionCreationPolicy.STATELESS)
    )

12. ExceptionTranslationFilter
 - 인증/인가 예외를 처리하는 필터
 - 인증 안 됨 : 401 Unauthorized
 - 권한 없음 : 403 Forbidden

13. AuthorizationFilter
 - 최종적으로 이 요청이 접근 가능한지 검사하는 필터
 - .authorizeHttpRequests(auth -> auth
        .requestMatchers("/auth/**").permitAll()
        .requestMatchers("/admin/**").hasRole("ADMIN")
        .anyRequest().authenticated()
    )
 - 인증정보가 Authenticated=true, Granted Authorities=[ROLE_USER] 일 경우 요청 경로가 ROLE_USER로 접근 가능한 곳이면 통과함
