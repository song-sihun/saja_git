## 1. 학습에 대한 태도와 관점 (공부의 즐거움과 접근법)
*   **공부의 동기 부여:** 학문적 내용을 취미로, 또는 재밌는 방식으로 접근하면 학습에 대한 흥미와 재미를 높일 수 있다.
*   **학습의 방향성:** 특정 기술이나 자격증 취득 그 자체가 목적이 되기보다, '재미를 느끼며 학습한다'는 경험 자체가 중요하다.
*   **지속적인 발전:** IT 분야는 빠르게 변화하므로, 현재 배우는 기술에만 국한되지 않고, 지속적인 관심과 공부를 통해 전문성을 유지하는 것이 중요하며, 이직에도 유리하다.
*   **학습 그룹의 중요성:** 혼자 학습하는 것보다 열정과 지향점이 같은 사람들과 함께 공부하고 교류할 때 시너지를 얻고 더욱 크게 성장할 수 있다.

## 2. 소프트웨어 개발의 핵심 원칙: 큰 그림 파악의 중요성
*   **개념(Concept) 중심의 학습:** 프로그래밍 시, 특정 언어의 문법이나 코드 구현 방식에 매몰되기보다 **전체적인 흐름(Flow)과 큰 그림(Big Picture)**을 이해하는 것이 가장 중요합니다.
*   **기술의 추상화 이해:** 모든 기술이나 언어는 상호 연결된 개념(객체)으로 이루어져 있으므로, 개별 기술을 배울 때도 다른 기술들과의 연관 관계를 넓게 바라보며 이해해야 합니다.
*   **언어의 교체 가능성:** 현재 자바를 사용하더라도, 미래에는 다른 언어로 대체될 수 있습니다. 하지만 웹 애플리케이션이 동작하는 **근본적인 흐름과 구조**는 바뀌지 않기 때문에, 큰 그림을 파악하면 어떤 언어가 되더라도 빠르게 적응할 수 있습니다.

## 3. 웹 애플리케이션의 구조적 이해 (클라이언트-서버 및 서버의 역할)
*   **클라이언트-서버 모델:** 웹 애플리케이션은 클라이언트(요청을 받는 쪽)와 서버(정보를 제공하는 쪽)가 네트워크를 통해 상호작용하며 동작하는 형태입니다.
*   **웹 서버와 웹 애플리케이션 서버의 구분:**
    *   **웹 서버 (Web Server):** 요청이 들어오면 정적인 데이터(이미지, HTML 파일 등)만 처리하여 응답해 주는 역할을 합니다. (예: Apache)
    *   **웹 애플리케이션 서버 (Web Application Server, WAS):** 요청을 받아 **동적 데이터 처리**를 담당합니다. 요청이 들어올 때마다 동적으로 다른 응답을 생성할 수 있는 핵심 기능을 수행합니다. (예: Tomcat)
*   **WAS의 내부 원리:** WAS는 서블릿(Servlet)을 통해 요청을 받고 응답을 만드는데, 서블릿의 생애(Life Cycle)를 관리해주는 **컨테이너(Container)**를 포함하고 있습니다.

## 4. 웹 개발의 표준 아키텍처와 패턴 (MVC 및 계층형 아키텍처)
*   **MVC 패턴의 출현:** 초기에 모든 처리를 하나의 파일에서 처리하던 방식은 너무 복잡하고 수정이 어려웠습니다. 이 문제를 해결하기 위해 **Model-View-Controller (MVC)** 라는 디자인 패턴이 등장했습니다.
*   **MVC의 원리:** 웹 애플리케이션 처리를 Model (데이터 및 비즈니스 로직), View (화면), Controller (요청 처리 및 흐름 제어) 세 부분으로 분리하여 구조화합니다.
*   **과정의 목표 아키텍처:** 본 강의 과정에서는 **레이어드 아키텍처(Layered Architecture)**를 기반으로 웹 애플리케이션을 구축하는 것을 목표로 합니다.
    *   **데이터 레이어:** 데이터베이스에서 데이터를 읽고 조작하는 부분.
    *   **서비스 레이어 (핵심):** 실제 비즈니스 로직과 핵심 알고리즘이 존재하는 가장 중요한 단계.
    *   **프레젠테이션 레이어:** 사용자에게 보여줄 화면(View)을 구성하는 부분.
*   **스프링 프레임워크의 역할:** 자바 환경에서 이러한 웹 애플리케이션을 구축할 때, 복잡한 골격(뼈대)을 제공하는 것이 **스프링 프레임워크(Spring Framework)**입니다. 스프링 프레임워크는 IoC(Inversion of Control), DI(Dependency Injection)와 같은 코어 기술을 기반으로 작동하며, 다양한 모듈을 레고 블록처럼 조합하여 필요한 부분만 선택적으로 사용하며 개발할 수 있게 합니다.

## 1. Spring MVC 핵심 원리 및 구조
- **[MVC 패턴의 핵심]:** 단순한 분리(Separation)를 넘어, *어떻게* 빠르게 처리가 이루어지게 할지(구현)에 초점을 맞춰야 합니다.
- **[모델 2 방식]:** 현재 Spring MVC는 Model 2 방식을 따릅니다.
- **[프론트 컨트롤러 (Front Controller)의 역할]:**
    *   요청을 '단일 입구'를 통해 받아들이는 것이 핵심입니다.
    *   들어온 요청을 분석하여 어떤 로직(핸들러)이 처리할지 분기하고 통제합니다. (보안 강화를 위한 문을 하나만 두는 개념)
- **[DispatcherServlet]:** Spring MVC에서 프론트 컨트롤러 역할을 수행하는 핵심 서블릿입니다.
    *   실제 웹 애플리케이션에서는 이 서블릿이 모든 요청을 받아들이는 진입점 역할을 합니다.
    *   요청을 받으면 URL 등을 기반으로 적절한 컨트롤러와 메서드를 찾아 호출합니다.
- **[Handler Adapter의 역할]:** 컨트롤러 메서드를 호출할 때, 매개변수에 선언된 타입에 맞게 Spring DI 컨테이너가 값을 자동으로 주입(Injection)해주는 역할을 합니다.

## 2. 데이터를 관리하는 스코프(Scope) 개념
데이터를 저장하고 유지하는 '범위'인 스코프(Scope)의 개념을 이해하는 것이 중요합니다.

- **스코프의 목적:** 여러 컴포넌트가 하나의 요청 안에서 데이터를 공유하고 접근할 수 있는 영역을 마련하기 위함입니다.
- **4가지 주요 스코프:**
    1.  **Page Scope (페이지 스코프):** 해당 페이지 내에서만 변수가 선언되어 사용되는 가장 국한된 범위입니다.
    2.  **Request Scope (요청 스코프):** 요청(Request)이 들어와서 응답이 나갈 때까지 생존하는 가장 기본적인 스코프입니다.
    3.  **Session Scope (세션 스코프):** 사용자가 접속(Session)이 시작되어 세션이 삭제될 때까지 데이터를 유지하는 범위입니다.
        *   **활용:** 로그인 상태 유지, 사용자별 상태 정보를 저장할 때 사용합니다.
        *   **특징:** 요청이 바뀌거나 내용이 바뀌어도 값을 유지할 수 있습니다.
    4.  **Application Scope (애플리케이션 스코프):** 애플리케이션이 생성될 때 만들어져 애플리케이션이 소멸될 때까지 유지되는, 시스템 전체의 공통 영역입니다.

## 3. View와 아키텍처 설계 원칙
- **[View Name의 사용]:** 컨트롤러에서 뷰의 구체적인 위치(디렉토리 경로, 확장자 등)를 직접 반환하는 대신, 단순한 *뷰 이름*만 반환하도록 설계되어 있습니다.
- **[View Resolver의 역할]:**
    *   뷰 이름을 받아서 실제 파일의 위치와 확장자 등을 결정해주는 객체입니다.
    *   **장점:** 컨트롤러가 뷰의 세부 경로에 대한 정보를 알 필요가 없어 **결합도를 낮출 수 있습니다.** (View가 JSP, Thymeleaf 등 바뀔 때도 컨트롤러 코드를 수정할 필요가 없어짐)
- **[핵심 컴포넌트 역할 숙지]:**
    *   **`HandlerMapping`:** 어떤 요청이 들어왔는지 파악하고, 어떤 핸들러(컨트롤러 메서드)가 처리할지 매핑합니다.
    *   **`HandlerAdapter`:** 실제 메서드 호출 및 매개변수 인젝션을 수행합니다.
    *   **`ViewResolver`:** 뷰 이름을 실제 파일 경로로 변환합니다.

## 4. 웹 기술 필수 요소: 유효성 검사(Validation) 및 상태 관리 (State Management)

### 4.1 유효성 검사 (Validation)
- **[필요성]:** 사용자로부터 입력받은 값이 비어 있거나, 특정 조건(예: 이메일 형식, 비밀번호 길이 등)을 만족하는지 자동으로 검증하는 과정이 필요합니다.
- **[구현 방식]:**
    *   과거에는 개발자가 직접 코드로 `if-else` 문을 작성해야 했지만, 이제는 **`@Valid`** 같은 어노테이션을 사용해 자동으로 처리하는 모듈을 사용합니다.
    *   **라이브러리:** `spring-boot-starter-validation` 등을 사용하며, 검증 조건은 `@NotNull`, `@Size` 등의 어노테이션으로 정의합니다.
- **[데이터 바인딩 및 메시지 처리]:**
    *   HTML 폼 태그(Form Tag)를 통해 데이터를 모델에 담아 보낼 때, `@Valid`을 사용합니다.
    *   실제 값이 누락되거나 조건에 맞지 않으면, Spring이 이를 감지하여 해당 필드에 에러 메시지를 자동으로 붙여줍니다.
- **[Redirect Attribute]:** 리다이렉트(페이지 이동) 시에는 데이터를 담아 보낼 공간이 부족합니다. 이럴 때 잠깐 데이터를 임시로 저장할 수 있는 **`RedirectAttributes`** 객체를 사용합니다.

### 4.2 상태 유지 기술 (State Management)
- **[필요한 이유]:** HTTP 프로토콜 자체는 *무상태(Stateless)* 프로토콜입니다. 즉, 요청과 응답이 끝나면 서버는 클라이언트가 누구인지, 어떤 작업을 했는지 알 수 없습니다. 따라서 상태를 유지하는 기술이 필수적입니다.
- **[주요 기술 2가지]:**
    1.  **쿠키 (Cookie):** 클라이언트(브라우저) 측에 정보를 저장하는 기술입니다.
        *   **사용:** 주로 사용자 ID나 임시 세션 ID 등 작은 정보를 저장하는 데 쓰입니다.
        *   **Spring 지원:** `@CookieValue` 어노테이션을 사용하면 요청(Request)에서 쿠키를 쉽게 가져올 수 있습니다.
    2.  **세션 (Session):** 서버(WAS) 측에 정보를 저장하는 기술입니다.
        *   **사용:** 사용자 로그인 정보, 장바구니 목록 등 서버가 반드시 기억해야 하는 핵심 상태 정보를 저장합니다.
        *   **획득 원칙 (매우 중요):** 세션 객체는 **`new HttpSession()`** 으로 직접 생성해서는 안 되며, 반드시 **`request.getSession()`** 메서드를 통해 얻어와야 합니다.
        *   **데이터 저장:** 세션에 값을 저장할 때 `session.setAttribute()`를 사용하며, 이 때 값의 타입은 `Object`가 가능합니다. (쿠키는 String만 가능)
        *   **구조:** 세션은 키(Key)와 값(Value)의 쌍으로 이루어진 맵(Map) 형태이며, 클라이언트(브라우저)마다 고유한 세션 ID가 발급됩니다.

## 1. 세션 정보 삭제 방법 및 원리

*   **기본 개념:** 쿠키(Cookie)와 달리 세션(Session) 정보는 서버 측에서 관리되며, 서버의 자바 코드를 통해 삭제를 수행해야 합니다.
*   **데이터 삭제 방법:** 세션에 저장된 특정 속성(Attribute)을 삭제할 때는 `session.removeAttribute("키")`를 사용합니다.
    *   *원리:* 이 메서드는 세션 전체를 지우는 것이 아니라, 해당 키에 해당하는 데이터만 서버에서 제거합니다.
*   **세션 전체 삭제:** 세션에 저장된 모든 정보를 완전히 초기화하려면 `session.invalidate()`를 사용합니다.
    *   *차이점:* `invalidate()`는 세션 객체 자체를 날려버리므로, 이 작업을 수행한 후에는 다시 세션을 생성하는 복잡한 과정을 거쳐야 합니다.
    *   *활용:* 로그아웃 시, 사용자가 의도적으로 모든 상태 정보를 리셋해야 하는 경우에 사용합니다.
*   **구현 주의사항:**
    *   세션 삭제 링크를 구현할 때는 Thymeleaf 문법을 사용하여 `<a th:href="@{/delete}?sessionId=${session.sessionId}">삭제</a>`와 같이 URL 파라미터로 세션 키 정보를 안전하게 넘겨주는 것이 중요합니다. (일반적인 쿼리 파라미터 사용 시 문법 오류가 발생할 수 있습니다.)

## 2. 세션 상태 활용 및 접근 제어 (로그인 구현)

*   **상태 유지의 필요성:** 사용자가 로그아웃하더라도 장바구니 정보처럼 특정 데이터는 유지되어야 할 수 있습니다. (장바구니는 세션/DB에 저장, 로그인 정보는 삭제 등)
*   **액세스 제어 구현:** 특정 페이지나 기능에 오직 로그인한 사용자만 접근하도록 제어할 수 있습니다.
    *   *구현 방법:* 사용자가 서버에 접속했을 때, 세션에 특정 키(예: `"login"`)가 존재하는지 여부를 확인하는 로직을 구현합니다.
    *   `if (session.getAttribute("login") != null)`과 같이 세션 속성 존재 여부를 검사하여, 존재하면 '웰컴 페이지'로 리다이렉트하고, 그렇지 않으면 '로그인 페이지'로 유도합니다.

## 3. 세션 관리의 모범 사례: `@ModelAttribute`와 Scope 활용

*   **직접 접근 지양:** 세션 데이터를 사용할 때마다 `session.getAttribute()` 등으로 직접 세션 객체에 접근하는 것은 가독성이 떨어지고 코드가 복잡해질 수 있습니다.
*   **권장 방식 (`@ModelAttribute`):** 스프링이 제공하는 `@ModelAttribute` 애너테이션을 사용하여 세션 속성을 자동으로 가져오는 것이 가장 모범적인 방식입니다.
    *   **장점:** 간결하고, 스프링 프레임워크가 관리하는 표준 방식입니다.
*   **초기값 설정 (Initialization):** 세션 속성을 사용하기 전에, 해당 속성에 초기 값을 설정(초기화)해 주는 과정이 필수적입니다.
    *   `@ModelAttribute`를 사용하여 필드를 선언하고, 초기값을 부여함으로써 세션에 해당 키와 초기 값이 등록됩니다.
*   **스코프 명시 (Scope Awareness):** 여러 스코프(Scope)가 존재하는 환경에서(요청, 세션, 애플리케이션 등), 만약 동일한 이름의 속성이 여러 스코프에 존재할 경우, 어느 스코프의 값을 사용하고 싶은지 명확하게 지정해야 합니다.
    *   `@Scope("session")` 등을 사용하여 현재 값이 **세션**에 저장된 값임을 명시적으로 지정하는 것이 안전합니다.
*   **예시 활용 (방문 횟수 카운트):** 방문 횟수와 같은 상태 정보는 세션을 사용하여 구현하며, `@ModelAttribute`를 통해 간편하게 접근하여 카운트를 증가시키는 방식으로 활용할 수 있습니다. (요청(Request) Scope를 사용할 경우 요청이 바뀔 때마다 초기화되어 카운트가 의미가 없습니다.)

## 4. 세션 상태 유지와 범위(Scope) 이해

*   **스코프의 이해:** 스프링 MVC는 데이터를 저장하는 여러 영역(Scope)을 제공합니다.
    *   **Request Scope:** 현재 하나의 HTTP 요청만을 위해 존재하며, 요청이 완료되면 데이터가 사라집니다.
    *   **Session Scope:** 특정 사용자의 세션 동안 데이터를 유지합니다. (로그인 상태, 장바구니 등)
    *   **Application Scope:** 웹 애플리케이션 전체에서 공유되는 데이터를 저장합니다. (전역 카운터 등)
*   **핵심:** 상태를 사용자 단위로 유지해야 하는 데이터(예: 장바구니)는 반드시 세션 스코프를 이용해야 합니다.

## 1. HTTP 통신의 기본 이해와 상태 유지의 필요성
HTTP는 웹 애플리케이션이 동작하는 기본적인 프로토콜입니다.
- **HTTP의 특징 (Stateless):** 클라이언트(Client)와 서버(Server)가 통신할 때 요청(Request)과 응답(Response)이 한 번 지나가면 서버는 이전 클라이언트의 상태를 기억하지 못합니다.
- **문제점:** 네트워크를 통해 정보를 주고받는 웹 환경에서는 사용자가 로그인했는지, 장바구니에 어떤 상품이 담겨있는지 등 '사용자의 상태'를 지속적으로 기억해야 할 필요가 있습니다.
- **해결책:** 프로토콜 자체의 한계를 극복하고 사용자의 상태를 유지하기 위해 외부 기술(쿠키나 세션)을 이용합니다.

## 2. 상태 유지 기술: 쿠키(Cookie)와 세션(Session) 비교
클라이언트의 상태를 유지하는 두 가지 주요 기술입니다.

### 🔹 쿠키 (Cookie)
*   **저장 위치:** 클라이언트(브라우저) 측에 정보가 저장됩니다.
*   **특징:**
    *   가장 큰 단점은 **보안 취약성**입니다. 브라우저에 저장된 정보는 탈취(예: 확장 프로그램, 개발자 도구)가 매우 쉽습니다.
    *   저장할 수 있는 데이터 형식의 제약이 있습니다. 기본적으로 키와 값(Key-Value) 형태의 문자열만 저장 가능합니다.
    *   브라우저의 자바스크립트 환경에서 동작하므로, 서버에서 사용하는 복잡한 자바 객체(Object)를 직접 저장할 수 없습니다.
    *   **장점:** 데이터를 서버로 보내지 않아도 클라이언트가 가지고 있기 때문에, 서버까지의 트래픽을 줄일 수 있고 접근 속도가 빠를 수 있습니다.

### 🔹 세션 (Session)
*   **저장 위치:** 서버 측(Server)에서 정보가 저장됩니다.
*   **특징:**
    *   서버가 상태를 관리하기 때문에, **복잡한 자바 객체나 리스트 등 다양한 자료형**의 데이터를 저장할 수 있습니다.
    *   상태 유지에 더 적합하며, 데이터 위변조에 대한 통제가 상대적으로 용이합니다.
    *   **작동 방식:** 요청을 보낼 때마다 세션 ID(세션의 키)를 통해 서버에 저장된 사용자 정보를 불러와 사용하는 방식으로 동작합니다.

## 3. 세션의 심화 이해 및 구현 방법
세션 객체는 사용자의 요청(Request)이 바뀌어도 정보가 유지되는 특성을 가집니다.

*   **세션 스코프 (Session Scope):**
    *   세션은 요청이 여러 번 바뀌더라도 **사용자가 세션을 삭제할 때까지** 객체를 지속적으로 유지합니다.
    *   따라서 사용자의 로그인 정보, 장바구니 목록 등 요청이 바뀌어도 유지되어야 하는 정보를 세션에 저장하여 관리합니다.
*   **세션 데이터 처리:**
    *   세션은 기본적인 자바의 맵(Map) 구조와 유사하게 동작합니다.
    *   **데이터 저장:** `session.setAttribute("키값", 객체)`를 사용하여 값을 저장합니다. (객체 형태 가능)
    *   **데이터 꺼내기:** `session.getAttribute("키값")`를 사용하여 저장된 값을 꺼내옵니다.
    *   **데이터 삭제:** `session.removeAttribute("키값")`를 사용하여 값을 제거합니다.
*   **Spring에서의 세션 접근:**
    *   Spring 환경에서는 `HttpServletRequest` 객체에 직접 접근하는 대신, `@SessionAttribute` 어노테이션 등을 사용하여 세션에 저장된 값을 간편하게 꺼내 쓸 수 있습니다.

## 4. 요청 흐름 제어: Forward와 Redirect
웹에서 요청이 발생했을 때 컨트롤러(Controller)가 응답을 처리하고 뷰(View)로 결과를 넘기는 방식은 두 가지로 나뉩니다.

### 🔹 포워딩 (Forwarding)
*   **특징:** 요청(Request)이 서버 내부에서 다른 자원(Resource)으로 전달되는 과정입니다.
*   **URL 변화:** 클라이언트가 보는 URL은 **변화하지 않습니다.** (내부적으로 흐름을 변경)
*   **요청 객체:** 요청 객체(Request Object)는 **하나**를 유지합니다. (페이지가 바뀌어도 같은 요청으로 간주됨)
*   **용도:** 같은 서버 내에서 단순히 페이지의 내용만 전환할 때 사용합니다.

### 🔹 리디렉트 (Redirect)
*   **특징:** 서버가 클라이언트에게 응답을 보내고, 클라이언트가 **새로운 요청**을 다시 보내게 하는 방식입니다.
*   **URL 변화:** 클라이언트가 보는 URL이 **바뀝니다.**
*   **요청 객체:** 첫 요청과 두 번째 요청은 **별개의 요청 객체**가 됩니다. (클라이언트가 직접 새 요청을 보내기 때문)
*   **용도:** 사용자가 특정 작업을 완료한 후, 브라우저 주소창의 URL 자체를 완전히 바꾸고 새로운 페이지를 보여줘야 할 때 사용합니다.

## 5. 핵심 패턴 및 세션 설정
*   **PRG 패턴 (Post/Redirect/Get Pattern):**
    *   **목적:** 사용자가 데이터를 POST 방식으로 전송(예: 회원가입, 글 작성)한 후, 새로고침을 해도 데이터가 중복으로 전송되는 오류(Double Submission)를 방지합니다.
    *   **흐름:** POST 요청이 들어오면 $\rightarrow$ 서버에서 처리 $\rightarrow$ **Redirect (새로운 GET 요청 유도)** $\rightarrow$ GET 요청을 통해 결과를 화면에 보여줍니다.
*   **세션 시간 설정 (Timeout):**
    *   세션은 기본적으로 브라우저가 닫힐 때까지 유지되지만, 보안 및 시스템 부하 관리 차원에서 유효 시간(Time Limit)을 설정할 수 있습니다.
    *   `setMaxInactiveInterval`을 이용해 '비활성 시간'을 지정하여, 해당 시간이 지나면 세션이 강제로 끊기도록 설정할 수 있습니다. (예: 30분 동안 사용 없으면 세션 만료)

## 1. `forward`와 `redirect`의 동작 방식 비교
- **Forward (내부 포워딩):**
    - 요청이 서버 내부에서 다른 리소스/뷰로 전달되며, 실제 URL이 변하지 않습니다.
    - 요청 객체(`Request`)가 유지되므로, `Model`이나 `Request` 객체를 통해 전달된 데이터를 이후 로직에서 문제없이 접근하고 사용할 수 있습니다.
    - **특징:** 요청 컨텍스트가 보존되어 데이터 처리 흐름이 자연스럽습니다.
- **Redirect (클라이언트 리다이렉트):**
    - 서버가 브라우저(클라이언트)에게 새로운 URL로 다시 요청하라는 명령(HTTP 3xx 상태 코드)을 보냅니다.
    - 요청 객체(`Request`)가 완전히 새로 생성되므로, 이전 요청에서 `Model`이나 `Request`에 저장했던 데이터는 유지되지 않고 사라집니다.
    - **결과:** 데이터를 유지하려면 반드시 특별한 방법을 사용해야 합니다.

## 2. 리다이렉트 시 상태 유지 및 데이터 전달 방법 (RedirectAttributes)
- **데이터 휘발성 문제 해결:** 리다이렉트는 요청의 흐름이 끊어지기 때문에, 이전 요청에서 생성한 데이터를 새 요청에서 사용할 수 없습니다.
- **`RedirectAttributes` 사용:** 이 문제를 해결하기 위해 Spring Framework는 `RedirectAttributes`라는 객체를 제공합니다.
    - 이 객체는 리다이렉트가 일어나는 동안만 임시로 데이터를 보관할 수 있는 "플래시 어트리뷰트(Flash Attribute)" 역할을 합니다.
    - 데이터를 `RedirectAttributes`에 저장한 후 리다이렉트를 수행하면, 다음 요청(새로운 GET 요청)의 뷰에서는 이 값을 안전하게 꺼내 사용할 수 있습니다.
- **PRG 패턴 (Post-Redirect-Get Pattern):**
    - 폼 제출(POST) 후에는 반드시 리다이렉트(Redirect)를 거쳐 GET 방식으로 페이지를 보여주는 것이 권장되는 패턴입니다.
    - **이유:** 사용자가 브라우저의 새로고침 버튼을 눌러도, POST 요청이 재전송되는 것을 막고, 오류나 재시도 시 데이터 무결성을 유지할 수 있습니다.

## 3. 에러 처리 및 전역 예외 처리 구현 (Exception Handling)
- **문제 제기:** 개발 과정에서 발생하는 기본 오류 페이지(WS 기본 오류 페이지)는 사용자에게 당황스럽거나 전문적이지 않아 사용자 경험(UX)을 해칩니다.
- **해결책 (커스텀 에러 페이지):** 개발자 본인이 원하는 형태의, 사용자 친화적인 커스텀 에러 페이지를 만들어 보여줄 필요가 있습니다.
- **`@ControllerAdvice` 및 `@ExceptionHandler` 사용:**
    - 전역적인 에러 처리를 담당하는 컨트롤러 역할을 하는 **`@ControllerAdvice`** 어노테이션을 사용합니다.
    - 이 클래스 내에서 **`@ExceptionHandler`** 메서드를 선언하면, 특정 예외(Exception)가 발생했을 때 이 메서드에 의해 가로채져(Handle) 원하는 방식으로 응답을 처리할 수 있습니다.
- **처리 방법 및 중요성:**
    - `@ControllerAdvice`를 사용하면 특정 예외(예: `ValidationException`, `ResourceNotFoundException` 등)가 발생할 때마다 개별적으로 다른 페이지나 메시지를 보여줄 수 있습니다.
    - 이는 애플리케이션 전체의 안정성과 사용자 인터페이스의 완성도를 높이는 핵심 기법입니다.
- **결론:** 예외 발생 시, 시스템 기본 응답 대신 컨트롤러에서 가로채 처리하여 시각적으로 매끄럽고 사용자에게 이해하기 쉬운 맞춤형 에러 페이지로 응답하는 것이 중요합니다.

## 1. 레이어드 아키텍처(Layered Architecture) 개요
*   **정의:** 소프트웨어를 여러 계층(Layer)으로 명확하게 분리하여 구조화하는 설계 패턴.
*   **구성 요소 및 역할:**
    *   **프레젠테이션 레이어 (Presentation Layer):** 사용자 인터페이스(UI)와 직접 상호작용하며, 사용자 요청을 받고 처리 결과를 사용자에게 표시하는 역할을 합니다. (예: 컨트롤러, View)
    *   **서비스 레이어 (Service Layer):** 비즈니스를 담당하는 핵심 레이어입니다. 애플리케이션의 핵심 기능(비즈니스 규칙 처리)이 가장 중요하게 구현되는 부분입니다.
    *   **데이터 레이어 (Data Layer) / 데이터 접근 계층 (Data Access Layer):** 데이터를 관리하고, 데이터베이스 또는 파일 시스템 같은 데이터 소스에 직접 접근하여 CRUD 작업 및 데이터 매핑을 수행합니다. (예: Repository, DAO)

## 2. 주요 계층별 역할 정의 및 의존성 원칙
*   **서비스 계층의 중요성:** 비즈니스 로직은 **서비스 레이어**에 집중되어야 합니다. 이 레이어가 애플리케이션의 핵심 기능(핵심 코드)을 담당하며, 데이터 모델과 조합 및 복잡한 계산을 실행하는 곳입니다.
*   **각 계층 간의 통신 원칙 (핵심):**
    *   **인접한 계층만 통신:** 각 계층은 오직 바로 인접한 상하위 계층과만 통신해야 합니다. (예: 컨트롤러 $\to$ 서비스 $\to$ 리포지토리 순서)
    *   **단방향 의존성:** 상위 계층은 하위 계층에 의존하지만, 하위 계층이 상위 계층을 호출하는 역방향 의존은 불가능합니다.
    *   **독립성 확보:** 각 계층은 서로 독립적으로 개발, 테스트, 유지보수가 가능해야 합니다.

## 3. 비즈니스 핵심 로직: 트랜잭션 관리 심화
*   **트랜잭션의 정의:** '나눌 수 없는 작업 단위(Atomic Unit of Work)'입니다. 하나의 작업은 전체가 성공하거나, 아니면 전체가 실패하여 아무것도 실행되지 않아야 합니다.
*   **트랜잭션 관리 주체 (가장 중요한 내용):**
    *   **트랜잭션 처리는 데이터 레이어가 아닌 서비스 레이어에서 수행해야 합니다.**
    *   (예시) 계좌 이체는 단순히 DB의 출금과 입금 두 기능을 호출하는 것이 아니라, '계좌 이체'라는 하나의 비즈니스 작업 단위로 묶여야 하며, 이 업무적 단위 관리는 서비스 레이어의 역할입니다.
*   **트랜잭션의 작동 원리 (Spring 활용):**
    *   서비스 메서드에 `@Transactional`과 같은 선언적 관리(Declarative Management) 방식을 사용합니다.
    *   ✅ **성공 시:** 트랜잭션 전체가 커밋(Commit) 처리됩니다.
    *   ❌ **실패 시:** 트랜잭션이 전체적으로 롤백(Rollback) 처리되어 오류 전파와 함께 취소됩니다.

## 4. 과정 마무리 및 다음 학습 로드맵

    2.  컨트롤러 $\to$ **서비스**를 호출하여 비즈니스 로직을 실행.

1. 웹 애플리케이션의 큰 그림
사용자 요청
→ DispatcherServlet
→ Controller
→ Service

→ DB

→ View 또는 JSON 응답

Spring MVC에서는 모든 요청이 먼저 DispatcherServlet으로 들어옴
이 DispatcherServlet이 프론트 컨트롤러 역할을 하면서, 어떤 컨트롤러의 어떤 메서드를 실행할지 결정
컨트롤러가 직접 처음부터 요청을 받는 것이 아니라, Spring MVC의 구조 안에서 요청이 매핑

2. MVC 구조
Model : 화면에 전달할 데이터
View : 사용자에게 보여줄 화면
Controller : 요청을 받고 흐름을 제어

컨트롤러는 보통 직접 HTML 경로 전체를 반환하지 않고 contact_form 같은 뷰 이름만 반환합니다. ViewResolver가 실제 파일 위치를 찾아줌

3. Validation
폼 입력값을 검증할 때 직접 if문을 많이 쓰는 대신, Spring에서는 @Valid와 검증 어노테이션을 사용
BindingResult는 @Valid 바로 뒤에 와야 한다

4. Cookie와 Session
HTTP는 기본적으로 Stateless

구분	Cookie	Session
저장 위치 : 브라우저 | 서버
저장 가능 데이터 : 문자열 중심 | 객체 저장 가능
보안 : 상대적으로 취약 | 상대적으로 안전
사용 예 : 자동 로그인 식별값, 간단한 설정 | 로그인 정보, 장바구니

세션 저장 : session.setAttribute("login", user);
세션 조회 : session.getAttribute("login");
세션 일부 삭제 : session.removeAttribute("login");
세션 전부 삭제 : session.invalidate();

5. Forward, Redirect

구분	Forward	Redirect
동작 위치 : 서버 내부 이동 | 클라이언트에게 새 요청 지시
URL 변경 : 안 바뀜 | 바뀜
Request 유지 : 유지됨 | 새 요청이라 사라짐
사용 예 : 단순 화면 전달 | POST 처리 후 결과 페이지 이동

폼 제출 후에는 보통 Redirect 씀
왜? 새로고침했을 때 POST 요청이 다시 전송되는 문제를 막기 위해서 = PRG 패턴

POST 요청
→ 서버 처리
→ Redirect
→ GET 요청으로 결과 페이지 표시

6. RedirectAttributes
Redirect는 새로운 요청이기 때문에 기존 Model 데이터가 사라짐
리다이렉트 후에도 잠깐 데이터를 넘기려면 RedirectAttributes를 사용


Spring MVC에서 요청이 들어와서 처리되고, 검증·세션·리다이렉트·예외 처리·서비스 계층·트랜잭션으로 이어지는 웹 백엔드의 기본 흐름 전체를 배운 날

요청은 Controller가 받고,
핵심 로직은 Service가 처리하고,
DB 접근은 Repository가 담당한다.
상태 유지는 Cookie/Session으로 하고,
POST 이후에는 Redirect로 중복 제출을 막는다.
