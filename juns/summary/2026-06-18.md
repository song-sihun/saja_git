## 1. 웹 토큰의 필요성 및 JWT 정의

### A. 데이터 전송 형식의 진화 (XML $\to$ JSON $\to$ JWT)
*   **문자열 기반 한계:** 초창기에는 데이터를 이름과 주소 등을 단순 문자열로 전달했으나, 데이터 값 자체를 구분하기 어려워(파싱 오류 가능성 높음) 구조적 문제가 발생했다.
*   **XML의 등장:** 데이터를 표준화된 태그 형태로 전송하는 XML 형식이 사용되었으나, 웹 환경에서 **구조가 무겁고(Verbose)** 값이 캡처하거나 추출하기가 복잡하다는 단점이 있었다.
*   **JSON으로의 발전:** XML의 복잡성을 개선하여 단순하고 가볍게 데이터를 표현할 수 있는 JSON 형태가 주류로 사용되었다.
*   **보안성 문제 인식:** JSON으로 값을 주고받을 때 데이터 자체가 암호화되지 않아 전송 과정에서 보안에 취약점이 존재함을 인지하게 되었다.

### B. JWT (JSON Web Token)의 정의와 필요성
*   JWT는 **JSON 형태로 만들어진 웹 토큰**이다. (JSON Web Token).
*   단순히 데이터를 주고받는 형태일 뿐, **그 자체로 인증을 수행하는 것은 아니며**, 서버가 발급한 유효한 증명서 역할을 한다.
*   **목적:** 클라이언트와 서버 간에 전송되는 데이터를 암호화하고 서명을 추가하여 보안성을 강화하며, 특히 분산된 환경에서 사용자 상태 정보(State)를 안전하게 유지하기 위해 사용된다.

## 2. JWT의 구조와 작동 원리

JWT는 세 가지 부분으로 구성되어 있으며, 이들이 점(`.` )으로 구분된다.
1.  **Header (헤더):** 토큰 타입과 해싱 알고리즘(예: HS256)을 정의한다.
2.  **Payload (페이로드/클레임):** 실제로 전달하고자 하는 사용자 정보나 데이터를 담는 부분이다.
    *   **주의:** 페이로드는 Base64로 인코딩만 되어있을 뿐, **암호화되지는 않았으므로 민감한 정보를 포함해서는 안 된다.** (누구나 디코딩하여 볼 수 있음)
3.  **Signature (시그니처):** 토큰의 위변조 여부를 검증하는 서명 부분이다.

### A. 핵심 원리: 무결성(Integrity) 확보
*   서버는 **Secret Key**라는 비밀 키를 가지고 Header와 Payload 내용을 조합하여 Signature를 생성한다.
*   클라이언트가 이 토큰을 보내면, 서버는 자신이 가진 Secret Key로 다시 Signature를 재계산하고, 전송된 Signature와 비교한다.
*   만약 값이 단 1비트라도 변조되었다면(예: 아이디를 임의로 변경), 계산된 서명값과 실제 받은 서명값이 달라져서 **변조 여부를 즉시 판별**할 수 있다.

## 3. 상태 기반(Stateful) 인증의 문제점과 JWT 도입 배경

### A. 기존 세션 방식의 한계 (상태 의존성)
*   전통적인 세션 기반 인증은 서버가 클라이언트의 모든 사용자 상태 정보(세션)를 **직접 저장 및 관리**한다.
*   시스템이 커져서 여러 대의 서버(로드 밸런싱 환경)가 동작하게 될 경우, 한 클라이언트가 A 서버에서 로그인한 세션 정보를 B 서버에서는 알 수 없게 된다. (문제 발생)

### B. 문제 해결을 위한 노력과 JWT 등장 배경
1.  **외부 저장소 사용:** 세션 정보를 개별 서버에 두지 않고, Redis 같은 **중앙 데이터베이스(DB)**에 모아두어 모든 서버가 공유하도록 했다.
    *   *한계:* 이렇게 중앙 DB를 사용하면 해당 DB가 다운되거나 과부하가 걸렸을 때 (단일 장애점, Bottleneck) 서비스 전체에 문제가 발생할 수 있다.
2.  **클라이언트 보유 방식 전환:** 상태 정보를 서버가 아닌 **클라이언트(사용자)**가 직접 갖고 들어오게 하는 방향으로 생각을 바꿨다.
3.  **보안성 확보의 필요성:** 그러나 클라이언트가 단순히 값을 가지고 오는 것은 쿠키 등의 취약점을 가질 수 있다. 따라서, 값을 안전하게 암호화하고 변조 불가능한 **표준화된 형태(JWT)**로 제공할 필요성이 생겼다.

## 4. JWT의 장점, 단점 및 구현 시 고려 사항

### A. JWT의 주요 이점 (장점)
*   **수평 확장성 용이 (Stateless):** 서버가 세션 정보를 자체적으로 저장하지 않기 때문에, 서버를 여러 대로 늘려도(Scale-out) 상태 관리 문제에서 자유롭다.
*   **DB 조회 불필요:** 토큰 자체에 필요한 사용자 정보가 담겨있으므로, 요청이 들어올 때마다 데이터베이스를 조회할 필요가 없어 트래픽 부하가 줄어든다.
*   **정보 공유 용이:** 여러 도메인이나 마이크로 서비스 간에 인증 정보를 쉽게 공유하고 사용할 수 있다.

### B. JWT의 단점 및 보완책 (보안 취약점)
1.  **탈취 시 무효화 어려움 (가장 큰 문제):** 토큰이 탈취되면 만료 시간(Expiration Time)까지 서버가 강제로 막아낼 방법이 없다.
    *   **👉 해결책: 리프레시 토큰(Refresh Token)**과 함께 사용한다. (Access Token의 유효 시간이 짧게 만들어, Access Token이 노출되어도 피해 시간을 최소화하고, Refresh Token을 통해 새로운 Access Token을 발급받는 방식으로 보안성을 높인다.)
2.  **민감 정보 저장 불가:** 페이로드는 암호화되지 않으므로 비밀번호나 주민등록번호 같은 민감한 개인 식별 정보를 절대 포함해서는 안 된다. (인증에 필요한 최소한의 식별자만 사용)

### C. 요약 정리: JWT의 역할
*   JWT는 '값을 전달하는 안전하고 표준화된 형식' 그 자체이며, 이 토큰을 받아서 **서버에서 서명 검증 과정을 거쳐야 비로소 인증 과정**이 시작된다.

## 1. JWT 개요 및 기본 개념 이해
- **JWT의 역할:** JSON Web Token(JWT)은 '토큰 형태' 자체를 의미하며, 그 자체가 인증이나 인가를 담당하는 것은 아닙니다. 토큰을 활용하여 개발자가 별도로 구현해야 합니다 (인증/인가 작업).
- **JWT 사용 흐름:** 서버가 클라이언트에게 JWT를 생성 및 발급하고, 클라이언트는 이후 요청 시마다 이 토큰을 첨부합니다.
- **검증의 중요성:** 수신된 토큰이 위조되지 않았는지 확인하려면 (서버가) 자신이 알고 있는 '시크릿 키'를 이용해 반드시 검증 과정을 거쳐야 합니다. 이 과정 없이는 정보 추출이 불가능하며, 이를 통해 보안성을 확보합니다.

## 2. JWT 생성의 핵심: 시크릿 키(Secret Key) 관리
- **시크릿 키의 용도:** 시크릿 키는 토큰에 '서명(Signature)'을 생성할 때 사용되는 비밀 값입니다. 이 서명이 곧 토큰의 위변조 방지 역할을 합니다.
- **시크릿 키 생성 방법 (두 가지):**
    1. **랜덤하게 생성 (권장):** 가장 보안성이 높은 방법으로, 임의의 알고리즘(예: HS256)을 사용하여 랜덤한 문자열 값을 얻습니다.
    2. **문자열 기반 생성:** 개발자가 원하는 특정 문자열을 입력하여 암호화된 방식으로 시크릿 키를 도출할 수 있습니다 (단, 이 문자열은 노출되지 않도록 관리해야 합니다).
- **설정 및 관리:** 애플리케이션 설정 파일(properties 등)에 시크릿 키를 명시적으로 등록하고, 최소 32바이트 이상의 충분한 길이와 난이도를 가진 값을 사용하는 것이 중요합니다.

## 3. JWT 구조화 및 토큰 발급 과정 실습
JWT는 `io` (발급 주체), `sub` (주제/로그인 ID), `iss` (발급자), `aud` (사용 권한 범위) 등 다양한 정보를 담을 수 있는 객체(Claim)입니다.

- **빌더 패턴 사용:** Spring Security의 `Jwts` 유틸리티 클래스와 빌더(Builder)를 사용하여 토큰에 필요한 클레임들을 순차적으로 추가합니다.
- **주요 필수 정보 (Claims):**
    *   **Issuer (`iss`):** 이 토큰을 누가 발급했는지 명시하는 주체입니다.
    *   **Subject (`sub`):** 이 토큰이 누구(사용자)를 위한 것인지 식별합니다 (예: 로그인 ID).
    *   **Expiration Time (`exp`):** 토큰의 유효 기간을 설정합니다. (일반적으로 시간을 밀리초 단위로 계산하여 지정).
    *   **발급 시간 (`iat`, `nbf`):** 토큰이 발급된 시간 및 사용할 수 있는 시작 시간 등을 설정할 수 있습니다.
- **커스텀 데이터:** 기본 정보 외에도 사용자 정의 클레임(Claim)을 추가하여 필요한 모든 비즈니스 정보를 담을 수 있습니다.

## 4. JWT 검증 및 활용 원리 (클레임 추출)
- **토큰 생성부터 사용까지의 과정:**
    1.  **생성:** 서버가 시크릿 키와 사용자 정보(Claim)를 이용하여 JWT 문자열을 만듭니다.
    2.  **전송:** 클라이언트에게 이 토큰을 전송합니다.
    3.  **검증 (Validation):** 클라이언트는 이후 API 요청 시마다 이 토큰을 첨부합니다. 서버는 **반드시 보유하고 있는 시크릿 키를 이용해 서명을 검증(Verify)**해야 합니다.
- **정보 추출:** 검증 과정이 성공적일 때만, 서버는 해당 JWT 문자열에서 담겨 있던 사용자 정보(클레임)들을 안전하게 꺼내어 비즈니스 로직에 사용합니다.
- **보안 원리 요약:** 서명이 일치하지 않거나 유효 기간이 지난 토큰은 검증 단계에서 거부됩니다. 즉, 시크릿 키를 아는 서버만이 토큰의 진위 여부를 판단하고 그 내용을 신뢰할 수 있습니다.

## 5. 토큰 보안 강화 방안: 액세스/리프레시 토큰
- **문제점 (액세스 토큰만 사용 시):** 액세스 토큰을 너무 길게 유지하면, 만약 이 토큰이 탈취되었을 때 공격자가 오랜 시간 동안 시스템에 접근할 위험(보안 취약성)이 높아집니다.
- **해결 방안: Access Token / Refresh Token 구조:**
    *   **액세스 토큰 (Access Token):** 유효 시간이 비교적 짧게 설정되어, 보안 위험을 최소화합니다. (실제 API 호출에 사용).
    *   **리프레시 토큰 (Refresh Token):** 액세스 토큰보다 유효 기간이 길며, 서버가 별도로 저장하고 관리하는 경우가 많습니다. 이 리프레시 토큰으로 새롭고 유효한 액세스 토큰을 재발급받아 사용합니다.
- **작동 원리:**
    1.  로그인 시 $\rightarrow$ (액세스 토큰 + 리프레시 토큰) 받음.
    2.  액세스 토큰 만료 $\rightarrow$ 클라이언트는 리프레시 토큰을 사용하여 서버에 새로운 액세스 토큰 발급 요청.
    3.  서버는 리프레시 토큰의 유효성을 검증 후, 새 액세스 토큰만 발행하여 전송.

*(참고: 이 과정은 JWT Tokenizer 같은 클래스를 구현하여 재발급 로직을 효율적으로 처리할 수 있습니다.)*

## 1. JWT 토큰 생성 및 보안 원칙 이해
- **JWT 작동 방식:** 이미 라이브러리(클래스)가 구현되어 있어, 개발자는 이 클래스를 활용하여 필요한 정보(요소)를 담아 문자열을 만드는 것에 중점을 둡니다.
- **시크릿 키 (Secret Key)의 중요성:** JWT를 생성하고 검증하는 데 사용되는 핵심 요소입니다. 시크릿 키가 노출되면 토큰이 위변조될 수 있으므로, 반드시 보안에 신경 써서 관리해야 합니다.

## 2. 액세스 토큰의 한계와 리프레시 토큰 도입 배경
- **Access Token (액세스 토큰)의 문제점:** 액세스 토큰은 탈취되었을 경우, 만료 시간까지 무효화(Revocation)시키기 어렵다는 치명적인 보안 취약점을 가집니다. 따라서 토큰 유지 시간을 너무 길게 설정하는 것은 위험합니다.
- **리프레시 토큰 (Refresh Token)의 필요성:** 액세스 토큰의 짧은 사용 주기와 사용자 경험 사이의 균형을 맞추기 위해 도입됩니다.
    *   **역할:** 리프레시 토큰을 이용하면 만료된 액세스 토큰을 서버 측에서 검증하고, 자동으로 새로운 액세스 토큰을 발급받아 사용할 수 있습니다.
- **리프레시 토큰의 관리 방식:** 서버 데이터베이스에 저장하여 사용자가 지속적으로 로그인 상태를 유지할 수 있도록 지원하는 역할을 합니다.

## 3. `JwtTokenAuthorizer` 클래스의 설계 및 구현 상세
- **클래스 목적:** JWT 토큰을 생성하고 검증하는 데 필요한 모든 기능을 모아놓은 유틸리티(Utility) 클래스로 설계합니다. (반복적인 코드 작성을 방지함)
- **생성자 로직:** `JwtTokenAuthorizer`를 초기화할 때, 액세스 시크릿 키와 리프레시 시크릿 키 두 가지 값을 필수적으로 받아와야 합니다.
    *   이 과정에서 각 토큰에 사용되는 전용 Secret Key가 생성됩니다.
- **주요 기능:**
    1.  **토큰 생성 (`createAccessToken`, `createRefreshToken`):** 사용자 정보(ID, Email, Name 등)와 역할 목록(List of Roles)을 Payload로 받아 두 종류의 토큰을 만들어냅니다. (이때 만료 시간을 설정할 수 있습니다.)
    2.  **토큰 검증 및 파싱:** 받은 토큰으로부터 필요한 값(예: 사용자 ID)을 추출하거나, 토큰의 유효성 자체를 검사하는 기능을 제공합니다.

## 4. 환경 설정 기반으로 토큰 상수 관리하기
- **개선 사항 (Best Practice):** 코드 내부에 상수로 하드코딩했던 만료 시간 (Expiration time)과 시크릿 키 같은 값들을 외부 설정 파일(`.yml`)에서 불러와 사용하도록 수정하는 것이 더 효율적입니다.
    *   이렇게 함으로써 애플리케이션을 재시작하거나 설정을 변경할 때 코드를 수정하지 않고도 환경에 맞춰 쉽게 값을 조정할 수 있습니다.

## 1. 세션 기반 인증의 한계와 문제점 (Sessions & Scalability Issues)

*   **세션(Session) 사용 방식:** 초기 인증 및 상태 유지를 위해 서버가 클라이언트별 정보를 유지하는 방식으로 활용됨.
*   **서버 확장성 문제 (Scale-out Failure):**
    *   단일 서버 환경에서는 문제가 없지만, 서버가 2대 이상 동작할 경우 세션 정보 공유에 어려움이 발생함.
    *   사용자가 처음 로그인한 서버(예: Server A)와 다음 요청을 보낸 서버(예: Server B)가 다를 경우, Server B는 사용자의 인증 정보를 알 수 없어 "미인증 사용자"로 판단하고 재로그인을 요구하게 됨.
*   **해결 방안 모색:** 서버들이 공통으로 접근 가능한 매체 (데이터베이스, Redis 등 캐시 DB)에 상태 정보를 저장해야 하지만, 트래픽이 증가할 경우 인증 관련 처리에 매우 까다로운 문제가 발생함.

## 2. JWT(JSON Web Token)의 필요성과 구조

*   **JWT 등장 배경:** 서버가 세션 정보와 같은 "상태"를 유지하는 방식에서 벗어나기 위한 대안으로 등장함.
*   **핵심 원리 (Statelessness):** 클라이언트가 필요한 정보를 자체적으로 가지고 들어오게 함으로써, 어떤 서버에 요청이 가더라도 해당 정보를 바탕으로 인증 처리가 가능해지므로 서버 간 상태 동기화 문제가 발생하지 않음.
*   **JWT의 역할:** JWT는 단순히 '정보를 담고 있는 토큰' 그 자체이며, 이를 안전하게 전송하고 검증하는 역할을 수행함 (물리적인 카드 비유).
*   **보안 문제 인식 및 해결:** 기존의 쿠키 방식은 클라이언트 측에서 정보가 쉽게 위·변조되거나 보안에 취약하다는 문제가 있었음. JWT는 이를 개선한 형태임.
*   **JWT의 구조:** 점(.)을 기점으로 세 부분으로 나뉘어 있음.
    1.  **헤더 (Header):** 토큰 생성 시 사용된 알고리즘 및 암호화 타입 정보 저장.
    2.  **페이로드 (Payload):** 실제 필요한 사용자 정보 등 데이터를 담는 영역. (🚨 **주의:** 이 내용은 누구나 디코딩하여 읽을 수 있으므로 비밀번호 같은 민감한 정보는 넣으면 안 됨.)
    3.  **시그니처 (Signature):** 토큰의 위변조를 방지하는 서명(사인). 데이터 내용과 서버가 가진 **Secret Key(비밀 키)**를 이용해 생성함.

## 3. JWT 생성 및 검증 원리

*   **JWT의 강점:**
    *   정보 내용은 노출될 수 있으나, 시그니처 덕분에 값이 임의로 조작되거나 위변조되는 것은 불가능함 (서버가 아는 Secret Key 없이는 생성 불가).
    *   이러한 '위조 방지' 기능은 JWT를 인증 시스템에서 매우 유용하게 만듦.
*   **JWT 생성 과정:** 토큰을 만들 때 반드시 **Secret Key**를 가지고 서명(Signature) 과정을 거쳐야 함. 이 시크릿 키는 서버만 알고 있어야 하며, 토큰과 같이 전송하는 클라이언트에게 노출되어서는 안 됨.
*   **JWT 검증 및 파싱 (Parsing):**
    *   클라이언트가 전달한 JWT를 받은 서버는 가지고 있는 Secret Key를 이용해 **시그니처 일치 여부**를 체크해야 함.
    *   서명까지 완벽하게 일치할 경우에만, 페이로드에 담긴 정보를 신뢰하고 인증 처리에 사용함.

## 4. 토큰 관리 패턴: Access Token과 Refresh Token

*   **토큰의 휘발성 문제 (Access Token):** 액세스 토큰(Access Token)은 탈취되었을 때 위험할 수 있으므로, **유효 시간을 짧게** 설정하는 것이 권장됨.
*   **재발급 메커니즘:** 짧은 주기로 만료되는 Access Token을 계속 재발급받기 위해 **리프레시 토큰(Refresh Token)**을 사용함.
    *   사용자는 리프레시 토큰을 이용해 새로운 Access Token을 요청하고 갱신하는 방식으로 보안성을 높임.

## 5. 실제 인증 흐름 구현 시 고려 사항 (Integrating Auth Flow)

*   **토큰 구조화:** Authentication 프로세스를 완성하기 위해 관련된 패키지(Security, User, Role 등)를 구성해야 함.
*   **Refresh Token 관리의 중요성:**
    *   Access Token은 서버가 상태를 기억할 필요가 없지만, **Refresh Token은 반드시 데이터베이스에서 관리되어야 함.**
    *   데이터베이스 관리를 통해 토큰 탈취 시 해당 Refresh Token을 무효화(Revocation)하거나 블랙리스트에 추가하여 재발급 요청 자체를 차단할 수 있음. (이는 시스템 보안의 핵심 요소임.)
*   **실제 사용 방식:**
    *   클라이언트가 서버로 트랜잭션을 보낼 때는 보통 **Bearer 타입**과 같은 표준 인증 방식을 이용함.
    *   파싱 시, 전송되는 토큰 값 앞에 불필요한 접두사(예: `Bearer `)가 붙지 않았는지 확인하는 로직을 추가하여 안정성을 높여야 함.

## 1. 인증 인가(Authentication)의 기본 구조 이해 및 필수 컴포넌트 설계
- **JWT 기반 인증 흐름:** 액세스 토큰(Access Token)은 탈취 위험 때문에 만료 시간을 짧게 설정해야 합니다.
- **리프레시 토큰 활용 (Refresh Token):** 사용자의 불편함을 최소화하기 위해, 리프레시 토큰을 이용해 액세스 토큰을 내부적으로 지속해서 재발급(갱신)하는 구조를 채택합니다.
- **데이터 관리:** 리프레시 토큰은 무효화를 확실히 관리해야 하므로 반드시 데이터베이스에 저장하고 관리할 전용 테이블이 필요합니다.

## 2. JPA 레파지토리 정의 및 구현 원칙
- **필요 엔티티 (Entities):** 인증 처리에 필요한 최소한의 엔티티로 `User`, `Role`, 그리고 `RefreshToken`이 필요합니다.
- **레파지토리 정의:** 세 가지 전용 JPA 인터페이스를 정의하고 사용해야 합니다.
    *   `UserRepository`: 유저 정보 조회를 위한 메서드 구현 (예: `findByUsername`).
    *   `RoleRepository`: 역할(Role) 관리를 위한 레포지토리.
    *   `RefreshTokenRepository`: 토큰 기반 검색 기능을 제공하는 것이 핵심입니다.
        *   **핵심 메소드:** 단순 ID 기준이 아닌, **토큰 값(`findRefreshTokenByToken`)**으로 리프레시 토큰 엔티티를 찾아오는 기능이 필요합니다.

## 3. 비즈니스 로직 처리: 서비스 레이어 (Service Layer) 구축
- **`UserService` 구현:**
    *   역할은 JWT 인증 시 데이터베이스에서 사용자 정보를 조회하는 역할에 집중하며, 회원가입 같은 복잡한 처리는 제외합니다.
    *   사용자 이름(`Optional<User> findByUsername`) 또는 ID로 사용자를 검색하고 찾아오는 로직을 담당합니다.
- **`RefreshTokenService` 구현:**
    *   리프레시 토큰의 라이프사이클 관리(저장, 조회, 삭제)를 전담하는 서비스입니다.
    *   **핵심 기능:**
        1. **토큰 저장 (Save):** `Transaction` 속성이 반드시 필요하며, 리프레시 토큰과 사용자 ID를 포함하여 DB에 저장합니다.
        2. **토큰 조회 (Find):** 주어진 토큰 값을 키로 사용하여 레코드 존재 여부를 확인하고 엔티티를 반환합니다.
        3. **토큰 삭제 (Delete):** 사용자가 로그아웃하거나 만료 시, 해당 리프레시 토큰을 DB에서 즉시 제거하는 기능을 수행합니다 (트랜잭션 필요).

## 4. 사용자 로그인 API 구현 및 유효성 검증 처리 (Controller & DTO)
- **컨트롤러 설계:** `UserController` 내에 JWT 기반의 로그인 요청 처리 로직(예: `POST /api/login`)을 담당하는 메서드를 정의합니다.
- **DTO 사용:** 전송되는 사용자 입력 값(`username`, `password`)은 별도의 DTO (`UserLoginDto`)를 사용하여 관리합니다.
- **데이터 검증 (Validation):**
    *   `@Valid` 어노테이션과 `BindingResult`를 활용하여 클라이언트가 보낸 데이터에 누락된 값이 있거나 형식이 잘못된 경우(예: 이메일 형식 오류)를 사전에 검출해야 합니다.
    *   유효성 검증 실패 시, 즉시 400 Bad Request 응답과 함께 구체적인 오류 메시지를 반환하는 로직을 구현합니다.

## 5. 최종 인증 로직 구현: 비밀번호 비교와 보안 고려 사항
- **핵심 비즈니스 흐름 (로그인 성공 경로):**
    1. **유저 정보 조회:** 전송된 사용자 이름으로 DB에 유저가 존재하는지 확인합니다 (`UserService` 호출).
    2. **비밀번호 일치 여부 검증:** 유저가 존재할 경우, 클라이언트가 보낸 비밀번호와 저장된 비밀번호(해시값)를 비교해야 합니다.
        *   **필수 요소:** 단순히 문자열 비교가 아닌, 반드시 `PasswordEncoder` 객체를 사용해야 합니다.
        *   **비교 메서드:** `passwordEncoder.matches(rawPassword, encodedStoredPassword)` 등의 방식으로 암호화된 값을 이용해 일치 여부를 확인합니다.
    3. **실패 처리:** 유저 존재 여부 또는 비밀번호 불일치 시, 클라이언트에게 401 Unauthorized 상태 코드를 반환하고 "비밀번호가 틀렸습니다" 같은 구체적인 오류 메시지 대신 **"아이디나 비밀번호 중 하나라도 잘못되었습니다"**와 같이 모호하게 안내하는 것이 보안상 매우 중요합니다. (정보 노출 방지)

## 1. 인증 성공 후 토큰 발급 과정의 이해
- **토큰 기반 인증의 필요성:** 사용자 ID와 비밀번호를 이용해 로그인이 성공적으로 인증된 이후, 상태 정보(State Information)를 유지하기 위해 토큰 시스템을 활용합니다.
- **다음 단계 예측:** 단순한 인증(로그인)을 넘어서 사용자가 시스템 내에서 무엇을 할 수 있도록 권한과 세션을 부여하는 과정이 필요하며, 이를 토큰 발급으로 처리합니다.

## 2. Access Token 및 Refresh Token 생성 및 관리
- **토큰 발급 주체와 방법:**
    - 인증 성공 후, 서버(Backend)가 사용자의 정보를 기반으로 접근 토큰(Access Token)과 재발급 토큰(Refresh Token)을 발행해야 합니다.
    - JWT(JSON Web Token) 라이브러리를 사용하여 토큰 생성 로직을 구현합니다.
- **토큰에 포함할 정보:** 각 토큰에는 사용자 정보와 권한(Role) 등의 정보를 담게 됩니다. (예: `Rolls` 리스트를 조회하여 사용).
- **Refresh Token의 DB 저장:**
    - Refresh Token은 보안과 관리 목적으로 반드시 데이터베이스(DB)에 별도의 엔티티(`RefreshTokenEntity`)로 저장해야 합니다.
    - 이 과정에는 사용자 ID와 생성된 토큰 값을 함께 기록하는 서비스 로직이 필요합니다.

## 3. 토큰 전송을 위한 쿠키(Cookie) 구현과 보안 설정
- **토큰 전송 매체 결정:** 발급받은 Access Token과 Refresh Token을 클라이언트에게 전달할 방법으로, 응답 바디나 HTTP 쿠키를 사용할 수 있습니다. (강의에서는 두 가지를 모두 활용하는 방안 제시).
- **쿠키 사용의 장점 및 구현 최적화:**
    - 토큰들을 쿠키에 저장하여 전송하는 것이 일반적이며, 코드가 중복되는 것을 막기 위해 'Private Method'나 헬퍼 함수(Helper)를 만들어 재활용하는 것이 효율적입니다.
    - **필수 보안 설정 (Security Attributes):**
        *   `HttpOnly`: 쿠키에 이 옵션을 적용하면 클라이언트 측 자바스크립트가 접근할 수 없어 XSS 공격을 방지합니다.
        *   `SetMaxAge`: 토큰의 유효 기간(만료 시간)을 지정하여 브라우저에 저장될 시간을 설정해야 합니다. (단위 주의: 밀리초 vs 초).
        *   `Secure`: HTTPS 프로토콜을 사용하는 경우 반드시 이 옵션을 활성화해야 안전합니다.

## 4. 클라이언트 응답 구조 설계 및 최종 흐름 정리
- **응답 DTO(Data Transfer Object) 활용:**
    - 응답할 데이터가 많아질 경우, 임의로 필드를 나열하기보다 모든 데이터를 담을 전용 객체(ResponseDto)를 생성하는 것이 매우 효율적입니다. (예: `LoginResponseDto`).
    - **객체 설계 원칙:** DTO는 값이 변경되면 안 되므로, 불변성(Immutability)을 가지도록 'Builder Pattern'을 사용하는 것이 가장 좋습니다.
- **최종 응답 구성 요소:** 성공적인 로그인 요청(`login` endpoint)의 응답에는 다음 내용들이 포함되어야 합니다:
    1. Access Token (쿠키 또는 바디)
    2. Refresh Token (쿠키 또는 바디)
    3. 사용자 기본 정보 (예: Username, User ID 등)
- **전체 인증 흐름 요약:**
    *   사용자 요청(ID/PW) → 1차 인증 성공 확인 → Access & Refresh 토큰 생성 및 DB 저장 → 트랜스포트 계층(쿠키/바디)을 통해 클라이언트에 안전하게 전송하며, 응답 DTO에 사용자 정보를 담아 반환합니다.
- **보안 설정의 중요성:**
    - 실제로 코드를 구현할 때는 Spring Security 프레임워크를 사용하여 인증 로직이 표준화되도록 설계해야 합니다. (애플리케이션 레벨에서 예외 처리를 하는 것이 가장 바람직함).

## 1. JWT 구현 과정 복습: 토큰의 전송 및 사용 흐름 이해
- **토큰 전달 방법:** 발급된 JWT는 응답 본문(Response Body)에 담아 보내고, 클라이언트 측에서도 쿠키(Cookie)에 함께 저장하여 사용하는 것이 일반적인 동작 방식임을 확인했다.
- **활용 시점:** API를 통해 토큰 값을 얻어 사용해야 하는 상황들이 발생하므로, 두 가지 방법(응답 본문 및 쿠키)으로 모두 처리하는 과정을 실습해 보았다.

## 2. JWT와 보안 시스템 연동의 필요성
- **통합적 구현의 중요성:** 단순히 토큰을 발급하고 주고받는 것을 넘어, 실제 서비스 환경에서는 반드시 웹 프레임워크의 보안 모듈(예: Spring Security)과 연동해야 한다.
- **시스템 효율화:** 모든 페이지가 접근할 때마다 JWT 유효성을 일일이 수동으로 검사하는 것은 비효율적이므로, 보안 시스템에 맡겨 이 과정을 자동화하고 처리하도록 구현해야 전체 시스템을 안정적으로 운영할 수 있다.

## 3. JWT 개념 학습: 실생활 비유를 통한 원리 이해
- **JWT의 핵심 역할:** JWT는 사용자의 신원(Authentication)을 증명하는 역할을 하며, 이를 통해 로그인 상태와 같은 '상태 정보'를 유지하게 해준다.
- **실생활 비유 (가장 중요한 설명):**
    - 도서관 카드나 스포츠 센터 회원 카드를 발급받았다고 가정한다. 이 카드가 곧 토큰이다.
    - 사용자는 시설에 방문할 때마다 이 물리적 카드(토큰)를 제시하기만 하면 된다.
    - 시스템은 단순히 "카드가 존재하는가?"뿐 아니라, **"이 카드의 유효 기간이 지났지 않았는가?", "현재 정지 상태는 아닌가?"** 등 토큰 내부에 포함된 정보를 체크하여 사용 가능 여부를 판단한다.
- **토큰의 구성 요소:** JWT를 생성할 때 사용자 정보(유효 기간, 이름 등)를 담아 토큰을 발급하며, 이 정보를 통해 서버는 해당 사용자의 세부 정보를 확인할 수 있다.

***
**✨ 학습 정리 및 제언:**
- JWT 개념이 처음 접하는 사람에게는 복잡하게 느껴질 수 있지만, 실제로는 사용자 정보가 담긴 '신분증 또는 인증 카드'와 같다는 원리를 이해하면 훨씬 쉽게 접근할 수 있다.
- 이번 내용을 바탕으로 로그인이 어떻게 상태 정보를 유지하고 관리하는지(세션 기반 vs 토큰 기반)를 비교하며 학습 흐름을 정리해 볼 것을 권장한다.




1. JWT가 필요한 이유

기존 세션 방식은 서버가 로그인 상태를 직접 저장한다.

문제는 서버가 여러 대가 되면 생긴다.

예를 들어 사용자가 A 서버에서 로그인했는데 다음 요청이 B 서버로 가면, B 서버는 세션 정보를 몰라서 미인증 처리할 수 있다. 이를 해결하려면 Redis 같은 중앙 저장소가 필요하지만, 이 저장소가 병목이나 장애 지점이 될 수 있다.

그래서 등장한 방식이 JWT 기반 인증이다.

JWT는 서버가 상태를 계속 들고 있는 대신, 클라이언트가 토큰을 들고 요청하게 만드는 방식이다. 서버는 토큰의 서명과 만료 시간을 검증해서 사용자를 인증한다.

2. JWT 구조

JWT는 점 . 기준으로 3부분이다.

Header.Payload.Signature
Header

토큰 타입과 알고리즘 정보가 들어간다.

예:

{
  "alg": "HS256",
  "typ": "JWT"
}
Payload

사용자 정보나 권한 같은 Claim이 들어간다.

예:

{
  "sub": "userId",
  "roles": ["USER"],
  "exp": 1234567890
}

중요한 점은 Payload는 암호화가 아니라 Base64 인코딩이라는 것이다.
즉, 누구나 디코딩해서 볼 수 있으므로 비밀번호, 주민번호, 민감정보를 넣으면 안 된다.

Signature

서버의 Secret Key로 Header + Payload를 서명한 값이다.

이 부분 덕분에 토큰이 위조되었는지 검증할 수 있다.
Payload를 누군가 조작하면 Signature가 달라지므로 서버가 바로 알아낼 수 있다.

3. JWT의 핵심 원리

JWT는 “내용을 숨기는 것”보다 위변조를 막는 것이 핵심이다.

서버는 토큰을 받을 때 Secret Key로 다시 서명을 계산한다.

받은 Signature == 서버가 다시 만든 Signature

이 값이 일치하면 신뢰할 수 있는 토큰이고, 일치하지 않으면 위조된 토큰이다.

즉, JWT 인증 흐름은 다음과 같다.

로그인 성공
→ 서버가 JWT 발급
→ 클라이언트가 토큰 저장
→ 이후 요청마다 토큰 전송
→ 서버가 토큰 검증
→ 검증 성공 시 사용자 인증 처리
4. Access Token과 Refresh Token

Access Token만 쓰면 문제가 있다.

Access Token의 만료 시간을 길게 잡으면 사용자는 편하지만, 탈취당했을 때 공격자가 오래 사용할 수 있다.


Access Token  : 짧은 수명, 실제 API 요청에 사용
Refresh Token : 긴 수명, Access Token 재발급에 사용

Access Token은 서버에 저장하지 않아도 된다.
하지만 Refresh Token은 DB에 저장해서 관리하는 것이 중요하다.

이유는 로그아웃, 탈취, 강제 만료 같은 상황에서 Refresh Token을 삭제하거나 무효화해야 하기 때문이다.

6. 로그인 처리 흐름

로그인 API의 핵심 흐름은 다음이다.

1. username/password 요청 받음
2. DTO Validation 수행
3. username으로 User 조회
4. PasswordEncoder.matches(raw, encoded)로 비밀번호 검증
5. 실패 시 401 반환
6. 성공 시 Access Token 생성
7. Refresh Token 생성
8. Refresh Token DB 저장
9. 토큰을 응답 바디 또는 쿠키로 전달

비밀번호 비교는 절대 문자열 비교하면 안 되고, 반드시 이렇게 해야 한다.

passwordEncoder.matches(rawPassword, encodedPassword)

그리고 로그인 실패 메시지는 보안상 구체적으로 말하지 않는 게 좋다.

나쁜 예:

비밀번호가 틀렸습니다.
존재하지 않는 아이디입니다.

좋은 예:

아이디 또는 비밀번호가 올바르지 않습니다.
7. 쿠키로 토큰 전달할 때 주의점

토큰은 응답 바디로 줄 수도 있고 쿠키로 줄 수도 있다.

쿠키를 쓴다면 보안 옵션이 중요하다.

HttpOnly : JS에서 쿠키 접근 방지, XSS 방어
Secure   : HTTPS에서만 전송
MaxAge   : 쿠키 만료 시간 설정
SameSite : CSRF 위험 완화

Access Token과 Refresh Token을 쿠키에 담는다면 중복 코드를 줄이기 위해 쿠키 생성 헬퍼 메서드를 따로 빼는 게 좋다.

8. Spring Security와 연동해야 하는 이유

JWT 발급만 한다고 끝이 아니다.

실제 서비스에서는 모든 요청마다 토큰을 검증해야 한다.

그걸 컨트롤러마다 직접 하면 코드가 지저분해진다.

그래서 Spring Security 필터에서 처리하는 구조로 가는 게 맞다.

최종 구조는 보통 이렇게 된다.

클라이언트 요청
→ JWT 인증 필터
→ Authorization 헤더 또는 쿠키에서 토큰 추출
→ 토큰 검증
→ 사용자 정보 추출
→ SecurityContext에 Authentication 저장
→ Controller 진입

즉, JWT는 인증 재료이고, Spring Security는 그 인증을 전체 요청 흐름에 적용하는 시스템이다.

9. 구현해야 할 순서

1. JwtTokenAuthorizer / JwtTokenizer 완성
2. RefreshToken 엔티티, Repository, Service 완성
3. AuthService에서 login / refresh / logout 구현
4. AuthController 만들기
5. 로그인 성공 시 Access + Refresh Token 발급
6. Refresh Token DB 저장
7. 쿠키 또는 응답 바디로 토큰 반환
8. JWT Filter 만들어서 요청마다 Access Token 검증
9. SecurityConfig에 JWT Filter 등록
10. 로그아웃 시 Refresh Token 삭제

JWT는 로그인 상태를 서버 세션에 저장하지 않고, 서명된 토큰으로 인증 상태를 증명하는 방식이다.
Access Token은 짧게 쓰고, Refresh Token은 DB에 저장해서 재발급과 로그아웃을 관리해야 한다.
