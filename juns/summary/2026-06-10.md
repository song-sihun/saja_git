## 1. JPA 핵심 원리 및 기술 이해

*   **영속성 컨텍스트(Persistence Context):** 애플리케이션 내에서 데이터를 임시로 관리하는 공간입니다. 커밋이 완료되는 시점에 이 영속성 컨텍스트가 분석을 통해 실제 데이터베이스에 저장, 수정, 삭제 등의 작업을 수행합니다.
*   **객체와 관계형 DB의 매핑 중요성:** JPA는 객체의 상태와 관계형 데이터베이스 간의 맵핑(Mapping)을 관리하는 핵심 역할을 합니다.
    *   스프링 JDBC나 MyBatis 같은 기술은 사용자가 직접 SQL 코드를 작성하고 이를 이용하지만, **JPA**는 개발자가 명시적으로 쿼리를 만들지 않아도 내부적으로 ORM 정보를 기반으로 쿼리를 생성해줍니다.
*   **JPQL vs. Native Query:**
    *   **JPQL (Java Persistence Query Language):** JPA가 제공하는 객체 지향 쿼리 언어입니다. 테이블명이 아닌 **엔티티명**을 주체로 사용하며, 컬럼명을 쓰지 않고 필드명을 사용합니다. 이는 데이터베이스 종류에 구애받지 않아(이식성) 가장 권장되는 방법입니다.
    *   **Native Query:** 특정 데이터베이스만 가진 고유한 기능(DB 종속적 능력)을 사용해야 할 때 제한적으로 사용하며, 이 경우 성능 향상을 위해 MyBatis나 Spring JDBC 등을 함께 활용하기도 합니다.

## 2. 고급 쿼리 작성 방법론 (JPQL, Criteria API, QueryDSL)

*   **JPA Repository 계층의 역할:** `JpaRepository`는 JPA가 제공하는 거의 모든 기능을 상속받은 핵심 인터페이스입니다. 일반적으로 직접 구현하기보다는 `JpaRepository`를 상속하여 사용하는 것이 표준적이고 일반적인 방식입니다.
*   **쿼리 메서드(Query Method) 활용:** 간단한 CRUD 작업이나 기본 조회 기능은 Repository 인터페이스에 메서드 이름만 정의해도 JPA가 자동으로 쿼리를 생성해줍니다 (예: `findByUsernameAndAgeGreaterThan`).
*   **Criteria API의 필요성 및 역할:**
    *   JPQL 코드는 내부적으로 문자열로 처리되기 때문에, 오타나 존재하지 않는 필드를 사용할 경우 실제 실행 시점(런타임)에 오류가 발생하며 컴파일 단계에서 오류를 잡기 어렵습니다.
    *   **Criteria API**는 이러한 문제점을 보완하여 **Java 코드로 쿼리를 작성**할 수 있게 합니다. 주요 목적은 JPQL의 유연성을 유지하면서도 개발 시점(컴파일 타임)에 오류를 발견하고, 복잡한 조건문 처리 등을 용이하게 하는 것입니다.
*   **QueryDSL의 도입 배경 및 강점:**
    *   Criteria API가 여전히 다소 복잡하게 느껴질 수 있어 등장했습니다. QueryDSL은 Criteria API와 마찬가지로 **쿼리 생성 과정을 더욱 간편하고 직관적인 형태로 제공하는 것을 목적**으로 합니다.
    *   이는 개발자가 쿼리를 동적으로, 그리고 간결한 코드로 작성할 수 있도록 도와줍니다. (💡참고: QueryDSL 사용을 위해서는 외부 API 의존성 추가와 빌드 설정을 변경해야 할 수 있습니다.)

## 3. 트랜잭션 관리와 데이터 로딩 전략

*   **지연 로딩(Lazy Loading) 문제점:** 지연 로딩은 필드를 실제로 접근할 때 쿼리가 날아가 데이터를 불러오는 방식입니다. 하지만 이 경우 트랜잭션이 종료된 이후 (예: View 레이어) 해당 데이터에 접근하려고 하면 오류가 발생하기 쉽습니다.
*   **권장되는 데이터 처리 전략 (Service Layer Hydration):**
    *   트랜잭션의 범위를 불필요하게 넓히는 것은 바람직하지 않습니다.
    *   데이터를 조회하고 비즈니스 로직을 수행하는 **서비스(Service) 레이어에서 필요한 모든 데이터를 미리 불러오거나 값을 채워주는(Hydrate)** 방식으로 코드를 구성해야 합니다.
    *   이렇게 하여 트랜잭션이 끝난 후에도 데이터가 완벽하게 준비되어 있어 (독립적으로) 프론트엔드 등 외부 계층에 전달될 수 있도록 하는 것이 바람직합니다.

## 4. RESTful API 아키텍처의 기본 개념

*   **REST vs. MVC:**
    *   **MVC(Model-View-Controller):** 요청이 들어왔을 때 **화면(View)**으로 응답하는 방식에 최적화되어 있습니다. (프론트와 백엔드가 강하게 결합됨)
    *   **RESTful API:** 요청이 들어왔을 때 **데이터(Data)** 형태로만 응답합니다. 이는 프런트단과 백엔단의 역할을 완전히 분리할 수 있게 합니다.
*   **자원 중심 설계 (Resource-Centric Design):**
    *   REST의 핵심은 모든 것을 '자원(Resource)'으로 간주하고, 자원을 식별하는 데 **URI (Uniform Resource Identifier)**를 사용하는 것입니다.
    *   예: `/customers`는 '고객들'이라는 집합을 의미하고, `/customers/{id}`는 'ID가 특정된 단일 고객 정보'라는 고유한 자원을 의미합니다.
*   **HTTP 메서드와 CRUD의 관계:**
    *   REST에서는 URI 자체가 자원(Resource)을 나타내며, **어떤 HTTP 메서드를 사용했는지**에 따라 그 동작이 결정됩니다 (행위).
    *   | 메서드 | 동작 원리 | 역할 (CRUD) | 예시 설명 |
    *   | :---: | :---: | :---: | :--- |
    *   | **GET** | 자원을 조회한다. | Read (읽기) | 고객 목록 조회 |
    *   | **POST** | 새로운 자원을 생성한다. | Create (생성) | 새 고객 정보 등록 |
    *   | **PUT / PATCH** | 기존 자원 정보를 수정한다. | Update (수정) | 고객 정보 업데이트 |
    *   | **DELETE** | 특정 자원을 삭제한다. | Delete (삭제) | 고객 정보 삭제 |

## 1. RESTful API 설계 원칙의 이해
- **설계 원칙의 강조:** RESTful은 단순히 기능을 구현하는 것이 아니라, 일관된 '약속(Design Principle)'을 가지고 시스템을 설계하는 방식이다.
- **자원(Resource) 중심 설계:** 핵심은 모든 데이터가 URI (Uniform Resource Identifier, 웹 주소)를 통해 자원으로 표현된다는 원칙이다.
- **CRUD의 약속화:** 특정 기능을 구현할 때 GET/POST/PUT/DELETE 등의 HTTP 메서드에 어떤 역할을 할지 *미리 정의하고 약속*하는 것이 중요하다.
    - `GET`: 자원 조회 (읽기)
    - `POST`: 자원 생성
    - `PUT`: 자원 수정
    - `DELETE`: 자원 삭제
- **목적:** 누구나 보고도 이해하기 쉽고, 직관적인 방식으로 소프트웨어를 개발하는 것을 목표로 한다.

## 2. Controller와 RestController의 역할 및 차이점
- **일반 Controller (MVC 패턴):**
    - **용도:** 서버 사이드 렌더링(Server-Side Rendering) 웹 애플리케이션을 만드는 데 목적을 둔다.
    - **기대 반환값:** 주로 View 이름이나 뷰 객체를 기대한다. (Model과 View를 결합하여 응답 화면 생성)
    - **작동 방식:** 요청 처리 후, 뷰 리졸버(View Resolver)를 통해 실제 HTML 페이지로 변환된다.
- **RestController:**
    - **용도:** RESTful API 서비스처럼 클라이언트에게 데이터 모델 자체를 직접 반환하는 데 특화되어 있다.
    - **기대 반환값:** View가 아닌, 순수한 데이터(JSON 또는 XML 형식) 그 자체를 반환한다.
    - **자동 적용 기능:** `@ResponseBody` 애너테이션이 기본적으로 포함되어 있어, 반환되는 객체가 자동으로 JSON이나 XML 형태로 변환된다.

## 3. Spring Boot의 데이터 처리 메커니즘 (Message Converter 중심)
- **MVC와 REST API의 흐름 차이:** 일반 컨트롤러가 View를 통해 응답하는 것과 달리, 레스트 컨트롤러는 데이터를 바로 반환한다.
- **메시지 컨버터(MessageConverter)의 역할 (핵심):**
    - 요청이 들어올 때: 클라이언트 측 데이터 형식(JSON/XML 문자열)을 자바 객체 타입으로 변환해준다.
    - 응답할 때: 자바 객체를 클라이언트가 이해할 수 있는 네트워크 전송용 형식(JSON/XML 문자열)으로 자동 변환하여 제공한다.
- **작동 원리:** 스프링 부트는 내부적으로 Jackson과 같은 라이브러리를 활용하여 이 데이터 변환 과정을 개발자가 신경 쓰지 않아도 자동으로 처리해준다 (메시지 컨버터 인터페이스 구현).
- **요청/응답 흐름:** 요청이 들어오면 `DispatchServlet`이 받아 핸들러 어댑터가 이를 처리하고, 최종적으로 데이터를 반환할 때 메시지 컨버터를 거쳐 JSON 형태로 변환되어 응답된다.

## 4. 고급 요청 처리 방법: RequestBody 및 파라미터 바인딩
- **@RequestBody 활용 (POST 요청):**
    - 클라이언트로부터 보낼 데이터가 단순히 폼(Form) 방식이 아니라, 구조화된 JSON이나 XML 형태일 때 사용한다.
    - 해당 애너테이션은 HTTP Body 전체를 읽어와 지정된 자바 객체(DTO 등)로 한 번에 매핑(바인딩)하여 받을 수 있게 한다.
- **파라미터 바인딩 및 필수값 설정:**
    - `@RequestParam`을 통해 URL 쿼리 파람터를 받아오는 것이 기본이다.
    - **필수 여부와 기본값 지정 (💡 중요):**
        - `required=true`(기본값)가 되어 있으면 해당 파라미터가 없을 경우 에러를 발생시킨다.
        - `required=false`로 설정하여 필수값이 아님을 명시하거나, `defaultValue`를 설정하여 값이 누락되었을 때 사용할 기본값을 제공할 수 있다.

## 1. REST API 테스트를 위한 도구 활용 및 실습
- **테스팅 환경의 필요성**: GET 요청 외의 POST, PUT, DELETE 등 다양한 HTTP 메서드를 테스트하려면 단순 브라우저 사용으로는 한계가 있다.
- **필요한 테스트 도구**: Postman 같은 전용 애플리케이션이나 커맨드라인의 CURL 명령을 활용할 수 있다. 강의에서는 인텔리제이(IntelliJ)가 제공하는 `.http` 파일을 이용해 테스트하는 방법을 안내했다.
- **POST 요청 테스트 절차**:
    - **파일 설정**: `.http` 확장자를 가진 파일을 생성하여 사용하는 것이 권장된다.
    - **요청 전송 (Body 및 Content Type)**: POST 방식 테스트 시, 필요한 데이터를 `Request Body`에 입력해야 하며, 이 때 보낼 데이터의 형태(예: JSON)를 명시하기 위해 반드시 `Content-Type`을 지정해야 한다 (예: `application/json`).
    - **데이터 처리 과정**: 서버는 요청 본문에서 지정된 컨텐츠 타입과 구조를 바탕으로 데이터를 받아 처리하고, 적절한 응답 코드와 함께 결과를 반환한다.

## 2. 레스트(REST) 아키텍처와 웹 API 이해
- **레스트풀 서비스 정의**: RESTful은 Representational State Transfer의 약자로, 자원(Resource)을 URI로 표현하고 행위는 메서드(HTTP Method)로 처리하는 아키텍처를 따른다. (핵심: 모든 것을 '자원'으로 간주함).
- **REST 원칙 이해**:
    - **자원 중심**: 서비스의 모든 콘텐츠와 데이터가 자원으로 표현되어야 한다.
    - **무상태성 (Stateless)**: 각 요청은 독립적이며, 서버는 클라이언트의 이전 상태 정보를 저장하지 않는다. 이 덕분에 서버 설계가 단순해지고 확장성이 높아진다.
    - **표준 메서드 사용**: HTTP 표준 메서드(GET, POST, PUT, DELETE)를 활용한다.
        - **수정 메서드 구분**: 데이터를 전체적으로 수정할 때는 `PUT`을, 부분적으로 수정할 때는 `PATCH`를 사용하는 것이 일반적이다.
- **REST와 웹 API의 관계 (실용적 관점)**: 엄밀히 따지면 REST 원칙은 매우 까다로워 완벽하게 지키는 서비스는 드물다. 따라서 실무에서는 복잡한 표준보다 필요에 따라 간결하게 사용하는 경우가 많으며, 이를 '웹 API'라고 부르는 경향이 있다.
- **응답 형식 (Response Format)**:
    - 기본적으로 JSON 형태로 응답하는 것이 일반적이다.
    - XML로도 응답하도록 설계를 할 수 있으나, 현재는 JSON 사용 비중이 압도적으로 높다. Spring MVC 등에서는 설정만으로 원하는 포맷(JSON/XML)을 선택할 수 있다.

## 3. Spring Boot를 이용한 CRUD 구현 및 응답 방식 설계
- **컨트롤러 구조**: `RestController` 어노테이션을 클래스 레벨에 붙여주면, 해당 클래스의 모든 메서드가 컨트롤러 역할을 수행한다.
- **라우팅 설정**: `@RequestMapping`과 같은 어노테이션을 통해 클라이언트가 접근할 공통 주소(URI)를 정의할 수 있다. (`/api/products` 등).
- **CRUD 구현 과정 (데이터 흐름)**:
    1.  **GET (Read - 조회)**: 전체 리스트나 단일 자원을 요청했을 때, 적절한 데이터를 담은 객체(DTO)의 목록을 반환한다.
    2.  **POST (Create - 생성)**: 클라이언트로부터 전송된 요청 본문(`@RequestBody`)의 데이터를 받아 새로운 자원으로 등록 처리하는 로직이 들어간다.
    3.  **PUT/PATCH (Update - 수정)**: 업데이트할 대상 ID와 함께 수정할 값을 요청 본문을 통해 받아 기존 데이터를 갱신한다.
    4.  **DELETE (Delete - 삭제)**: 특정 ID를 기준으로 자원 삭제 처리를 수행한다.
- **개발 범위의 이해**: 초기 단계에서는 데이터베이스와의 실제 연동(Service/Repository 계층) 없이, 컨트롤러 단에서 Mock Data(가짜 리스트 등)를 이용하여 요청 및 응답 흐름 자체를 테스트하는 것이 중요하다.

## 1. RESTful 원칙과 Web API의 등장 배경
*   **RESTful 개념 이해:** 레스트풀(RESTful)은 URI를 통해 자원(Resource)을 정의하고, 메서드(GET, POST 등)를 통해 해당 자원에 대한 행위(CRUD)를 정하는 약속 기반 아키텍처입니다.
    *   **자원 식별:** 클라이언트는 URI만 보고도 어떤 종류의 데이터가 제공되는지 유추할 수 있어야 합니다.
    *   **API의 역할 (약속):** API는 단순히 데이터를 전달하는 것을 넘어, 요청과 응답의 형태와 의미에 대한 명확한 '약속'을 지키는 것이 핵심입니다.
*   **Web API로의 진화:** 엄격하게 모든 RESTful 규칙을 준수하려는 노력은 구현 과정에서 과도한 복잡성을 초래할 수 있습니다 (배보다 배꼽이 더 큰 상황).
    *   따라서 웹 개발 환경에서는 이러한 엄격한 규칙들을 다 지키기보다는 **적정 수준의 가이드라인**을 따르며 사용하는 경향이 생겨났고, 이를 'Web API'라고 부르게 되었습니다.
*   **API 데이터 제공 범위:** API는 프론트엔드(클라이언트 화면)에만 데이터를 제공하는 것이 아닙니다. 공공데이터 활용이나 백엔드 서버 내부의 다른 로직에서 정보를 가공하여 사용할 수 있도록 **정보를 제공**하는 역할을 합니다.

## 2. 데이터 포맷 표준화 및 다중 형식 지원
*   **JSON (JavaScript Object Notation)의 지배력:**
    *   현재 API 통신에서 가장 보편적으로 사용되는 데이터 형식입니다. 과거부터 프론트엔드 개발(JavaScript)과 밀접하게 연관되어 왔기 때문에, JSON 형태로 변환하고 사용하는 것이 매우 편리합니다.
    *   JSON은 키(Key): 값(Value)의 쌍으로 구성되며, 문자열, 숫자, 객체, 배열 등 다양한 타입을 표현할 수 있습니다.
*   **다중 포맷 지원 (XML과의 관계):**
    *   실제 데이터 통신 시 반드시 JSON만 사용할 필요는 없습니다. XML처럼 다른 형식도 가능합니다.
    *   여러 데이터를 처리하는 라이브러리(Converter)를 활용하여, 서버가 어떤 형태로 변환할지 명시적으로 지정해줘야 합니다 (예: XML로 리턴하고 싶다면 관련 라이브러리 의존성을 추가).
*   **응답 포맷 제어:**
    *   서버 측에서 응답 형태를 결정하는 방법은 여러 가지가 있습니다.
        *   `@RequestMapping` 등의 어노테이션을 이용해 `consumes` (요청 예상 형식)와 `produces` (응답할 형식) 속성을 지정합니다.
        *   **Accept 헤더 활용:** 클라이언트(사용자)가 요청 시 HTTP 헤더의 `Accept` 값을 통해 "나는 XML 형태로 응답받고 싶다"와 같이 원하는 포맷을 알려줄 수 있으며, 서버는 이에 맞춰 유연하게 응답 형식을 바꿔 제공할 수 있습니다.

## 3. HTTP 응답 제어: `ResponseEntity` 활용 방법
*   **문제 인식:** 기존의 API 개발 방식은 주로 데이터를 보내는 것(Body)에만 초점을 맞추었기 때문에, 데이터가 없거나 요청이 잘못되었을 때 어떤 상태 코드를 돌려줄지까지 명확하게 제어하기 어려웠습니다.
*   **`ResponseEntity`의 역할 (응답 전체 제어):**
    *   `ResponseEntity<T>`는 단순히 응답할 데이터(Body)만 보내는 것이 아니라, **HTTP 응답을 구성하는 모든 요소**를 객체로 감싸서 반환하게 해주는 클래스입니다.
    *   이를 통해 개발자는 API의 상태 코드(`Status Code`), HTTP 헤더(`Headers`), 그리고 실제 본문(Body) 내용을 종합적으로 제어할 수 있게 됩니다.
*   **구현을 통한 효과:**
    1.  **상태 코드 명시적 반환:** 데이터가 없는 경우, 기본값인 200 OK를 사용할 필요 없이 `HttpStatus.NOT_FOUND` (404)와 같이 요청의 상황에 맞는 정확한 HTTP 상태 코드를 지정하여 보낼 수 있습니다.
    2.  **정확하고 상세한 약속 제공:** 클라이언트가 정보를 요청했을 때, 단순히 "실패했습니다"가 아니라 "ID 값이 유효하지 않습니다(Bad Request)" 또는 "권한이 없습니다(Unauthorized)"와 같이 **구체적이고 디테일하게 오류의 원인과 상태를 알려줄 수 있습니다.**
*   **요약:** `ResponseEntity` 사용은 REST API의 목적(정보 제공 및 약속)을 가장 완벽하게 구현하는 방법이며, 클라이언트에게 더 명확하고 신뢰성 높은 상호작용 경험을 제공합니다.

## 1. 메모 CRUD API 설계 및 구현 준비
- **개념적 준비:** 실제 데이터베이스 사용 전, `Map` 자료구조를 임시 저장소로 사용하여 데이터를 관리하는 컨트롤러를 설계했습니다. (Key: Long 타입 ID, Value: String 메모 내용)
- **ID 자동 생성:** 데이터가 추가될 때마다 고유한 ID를 자동으로 할당하기 위해 `AtomicLong` 클래스를 활용합니다. 이는 각 데이터 타입별로 안전하게 카운터를 증가시키고 다음 번호를 가져올 수 있게 합니다.
- **CRUD 정의 및 흐름 설계:** 메모(Memo) 데이터를 이용해 가장 기본적인 CRUD (Create, Read, Update, Delete) 기능을 구현하는 목표를 설정하고 API 엔드포인트 구조(`GET /api/memos`, `POST /api/memos/{id}` 등)를 계획했습니다.

## 2. GET, POST를 이용한 데이터 조회 및 생성 (Read & Create)
- **메모 전체 리스트 조회 (READ):**
    - HTTP 메서드: `GET`
    - 경로: `/api/memos`
    - 기능: 저장된 모든 메모 항목을 목록 형태로 반환합니다.
- **ID 기반 단일 메모 조회 (READ):**
    - 패턴: `@GetMapping("/api/memos/{id}")`와 같이 `@PathVariable`을 사용하여 URL 파라미터로 ID를 받습니다.
    - 데이터 처리: `Map.get()` 메서드를 사용해 해당 ID의 메모를 가져옵니다.
    - 예외 처리를 위해 `Optional` 또는 `Default` 패턴을 사용하여 ID가 존재하지 않을 경우를 대비한 로직도 적용했습니다.
- **메모 생성 (CREATE):**
    - HTTP 메서드: `POST`
    - 경로: `/api/memos`
    - 데이터 전달: 전송할 메모 내용을 `@RequestBody`를 통해 JSON 형태로 받아옵니다.
    - 결과 처리: 새롭게 저장된 객체(DTO 또는 엔티티)의 ID 값을 반환하며, 이 과정을 테스트했습니다.

## 3. PUT, DELETE를 이용한 데이터 수정 및 삭제 (Update & Delete)
- **메모 수정 (UPDATE):**
    - HTTP 메서드: `PUT`
    - 경로: `/api/memos/{id}`
    - 처리 과정: ID와 함께 수정할 새 메모 내용을 요청 바디(`@RequestBody`)로 받습니다. 실제로 수정을 진행하기 전, 해당 ID가 맵에 존재하는지 먼저 확인하는 로직(예: `containsKey()`)이 필요합니다.
    - 실행: 존재 여부를 확인한 후, `Map.put()` 메서드를 사용하여 기존 데이터를 새로운 값으로 덮어씁니다.
- **메모 삭제 (DELETE):**
    - HTTP 메서드: `DELETE`
    - 경로: `/api/memos/{id}`
    - 처리 과정: ID를 파라미터로 받아 해당 메모의 존재 여부를 확인합니다.
    - 실행: 맵의 `remove()` 기능을 사용하여 데이터를 삭제하고, 성공 및 실패(예외) 메시지를 반환할 수 있습니다.

## 4. 아키텍처 패턴 이해: DTO와 엔티티의 역할
- **데이터 전달 객체 (DTO/Domain):** 애플리케이션 계층을 거쳐 값을 임시로 담아 전달하는 목적이 주된 역할을 합니다. 컨트롤러에서 서비스, 서비스에서 리포지토리 등으로 데이터를 넘겨줄 때 사용합니다.
- **JPA 엔티티 (@Entity):** 데이터베이스의 구조(테이블 스키마)를 반영하여 정의된 객체입니다. JPA가 이 클래스를 인식하고 실제로 데이터 저장 및 조회를 담당할 수 있게 하려면 반드시 `@Entity` 같은 어노테이션이 붙어 있어야 합니다.
- **레이어 간 분리의 중요성:**
    - 만약 모든 레이어에서 엔티티(DB 구조)를 직접 사용하게 되면, 컨트롤러와 같이 비즈니스 로직 계층에 JPA 관련 종속성까지 가져오게 됩니다.
    - 프로젝트가 커지거나 모듈이 분리될 경우 (예: 다른 API 서비스와의 연동), 특정 레이어(컨트롤러 등)가 데이터베이스 접근 방식(JPA)에 종속되는 문제가 발생할 수 있습니다.
    - 따라서 **DTO를 사용하여 데이터를 전달하는 것**은, 각 계층이 서로의 구현 상세(Persistence 관련 기술 등)로부터 독립적으로 작용하도록 돕는 중요한 분리 원칙입니다.

## 1. 데이터 전송 객체(DTO)와 엔티티 분리 전략
*   **DTO (Data Transfer Object)의 정의:**
    *   데이터를 담아서 계층(Layer: Controller $\to$ Service $\to$ Repository 등) 간에 전달하는 역할을 하는 단순한 객체입니다.
    *   `Value Object`로도 불립니다. (값을 담는다는 공통점 때문)
*   **DTO와 Entity의 관계 및 문제점:**
    *   Entity 역시 데이터를 담는 객체이므로, DTO와 역할이 유사하게 보일 수 있습니다.
    *   하지만 JPA를 사용할 때 엔티티에 `@Entity` 등의 어노테이션을 붙이면, 해당 라이브러리(JPA)에 강하게 종속됩니다.
    *   **문제:** 컨트롤러처럼 데이터 전송의 주 목적만 있는 레이어까지 Entity 객체를 가져다 사용하면, 컨트롤러 코드까지 JPA 라이브러리에 불필요하게 종속되는 문제가 발생합니다.
*   **객체 분리 전략 (권장 사항):**
    *   구조가 복잡해지거나 규모가 커질 경우, 역할에 따라 DTO와 도메인/엔티티를 명확히 분리하는 것이 좋습니다.
    *   **사용 원칙:** 클라이언트로부터 받는 입력 값이나 API 응답(출력)을 위한 객체는 **DTO**를 사용하고, 데이터베이스의 구조와 지속성 관련 로직은 **Entity**에 남겨두어 관심사 분리를 달성합니다.
    *   **장점:** 각 객체의 역할을 명확히 구분하여 시스템의 모듈성과 유지보수성을 높입니다.

## 2. 도메인 객체를 활용한 REST API 구현 실습
*   **개념 적용의 실습:**
    *   기존에 간단하게 String 타입을 이용해 데이터를 처리했던 코드를, 실제 도메인을 나타내는 `Memo`와 같은 **도메인 클래스(객체)**를 사용하도록 리팩토링하는 과정을 수행했습니다.
    *   이를 통해 문자열처럼 단순한 값을 다루는 것보다 객체를 사용했을 때의 확장성과 안전성을 이해할 수 있습니다.
*   **API 구현 흐름:**
    *   요청을 받는 엔드포인트(`Controller`)에서는 DTO를 활용하여 입력값을 받습니다.
    *   서비스 레이어에서는 이 DTO에 담긴 값들을 이용하여 실제 도메인 객체(Entity)로 변환하고 비즈니스 로직을 수행합니다.
    *   이 과정은 DTO $\to$ Entity $\to$ (응답 시 다시) DTO 형태로 데이터가 흘러가며, 관심사 분리가 이루어집니다.

## 3. cURL을 이용한 외부 API 테스트 방법론
*   **테스트의 중요성:**
    *   프런트엔드(그래픽 UI) 없이도 RESTful API 엔드포인트에 접근하고 기능을 검증할 수 있는 강력한 도구가 바로 `cURL`입니다. (Mac/Linux에 기본 설치되어 있으며, Windows에서도 별도 설치 가능합니다.)
*   **기본 테스트 원리:**
    *   가장 기본적인 GET 요청은 URL만 입력하여 테스트할 수 있습니다.
    *   API의 기능을 깊이 있게 검증하려면 다양한 옵션을 활용해야 합니다.
*   **핵심 cURL 사용 옵션 및 활용:**
    *   **헤더(Header) 및 데이터 전송 명시:** 단순히 데이터를 보내는 것을 넘어, `Content-Type` 등의 헤더 정보를 지정하고 API에 어떤 형태로 데이터를 넣을지 사전에 알려줘야 합니다. (`-H` 옵션 사용)
    *   **메서드 지정:** POST처럼 특정 HTTP 메서드를 사용할 때는 반드시 해당 옵션을 명시해야 합니다. (`-X [POST/PUT 등]`)
    *   **데이터 바디 전송:** 실제 데이터를 포함하여 보낼 경우, JSON 형식 등으로 작성한 본문 데이터가 필요합니다. (예: `-d` 또는 `--data` 사용)
    *   **장점:** cURL을 활용하면 인증 처리(Security), 특정 HTTP 메서드 호출 등 복잡한 시나리오를 코드 구현 없이 빠르고 정확하게 테스트할 수 있습니다.
