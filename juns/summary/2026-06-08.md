# 강의 요약

## 목차
1. JPA 도입 배경 및 발전 과정 이해
2. ORM과 객체-관계 모델의 차이점
3. 엔티티와 영속성 컨텍스트 개념
4. 연관 관계 매핑 상세 이해 (Association Mapping)
5. 엔티티 라이프사이클 제어 옵션 및 성능 최적화

---

## 1. JPA 도입 배경 및 발전 과정 이해
- **데이터 관리의 필요성:** 소프트웨어가 동작하는 과정에서 발생하는 데이터는 반드시 변수에 담기거나 시스템에 저장되어야 합니다. 데이터를 효율적으로 관리하기 위해 DBMS(데이터베이스 관리 시스템)가 사용됩니다.
- **기술 스택의 진화:**
    - 초기에는 DBMS와 연결하고 데이터를 조작할 때 **JDBC** 기술을 직접 사용해야 했으며, 이는 코드가 복잡하고 구현할 부분이 매우 많았습니다.
    - 이러한 어려움을 해결하기 위해 **MyBatis**나 **Spring Data JPA** 같은 프레임워크가 등장했습니다. 이들은 개발자가 핵심적인 부분(SQL 쿼리 정의 및 값 바인딩)만 알려주면 나머지 코드들을 자동으로 처리해 주었습니다.
    - **JPA (Java Persistence API)**는 여기서 한 단계 더 나아가, 객체와 관계형 데이터베이스 간의 *관계* 정보만을 알려주면 복잡한 쿼리와 매핑 과정까지 알아서 처리할 수 있는 표준 기술입니다.

## 2. ORM과 객체-관계 모델의 차이점
- **ORM (Object Relational Mapping):** 가장 핵심적인 개념으로, 객체 지향 모델(Java 객체)과 관계형 데이터베이스 간의 이질성(불일치)을 해결하는 기술입니다.
- **문제 정의:** 전통적으로 객체는 개체의 자체를 포함할 수 있는 반면, 관계형 DB는 주로 `외래 키(Foreign Key)`라는 제약 조건을 이용해 테이블 간의 관계를 표현합니다.
- **ORM의 필요성:** ORM은 이 두 가지 설계 방식의 차이점(객체 지향 vs 관계형)을 메우기 위해 등장했습니다.

## 3. 엔티티와 영속성 컨텍스트 개념
- **엔티티 (Entity):** 객체가 데이터베이스 테이블과 실제 개체의 관계를 나타내도록 표현한 것입니다. JPA에서는 `@Entity` 어노테이션을 사용하여 이 클래스가 DB의 한 테이블에 대응함을 명시합니다.
- **영속성 컨텍스트 (Persistence Context, NTC):** 트랜잭션이 시작되는 순간부터 종료될 때까지 해당 트랜잭션 내에서 관리되는 데이터들의 개념입니다. JPA는 이 영속성 컨텍스트를 통해 객체의 상태 변화(추가/수정/삭제)를 추적하며 DB에 반영합니다.
- **핵심 역할:** 이 컨텍스트 덕분에 개발자는 매번 데이터를 저장하고 읽어오는 과정을 명시적으로 할 필요 없이, 마치 메모리 상의 객체를 다루듯이 작업할 수 있습니다.

## 4. 연관 관계 매핑 상세 이해 (Association Mapping)
- **연관 관계의 표현 방식:** 관계형 DB는 외래 키를 통한 제약조건으로 관계를 정의하지만, JPA에서는 오직 '객체(Object)' 간의 관계로 처리합니다.
- **카디널리티(Cardinality) 종류 (4가지):** 엔티티 간의 연관 관계를 설정할 때 다음 4가지 유형 중 하나로 지정해야 합니다.
    *   일대일 (One-to-One, @OneToOne)
    *   일대다 (One-to-Many, @OneToMany)
    *   다대일 (Many-to-One, @ManyToOne)
    *   다대다 (Many-to-Many, @ManyToMany)
- **관계의 주인(Owner):** 연관 관계가 성립할 때, 실제 외래 키 값을 가지고 있는 쪽을 '관계의 주체'라 부르며 이쪽에 매핑 설정이 필수입니다.
    *   관계의 주인이 되는 측에는 `@JoinColumn` 등을 사용하여 데이터베이스 컬럼 이름을 명확히 지정해야 합니다.
    *   관계의 주인이 아닌 반대쪽(예: `@OneToMany`)은 `mappedBy`를 사용해 관계를 맺는 필드의 이름을 지정합니다.

## 5. 엔티티 라이프사이클 제어 옵션 및 성능 최적화
- **캐스케이드 (Cascade):** 부모 객체의 생명주기가 변경될 때(저장, 삭제 등) 연관된 자식 엔티티의 상태도 함께 처리할지 결정하는 옵션입니다.
    *   `PERSIST`: 저장 시 같이 저장합니다.
    *   `REMOVE`: 삭제 시 같이 삭제합니다.
    *   `ALL`: 모든 생명주기 이벤트에서 함께 적용됩니다.
- **고아 객체 (Orphan Removal):** 연관 관계가 끊어진 엔티티에 대해, 이 고아 객체가 발견되었을 때 자동으로 함께 삭제할지 여부를 지정하는 옵션입니다.
- **지연 로딩 vs 즉시 로딩 (FetchType):** 연관 데이터를 언제 가져올 것인가를 결정합니다. 이는 애플리케이션의 성능 최적화와 직결됩니다.
    *   **LAZY (Lazy Loading, 기본값):** 필요할 때(사용할 시점) 관련 데이터를 불러옵니다. 리스트 목록 조회처럼 모든 데이터를 당장 불러오지 않아 성능 부하가 적습니다. (권장됨)
    *   **EAGER (Eager Loading):** 엔티티를 조회하는 즉시 관련된 데이터도 모두 가져옵니다. 필요한 경우 사용하지만, 과도하게 사용할 경우 불필요한 네트워크 트래픽과 성능 저하를 초래할 수 있습니다.

- **N+1 문제와 해결:**
    *   데이터베이스에서 N개의 엔티티 목록을 조회할 때마다 관련 데이터를 추가로 조회하는(쿼리가 반복되는) 문제가 발생합니다 (N+1 문제).
    *   **해결 방법:** `@Query`를 사용하거나 `JOIN FETCH` 구문을 사용하여 관련된 모든 데이터를 한 번의 쿼리로 가져오는 것이 가장 효율적입니다.

- **다대다 관계 구현:**
    *   관계형 DB에서 다대다 관계는 반드시 '중간 테이블(Join Table)'을 생성하여 매핑해야 합니다. JPA에서도 이 중간 엔티티를 통해 연관 관계가 이루어집니다.

4. 영속성 컨텍스트를 활용한 CRUD 작업 흐름 관리

---

## 1. 엔티티 설계 및 명명 규칙 (Naming Convention) 확립의 중요성
- **기본 요소 정의:** 애플리케이션 초기 단계에서는 기본적인 엔티티(`Employee`, `Project`)와 식별자(`Id`)가 필수적으로 요구됩니다.
- **규칙 준수:** 개발 프로젝트를 시작할 때 팀 내부에서 정해진 표준(Naming Convention) 규칙이 존재하며, 이를 반드시 파악하고 지키는 것이 중요합니다.
- **Case 활용:** 테이블 이름이나 필드명에 대문자를 사용할지 소문자를 사용할지에 대한 관례가 있습니다. (과거에는 대문자 사용을 선호하는 경향이 강했으나, 최근에는 편의성을 위해 소문자를 사용하는 추세)

## 2. 다대다(Many-to-Many) 관계 매핑 이해하기
- **관계 모델링:** 사원(Employee)과 프로젝트(Project)처럼 두 엔티티가 서로 직접적인 기본 키 관계를 가지지 않는 경우, 이 둘의 연결을 위한 관계 테이블이 필요합니다.
- **매핑 방법론:** JPA에서 다대다 관계는 중간 매개 역할을 하는 조인 테이블(Join Table) 개념으로 모델링하며, `@ManyToMany` 어노테이션 등을 사용하여 구현합니다.
- **관계 주인 설정:** 두 엔티티 중 한쪽을 '관계의 주인(Owner)'으로 지정해야 합니다. 나머지 쪽은 해당 주인을 따라가는 방식으로 매핑됩니다 (양방향 관계).
- **기술적 설정:** `<JoinTable>` 등의 설정을 통해 중간 테이블의 이름, 그리고 양쪽 엔티티의 어느 필드를 조인 컬럼으로 사용할지 명시해 줍니다.

## 3. JPA 구현 시 고려 사항과 순환 참조 처리 (Pitfalls)
- **관계 매핑 완성도:** 다대다 관계를 정의할 때는 반드시 두 방향 모두에서 적절하게 `@OneToMany`나 관계 필드를 추가해야 합니다. 단순히 주 엔티티에만 매핑하면 데이터 무결성에 문제가 발생합니다.
- **순환 참조(Circular Dependency) 주의:** 엔티티가 서로의 리스트를 포함하는 구조(`Employee`가 `Project` 리스트, `Project`가 `Employee` 리스트 등)일 때, 해당 엔티티에 `toString()`과 같은 메서드를 구현하면 무한 루프에 빠져 시스템 오류(StackOverflowError 등)를 발생시킬 수 있습니다.
- **해결책:** 불필요하거나 위험할 수 있는 메서드(`toString()`)는 따로 커스텀 로직을 포함하는 별도의 메서드를 만들어 활용하는 것이 안전합니다.

## 4. 영속성 컨텍스트를 활용한 CRUD 작업 흐름 관리
- **트랜잭션 범위 필수:** 데이터베이스 작업을 수행할 때는 반드시 `@Transactional`과 같은 트랜잭션 처리가 이루어져야 합니다.
- **연관 관계 처리의 중요성:** 엔티티 A와 B가 다대다로 연결되어 있을 때, 단순히 A만 저장한다고 해서 자동으로 B와의 연결까지 완료되지 않습니다. 따라서 데이터를 저장하거나 수정할 때는 관련된 *모든* 필드(예: `Employee` 객체에 `Project`를 추가)를 수동으로 설정한 후 함께 영속화해야 합니다.
- **트랜잭션 경계 이해:** 트랜잭션이 커밋되면 연결된 모든 데이터가 DB에 반영되지만, 새롭게 생성된 엔티티는 별도의 과정을 거쳐야 완전히 영속성 컨텍스트와 관계를 맺습니다 (지연 로딩/즉시 로딩 동작 이해).

## 5. 비즈니스 로직 보호: 편의 메서드(Convenience Method) 도입
- **문제 제기:** 다대다 양방향 관계를 직접 코드로 관리할 때, 누락되는 부분이 생기거나 일관성이 깨지기 쉽습니다 (예: `A`에 연결만 했는데, `B` 쪽 리스트 업데이트를 잊는 경우).
- **편의 메서드의 역할:** 이러한 복잡하고 반복적인 연관 관계 설정 및 업데이트/삭제 로직을 하나의 전용 메서드(Convenience Method)로 캡슐화합니다.
- **효율성 증대:** 예를 들어, `employee.addProject(project)`라는 메서드를 만들어 사용하면, 이 단일 호출 안에서 A와 B 양쪽 엔티티의 리스트에 연결 및 업데이트 처리를 일괄적으로 수행하므로 코드가 간결해지고 비즈니스 로직 오류를 방지할 수 있습니다.
- **권장 사항:** 복잡한 연관 관계가 포함된 모든 핵심 엔티티에는 이러한 편의 메서드를 추가하여 사용함으로써 코드의 안정성과 가독성을 높이는 것이 좋습니다.

---

## 1. 데이터 업데이트 및 삭제 시 고려사항 (CRUD 연관 관계 관리)
- **업데이트(Update) 처리:** 특정 엔티티 정보를 수정할 때, 반드시 기존 데이터를 먼저 조회(Find)하여 현재 상태를 확인하는 과정이 필요하다.
- **삭제(Delete)와 관계 무결성:** 한 엔티티를 삭제할 경우, 해당 엔티티와 연결된 다른 테이블이나 관계 정보들(예: 사원과 프로젝트의 관계)도 함께 삭제되도록 관리해야 한다. (Cascade Delete 고려)

## 2. JPA를 활용한 엔티티 간의 관계 설정: 1대1 매핑 심화
- **관계 타입 검토:** 연관 관계 설정을 진행하며, 중간 테이블을 포함하는 N:M 관계 외에도 1대1(OneToOne) 관계가 존재함을 확인한다.
- **1대1 매핑 예시 (Person $\leftrightarrow$ Passport):** '사람'과 '여권'처럼 일대일로 연결되는 엔티티를 설정할 경우, 다음과 같은 핵심 고려 사항이 있다.
    *   **주인(Owner) 결정:** 두 엔티티 중 어느 쪽이 관계의 주인(Foreign Key를 소유하는 측)이 될지 명확히 결정해야 한다. (예: 여권 테이블이 사람 정보를 참조하며 주인이 됨).
    *   **유니크 제약조건 추가:** 만약 한 사람이 다른 여러 장의 여권을 가질 수 없도록 제한하려면, 관계가 주인인 컬럼에 `Unique` 제약 조건을 필수로 추가해야 한다. (`@Column(unique = true)`)

## 3. 객체 일관성 유지와 코드 패턴 적용 (양방향 매핑과 편의 메서드)
- **JPA 매핑 어노테이션 활용:**
    *   **컬럼 이름 별칭 지정:** 실제 데이터베이스 컬럼명과 Java 클래스 필드명이 다를 경우, `@Column` 애너테이션을 사용하여 DB 컬럼명을 정확하게 매핑해주는 것이 중요하다.
    *   **널 값 포함 여부 설정:** 특정 컬럼이 반드시 값을 가져야 할 때 (Non-Null) 유효성 검사 설정을 추가하는 것을 고려해야 한다.
- **양방향 연관 관계의 일관성 유지:**
    *   엔티티 간의 연관 관계(Bi-directional Mapping)를 설정할 때는, 양쪽 엔티티 모두에서 해당 관계 필드를 포함하여 매핑해야 한다 (예: `Person`과 `Passport` 둘 다 서로를 참조).
    *   **데이터 일관성 유지 원칙:** 한쪽에만 정보를 넣어주면 JPA가 데이터 무결성을 제대로 유지하지 못할 수 있으므로, 양쪽 모두에서 연관 관계 정보가 누락되지 않도록 관리해야 한다.
- **편의 메서드(Utility Methods) 사용:**
    *   엔티티 간에 복잡한 연관 관계를 설정하고 데이터를 저장하는 과정은 매번 반복적이고 오류가 발생하기 쉽다.
    *   이러한 상황을 개선하기 위해, 엔티티 클래스 내부에 **`setPassport()`** 와 같이 양방향 연관 설정을 한 번에 처리할 수 있는 편의 메서드(Utility Method)를 구현하는 것이 효율적이다. (예: 이 메서드 하나로 어느 쪽만 정보를 설정해도 반대편까지 자동으로 업데이트되게 만듦).

## 1. JPA의 연관 관계 매핑 및 주도권 이해 (Relationship Mapping & Ownership)
- **관계의 종류:** 엔티티 간에는 일대일(One to One), 일대다(One to Many), 다대일(Many to One), 다대다(Many to Many) 등 다양한 카디널리티로 관계를 매핑할 수 있다.
- **정규화와 테이블 설계:** 실제로 여러 정보를 하나의 테이블에 모두 저장하는 것은 비효율적(불필요한 공간 발생)이므로, DBMS는 정규화 과정을 거쳐 적절하게 테이블을 분리하고 이들 간의 관계를 정의해야 한다.
- **관계 매핑 메커니즘:** JPA에서는 이러한 테이블 간의 관계를 `@OneToOne`, `@OneToMany` 등의 어노테이션으로 표현한다.
- **컬럼 및 이름 설정:** 데이터베이스 컬럼명과 엔티티 필드명이 다를 경우, `@Column` 애너테이션을 사용하여 이를 매핑할 수 있다.
- **관계의 주인 (Owner):** 연관 관계에서 '주인'은 영속성 컨텍스트에 변경을 반영하는 책임을 가지는 쪽이다. 주로 외래 키(Foreign Key) 값을 가지고 있는 쪽이 주인이 되며, 이를 이해하고 코드를 작성해야 한다.

## 2. 연관 관계 처리를 위한 설계 패턴 및 주의사항
- **편의성 메서드 (Convenience Method):** 엔티티에 `save()`와 같은 비즈니스 로직을 수행하는 편의성 메서드를 제공하는 것이 좋다.
    - 예시: `Person` 엔티티에 패스포트를 추가할 때, 단순히 `person`에만 값을 넣는 것이 아니라 **패스포트에도 해당 `person` 정보가 들어가도록** 처리해주는 로직(예: 양방향 참조 설정)을 메서드 내에 캡슐화하면 사용자가 코드를 작성할 때 일관성 있게 사용할 수 있어 편의성을 높인다.
- **캐스케이드 옵션 (Cascade Type):** 특정 엔티티가 삭제되거나 수정될 때 연관된 다른 엔티티도 함께 처리(예: `PERSIST`, `REMOVE`)하도록 옵션을 지정하여 데이터 무결성을 유지한다.

## 3. 지연 로딩과 순환 참조 문제 해결 방안 (Performance & Cyclic Dependencies)
- **양방향 매핑의 위험성:** 객체지향적으로는 엔티티 A가 B를 알고, B도 A를 아는 양방향 관계가 자연스러우나, JPA의 동작 시점에서는 몇 가지 문제가 발생할 수 있다.
    - **문제 1: 지연 로딩 (Lazy Loading) 문제:** 주로 주인이 아닌 쪽(비주인 측)에서 데이터를 조회하는 과정에서 지연 로딩 방식이 제대로 작동하지 않거나 예상치 못한 오류를 일으킬 수 있다.
    - **문제 2: 순환 참조 및 스택 오버플로우:** 엔티티 간에 양방향의 관계 필드를 모두 포함하고 있을 때, 프레임워크가 객체를 초기화하거나 `toString()` 메서드를 호출할 경우(특히 List 같은 컬렉션에서) 무한히 서로를 참조하며 데이터를 채우려고 시도한다.
        - **결과:** 이 과정이 반복되어 결국 `StackOverflowError`와 같은 오류를 발생시킬 수 있다.
    - **해결 방안:**
        *   필요한 정보만 명확하게 접근하도록 관계 설계를 신중히 해야 한다 (양방향 참조 모두가 꼭 필요한지 판단).
        *   엔티티의 `toString()` 메서드 등에서 연관 관계 필드를 직접 사용하지 않고, 관련 내용을 제외하고 사용자 정의 형태로 처리하는 것이 좋다.

## 4. 상속(Inheritance) 전략 설계하기 (Advanced JPA Topics)
- **개념:** 객체 지향적 특징 중 하나인 상속 개념을 데이터베이스 테이블 구조로 매핑하는 방식이다. 공통 속성을 가진 부모 클래스(`Vehicle`)와 이를 상속받은 자식 클래스들(`Truck`, `Bus`, `SportsCar`)이 존재할 때, 이들을 테이블로 어떻게 설계할지 결정해야 한다.
- **세 가지 주요 전략:** JPA는 상속 관계를 매핑하는 세 가지 방법을 제공한다.
    1. **싱글 테이블 전략 (Single Table):**
        *   모든 부모와 자식 엔티티의 컬럼을 하나의 거대한 테이블에 모두 담는다.
        *   공통 속성을 위해 `type` 등의 구분 필드를 반드시 추가해야 한다.
        *   (장점) 조회 시 성능이 빠를 수 있다. (단점) 데이터가 적은 클래스까지도 빈 값(NULL)을 가지게 되어 테이블 구조가 비효율적일 수 있다.
    2. **Joined Table 전략:**
        *   부모 엔티티는 공통 속성을 저장하는 기본 테이블을 갖는다.
        *   각 자식 엔티티는 자신만의 고유한 추가 속성만을 가진 별도의 테이블을 둔다.
        *   자식 테이블은 부모 테이블의 Primary Key를 Foreign Key로 참조한다.
        *   (특징) 데이터가 적절히 분리되어 정규화에 유리하다. (단점) 데이터를 조회할 때 여러 테이블을 조인해야 하므로 성능 오버헤드가 발생할 수 있다.
    3. **테이블 퍼 클래스 전략 (Table Per Class):**
        *   각 엔티티(부모, 자식 포함 모든 클래스)가 독립적인 자체 테이블을 갖는다.
        *   상속 관계의 정보를 관리하기 어렵고 조회 시 데이터가 분산되어 효율성이 떨어질 수 있다.

- **결정 기준:** 어느 전략이 '정답'은 없으며, 애플리케이션이 어떤 종류의 데이터를 주로 다루는지(데이터 크기, 트랜잭션 빈도 등)에 따라 가장 적합한 방식을 선택해야 한다.

## 1. JPA의 핵심: 상속 관계 매핑 전략
- **핵심 개념**: JPA는 객체 지향적 설계(상속 등)를 하는 엔티티와 관계형 데이터베이스 테이블 사이의 매핑 방식을 정의하는 것이 핵심입니다.
- **상속 적용**: 부모 클래스부터 자식 클래스로 이어지는 상속 구조의 엔티티들을 어떻게 단일한 테이블 혹은 여러 개의 테이블로 저장할지 결정해야 합니다.
- **전략적 고민**: 상속 관계가 복잡해질 때, 데이터를 하나의 거대한 테이블에 담을지(Single Table), 아니면 각자의 역할에 맞는 개별 테이블로 분리할지(Joined/Per Class) 등 다양한 구조적 설정을 고려하게 됩니다.

## 2. 객체와 데이터베이스 상속 매핑 3가지 전략 비교
상속된 엔티티를 DB 테이블로 구현하는 세 가지 주요 전략이 존재합니다.

### A. Single Table 전략 (단일 테이블 전략)
- **개념**: 모든 상속 클래스의 속성(컬럼)을 하나의 거대한 테이블에 통합하여 관리합니다.
- **구현 방식**: 부모 엔티티가 가진 공통 컬럼들과, 자식 엔티티들이 가지고 있는 개별 컬럼들을 모두 포함하는 단일 테이블이 생성됩니다. (예: `TYPE`이라는 필드를 추가하여 어떤 종류의 차량인지 구분).
- **장점**: 데이터 조회(Read) 시 JOIN 작업이 필요 없어 가장 빠르고 간편합니다. 데이터를 하나의 쿼리로 가져올 수 있습니다.
- **단점**: 클래스가 많고 속성이 복잡해지면 테이블에 불필요한 `NULL` 값으로 채워진 공간(데이터 밀도 저하)이 발생할 수 있습니다.

### B. Joined Table 전략 (조인 테이블 전략)
- **개념**: 상속 구조를 이루는 각 엔티티마다 별도의 독립적인 테이블을 생성하고, 이들을 Primary Key와 Foreign Key로 연결(JOIN)하여 사용합니다.
- **구현 방식**: 부모 엔티티의 공통 속성들은 하나의 메인 테이블에 저장되고, 자식 엔티티의 고유 속성은 해당 자식 전용 테이블에 분리되어 저장됩니다. (예: `Car`와 `Truck`은 각자 테이블을 가지고 `Vehicle` 테이블과 연관 관계를 맺음).
- **장점**: 데이터 중복 없이 각 클래스별로 필요한 컬럼만 갖게 되어 정규화된 구조를 유지하기 좋습니다.
- **단점**: 데이터를 조회할 때마다 여러 테이블을 JOIN해야 하므로, Single Table 전략 대비 성능 오버헤드가 발생할 수 있습니다.

### C. Table Per Class 전략 (클래스당 테이블 전략)
- **개념**: 상속 관계의 구조를 고려하지 않고, 각 클래스를 독립적인 개별 엔티티로 취급하여 각각 별개의 테이블에 모두 저장하는 방식입니다.
- **구현 방식**: 부모 클래스가 가진 모든 컬럼(공통 정보)과 자식 클래스 고유의 컬럼을 포함한 완전한 형태의 테이블이 생성됩니다. (이 경우, 상위 클래스의 정보를 구현할 때도 필요하다면 그 정보를 중복하여 가져와야 합니다.)
- **장점**: 각 엔티티가 완벽하게 독립된 구조를 가집니다.
- **단점**: 공통 정보(부모의 속성)가 여러 테이블에 중복되어 저장될 위험이 있습니다.

## 3. Spring Data JPA란 무엇인가? (개념 및 장점)
- **도입 배경**: 순수한 JPA를 사용하면 데이터 접근 객체(DAO/Repository)와 관련된 반복적인 코드(Boilerplate Code), 예를 들어 기본적인 CRUD 메서드나 트랜잭션 관리를 개발자가 직접 작성해야 하는 비효율성이 있었습니다.
- **Spring Data JPA의 역할**: Spring 프레임워크가 JPA 위에 추가적인 추상화 레이어를 제공하여, 이러한 보일러플레이트 코드를 획기적으로 줄여주고 생산성을 높이는 프로젝트입니다.
- **핵심 장점**:
    *   **자동 구현 (Automatic Implementation)**: 인터페이스만 선언하면 기본적인 CRUD(Create, Read, Update, Delete) 기능이 자동으로 구현됩니다.
    *   **쿼리 메서드 기반 개발**: 메서드의 이름 규칙만으로 복잡한 JPQL 쿼리를 자동 생성할 수 있습니다. (예: `findByNameAndAgeGreaterThan()`).
    *   **편의성 및 안정성**: 스프링 프레임워크 위에서 동작하므로 트랜잭션 관리, JPA 환경 등과 완벽하게 통합되어 개발이 매우 간편합니다.

## 4. 실제 사용을 위한 구현 구조 및 설정
- **Repository 계층 구조**: Spring Data는 레거시 `Repository` 인터페이스를 기반으로 상속 구조를 제공합니다. (예: `JpaRepository`)
    *   $\text{Repository} \rightarrow \text{CrudRepository} \rightarrow \text{PagingAndSortingRepository} \rightarrow \mathbf{JpaRepository}$ 순서로 기능이 확장됩니다.
- **주요 사용법**: 개발자는 가장 상위의 `@Repository` 인터페이스를 상속받는 `JpaRepository`만을 사용해도 기본적으로 모든 기능을 사용할 수 있습니다. (실질적으로는 자식 클래스만 명시하여 원하는 기능만 가져다 씁니다.)
- **프로젝트 설정 필수 사항**: Spring Data JPA가 정상적으로 작동하기 위해서는 프로젝트 의존성(Dependency)에 다음과 같은 라이브러리를 반드시 추가해야 합니다:
    1.  `Spring Data JPA`
    2.  데이터베이스 드라이버 (예: MySQL Driver)
    3.  트랜잭션 및 기타 지원 모듈 (예: H2 Database Tools 등)
- **설정 작업**: `application.properties` 또는 `application.yml` 파일에 데이터베이스 연결 정보(Data Source URL, Username, Password, Driver Class 등)와 JPA 구현체 설정(`hibernate.hbm2ddl.auto`)을 명시적으로 정의해야 합니다.

## 1. 학습 목표: Spring Data JPA 이해하기
- **학습 목적:** 단순히 사용하는 것을 넘어, JPA가 내부적으로 어떻게 동작하는지 깊이 있게 이해하고 이를 Spring 환경에서 적용하는 것이 목표입니다.
- **접근 방식의 중요성:** 프레임워크에 감싸져 있어 내부 작동 원리를 들여다보기가 쉽지 않으므로, 직접 설정을 건드리며 동작 메커니즘을 파악합니다.

## 2. 프로젝트 준비 및 데이터 소스 설정
- **버전 관리 주의사항:** 현재 사용 중인 Spring Boot 버전(4.x)과 관련된 미지원 부분이 있을 수 있으므로, 학습의 안정성을 위해 이전 버전(3.x 등)으로 낮춰서 진행하는 것을 권장합니다.
- **데이터 소스 필수 설정:** JPA를 사용하여 데이터베이스에 접속하거나 데이터를 다룰 때 `application.yml` (또는 properties) 파일에 데이터소스 설정을 반드시 추가해야 합니다.
    - **주의사항:** YAML 설정의 경우 띄어쓰기, 들여쓰기 등의 사소한 오타나 공백 문제가 치명적으로 작용할 수 있으므로 세심한 확인이 필요합니다.

## 3. Spring Data JPA 속성 설정 심화
- `spring.jpa.*` 설정을 통해 하이버네이트(Hibernate)의 동작 방식을 제어하고 로깅 및 출력되는 정보를 제어합니다.
    - **`hibernate.ddl-auto`:** 엔티티 클래스를 기반으로 데이터베이스 스키마를 생성하는 옵션입니다. (`create`, `update` 등 사용 가능하며, 수업에서는 `update`를 주로 사용했습니다.)
    - **`show-sql`:** 실행되는 SQL 쿼리를 콘솔에 출력할지 여부를 결정합니다. (진단 및 학습 시 매우 유용)
    - **`spring.jpa.properties.*`:** 하이버네이트에게 추가적인 정보를 전달하는 속성들을 지정할 수 있습니다.

## 4. JPA 리포지토리와 Repository 패턴 이해
- **JPA의 추상화:** 개발자가 직접 `EntityManager` 등을 이용하여 복잡하게 데이터베이스 조작을 할 필요가 없습니다. Spring Data JPA를 이용하면 인터페이스만 정의해도 구현체가 자동으로 생성됩니다.
- **`JpaRepository` 활용:** 핵심은 특정 엔티티 타입(Entity)과 해당 엔티티의 기본 키 타입(Primary Key Type) 두 가지 정보를 지정하여 `CrudRepository` 또는 `PagingAndSortingRepository` 같은 상위 추상 클래스를 상속받는 것입니다.
    - **구현 방식:** 개발자는 리포지토리를 인터페이스로 정의하기만 하면, Spring이 이 인터페이스를 기반으로 데이터베이스 접근 로직을 가진 구현체(Bean)를 자동으로 생성해줍니다.

## 5. 엔티티 CRUD 작업 및 고급 조회 기능
- **엔티티(Entity) 정의:** `@Entity` 어노테이션을 사용하여 어떤 클래스가 데이터베이스 테이블에 매핑될지 지정합니다. (`@Id`, `@Column` 등을 활용하여 기본 키와 컬럼 설정을 합니다.)
- **데이터 저장 (Create):** 리포지토리에서 제공하는 `save(entity)` 메서드를 호출하면, JPA가 내부적으로 해당 엔티티를 영속성 컨텍스트에 등록하고 데이터베이스에 커밋합니다.
- **조회 기능의 확장:** 개발자가 직접 쿼리를 작성하지 않아도 다음과 같은 기능을 메소드 이름만으로 구현할 수 있습니다.
    - `findBy*`: 특정 컬럼 값을 이용한 조회 (예: `findUserByEmail(String email)`)
    - `findById`: 기본 키를 통해 엔티티 조회
    - **Pagination:** 페이지네이션 정보를 넣어 데이터를 가져올 수도 있으며 (`Pageable`), 필요시 조건절을 조합하여 사용할 수 있습니다.

## 6. Null 처리의 핵심, Optional 클래스 활용
- **문제 인식 (NPE 방지):** JPA가 데이터베이스에서 값을 조회할 때, 해당 값이 존재하지 않을 경우 일반적인 `null` 타입을 반환합니다. 이 `null` 값에 대해 메서드 호출(예: `user.getName()`)을 시도하면 `NullPointerException`이 발생합니다.
- **Optional의 역할:** Java API가 제공하는 `Optional<T>` 클래스는 값이 *있거나* 또는 *없음*을 명확하게 표현하기 위한 컨테이너입니다. 리포지토리 메서드들이 조회 결과를 `Optional` 타입으로 감싸서 반환해줍니다.
- **핵심 활용 방법:**
    - **`.orElse(대안값)`:** 값이 존재하지 않을 경우 (null일 경우) 우리가 지정한 기본값을 대신 사용합니다. (가장 일반적인 대체 처리 방식)
    - **`.ifPresent(추가로할동작)`:** 값이 있을 때만 특정 동작을 수행하고 싶을 때 사용합니다.
    - **`.orElseThrow()`:** 값이 없을 경우 예외(`Exception`)를 직접 발생시키고 싶을 때 사용합니다.

## 7. 서비스 레이어 구축 원칙과 아키텍처
- **책임 분리 (Architecture):** 비즈니스 로직(실제 업무 처리)은 리포지토리에서 분리하여 `Service` 클래스에 구현해야 합니다.
    - **Repository:** 단순히 데이터베이스 접근(CRUD)만 담당합니다.
    - **Service:** 데이터를 이용한 트랜잭션 관리, 복잡한 계산, 비즈니스 규칙 적용 등 핵심 로직을 처리합니다.
- **구현 방법:** 서비스 클래스 역시 `@Service` 어노테이션을 붙여 빈으로 등록하고, 필요한 리포지토리는 생성자(Constructor)를 통해 주입받아 사용하는 것이 권장됩니다 (의존성 주입).
