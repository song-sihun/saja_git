## 1. 학습 방법론 및 프로젝트 방향 설정

*   **학습의 중요성:** 지식을 수동적으로 듣기만 하는 것보다는 직접 코드로 구현하고 경험을 반복하는 과정(반복 학습)이 가장 중요하다.
*   **프로젝트 진행 원칙:**
    *   너무 크고 복잡한 주제를 설정하기보다는, 본인이 잘 알고 쉽다고 느끼는 작은 규모의 주제부터 시작하는 것이 좋다.
    *   작은 규모의 프로젝트를 반복적으로 진행하며 익숙해진 후 점차 규모를 늘려나가는 것이 포기하지 않고 학습하는 데 도움을 준다.
*   **학습 목표:** 이 과정의 궁극적인 목표는 수업에서 배우지 않은 기술이라도 스스로 학습하여 프로젝트에 적용할 수 있는 능력을 키우는 것이다.

## 2. 웹 애플리케이션 개발 흐름과 주요 기술 스택

*   **개발 목표:** 궁극적으로 요청이 들어왔을 때 화면(View)으로 응답하는 웹 애플리케이션을 만드는 것이 목표이다.
*   **기술 단계별 학습 로드맵:**
    *   **초기:** 스프링의 코어(Core) 개념을 먼저 학습한다.
    *   **데이터 접근:** 데이터베이스 접근을 위해 세 가지 주요 프레임워크를 알아야 한다.
        *   **JDBC:** 기본적인 자바 코드를 이용한 데이터 접근 방식.
        *   **MyBatis:** 프레임워크 중 하나로, 과거 국내 환경에서 점유율이 높았음.
        *   **JPA (Java Persistence API):** 객체와 관계형 데이터베이스를 매핑(ORM)하여, 객체 지향적으로 데이터를 처리하는 현대적인 방식.
    *   **프레임워크 활용:** 스프링은 **Spring Data**라는 프로젝트를 통해 JDBC와 JPA 등 외부 프레임워크들을 유사한 사용 방식으로 통합하여 사용할 수 있게 지원한다.
*   **응용 및 심화 학습:**
    *   **Web MVC:** 요청을 처리하고 응답하는 웹 구조를 학습한다.
    *   **Spring Security:** 애플리케이션의 인증(Authentication) 및 인가(Authorization) 기능을 구현하여 애플리케이션을 안전하게 만드는 가장 고급 단계의 기술이다.
    *   **학습 원리:** Spring Security처럼 복잡한 기술도 스프링 프레임워크가 대부분의 복잡한 로직(Default Logic)을 제공하므로, '약속(규칙)'에 따라 필요한 정보만 알려주면 된다는 관점으로 접근해야 한다.

## 3. 핵심 원리: 제어의 역전 (IOC) 이해

*   **IOC 정의 (Inversion of Control):**
    *   객체 생성 및 코드 실행의 '제어권'을 개발자(사용자)가 직접 갖는 것이 아니라, 스프링 프레임워크(컨테이너)에게 넘겨주는 개념이다.
*   **IOC의 장점:**
    *   **결합도(Coupling) 감소:** 사용되는 객체를 직접 생성하는 코드가 없어지므로, 사용 객체와 구체적인 구현체 간의 의존성(결합도)이 낮아진다.
    *   **유연성:** 실제 구현체가 교체되어도 사용자의 코드는 전혀 수정할 필요가 없다.
*   **작동 원리 (빈 관리):**
    *   애플리케이션에서 사용하는 객체(Bean)의 생성부터 소멸까지의 라이프사이클 관리를 컨테이너(스프링 컨테이너)에게 위임한다.
    *   **빈 등록 방법 (Bean 등록):** 컨테이너에게 어떤 빈을 관리하게 할지 알려줘야 한다.
        1.  **XML 파일:** `<bean>` 엘리먼트를 통해 빈을 정의.
        2.  **Java Config:** `@Bean` 어노테이션을 사용하여 Java 코드 레벨에서 빈을 설정.
        3.  **Component Scan:** `@ComponentScan`을 통해 지정된 패키지(Base Package)의 클래스를 스캔하여 자동으로 빈 등록을 시도.
*   **주입 방식 (Dependency Injection, DI):**
    *   필요한 객체(의존성)를 직접 찾거나(`Lookup`), 컨테이너가 필요한 시점에 넣어주는(Injection) 방식이다.
    *   **주입 방법:**
        1.  **생성자 주입 (Constructor Injection):** 생성자를 통해 의존성을 받는다. (가장 바람직한 방식)
        2.  **설정자 주입 (Setter Injection):** Setter 메서드를 통해 의존성을 받는다.
        3.  **필드 주입 (Field Injection):** 필드에 직접 주입하는 방식. (편리하지만, 스프링에 강하게 종속되므로 권장하지 않음)

## 4. 스프링 빈 관리 심화 및 아키텍처 패턴

*   **빈 생명주기 관리:** 컨테이너는 단순히 생성만 하는 것이 아니라, 빈이 사용되는 동안 필요한 시점에 작업을 수행할 수 있도록 관리한다.
    *   `@PostConstruct`: 빈이 초기화된 직후 실행되는 메서드.
    *   `@PreDestroy`: 빈이 소멸되기 직전에 실행되는 메서드.
*   **패키지 스캔 제어:**
    *   **Base Package:** 기본적으로 `@SpringBootApplication` 어노테이션이 붙은 위치를 기준으로 스캔이 시작된다.
    *   **기타 스캔:** `@ComponentScan` 등을 이용해 기본 패키지와 다른 외부 패키지까지 빈을 추가적으로 스캔할 수 있다.
*   **설정 환경 제어 (Profile):**
    *   애플리케이션의 실행 환경(개발 환경, 운영 환경, 테스트 환경 등)에 따라 다른 설정을 로드하여 동작하게 할 수 있다.
*   **통합 테스트 도구 (CommandLineRunner):**
    *   애플리케이션이 구동된 후, 빈들이 모두 세팅된 상태에서 테스트 코드를 실행하여 애플리케이션을 검증하는 데 사용되는 인터페이스.
*   **아키텍처 패턴 (Layered Architecture):**
    *   애플리케이션의 구조를 설계하는 방법론이다.
    *   **레이어 분리:** 데이터베이스 접근(Data Layer), 비즈니스 로직 처리(Service Layer), 사용자 인터페이스(View Layer) 등 각 기능별 역할을 분리하여 구조화하는 것이 가장 단순하면서도 가장 많이 사용되는 구조이다.

## 1. 어노테이션(Annotation)의 정의 및 이해
어노테이션은 특정 코드 요소(클래스, 필드, 메서드 등)에 **메타데이터(Metadata)**를 붙여서, 이 코드가 프레임워크나 다른 컴포넌트에 어떤 역할을 하거나 어떻게 동작해야 하는지 알려주는 표식입니다.

*   **어노테이션을 이해해야 하는 이유:** 단순히 사용법을 아는 것을 넘어, 이 어노테이션이 *실제로 어떻게* 동작하는지 그 메커니즘(Contract)을 이해하는 것이 중요합니다.
*   **핵심 정의 요소:**
    *   **`@Target`:** 해당 어노테이션을 코드의 어느 부분(클래스, 필드, 메서드, 생성자 등)에 사용할 수 있는지 범위를 지정합니다. (예: `@Controller`는 클래스 위에서만 사용 가능)
    *   **`@Retention`:** 해당 어노테이션이 언제까지 유지되어야 하는지(어디서 접근 가능한지)를 정의합니다.
        *   `@Retention(RetentionPolicy.SOURCE)`: 소스 코드 단계에서만 유지됨.
        *   `@Retention(RetentionPolicy.CLASS)`: 컴파일된 클래스 파일(.class)에 포함됨.
        *   `@Retention(RetentionPolicy.RUNTIME)`: **가장 중요.** 프로그램 실행 시점(런타임)에도 정보가 남아있어 프레임워크가 코드를 검사할 때 사용할 수 있습니다. (예: `@Autowired`)
*   **어노테이션의 역할 (약속):** 프레임워크는 어노테이션을 보고 "이 메서드는 어떤 일을 해야 한다", "이 필드는 반드시 값이 있어야 한다"와 같은 **약속(Contract)**을 인식하고 그에 따라 동작합니다.

## 2. 리플렉션(Reflection) 기술의 원리
리플렉션은 **실행 시간(Runtime)**에 프로그램의 구조적 정보(클래스, 메서드, 필드)를 읽어와 검사하거나 조작할 수 있는 자바의 기술입니다.

*   **기본 원리:** 개발자가 명시적으로 상속 관계를 만들지 않아도, 프레임워크는 리플렉션 기술을 이용해 객체의 내부 구조를 조사하고 원하는 기능을 구현합니다.
*   **주요 기능 및 사용법:**
    *   **`getClass()`:** 객체의 클래스 객체(Class object)를 얻어냅니다.
    *   **`getDeclaredMethod()`/`getDeclaredMethods()`:** 특정 이름이나 모든 메서드 목록을 포함하는 메서드 객체(Method object)를 얻어낼 수 있습니다. (클래스 내의 사적(private) 메서드 포함 가능)
    *   **`getConstructor()` / `getPrimaryConstructor()`:** 객체를 생성할 때 사용할 수 있는 생성자 객체(Constructor object)를 얻어냅니다.
    *   **접근 및 조작:** 리플렉션을 사용하면 `private` 접근 제한자 등에 관계없이 객체의 필드나 메서드에 접근하고 값을 설정하거나 호출할 수 있습니다.
*   **이점:** 프레임워크가 사용자의 클래스에 강하게 결합되지 않고도, **메타데이터를 기반으로 동적으로 동작**할 수 있게 만듭니다.

## 3. 프레임워크 작동 원리 이해 및 심화 응용
두 기술을 결합하면, 프레임워크는 훨씬 복잡하고 유연한 방식으로 코드를 제어할 수 있습니다.

*   **핵심 메커니즘:** 프레임워크는 리플렉션을 통해 객체와 메서드를 얻어내고, 그 객체들에서 **어노테이션의 존재 유무**를 확인합니다.
*   **동작 순서 (예시):**
    1.  Spring은 서비스 클래스 내의 모든 메서드(`getDeclaredMethods()`)를 리플렉션으로 가져옵니다.
    2.  각 메서드가 특정 어노테이션(예: `@Cacheable`)을 가지고 있는지 확인합니다. (`hasAnnotation()`)
    3.  어노테이션이 발견되면, 해당 어노테이션 객체로부터 필요한 값(`value`, `number` 등)을 추출합니다.
    4.  실제 **비즈니스 로직이 포함된 메서드**를 `invoke()` 메서드를 통해 실행시켜 줍니다.
*   **심화 응용:**
    *   **값 지정과 강제성:** 어노테이션 정의 시 기본값(`default`)을 설정하거나, 특정 값이 반드시 필요하도록 강제할 수 있습니다 (값이 없으면 오류 발생).
    *   **전체 실행 vs. 조건부 실행:** 전체 메서드를 순회하며 실행할 수도 있고, 특정 어노테이션이 붙은 메서드만 골라서 실행할 수도 있습니다.
*   **결론:** 어노테이션과 리플렉션은 마치 **'약속'**과 같습니다. 개발자는 이 약속(Annotation)만 잘 붙여주면, 프레임워크(Spring)가 내부적으로 복잡한 리플렉션 코드를 사용하여 마치 상속받은 것처럼 원하는 기능을 수행하게 됩니다.

## 1. 프레임워크의 동작 원리 이해 (Reflection & Annotation)
(시간대: 11:04:26 ~ 11:13:20)

*   **핵심 개념 이해에 집중:** 에노테이션(Annotation)이나 리플렉션(Reflection)과 같은 고급 기술들은 개발자가 직접 코드로 구현할 필요가 없습니다.
*   **원리 파악의 중요성:** 중요한 것은 이러한 기술들이 '어떻게 동작하는지' 그 원리와 개념을 이해하는 것입니다.
*   **Reflection의 역할:** 스프링 프레임워크 등이 동작하는 배경에는 리플렉션 기술이 사용됩니다. 이 기술을 통해 다음과 같은 것이 가능합니다.
    *   객체를 `new` 키워드 없이 생성하고 타입을 받아낼 수 있습니다.
    *   private 필드에 접근하여 값을 읽거나 수정할 수 있습니다.
    *   private 메서드를 얻어내고 강제로 실행(invoke)시킬 수 있습니다.
*   **학습 목표:** 직접 코드를 작성하는 것보다는, "이런 기술이 존재하며 이렇게 동작할 수 있구나"라는 수준의 상상력을 기르는 것이 중요합니다.

## 2. 시스템 아웃풋의 한계와 로깅의 필요성
(시간대: 11:13:25 ~ 11:20:20)

*   **System.out.println의 문제점:** 개발 과정에서 디버깅 목적으로 `System.out.println`을 사용하면 여러 문제가 발생합니다.
    *   **성능 저하:** 콘솔 출력은 시스템 자원을 많이 차지하여 애플리케이션의 성능을 저하시킬 수 있습니다.
    *   **배포의 위험:** 개발된 코드를 실제 운영 환경(고객사 납품 등)에 인계할 때, 디버그용 로그가 그대로 남아 품질 검사나 시스템 운영에 방해가 됩니다.
*   **로깅(Logging)의 등장:** 시스템의 동작 상태나 이벤트 정보를 기록하기 위해 전용 로깅 시스템을 사용해야 합니다.

## 3. 로깅 프레임워크의 핵심 기능과 장점
(시간대: 11:20:20 ~ 11:41:02)

## 1. 어노테이션(Annotation)의 이해 및 활용
어노테이션은 코드에 메타데이터(표식)를 붙이는 역할을 합니다. 개발자가 직접 구현하는 요소는 아니지만, 컴파일러나 프레임워크가 이 표식들을 읽어내어 특정 동작을 수행하게 만듭니다.

*   **역할:** 어노테이션 자체는 단순한 '표식(Marker)' 역할을 하며, 실제 중요한 것은 이 표식을 프레임워크가 어떻게 읽어와 일을 처리할지 정의하는 것입니다.
*   **작동 원리 (Spring Framework):** 스프링 프레임워크와 같은 프레임워크는 클래스 위에 붙은 어노테이션의 존재 여부와 그 값(Parameter)을 감지하여, 해당 객체를 어떻게 초기화하고 어떤 로직을 수행할지 스스로 처리합니다.
*   **기술적 배경:** 이러한 동작은 내부적으로 **리플렉션(Reflection)** 기술을 활용합니다.
    *   리플렉션은 객체에 직접 사용되는 것이 아니라, 뒷단에서 객체 내부 구조를 분석하고 조작할 수 있게 해주는 기술입니다.
*   **핵심 개념 (이용 vs 구현):** 개발자는 모든 내부 동작 원리를 알 필요는 없으며, 마치 세탁기를 사용하듯, 이미 잘 만들어진 객체(Spring이 제공하는 기능)를 어떻게 효과적으로 '이용'할지에 집중하는 것이 중요합니다.

## 2. 로깅(Logging) 시스템의 필요성과 표준 구조
로그를 남기는 것은 시스템의 동작 과정을 추적하고, 문제를 진단하며, 비즈니스 분석 자료로 활용하는 데 필수적입니다.

*   **필요성:**
    *   실행 여부 및 흐름 추적: 단순 `System.out.println` 사용은 로그를 남기는 기능이 제한적이고 효율성이 떨어집니다.
    *   운영 및 분석: 누적된 로그 데이터를 분석하여 애플리케이션 개선 방향을 찾거나 문제를 추적하는 데 사용됩니다.
*   **표준화의 중요성 (SLF4J):**
    *   로그 로깅은 표준화된 인터페이스를 사용해야 합니다. 현재 업계 표준은 **SLF4J**입니다.
    *   SLF4J는 **패사드 패턴(Facade Pattern)**을 채택하여, 실제 로깅 구현체(Logback, Log4j2 등)와 사용자 코드 사이에 결합도를 떨어뜨립니다.
    *   **장점:** 어떤 로깅 라이브러리(구현체)를 사용하든, 개발자의 코드를 전혀 수정하지 않고도 (의존성만 변경하여) 시스템 전체를 교체할 수 있습니다.
*   **로그 레벨(Log Level):** 로그 레벨은 로그의 중요도나 심각도에 따라 메시지를 구분하는 표준 방식입니다.
    *   **대표 레벨 (심각도 순):** `TRACE` $\rightarrow$ `DEBUG` $\rightarrow$ `INFO` $\rightarrow$ `WARN` $\rightarrow$ `ERROR` $\rightarrow$ `FATAL`
    *   **활용:** 이 레벨 구분을 통해 개발 단계(디버그 레벨까지 모두 출력)와 운영 단계(중요한 `INFO`나 `ERROR`만 출력)의 로그 출력을 분리하여 효율성을 높일 수 있습니다.

## 3. 로깅 설정의 심화 학습 (레벨, 패턴, XML)
로깅 시스템을 효과적으로 관리하기 위해서는 다양한 설정을 할 수 있습니다.

*   **설정 방법 및 난이도:**
    *   **Properties/YAML:** 간단한 설정(Root 레벨의 로그 레벨 변경 등)에는 적합합니다.
    *   **XML:** 설정이 복잡해지고, 여러 종류의 어펜더(출력 지점)를 정의해야 할 때는 XML 설정을 사용하는 것이 표준적이며 가장 강력합니다.
*   **핵심 구성 요소 (XML 기반):**
    *   **Appender (어펜더):** 로그 메시지를 어느 곳에 출력할지 지정하는 대상입니다. (예: `Console`에 출력, `File`에 저장)
    *   **Layout/Pattern (패턴):** 로그 메시지가 어떤 형식(Format)으로 찍힐지 결정합니다. (예: `[연월일 시:분:초] [레벨] [스레드이름] 메시지` 형식 지정)
    *   **필드 커스터마이징:** 패턴을 통해 타임스탬프, 스레드 이름, 로그 레벨 등 원하는 정보를 가져오고, 심지어 색상(Color)까지 커스터마이징할 수 있습니다.
    *   **파일 관리 기능:** 로그 파일이 너무 커지는 것을 방지하기 위해 파일 크기 제한(`maxSize`)이나 보관 개수 제한(`maxHistory`) 등의 정책을 설정할 수 있습니다.
*   **고급 설정의 특징:**
    *   **프로파일 활용:** 환경(Profile)별로 다른 로그 레벨을 적용할 수 있습니다. (개발 환경에서는 `DEBUG` 레벨, 운영 환경에서는 `INFO` 레벨 등)
    *   **모듈화:** 애플리케이션 전체 설정과 로그 설정을 분리하여 (예: `logback-spring.xml` 사용) 시스템의 복잡도를 낮추고 유지보수성을 높일 수 있습니다.

## 1. 로깅 시스템 설정 및 베스트 프랙티스
**A. 로깅 설정 구조 이해**
*   **어펜더(Appender) 정의:** 로그를 *어디에* 출력할지 정의하는 부분입니다. (예: 콘솔, 파일).
*   **로거(Logger) 정의:** 로그를 *어떤* 곳에 남길지 설정하는 부분입니다.
*   **설정 메커니즘:** `logback-spring.xml`과 같은 설정 파일을 이용해 로그 시스템을 매우 디테일하게 설정할 수 있습니다.
*   **로그 파일 경로:** 설정된 경로(예: `loggers/` 디렉토리)에 프로젝트 이름과 시간 정보 등을 포함한 파일명이 자동 생성됩니다.

**B. 로깅 최적화 및 보안 고려사항**
*   **로그 레벨 사용:** 로그 레벨(DEBUG, INFO, WARN 등)을 적절히 사용하여 애플리케이션의 상황에 맞는 로그를 관리하는 것이 중요합니다.
*   **성능 최적화:** 성능 저하를 막기 위해 문자열을 반복적으로 결합하는 방식보다는 조건 체크(`if` 문 등)를 활용하는 것이 좋습니다.
*   **보안 주의사항:** 로그에 사용자 이름이나 **패스워드**와 같은 민감한 정보가 노출되지 않도록 반드시 주의해야 하며, 필요한 경우 해시 처리 등을 고려해야 합니다.
*   **활용 범위:** `System.out.println` 대신 전용 로깅 라이브러리를 사용하는 것이 모범 사례입니다.

## 2. 웹 애플리케이션의 구조적 문제점과 MVC 패턴의 등장
**A. 웹 개발 초기 구조의 문제점 (Monolithic 구조)**
*   **기존 방식:** 과거에는 웹 요청을 처리하는 서블릿(Servlet) 하나의 객체가 요청 수만큼 생성되었으며, 이 서블릿이 요청 처리, 데이터베이스 접근, 응답 화면 생성 등 모든 역할을 독점적으로 수행했습니다.
*   **문제점 (비대화):** 하나의 객체가 너무 많은 역할(비즈니스 로직, 데이터 접근, 프레젠테이션 로직)을 수행하면서 코드가 비대해지고, 유지보수 및 수정이 극도로 어려워지는 문제가 발생했습니다.

**B. MVC 패턴 도입의 목적**
*   **목표:** 코드의 책임을 분리하여(Separation of Concern) 각 구성 요소가 자신의 역할에만 집중하도록 분리하는 것입니다.
*   **MVC의 정의:** 웹 개발에서 역할을 세 가지 요소로 분리합니다.
    *   **Model (모델):** 핵심 로직과 데이터 처리(DB 접속)를 담당합니다. (데이터 자체의 변화와 로직 변화)
    *   **View (뷰):** 사용자에게 보여지는 화면(UI)을 담당합니다. (디자인 변경)
    *   **Controller (컨트롤러):** 클라이언트의 요청을 받고, Model과 View가 유기적으로 동작하도록 조정(제어)하는 역할을 수행합니다.

## 3. MVC 패턴의 발전 및 Front Controller 도입 (MVC Model 2)
**A. View 계층의 변화 (JSP 지양)**
*   **JSP의 문제점:** JSP 파일 내에서 자바 코드(스크립틀릿)가 직접 동작할 수 있습니다. 이는 HTML과 자바 코드가 혼재되어 가독성이 떨어지고, 자바 코드가 노출됨으로써 보안 취약점(코드 분석 및 악의적 코드 삽입)에 매우 취약합니다.
*   **대안:** 현재는 JSP 사용을 지양하고, Thymeleaf와 같은 **템플릿 언어**를 사용합니다. 템플릿 언어는 HTML 태그처럼 보이지만, 내부적으로만 로직(조건문, 반복문 등)을 처리하도록 하여 코드를 깔끔하게 분리합니다.

**B. Front Controller 패턴의 도입**
*   **필요성:** 초기 방식은 요청이 들어올 때마다 여러 개의 서블릿 객체(진입점)를 만들거나, 너무 많은 진입점을 갖게 되어 보안과 관리가 매우 복잡했습니다.
*   **Front Controller 역할:** 모든 외부 요청(클라이언트의 요청)이 오직 **하나의 게이트웨이(프론트 컨트롤러)**를 통해서만 서버에 진입하도록 구조화합니다.
*   **장점:**
    *   **통제:** 모든 요청을 한곳에서 받기 때문에 접근 통제(보안)가 용이해지고, 어떤 로직이 실행되어야 하는지 중앙에서 쉽게 분기(라우팅)시킬 수 있습니다.
    *   **결론:** MVC Model 2는 모든 요청에 대한 입구를 하나로 통일하여 시스템의 안정성과 관리 효율성을 극대화했습니다.

## 1. MVC 패턴의 이해와 필요성
- **MVC란?** 웹 애플리케이션의 구조를 Model, View, Controller 세 가지 역할로 분리하여 개발하는 디자인 패턴이다.
    - **Model:** 실제 비즈니스 로직을 처리하는 부분 (데이터와 로직).
    - **View:** 사용자에게 보여주는 화면(화면 출력)을 담당하는 부분 (JSP, Thymeleaf 등).
    - **Controller:** 사용자의 요청을 받아 어떤 로직을 수행하고 어떤 View를 보여줄지 중재(제어)하는 역할.
- **MVC의 필요성:** 기존의 방식은 요청 처리, 로직 수행, 화면 생성을 하나의 파일에서 처리하여 복잡하고 유지보수가 어려웠다. MVC 패턴을 통해 역할을 분리함으로써 시스템의 효율성과 확장성을 높였다.

## 2. 웹 애플리케이션 보안 및 구조의 발전 과정
- **보안의 중요성 증가:** 웹 애플리케이션은 초기에는 비교적 자유로웠으나, 시간이 지나며 악의적인 사용자(해커, 도둑)가 늘어나면서 데이터베이스 유출, 사용자 정보 탈취 등의 보안 위협이 증가했다.
- **구조적 안정성의 요구:** 이러한 보안 위협과 복잡한 서비스 요구사항을 처리하려면, 기존의 단순한 구조를 벗어나 더욱 안전하고 체계적인 구조로 웹 애플리케이션을 설계할 필요가 생겼다.
- **프레임워크의 역할:** 개발자가 모든 복잡한 요청 처리 로직(예: 요청을 빠르게 분기하고 처리하는 컨트롤러 구현)을 처음부터 만들 필요가 없게 되었다. 스프링 같은 프레임워크가 이미 잘 구현된 틀을 제공함으로써 개발자는 핵심 비즈니스 로직에만 집중할 수 있게 되었다.
- **기술적 진화:** 초기에는 Struts 같은 프레임워크가 주류였으나, 스프링 프레임워크가 MVC 모델을 훨씬 더 견고하게 구현하며 현재까지 가장 널리 사용되는 방식으로 자리 잡았다.

## 3. Spring MVC의 핵심 동작 원리 및 구성 요소
- **핵심 아키텍처:** Spring MVC는 요청(Request)이 들어올 때, 요청을 처리하는 **DispatcherServlet**이라는 핵심 요소가 모든 요청을 받는다.
- **요청 흐름의 작동 방식:**
    1. **요청 수신:** 웹 서버에 들어온 모든 요청을 `DispatcherServlet`이 가로챈다.
    2. **라우팅 및 매핑:** `DispatcherServlet`은 요청된 URL과 요청 방식(GET/POST 등)을 바탕으로 **HandlerMapping**을 통해 적절한 Controller와 메서드(핸들러)를 찾아낸다.
    3. **메서드 실행:** **HandlerAdapter**가 찾아낸 Controller의 메서드를 호출하고, 필요한 값(예: 사용자 ID, 검색 조건)을 자동으로 추출하여 메서드 파라미터로 주입(Dependency Injection)해준다.
    4. **View 결정 및 응답:** Controller는 실제 화면을 반환하는 대신, **View Name**만 반환한다. **ViewResolver**가 이 View Name을 기반으로 실제 View 파일의 위치(경로와 확장자)를 결정하여 사용자에게 응답한다.
- **Spring Boot의 장점:** 과거에는 위와 같은 모든 설정을 수동으로 해주어야 했지만, Spring Boot을 사용하면 필요한 의존성만 추가하는 것만으로 대부분의 복잡한 설정이 자동으로 처리되어 개발 편의성이 혁신적으로 높아졌다.

## 4. Spring Boot을 이용한 실제 구현 및 개발 흐름
- **프로젝트 환경 설정:** Spring Boot 프로젝트를 생성하고, 웹 개발에 필요한 의존성(`spring-boot-starter-web` 등)을 추가한다.
- **Controller 구현:**
    - `@Controller` 어노테이션을 붙여 해당 클래스가 요청을 처리하는 역할을 담당함을 명시한다.
    - `@GetMapping` 등 매핑 어노테이션을 사용하여 특정 URL 패턴과 HTTP 메서드에 맞는 메서드를 정의한다.
- **실행 및 동작 확인:**
    - 서버를 구동하고 브라우저로 요청을 전송하면, `DispatcherServlet`을 통해 요청이 처리되어 정의된 View 이름에 해당하는 화면(HTML)이 클라이언트에게 응답된다.
- **핵심 원리 이해:** 서버를 띄우는 과정에서 Spring 프레임워크가 모든 Controller를 미리 읽어와 **URL 중복 여부** 등의 설정을 점검하는 과정이 선행된다. 이 과정에서 URL 중복이 발생하면 서버 시작 단계에서 오류가 발생한다.

## 5. View와 Data 응답 방식 (MVC vs. REST)
- **MVC 방식 (기본):** Controller가 View 이름(문자열)을 반환하면, ViewResolver가 이를 해석하여 최종 HTML 페이지를 생성하고 응답한다. (View를 반환함)
- **REST 방식:** API 형태로 데이터를 주고받을 때 사용한다.
    - `@RestController` 또는 `@ResponseBody` 어노테이션을 Controller나 메서드에 붙이면, View 이름을 반환하는 대신 해당 메서드의 반환 값 자체가 최종 응답 데이터(주로 JSON 형태)가 된다. (View가 아닌 데이터를 응답함)
- **요약:**
    - **MVC Controller:** 화면 전체를 구성하는 템플릿 View를 반환할 때 사용한다.
    - **REST Controller:** 데이터 구조체나 값을 직접 반환하여, 클라이언트 측에서 이를 활용할 API 응답을 만들 때 사용한다.



스프링은 객체를 직접 만들지 않게 함
- Bean으로 등록하고 컨테이너가 관리함
- 필요한 객체는 DI로 주입함
- 어노테이션은 스프링에게 역할을 알려주는 표식임
- 스프링은 리플렉션으로 그 표식을 읽음
- 운영에서는 println 대신 Logging을 써야 함
- 웹 요청은 DispatcherServlet이 받고 Controller로 연결함
- Controller는 View 또는 JSON 데이터를 응답함

스프링은 개발자가 모든 흐름을 직접 제어하지 않고, 정해진 규칙과 어노테이션을 통해 프레임워크가 객체 생성, 요청 처리, 응답 흐름을 대신 관리하게 해주는 구조임.

Spring MVC에서는 DispatcherServlet이 요청을 받고, HandlerMapping을 통해 요청 URL에 맞는 컨트롤러 메서드를 찾은 뒤 실행한다. 컨트롤러가 반환한 값이 뷰 이름이면 ViewResolver가 화면을 찾고, 데이터면 HttpMessageConverter가 JSON 같은 응답으로 변환해서 클라이언트에 보낸다.


[클라이언트 요청] 
       ↓
 1. DispatcherServlet이 요청 접수
       ↓
 2. HandlerMapping으로 컨트롤러 매핑 (컨트롤러 객체는 '싱글톤 스코프'로 서버에 항상 대기 중)
       ↓
 3. 컨트롤러 실행 
    - 뷰 반환 시: 'Request 스코프'인 Model 객체에 데이터를 담아서 반환
    - 데이터 반환 시: HttpMessageConverter가 JSON 변환 후 즉시 응답
       ↓
 4. ViewResolver가 화면을 찾음
       ↓
 5. View 렌더링 (Model에 담긴 'Request 스코프(요청-응답)' 데이터를 HTML에 녹여냄)
       ↓
 6. 응답 완료 (Model 데이터 소멸, 만약 'Session 스코프'에 저장한 데이터가 있다면 브라우저 종료 시까지 유지)
