## 1. 상태 정보 유지의 필요성 및 기존 방식의 한계 (Session/Cookie)
- **상태 유지(State Management):** HTTP는 기본적으로 요청마다 서버가 사용자의 상태 정보를 알지 못하는 무상태(Stateless) 프로토콜이다. 서비스 이용 시 사용자 상태를 유지하기 위해 쿠키나 세션 같은 기술을 사용한다.
- **쿠키/세션 작동 방식:**
    - **쿠키:** 서버가 생성한 '증표'(정보)를 클라이언트가 요청마다 가지고 온다. (예: 스포츠센터 회원 카드)
    - **세션:** 중요한 사용자 정보는 서버(Server-Side)에 저장하고, 클라이언트에게는 식별자(Session ID)만 보내 상태 정보를 유지한다. 이는 정보 노출의 위험을 줄여준다.
- **선행 지식 중요성:** JWT를 이해하기 위해서는 쿠키와 세션을 이용한 '상태 유지' 개념이 반드시 선행되어야 한다.

## 2. JWT 도입 배경: 서비스 확장성 및 분산 환경 문제 해결
- **서버 스케일 아웃(Scale Out) 문제:** 서비스가 대규모로 커지면 하나의 서버로는 모든 요청을 처리할 수 없고, 여러 대의 서버가 요청 처리를 분담해야 한다.
- **분산 시스템의 인증 문제:** 세션 기반으로 상태 정보를 유지할 경우, 한 서버에만 그 사용자의 인증 정보(세션)가 저장되어 있어 다른 서버로 요청이 분산될 때 해당 사용자 인증 여부를 알 수 없게 되는 문제가 발생한다. (서버 간 동기화 문제).
- **JWT의 역할:** 이러한 문제를 해결하기 위해 상태 정보를 서버 측이 아닌 클라이언트(토큰 자체)에 포함하여 전송하는 방식을 사용해야 했다.

## 3. JSON Web Token (JWT) 이론 및 구조 분석
- **작동 원리:** JWT는 사용자 정보가 담긴 토큰을 클라이언트에게 전달하며, 모든 인증 정보를 서버 측 DB에 저장할 필요 없이 상태를 유지할 수 있도록 설계된 웹 토큰이다. 이 과정 덕분에 **Stateless(무상태성)** 처리가 가능하다.
- **JWT 구조 (3가지 구성요소):** JWT는 Base64 URL 인코딩 방식의 세 부분으로 이루어져 있다.
    1.  **Header:** 사용된 토큰 타입과 암호화 알고리즘을 명시한다.
    2.  **Payload:** 사용자 ID, 권한 등 실제로 전달하고 싶은 정보(Claims)가 담긴 핵심 영역이다. (Key-Value 형태로 저장 가능).
    3.  **Signature (서명):** Payload와 Header를 합치고 **비밀 키(Secret Key)**를 이용해 생성하는 해시값이다.
- **JWT의 보안 메커니즘:**
    - 토큰 값이 중간에 변조되더라도, 서명(Signature)을 재계산할 때 사용되는 비밀 키가 없으면 서명 값까지 일치시키기 어렵다. 서버는 이 시그니처 값을 통해 전송된 데이터가 위변조되지 않았음을 검증한다.
    - **보안 장점:** 정보를 전달하는 과정에서 변조 여부를 체크할 수 있어, 단순하게 값만 노출되는 것보다 훨씬 안전하다.

## 4. 보안 강화를 위한 토큰 활용 전략: Access와 Refresh Token
- **JWT의 단점 (탈취 위험):** JWT 자체는 비밀 키로 서명을 검증하지만, 일단 탈취된 토큰을 막을 방법은 없다. 또한 유효 기간(Expiry Date) 설정이 매우 짧으면 사용자가 매번 재인증하는 번거로움이 발생한다.
- **솔루션: 두 가지 토큰 분리 전략:** 이 문제를 해결하기 위해 역할을 나눈 2개의 토큰을 사용한다.
    1.  **Access Token (액세스 토큰):** 실제 인증(API 접근)에 사용되는 토큰. 유효 기간이 **짧게** 설정된다. (빠르게 요청 처리가 가능해야 하므로 서버 DB에 저장하지 않는다.)
    2.  **Refresh Token (리프레시 토큰):** Access Token의 유효기간이 만료되었을 때, 새로운 Access Token을 발급받는 용도로 사용되는 토큰. 유효 기간이 **길게** 설정되며, 이 값은 서버(DB)에 저장하여 관리한다.
- **작동 흐름:**
    1.  로그인 시, 시스템은 Access Token과 Refresh Token 두 개를 모두 생성한다.
    2.  Refresh Token을 DB에 저장하고 사용자에게 전달하며, Access Token은 클라이언트가 바로 사용할 수 있도록 제공한다.
    3.  Access Token이 만료되면, 사용자는 Refresh Token을 이용해 서버에 새로운 Access Token 발급을 요청하고 인증 과정을 이어간다.

## 5. 실습을 통한 JWT 생성 및 인증 로직 구현
- **JWT 토큰 라이브러리 활용:** 실제 코드에서는 `JwtTokenProvider`와 같은 유틸리티 클래스를 사용하여 토큰 생성, 검증(Validation), 파싱 등의 작업을 간편하게 처리한다.
- **토큰 생성 과정 (주요 원칙):**
    - **빌더 패턴 사용:** 복잡하고 선택적일 수 있는 여러 개의 속성들(발급자, 주체 등)을 가진 객체를 만들 때, 필수적인 값만 쉽게 설정할 수 있도록 빌더 패턴(`builder` 등)을 사용하는 것이 효율적이다.
    - **DTO 설계 (Response DTO):** API 응답에 필요한 데이터만을 모아두는 별도의 DTO를 사용하면 코드가 깔끔해지고 재사용성이 높아진다.
- **로그인 인증 흐름 구현:**
    1.  사용자가 ID와 암호화된 비밀번호(Password)를 전송한다.
    2.  **Validation 처리:** 서비스가 시작되기 전에 입력값의 형식적 유효성(예: 공백 여부, 최소 길이 등)을 먼저 체크한다. (Bean Validation 활용).
    3.  **비밀번호 검증:** DB에서 조회한 비밀번호와 전송된 비밀번호를 직접 비교하는 것이 아니라, 암호화 알고리즘(`PasswordEncoder`)의 매치 메서드를 통해 안전하게 일치 여부를 확인한다.
    4.  **토큰 발급 및 저장:** 인증이 성공하면 Access Token과 Refresh Token 두 개를 생성하고, Refresh Token을 DB에 반드시 저장한 후 사용자에게 토큰들을 반환(응답 본문 또는 쿠키)한다.

2. Stateless 환경에서의 사용자 인증 구현 원리 (필터 사용)
3. 액세스 토큰 추출 및 유효성 검증 로직 구현
4. Spring Security Context에 권한 정보 주입 방법
5. 커스텀 UserDetails 및 UserDetailsService의 필요성

## 1. JWT를 활용한 인증 개요 및 플로우 이해
*   **JWT 도입 배경:** 기존 세션 기반 방식의 한계(Stateful)를 극복하기 위해 사용됨 (Stateless).
*   **인증 과정 흐름:**
    *   클라이언트가 ID와 비밀번호를 전송하여 서버에 로그인 요청.
    *   서버는 인증 성공 시, **액세스 토큰(Access Token)**과 **리프레시 토큰(Refresh Token)**을 발급하고 클라이언트에게 전달.
    *   클라이언트는 받은 토큰을 로컬 스토리지나 쿠키 등에 저장합니다.
    *   이후 API 요청 시, 클라이언트는 HTTP 헤더나 쿠키 등을 통해 토큰을 서버로 포함하여 전송합니다.
    *   서버는 수신된 토큰을 검증하고 유효할 경우에만 요청을 처리합니다.

## 2. Stateless 환경에서의 사용자 인증 구현 원리 (필터 사용)
*   **문제 인식:** 매번 요청이 들어올 때마다 해당 사용자가 '인증된 사용자인지'를 확인해야 합니다. 이 체크 로직은 어느 계층에서 처리되어야 할까요?
*   **솔루션: 필터(Filter) 활용:** 웹 애플리케이션의 요청 흐름 가장 앞단에서 동작하는 **필터**를 구현하여 인증 검증을 수행하는 것이 가장 효율적입니다. (예시: `OncePerRequestFilter` 상속받아 사용).
*   **흐름 요약:** 요청이 서버에 도달하기 직전에 필터가 토큰을 추출하고 유효성을 검사합니다. 이후 Spring Security의 인증/인가 메커니즘과 연결하여 사용자 정보를 로드합니다.

## 3. 액세스 토큰 추출 및 유효성 검증 로직 구현
*   **토큰 추출 경로 확보:** 클라이언트가 전송하는 토큰은 쿠키(Cookie) 또는 HTTP 요청 헤더(Header)를 통해 전달될 수 있으므로, 두 가지 모두에서 토큰을 추출할 수 있도록 로직을 구성해야 합니다.
    *   `HttpServletRequest` 객체를 활용하여 쿠키 값과 헤더 정보를 조회합니다.
*   **토큰 검증 (Validation):**
    *   추출된 액세스 토큰은 반드시 유효성을 검증해야 합니다.
    *   유효성 검사 결과, **만료되었거나 형식이 잘못되었다면** 요청 처리를 중단하고 오류를 반환합니다.

## 4. Spring Security Context에 권한 정보 주입 방법
*   **인증 성공 시 처리:** 토큰이 유효하다는 것이 확인되면, 해당 사용자의 정보를 추출하여 Spring Security의 **Security Context Holder**에 저장해야 합니다.
*   **사용자 정보 추출 (Claims):** JWT 라이브러리(`JwtTokenProvider` 등)를 사용하여 토큰으로부터 사용자 ID(Subject), 닉네임, 권한 등의 클레임(Claims)을 가져옵니다.
    *   *(주의사항: 토큰 발급 시 사용했던 키와 대소문자를 정확히 맞춰 정보를 추출해야 함.)*
*   **권한 정보 변환:** JWT에서 가져온 원시 데이터 형태의 권한 리스트(`List<String>`)를 Spring Security가 요구하는 객체 형태로 변환하는 작업이 필수적입니다.
    *   `GrantedAuthority` 인터페이스를 구현하거나 이를 포함하는 방식으로 변환하여 사용해야 합니다.
*   **최종 저장:** 추출하고 변환된 사용자 정보(Principal)와 권한 정보를 `SecurityContextHolder`에 설정함으로써, 이후의 요청들을 처리하는 모든 로직에서 이 사용자가 인증되었음을 보장합니다.

## 5. 커스텀 UserDetails 및 UserDetailsService의 필요성
*   **문제 제기:** 기본 `UserDetailsService`는 데이터베이스에 저장된 최소한의 정보(ID, 비밀번호, Role 등)만을 담고 있습니다. 하지만 JWT 기반 시스템에서는 이메일 주소, 아이콘 URL 등 더 풍부한 정보를 클라이언트가 요구할 수 있습니다.
*   **해결책:**
    1.  **커스텀 `UserDetails` 구현:** 필요한 추가 정보(이메일, 사용자 ID 등)를 담을 수 있도록 기존 `UserDetails` 객체를 상속받거나 커스터마이징합니다.
    2.  **커스텀 `UserDetailsService` 구현:** Spring Security가 인증 과정을 거칠 때 (사용자 정보를 로드할 때), 데이터베이스 접근 로직을 담당하는 인터페이스를 직접 구현하여, 필요한 추가 데이터를 포함한 사용자 객체를 제공해야 합니다.

## 1. JWT 기반 보안 인증의 작동 원리 이해
- **전통적인 인증 방식과의 차이점:** 로그인이 되는 순간만 필요한 것이 아니라, 이후 모든 요청(Request)마다 토큰을 가지고 들어와야 하므로 매번 토큰 검증과 사용자의 인증 상태 확인이 필수적이다.
- **필터의 역할 증대:** Spring Security 자체 기능 외에도 CSRF 체크나 커스텀 비즈니스 로직에 대한 체크가 필요할 수 있다. 따라서 구현한 필터를 기존 Spring Security의 필터 체인(Filter Chain) 중간에 끼워 넣어 함께 동작하도록 구성해야 한다.
- **필수 요구 사항:** JWT를 이용해 인증된 사용자 정보를 추출하고, 이 정보를 스프링 시큐리티가 인식하는 방식으로 시스템 내부에 전달(Context 설정)해야 한다.

## 2. 사용자 정보 관리를 위한 커스텀 로직 구현 (UserDetailsService)
- **확장된 사용자 정보 모델 정의:** JWT 환경에서는 일반적인 Spring Security의 `UserDetails`만으로는 부족하다. 이름, 이메일 등 추가적인 정보를 포함하기 위해 반드시 사용자 정의(`Custom`) `UserDetails` 객체를 만들고 사용해야 한다.
- **커스텀 UserDetailsService 구현:** 새로운 `UserDetails`를 사용할 수 있도록 `UserDetailsService` 인터페이스를 확장하여 커스터마이징 해야 한다. 이는 데이터베이스에서 사용자의 기본 정보(유저네임, 비밀번호 등)를 불러오는 핵심 로직이다.
- **데이터 일관성 유지 (Username vs Email):** 실제 시스템의 로그인 ID가 이메일이 아닌 유저네임이라면, JWT 토큰 발급 시나 UserDetailsService에서 데이터를 가져올 때 모든 필드(클레임, Subject 등)에 유저네임을 기준으로 사용해야 한다.
- **권한 정보 처리:** 데이터베이스와 Spring Security 환경 간의 권한 이름 규칙 차이를 고려해야 한다. (예: DB는 `ROLE_` 접두사 없이 저장될 수 있지만, Spring Security가 요구하는 포맷을 위해 로직에서 적절히 변환해 주어야 함.)

## 3. 토큰 정보를 바탕으로 Security Context에 인증 객체 저장
- **인증의 핵심 목표:** 필터 단계를 통과한 후, 애플리케이션 전체의 보안 관련 컴포넌트가 "현재 요청을 보낸 사용자가 누구인지(Who)"를 정확히 알 수 있도록 상태(State)를 공유하는 것이 목적이다.
- **`Authentication` 객체 생성 (JWT Authentication Token):** 인증이 성공적으로 완료되면, `UsernamePasswordAuthenticationToken`과 같은 표준 객체를 이용해 인증 정보(`Authentication` 객체)를 생성해야 한다. 이 객체에는 Principal(사용자 식별 정보), Credentials(인증 자격), 그리고 Authorities(권한 목록)가 포함된다.
- **SecurityContextHolder 사용:** 이렇게 생성된 `Authentication` 객체는 반드시 Spring Security가 관리하는 저장소인 `SecurityContextHolder`에 넣어주어, 요청 처리 과정 중 언제든지 이 정보를 조회할 수 있도록 만들어야 한다.

## 4. 필터 체인 설정 및 동작 흐름 확립
- **필터의 구현과 적용은 별개:** 단순히 커스텀 필터를 작성했다고 해서 자동으로 동작하는 것은 아니다. 해당 필터가 실제 Spring Security 필터 체인의 어느 지점에서 실행되어야 하는지 명시적으로 지정해 주어야 한다.
- **SecurityConfig 설정 필수:** `WebSecurityConfigurerAdapter` 또는 Spring Boot의 보안 설정을 통해, 커스텀으로 구현한 필터를 기존 필터 체인에 정확하게 추가(Register) 해줘야만 인증 및 권한 검증 로직이 제대로 작동한다.

## 1. JWT 기반 인증 방식의 이해: 세션 기반 vs. 토큰 기반

### - 핵심 내용 bullet point
*   **기존 세션 기반 인증 방식:** 스프링 시큐리티는 기본적으로 사용자의 `로그인` 처리를 담당하며, 인증 정보(Authentication)를 요청이 들어올 때마다 **세션(Session)**과 **쓰레드 로컬(ThreadLocal)**에 저장합니다. 이를 통해 다른 요청에서도 사용자 정보를 확인할 수 있습니다.
*   **JWT의 필요성 및 동작 원리:** JWT(JSON Web Token)는 상태가 없는(Stateless) 인증 방식을 제공하며, 세션을 이용하지 않아도 합니다.
    1.  사용자가 ID/PW를 전송하여 유효성을 검사합니다.
    2.  검증이 성공하면, 시스템은 **JWT 토큰**을 생성하여 클라이언트에게 응답으로 보냅니다.
    3.  로그인 과정은 이 토큰 발행을 끝점으로 합니다.
*   **장점:** 서버 측에 세션 정보를 저장할 필요가 없어 확장성이 뛰어나며 마이크로 서비스 아키텍처(MSA) 환경에서 유리합니다.

## 2. Spring Security 구현 상세 과정: Security Context 구성 및 필터 활용

### - 핵심 내용 bullet point
*   **JWT를 이용한 인증 정보 재구성:** 토큰 기반으로 동작하기 때문에, 매 요청마다 클라이언트가 전송하는 토큰을 통해 사용자 정보를 가져와야 합니다.
    1.  **토큰 획득 방법:** 사용자가 보낸 토큰은 주로 **HTTP 쿠키(Cookie)**나 **헤더(Header)**를 통해 전달받습니다.
    2.  **SecurityContext 구성:** 획득한 토큰으로부터 사용자 정보들을 추출하고, 이를 기반으로 `Authentication` 객체를 생성해야 합니다.
    3.  **정보 주입:** 이 완성된 `Authentication` 객체를 반드시 **Spring Security의 ContextHolder에 저장**하여, 이후 애플리케이션 내부의 필터나 로직들이 현재 사용자가 인증된 사용자임을 인식하게 만듭니다.
*   **필터 체인(Filter Chain) 활용:** 보안 처리 로직은 특정 위치에 삽입되어야 합니다.
    1.  새로 작성하는 JWT 관련 필터는 `OncePerRequestFilter`를 상속받아 **기존 필터 체인이 실행되기 전(`addFilterBefore`)** 작동하도록 설정합니다.
    2.  필터가 모든 작업을 마치면 다음 필터로 넘어가기 위해 반드시 `doFilter()` 메서드에서 요청과 응답을 재전달해야 합니다.

## 3. Stateless 환경 설정을 위한 보안 강화 설정 (Session 정책 및 CORS)

### - 핵심 내용 bullet point
*   **Stateless Session 관리 필수:** JWT를 사용하고 서버가 세션을 이용하지 않도록 하려면, 반드시 Spring Security 설정에서 세션 처리를 비활성화해야 합니다.
    *   `sessionCreationPolicy(STATELESS)`로 설정하여, 시큐리티가 어떠한 경우에도 세션을 생성하거나 사용하는 로직이 없음을 명시합니다.
*   **CORS (Cross-Origin Resource Sharing) 설정:** 프런트엔드와 백엔드를 서로 다른 서버나 포트에서 운영하는 환경(SPA + API 서버 등)에서는 반드시 CORS 설정을 해야 합니다.
    *   이는 한 도메인/서버가 아닌, **다른 출처(Origin)**의 요청이 자원에 접근할 때 발생하는 보안 오류를 처리하기 위함입니다.
    *   **주요 설정 요소:** 허용할 아원리전(Allowed Origins), 허용할 HTTP 메서드(GET, POST 등), 그리고 헤더 정보 등을 구체적으로 지정해주어야 합니다.

## 4. 학습 요약 및 다음 단계 과제

### - 핵심 내용 bullet point
*   **핵심 이해 사항:** JWT를 이용한 인증 방식은 토큰을 주고받는 과정과, 이 토큰 정보를 추출하여 Spring Security의 `SecurityContextHolder`에 적절히 주입하는 필터 구현 과정을 숙지해야 합니다. 또한, 세션 사용을 완전히 배제하고(Stateless) 외부 통신 환경까지 고려한 CORS 설정을 완료해야 합니다.
*   **다음 학습 목표:** 현재는 기본적인 JWT 인증/인가만 처리했으므로, 이후에는 다음과 같은 고급 보안 주제를 추가로 학습해야 합니다.
    1.  **오류 처리(Exception Handling):** 토큰이 만료되거나 유효하지 않은 경우 등, 발생하는 다양한 오류 상황에 대한 적절한 API 응답 및 처리가 필요합니다.
    2.  **Refresh Token 구현:** Access Token의 만료 문제를 해결하기 위해 Refresh Token을 이용해 새롭게 접근 토큰을 발급받는 로직(토큰 갱신)을 추가적으로 구현해야 합니다.

## 1. 액세스 토큰(Access Token)과 리프레시 토큰(Refresh Token)의 역할 이해 및 재발급 흐름
**핵심 내용 bullet point**
*   **토큰 용도 구분:** Access Token과 Refresh Token은 기능상 비슷해 보이지만 그 목적이 다릅니다.
    *   **Access Token (액세스 토큰):** 사용자의 '인증 상태'를 확인하는 데 주로 사용됩니다. 이 토큰의 유효성은 짧아 주기적으로 재발급이 필요합니다.
    *   **Refresh Token (리프레시 토큰):** 액세스 토큰을 재발급(Reissue)하기 위해 사용되는 장기적인 인증 수단입니다.
*   **재발급 흐름:** Access Token의 만료에 대비하여, 클라이언트가 Refresh Token을 서버로 전송합니다.
    1.  서버는 요청된 Refresh Token이 쿠키나 데이터베이스에 저장된 토큰과 일치하는지 검증합니다.
    2.  토큰의 유효성이 확인되면 (그리고 만료되지 않았다면), 새로운 Access Token을 재발급하여 클라이언트에 전달합니다.
*   **예외 처리 시점:** 이 과정에서 Refresh Token이 누락되거나, 토큰 값이 다르거나(불일치) 등 문제가 발생할 경우 적절한 오류(Error)를 반환해야 합니다.

## 2. JWT 기반 애플리케이션의 예외 처리 구조 설계 (Exception Handling)
**핵심 내용 bullet point**
*   **커스텀 예외 핸들러 구현:** 스프링 시큐리티가 제공하는 `AuthenticationEntryPoint` 인터페이스 등을 상속받아 커스텀 예외 처리를 위한 클래스를 구현합니다.
    *   이는 애플리케이션 전반에 걸쳐 특정 오류(예: 인증 실패) 발생 시 일관된 방식으로 처리할 수 있게 만듭니다.
*   **적절한 핸들링 로직 구성:** 어떤 종류의 예외가 발생했는지 확인하고, 이에 따라 로그를 남기거나, 사용자에게 적절한 메시지를 반환하는 로직을 구현해야 합니다. (예: 요청 객체, 발생 예외(Exception), 응답 스트림 등을 인자로 받는 메서드를 오버라이딩)
*   **구현의 목표:** 단순히 오류 메시지만 보여주는 것을 넘어, 개발자가 원하는 방식으로 시스템 전반에 걸쳐 일관되고 체계적인 예외 처리 흐름을 구축하는 것이 중요합니다.

## 3. 페이지 요청 오류와 데이터 요청 오류의 구분 원칙
**핵심 내용 bullet point**
*   **오류 처리 방식의 분리 필요성:** 애플리케이션에서 발생하는 에러 처리는 크게 두 가지 상황으로 나누어 접근해야 합니다. 이 둘을 동일하게 처리해서는 안 됩니다.
    1.  **전체 페이지(View) 요청 실패 (Global Error):** 사용자가 웹페이지 전체에 접속하려고 할 때 문제가 발생한 경우입니다. (예: 인증 자체가 되어 있지 않아 페이지 진입 자체를 막을 때).
        *   → 이 경우, 오류 메시지를 포함한 **뷰(View)** 형태로 전체 페이지에 응답하는 것이 적절합니다.
    2.  **부분 데이터 요청 실패 (Partial Data Error):** 이미 화면은 정상적으로 보이나, 특정 컴포넌트나 API를 통해 데이터를 가져오려 할 때만 문제가 발생한 경우입니다.
        *   → 이 경우는 전체 뷰가 아닌 **데이터(JSON 등)** 형태로 응답하며, 해당 데이터만 에러 처리하는 별도의 로직이 필요합니다.
*   **실제 적용:** 요청이 REST API를 통해 온 것인지 (데이터 요청), 아니면 전통적인 웹페이지 접근을 통한 것인지를 구분하는 로직(`isRestRequest`와 같은 검증)을 사용하여, 상황별로 적절하게 예외 처리를 분기(Branching)해야 합니다.

## 4. 공통화된 에러 코드 관리를 위한 Enum 활용
**핵심 내용 bullet point**
*   **표준화 및 관리:** JWT 인증 과정에서 발생하는 다양한 종류의 오류 유형(예: 사용자 없음, 유효하지 않은 토큰 등)들을 체계적으로 관리할 필요가 있습니다.
*   **Enum 도입의 장점:** 단순한 문자열이나 코드를 사용하는 대신 **`Enum` (열거형)** 구조를 사용하면, 각 예외 코드와 해당 코드에 연결된 설명 메시지를 묶어 관리하기 매우 용이합니다.
    *   예: `JWT_EXCEPTIONS` Enum을 만들어 토큰 유형과 상태별 코드를 정의하고, 이를 통해 오류 처리 로직 전반에서 일관성을 유지할 수 있습니다.
*   **정적 메서드 활용:** Enum 내부의 정적(Static) 메서드를 추가하여, 외부에서 코드 값만으로도 해당 예외와 연결된 메시지 등을 편리하게 가져다 쓸 수 있도록 기능을 확장하는 것이 좋습니다.

## 1. 오류 및 예외 처리의 고도화 전략
*   **문제 인식**: 기본적인 `try-catch` 방식을 넘어, 애플리케이션의 안정성을 높이기 위해 정교하게 예외(Exception) 발생 시를 처리하는 것이 중요함.
*   **구조적 접근 필요성**: 단순히 에러가 났다고만 알리는 것을 넘어, 어떤 종류의 오류인지 명확한 **오류 코드(Error Code)**와 상세 메시지를 사용자 또는 개발자에게 제공해야 문제 파악 및 대응이 용이함.
*   **정밀 제어 방법**:
    *   Enum 같은 구조체를 활용하여 정해진 오류 코드를 관리하면, 다양한 상황에서 일관성 있게 예외 처리를 수행할 수 있음.
    *   오류 코드를 바탕으로 특정 로직(예: `findByCode`)을 실행하거나 다르게 처리하는 분기 처리가 가능해야 함.

## 2. 구조적 에러 코드 구현과 전역 핸들링
*   **응답 객체 설계**: 오류 발생 시, 응답 본문(Response Body)에 단순히 에러 메시지만 넣는 것이 아니라, `error_code`와 `error_message` 같은 구조화된 정보를 담아 전달하는 것이 사용자 친화적임.
*   **직렬화 및 매핑**: 자바 객체 형태로 만든 오류 정보 (DTO)를 실제로 HTTP 응답 본문(JSON 문자열)에 담으려면, `ObjectMapper`와 같은 라이브러리를 사용하여 해당 객체를 JSON 문자열로 변환하는 과정이 필요함.
*   **HTTP 통신 레벨 이해**:
    *   Spring 프레임워크가 개발자가 직접 지정하지 않아도 Content-Type을 설정하고 응답을 전송하지만, 내부적으로는 `HttpServletResponse`의 기능을 이용해 콘텐츠 타입을 명시(예: `application/json`)해야 함.
*   **전역 예외 처리 구현 (Global Exception Handling)**:
    *   **@ControllerAdvice / @ExceptionHandler 활용**: 특정 컨트롤러에 의존하지 않고 애플리케이션 전반에서 발생 가능한 모든 예외를 포괄적으로 잡아내어 일관된 방식으로 처리할 수 있음.
    *   **검증 오류 처리 강화**: `@Valid` 과정에서 발생하는 `MethodArgumentNotValidException` 등의 검증 실패 예외는 `BindingResult` 객체로부터 개별 필드의 에러 목록(`getFieldError()`)을 추출하여, 어떤 필드에 왜 문제가 생겼는지 상세하게 응답해야 사용자 경험이 좋음.
    *   **커스텀 로직 적용**: Filter나 Interceptor 단에서 다양한 유형의 예외(예: `ExpiredToken`, `BadCredentialsException` 등)를 잡아서 각각 다른 로그 기록이나 처리 로직을 수행하도록 커스터마이징 할 수 있음.

## 3. JWT와 리프레시 토큰을 활용한 인증 흐름 이해
*   **인증 프로세스 (로그인 시점)**: 사용자가 로그인 요청을 보내면, 시스템은 사용자 정보 검증 후, **액세스 토큰(Access Token)**과 **리프레시 토큰(Refresh Token)** 두 가지를 발급함.
    *   이때 리프레시 토큰은 보안을 위해 반드시 데이터베이스에 저장되어야 함.
*   **토큰의 목적 및 역할 분담**:
    *   **액세스 토큰 (Access Token)**: 실제 API 요청 시 사용되며, 유효 시간이 매우 짧음. 주로 인증(Authentication) 목적으로 사용됨.
    *   **리프레시 토큰 (Refresh Token)**: 액세스 토큰이 만료되었을 때 새로운 액세스 토큰을 갱신받는 용도로만 사용함.
*   **보안 메커니즘의 중요성 (토큰 탈취 대응)**:
    *   액세스 토큰은 유효 기간이 짧아 탈취되더라도 위험도가 낮음.
    *   리프레시 토큰을 DB에 저장하고, 사용자가 로그아웃하거나 관리자 페이지에서 강제 만료 처리가 필요할 때 이 값을 **삭제(Revocation)**하여 무효화해야 함. 서버 측에서 해당 리프레시 토큰의 유효성을 주기적으로 검사하는 과정이 필수적임.
*   **인가 및 권한 부여 (Authorization)**:
    *   Spring Security는 단순히 '누구인지'를 확인하는 인증(Authentication)을 넘어, 사용자가 특정 페이지나 API에 접근할 수 있는지('무엇을 할 수 있는지')를 검사하는 인가(Authorization) 기능을 제공함.
    *   JWT를 통해 얻은 사용자 정보를 Spring Security Context에 저장하여, 보안 필터들이 정상적으로 권한 체크(`@Role`, `@Secured` 등)를 수행할 수 있도록 지원하는 것이 핵심 로직임.

## 4. 종합 요약 및 학습 방향
*   **전반적인 흐름 파악**: 전체 과정은 단순하게 View(화면)를 반환하는 것에서 벗어나, API 기반의 요청/응답 구조와 보안 메커니즘(JWT, Refresh Token, Spring Security Filter Chain)까지 아우르는 복잡한 과정을 이해해야 함.
*   **지식 통합 능력 요구**: Spring MVC가 제공하는 편의 기능 뒤에는 `ServletResponse`, `Content-Type` 지정 등 실제 HTTP 통신 원리가 숨어 있으므로, 추상화된 개념에 의존하기보다 그 원리를 함께 이해하려는 노력이 필요함.
*   **권장 학습 방향**: 전체 흐름을 구조적으로 파악한 후, 부족하거나 이해가 어려운 부분을 심화 학습하고 직접 손봐보는(도전해보는) 과정이 가장 효과적임.
