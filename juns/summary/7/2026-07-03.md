## 1. 강좌 오리엔테이션 및 학습 목표 설정
- **주요 주제 전환:** React 기반 웹 개발에서 한 단계 나아가, 보다 효율적이고 강력한 Next.js 프레임워크의 개념을 학습합니다.
- **학습 접근법 강조 (AI 시대):** 단순히 코드를 따라 치는 것보다, 전체적인 시스템 흐름(Flow)과 기술이 왜 필요한지 하는 **개념적 이해가 가장 중요**함을 강조합니다.
    * AI의 도움으로 코드 작성 속도는 엄청나지만, 구조와 근본 원리를 아는 능력이 필수적입니다.
    * 개발자는 요구사항 분석 능력, 비즈니스 로직 파악 능력 등 'AI가 대체하기 어려운 고차원적인 사고'에 집중해야 합니다.

## 2. React 라우팅의 필요성 이해 (기술적 배경)
- **React SPA(Single Page Application)의 한계:** 리액트만으로 애플리케이션을 구축할 경우, 모든 내용 처리가 단일 페이지에서 이루어집니다.
- **라우터(Router)가 필요한 이유:** 전통적인 웹 개발에서는 URL(Uniform Resource Locator) 변화에 따라 백엔드 서버가 다른 콘텐츠를 응답했지만, SPA 환경에서는 URL이 바뀌지 않고 하나의 주소(`localhost:5173`)만 유지되는 문제가 있었습니다.
    * 이로 인해 사용자가 북마크하거나 '뒤로 가기/앞으로 가기' 같은 브라우저 기능을 사용할 때 오류가 발생할 수 있습니다.
- **React Router의 역할:** 리액트 라우터는 이러한 문제를 해결하기 위해, URL의 변화에 맞게 페이지나 컴포넌트를 동적으로 전환하는 모듈을 제공합니다.

## 3. Next.js와 React 아키텍처 비교 분석 (핵심)
- **Next.js 도입 배경:** 기존 리액트 라우터 사용 과정에서 `Router` 같은 엘리먼트 안에 수많은 코드를 추가해야 하는 불편함이 발생했고, 이를 해소하기 위해 Next.js가 등장했습니다.
- **React와 Next.js의 관계:** Next.js는 React를 대체하는 것이 아니라, 리액트가 가지고 있던 한계점(특히 성능과 SEO)을 보완하여 함께 작동하도록 도와주는 프레임워크입니다.
    * 따라서 일반적으로 리액트만 독자적으로 사용하기보다는 **Next.js와 함께 사용하는 것**이 일반적이며 권장됩니다.
- **핵심 차이: 렌더링 방식 (SSR vs CSR):**

| 구분 | React (기본) - Client Side Rendering (CSR) | Next.js (강점) - Server Side Rendering (SSR/SSG) | 중요성 및 효과 |
| :--- | :--- | :--- | :--- |
| **동작 방식** | 서버는 빈 `index.html`과 자바스크립트 파일만 전송합니다. 브라우저(클라이언트)에서 JS가 다운로드되어 전체 페이지를 '그려내고' (렌더링), 동작합니다. | 서버에서 데이터베이스를 통해 데이터를 가져와, **완성된 HTML 문서** 형태로 웹페이지 구조를 만들어 응답합니다. | 클라이언트 부하 감소 및 초기 로딩 속도 향상에 유리합니다. |
| **SEO 적합성** | 빈 HTML을 받기 때문에 검색 엔진 크롤러가 콘텐츠(실제 내용)를 읽기 어렵습니다 (No SEO). | 서버에서 이미 완성된 HTML 구조가 응답되므로, 페이지 소스 보기에서도 실제 컨텐츠가 바로 노출되어 SEO에 매우 유리합니다. | **SEO 최적화**가 가장 큰 장점입니다. |
| **라우팅 방식** | `react-router` 같은 외부 모듈이 필요하며 복잡합니다. | 파일 시스템 기반 라우팅을 내장하고 있습니다. (예: `pages/about.js`는 `/about` URL로 자동 인식). | 개발 생산성 및 구조가 간편해집니다. |
| **작동 범위** | 모든 코드가 브라우저에서 실행되어야 합니다. | 서버에서 동작할 수 있는 부분은 서버가 처리하고, 사용자와의 상호 작용(클릭 이벤트 등)이 필요한 부분만 클라이언트에 맡깁니다. | 성능과 기능 구현의 균형을 맞춥니다. |

## 4. 프론트-백엔드 분리 구조 및 구현 방식
- **요청 흐름의 변화 (전통적 vs. Next.js):**
    * **기존 백엔드 서버:** 화면 전체를 응답할 수 있는 웹 어플리케이션 역할을 했습니다. (프레젠테이션 레이어 포함)
    * **Next.js 구조 (현대적 방식):** 백엔드는 순수하게 **데이터(Data)**만 제공하는 역할(API, REST API)에 집중하고, 프론트 서버가 이 데이터를 받아와 화면을 구성하여 클라이언트에게 응답합니다.
- **네트워크 및 포트:**
    * 물리적으로는 별도의 포트를 가진 백엔드 서버와 프론트 서버가 존재하며, 실제 사용자는 프론트 서버에 요청하게 됩니다.
    * 프론트 서버가 중간에서 데이터를 받아 가공(Process)한 후 클라이언트에게 전달하는 **중간 구조**를 갖습니다.
- **Next.js 프로젝트 내부 이해:**
    * Next.js 프로젝트는 앱 디렉토리 내의 파일 시스템(`page.js`, `layout.js` 등)이 곧 라우팅 구조가 됩니다.
    * 서버 측에서 동적으로 HTML을 생성하고 응답하는 원리가 핵심입니다.

***

### 💡 요약 정리: 개발자의 관점 (Concept Over Code)
- 기술의 깊은 동작원리(예: 요청 시 어떤 파일이 어느 단계로 다운로드되는지)를 머릿속에 그려내는 **'흐름 파악 능력'**이 가장 중요합니다.
- AI가 아무리 코드를 잘 생성해도, 개발자는 '어떤 구조로 만들 것이며', '왜 이 기술을 사용해야 하는지'라는 근본적인 설계 의도(비즈니스 로직)를 가져야 합니다.
- 본인의 지식을 깊게 채우고, 기술의 배경과 흐름을 파악하는 인재가 되는 것이 궁극적인 목표입니다.

## 1. Next.js 프로젝트 구조 이해하기 및 서버 렌더링의 원리
- **앱 디렉토리 활용:** 생성된 코드는 주로 `app` 디렉토리 안에 구성하는 것이 일반적이다.
- **글로벌 CSS 적용:** 전체 페이지에 공통으로 적용되는 CSS는 `global.css` 파일에 작성한다.
- **레이아웃 역할 (`layout.js`):**
    - `layout.js`는 전체적인 웹페이지의 골격(뼈대)을 정의하는 역할을 한다.
    - 이 파일은 HTML 뼈대를 만들고, 내부 콘텐츠를 `children` 프롭스로 받아 해당 위치에 배치한다.
- **서버 렌더링 (Server Rendering):**
    - Next.js는 클라이언트가 요청을 하면 서버 측에서 이미 완성된 전체 페이지(HTML)를 생성하여 응답으로 전송하는 것이 핵심이다.
    - 이 때문에 최종적으로 웹페이지의 코드가 HTML 소스에 그대로 노출되는 것을 확인할 수 있다.
- **포트 설정:** 기본 포트는 3000번이지만, `package.json`이나 서버 실행 옵션을 통해 원하는 대로 변경할 수 있다.

## 2. 파일 기반 라우팅(File-Based Routing) 설정 방법
- **개념 설명:** Next.js는 파일 시스템 자체를 기준으로 URL 경로(라우팅 구조)를 자동 정의해 주는 '파일 기반 라우팅'을 제공한다.
- **정적 페이지 생성 (Static Pages):**
    - 특정 디렉토리(예: `about`)를 만들고 그 안에 `page.js` 파일을 만드면, 해당 폴더 이름과 파일명에 따라 URL이 자동으로 생성된다 (`/about`).
- **동적 라우팅 (Dynamic Routing):**
    - URL 경로의 일부가 가변적인 데이터를 담을 경우, 대괄호 `[]`를 사용하여 동적 세그먼트(예: `[id]`)로 지정한다.
    - 이를 통해 ID 값 등이 변경되어도 동일한 컴포넌트로 접근할 수 있다.

## 3. 서버 컴포넌트와 클라이언트 컴포넌트 구분 사용법 (핵심 이론)
- **두 가지 컴포넌트의 종류:** Next.js에서 사용하는 모든 컴포넌트는 크게 서버 컴포넌트(Server Component)와 클라이언트 컴포넌트(Client Component) 두 가지로 나뉜다.
- **서버 vs. 클라이언트 실행 환경:**
    - **서버 컴포넌트 (기본값):** Node.js 서버에서 동작하며, 데이터를 가져오거나 백엔드 통신이 필요한 초기 렌더링에 유리하다. (브라우저 기능 사용 불가)
    - **클라이언트 컴포넌트:** 브라우저(Client Browser)에서 실행되며, 상태 관리(`useState`), 생명주기 관련 로직(`useEffect`) 등 인터랙션이 필요할 때 사용한다.
- **컴포넌트 명시적 분리:**
    - 클라이언트 측 동작을 위한 컴포넌트는 해당 파일 맨 상단에 `"use client"` 지시문을 추가하여 반드시 선언해야 한다. (예: `useState`를 사용하면 필수)
- **함께 사용하는 원칙:** 일반적으로는 서버에서 데이터 가져오기(SSR)를 하고, 인터랙션이 필요한 부분만 클라이언트 컴포넌트로 분리하는 것이 효율적이다.

## 4. 효율적인 코드 아키텍처 설계: API 로직 분리하기
- **API 로직 분리의 중요성:** 백엔드 서버와 통신하여 데이터를 가져오거나(Fetching), 데이터를 전송(Posting)하는 등의 비즈니스 로직을 컴포넌트 본체 안에 직접 구현하면 코드가 복잡해진다.
- **`lib` 디렉토리 활용:** 이러한 API 접근 코드들을 별도의 `lib` 디렉토리에 함수 형태로 분리하여 관리한다. (예: `api.js`)
- **코드의 역할 분담:**
    - 컴포넌트(Component): UI 구조와 사용자 경험을 담당하며, 비즈니스 로직은 외부 모듈에서 가져와 사용한다.
    - API 파일 (`lib`): 데이터 접근 및 서버와의 통신(예: `async`, `fetch`)에만 집중한다.
- **데이터 캐싱 활용:** 데이터를 가져올 때는 성능 최적화를 위해 캐시 옵션(`cache`)을 설정할 수 있으며, 매번 새로운 데이터를 가져와야 할 경우 `no-store` 등의 옵션을 사용한다.

## 5. 실습을 통한 전체 구조 구현 및 상태 관리 이해
- **ToDo 앱 구축 과정:** 실제 애플리케이션(예: ToDo 목록)을 만들 때의 컴포넌트 분해 원칙을 적용하여 진행했다.
    1.  전체 페이지 (`page.js`)를 정의하고, 페이지에 들어갈 주요 구조물들을 배치한다.
    2.  각 기능을 작은 컴포넌트로 분리하여 재사용성을 높인다 (예: `TodoCard`, `AddTodoForm`).
- **컴포넌트의 역할:** 이렇게 만들어진 하위 컴포넌트들은 그 자체로 페이지 역할을 하는 것이 아니라, 상위 페이지 컴포넌트에서 '조립(Assemble)'되어 사용되는 구성 요소이다.
- **핵심 정리:** Next.js는 서버와 클라이언트의 역할을 구분하고, 라우팅을 파일 시스템으로 간편하게 처리하며, API 로직과 UI를 분리하여 대규모 애플리케이션 개발에 효율적인 구조를 제공한다.

## 1. 컴포넌트 분리 및 개발 구조 이해 (Component Architecture)
- **컴포넌트 재사용성:** React를 이용해 만들었던 컴포넌트(예: 입력창, 리스트, 버튼 등)는 Next.js에서도 기본적인 원리로 활용할 수 있다.
- **구조화된 조립 방식:** 페이지(`page.js`)에서 작은 기능 단위의 컴포넌트들("Add to the Form", "Add to the List" 등)을 가져와 조립하는 방식으로 개발한다.
- **CSS 스타일링 방법:** `[컴포넌트 이름].module.css` 형태로 모듈화된 CSS를 사용하는 것이 일반적이다. 이 방식은 클래스명을 특정 컴포넌트에 국한시켜 충돌을 방지하고 관리하기 용이하게 한다.
- **학습 가이드라인:** 단순히 코드를 복사/붙여넣기 하기보다는, 직접 손으로 코드를 작성하며 실행해 보는 과정(오류 발생 포함)이 개념 이해에 훨씬 효과적이다.

## 2. 데이터 가져오기 (Fetching Data): 서버 측 렌더링과 비동기 처리
- **Next.js의 차별점 (SSR):** React가 기본적으로 클라이언트(브라우저)에서 실행되는 방식이었다면, Next.js는 서버(Server)에서 초기 HTML을 먼저 생성하여 브라우저에 응답하는 형태를 띤다.
    *   ➡️ 이 때문에 컴포넌트 내부의 자바스크립트 코드가 **이미 완성된 HTML** 형태로 클라이언트에게 전송된다는 점이 가장 큰 차이점이다.
- **데이터 가져오기 원칙:** 데이터를 불러오는 API 호출은 반드시 비동기 방식으로 동작해야 한다.
    *   `async/await` 키워드를 사용하여 서버에서 데이터를 안전하게 읽어와야 하며, 이 데이터가 컴포넌트의 렌더링에 사용된다.
- **데이터 흐름 관리:** API를 통해 가져온 ToDo 목록은 리스트를 표시하는 자식 컴포넌트에게 Props 형태로 전달된다. 또한, 데이터가 없을 경우(배열 길이가 0인 경우) 사용자 친화적인 안내 메시지를 출력하도록 처리할 수 있다.

## 3. 상태 변경(Mutation) 관리: CRUD 작업의 원칙
- **상태를 변경하는 흐름:** 사용자의 상호작용(클릭, 제출 등)에 의해 서버의 데이터가 실제로 수정될 때는 다음 단계를 거쳐야 한다.
    1.  **이벤트 발생 및 API 호출:** 사용자 액션에 따라 관련 컴포넌트에서 API를 호출하여 서버 측 데이터를 변경한다 (예: `toggleTodo`, `deleteTodo` 등).
    2.  **클라이언트 상호작용 처리 (`'use client'`):** 브라우저의 인터랙션(e.g., 알림창, 이벤트 기본값 방지)이 필요한 로직은 반드시 클라이언트 컴포넌트(`'use client'`) 내에서 작성해야 한다.
    3.  **서버 상태 동기화 (Refresh):** 서버 측 데이터가 성공적으로 수정된 후에는, 브라우저에 표시되는 화면도 최신 상태로 업데이트되어야 하므로 **`router.refresh()`** 명령을 반드시 호출하여 강제 리렌더링을 유발해야 한다.
- **데이터 생성 (Add To Do):** 폼(Form) 태그를 사용하여 데이터를 전송하고, 서버 측 핸들러 함수(`handleSubmit`) 내에서 API 호출 후 `router.refresh()`를 실행한다. 이때 기본적으로 발생하는 폼 제출 이벤트(Default Action)는 방지하는 것이 좋다 (`e.preventDefault()`).

## 4. 핵심 개념 정리: 클라이언트와 서버의 역할 구분
- **Next.js 작동 원리:** Next.js가 내부적으로 React API를 이용하고 있어 기본적인 동작은 매우 유사하다.
- **가장 중요한 포인트:** 개발할 때 반드시 코드가 어디에서 실행되는지(서버 vs. 클라이언트)를 구분하여 생각하는 것이 핵심이다.
    *   **서버 전용 로직:** 서버 측 데이터 접근 및 초기 렌더링을 담당한다. (브라우저에서는 동작 불가)
    *   **클라이언트 전용 로직:** 사용자 인터랙션, 이벤트 핸들러 등 브라우저 환경에서만 동작하는 부분을 처리한다.
- **요약:** 어떤 기능을 구현하느냐에 따라 서버와 클라이언트를 명확히 구분하고 그 역할에 맞는 코드를 작성할 수 있어야 한다.

## 1. Next.js 학습 목표 및 필요성
- **학습 목적:** 단순히 기능을 구현하는 것을 넘어, React가 *어떻게*, Next.js가 *왜* 그렇게 동작하는지 원리를 깊이 있게 이해하는 데 중점을 둡니다.
- **Next.js의 중요성:** 백엔드 전문가의 관점에서 리액트만으로는 아쉬움이 남으며, 실질적인 서비스 개발에는 서버 측 렌더링(SSR)을 처리할 수 있는 Next.js와 같은 프레임워크가 필수적입니다.
- **핵심 목표:** 이 과정을 통해 프론트엔드와 백엔드가 협업하는 과정에서 발생하는 데이터 흐름과 아키텍처를 이해하는 것이 가장 큰 도움이 됩니다.

## 2. 실습 가이드라인 및 디버깅 팁
- **단계별 실행 권장:** 코드를 한 번에 모두 실행시키기보다, 컴포넌트를 하나씩 추가하며 '이렇게 추가하면 어떻게 동작하는지' 과정을 관찰하며 이해하는 것이 중요합니다.
- **개발자 도구 활용:** 페이지가 로드될 때 서버에서 클라이언트에게 어떤 형태의 HTML 코드와 데이터(JSON)를 넘겨주는지를 개발자 도구의 네트워크 탭 등을 활용하여 확인해 보세요.
- **캐시 오류 관리 (Caching):** Next.js 환경에서는 코드를 수정한 후에도 이전 캐시 때문에 컴포넌트를 찾지 못하는 등의 오류가 발생할 수 있습니다. 이때 관련 명령(e.g., `npm cache clean`)을 사용하여 클린하게 재실행하면 해결되는 경우가 많습니다.

## 3. 프론트엔드 개발자의 관점 전환과 마인드셋
- **기술 학습의 과정:** 꾸준히 공부하다 보면 새로운 기술을 익힐 때 예전만큼 어렵지 않다는 것을 스스로 체감하게 되지만, '처음과 같다'고 생각해서는 안 됩니다. 지속적인 노력이 필요합니다.
- **지식의 통합적 사고:** 어떤 기술도 단편적으로만 바라보지 말고, 여러 기술들을 아우르는 넓은 시야를 갖추어야 합니다. 학습한 지식을 능동적으로 프로젝트에 적용하려는 자세가 중요합니다.
- **개발자로서의 관점 유지 (Two Views):**
    *   **기술적 사고:** 모든 기술은 '왜 만들어졌을까?', '어떤 규칙 하에서 동작하도록 설계되었을까?'라는 질문을 던지며 원리부터 접근해야 합니다.
    *   **사용자 중심 디자인:** 제품을 제공할 때는 개발자의 자신감이나 편의성보다는, **최종 사용자(User)**가 가장 편리하게 사용할 수 있는 관점에서 설계하고 생각하는 습관이 필수적입니다.

## 4. Next.js의 심층 동작 원리 (Server vs Client Component)
- **기본 구조:** Next.js는 React를 기반으로 하지만, 클라이언트 브라우저에서만 동작하던 기존 리액트의 단점들을 보완했습니다.
- **핵심 기능: 서버 사이드 렌더링(SSR):**
    *   Next.js는 페이지가 보여지기 위해 필요한 HTML을 **서버 측**에서 미리 완성하여 응답으로 전송합니다. (클라이언트 측 렌더링 대비 큰 강점)
    *   **SEO 개선:** 서버가 HTML 전체를 만들어 보내주기 때문에 검색 엔진 최적화(SEO)에 매우 유리하며, 콘텐츠 노출도가 높아집니다.
- **Server Component와 Client Component의 분리:**
    *   **Server Component (서버 컴포넌트):** 서버에서만 동작하는 부분입니다. 데이터 패칭이나 비즈니스 로직을 처리합니다. 웹 브라우저가 접근할 수 없는 서버 리소스에 의존하여 작동할 수 있습니다.
    *   **Client Component (클라이언트 컴포넌트):** 인터랙션(상호작용)이 필요한 부분으로, `use client` 지시어를 사용해 선언하며 브라우저에서 동작합니다.
- **데이터 패칭 방식의 차이:**
    *   **React 방식:** 데이터 가져오기를 위해 주로 `useEffect` 같은 라이프사이클 훅을 이용하고 로딩 상태 관리(Loading State)가 필수적입니다.
    *   **Next.js 방식:** 서버 컴포넌트 자체가 비동기적으로 데이터를 요청하고 받아올 수 있어, 별도의 로딩 상태 관리가 필요 없으며 코드 구조가 간결해집니다.

## 5. CSS 트렌드: Tailwind CSS 이해와 적용
- **Tailwind CSS의 등장 배경:** 전통적인 CSS 방식은 클래스 이름을 직접 지정해야 하고(수작업), 스타일을 관리하기 어렵고, 사용하지 않는 코드가 많아 유지 보수가 힘든 단점들이 있었습니다.
- **Utility-First 접근:**
    *   Tailwind는 '유틸리티 우선(Utility-First)' 방식으로 동작합니다. 개발자가 원하는 속성(예: 배경색, 패딩, 라운드)을 클래스 이름으로 직접 제공받아 사용합니다. (예: `bg-red-500`, `p-4`)
    *   이는 마치 미리 정의된 CSS 조각들(Utility Class)의 조합처럼 작동하여, 커스텀 CSS 파일을 따로 작성할 필요가 없습니다.
- **작동 원리 및 장점:**
    *   **원리:** 클래스 이름에 이미 모든 스타일 규칙이 담겨 있습니다. 원하는 요소에 이 클래스를 부여하기만 하면 스타일링이 즉시 적용됩니다.
    *   **효율성:** 사용되지 않는 CSS는 빌드 과정에서 자동으로 제거되어(Purging) 파일 크기가 작고, 개발 속도가 빠르며 일관성이 높습니다. (Post-in CSS 개념)
- **활용 방안:** 클래스 이름 규칙을 파악하고 다양한 유틸리티를 활용하여 실제 프로젝트에 적용해 보는 연습이 중요합니다.

## 1. 테마 및 CSS 프레임워크 복습 및 준비 과정
- **프레임워크 사용:** Tailwind CSS 같은 유틸리티 기반 클래스 구조를 활용하여 디자인을 적용하는 방법을 다루었습니다.
- **예제 목표 설정:** 학습한 내용을 바탕으로 실제로 Dark Mode 토글 기능을 구현해보는 예제를 시작했습니다 (About 페이지 수정).

## 2. 다크 모드 토글 기능 구현 원리 이해
- **훅(Hook) 활용:** React의 `useState`와 `useEffect` 같은 훅을 사용하여 컴포넌트 상태를 관리하며 인터랙션을 구현합니다.
    - `useState`: 현재 테마 상태(`isDark`)를 저장하고, 버튼 클릭 시 이 값을 반전(toggle)시키는 로직을 담당합니다.
    - `useEffect`: 특정 의존성 배열(여기서는 `isDark` 값)이 변경될 때만 필요한 부수 효과(Side Effect)를 실행하도록 합니다.
- **동작 원리:** 사용자가 모드 전환 버튼을 클릭하면, 상태가 바뀌고 이 변화가 다시 DOM에 반영되어 테마의 클래스 이름(`isDark`)을 반전시키는 과정을 거치게 됩니다.

## 3. 글로벌 CSS를 이용한 다크 모드 활성화 기법 (핵심)
- **문제 진단:** 단순히 컴포넌트 내부 상태만 변경하는 것만으로는 전체 페이지의 색상이 제대로 바뀌지 않는 문제가 발생했습니다.
- **해결책 제시:** 테마 전환을 페이지 전반에 걸쳐 적용하려면, 반드시 글로벌 CSS 영역(도큐먼트 레벨)에 해당 클래스(`dark`)를 추가하거나 제거해야 합니다.
    - Javascript 코드가 버튼 클릭 시 **실제 도큐먼트의 클래스 이름**에 `dark` 클래스를 추가/삭제하도록 로직을 수정했습니다.
- **원리 설명:** 이 과정을 통해 전체 엘리먼트들의 스타일이 변경될 수 있도록 최상위 레벨에서 테마 설정을 해주어야 합니다.

## 4. 배운 패턴의 확장 및 응용 방안
- **패턴 일반화:** 다크 모드 구현 방식은 특정 컴포넌트에 국한되지 않고, 모든 웹 페이지 요소에 공통적으로 적용할 수 있는 디자인 시스템 패턴입니다.
- **응용 가능성:** 이번에 익힌 `useState`와 `useEffect`를 이용해 상태를 관리하고 글로벌 클래스를 조작하는 원리는 투두 리스트나 다른 복잡한 UI 컴포넌트에도 동일하게 적용하여 테마 전환 기능을 구현할 수 있습니다.
- **최종 목표:** 자주 사용되는 디자인 패턴에 대해서도 지속적으로 다루면서 개발 능력을 확장해 나가는 것이 중요함을 강조했습니다.
