## 1. 스프링 프레임워크가 필요한 이유 (Spring Necessity)
*   **프레임워크의 역할:** 스프링 프레임워크는 애플리케이션 개발 시 탄탄하게 인정받은 '뼈대' 역할을 제공하여 개발의 효율성과 생산성을 극대화합니다.
*   **장점 (기성품의 이점):** 애플리케이션을 처음부터 모든 재료를 가지고 구현할 수도 있지만, 시간, 비용, 높은 실력 등 많은 리소스가 필요하며 품질 보장이 어렵습니다. 스프링은 검증된 구조를 제공하여 이러한 문제들을 해결해 줍니다.
*   **유연성:** 스프링은 특정 모듈에 국한되지 않으며, 테스트를 위한 JUnit이나 외부 라이브러리 등 다른 프레임워크나 모듈들을 자유롭고 유연하게 결합하여 사용할 수 있습니다.
*   **역사적 배경 (EJB의 한계):** 과거의 기술(예: EJB)은 분산 처리나 트랜잭션 등 공통 기능을 잘 처리했지만, 특정 기술에 지나치게 종속적이라는 단점을 가졌습니다. 스프링은 이러한 종속성을 줄여 유연하게 설계되었습니다.

## 2. 스프링의 핵심 원리: 느슨한 결합과 IoC/DI
*   **느슨한 결합(Loose Coupling):**
    *   객체 간의 의존 관계를 최소화하여, 한 부분이 변경되어도 다른 부분에 미치는 영향(영향도)을 줄여주는 구조입니다.
    *   (예시) TV 유저가 TV 기종이 바뀌더라도 코드 수정 없이 동작할 수 있도록 설계하는 것이 좋은 예입니다.
*   **IoC (Inversion of Control, 제어의 역전):**
    *   객체(Bean)를 직접 생성하거나 관리하는 것이 아니라, 스프링 프레임워크(IoC 컨테이너)에게 객체 생성과 생명주기(Life Cycle) 관리를 맡기는 원리입니다.
    *   프로그래머가 '제어'를 하던 것을 프레임워크가 대신 '제어'해주는 개념입니다.
*   **DI (Dependency Injection, 의존성 주입):**
    *   필요한 객체(의존성)를 직접 가져오지 않고, 프레임워크가 적절한 시점에 주입해주는 방식입니다.
    *   **주입 방법:**
        *   **Dependency Lookup:** 개발자가 컨테이너에게 명시적으로 객체를 요청(Lookup)하여 가져오는 방식.
        *   **Dependency Injection:** 프레임워크가 적절한 시기에 객체를 자동으로 주입해주는 방식.
        *   주입 위치는 **생성자(Constructor), 설정자(Setter), 필드(Field)**에 할 수 있습니다.

## 3. 자바 객체 구조를 이해하는 방법: 애너테이션과 리플렉션
*   **Annotation (애너테이션):**
    *   상속 관계를 사용하지 않고도 객체가 어떤 역할(예: `@Controller`, `@Service`)을 하는지 표시(메타데이터)하는 기술입니다.
    *   애너테이션은 코드에 '태그'를 붙이는 것과 같으며, 이 태그를 통해 클래스의 역할을 구분할 수 있습니다.
    *   애너테이션에는 어떤 시점에, 어느 위치에, 어떤 값을 가질지 등을 정의할 수 있습니다.
*   **Reflection (리플렉션):**
    *   애너테이션은 런타임에 리플렉션이라는 기술을 이용해 프레임워크가 동작합니다.
    *   프레임워크는 클래스에 붙어 있는 애너테이션을 읽어(Metadata) 객체 생성, 메서드 호출 등 객체의 동작 방식을 결정하고 조절합니다.

## 4. 운영 환경의 필수 요소: 로깅(Logging)
*   **로깅의 중요성:** 개발 단계(디버깅) 뿐만 아니라, 애플리케이션이 실제 운영되는 환경에서 필수적입니다.
    *   **사용자 패턴 분석:** 사용자들의 이용 흐름이나 문제 발생 지점을 파악하여 서비스 개선에 활용합니다.
    *   **성능 분석:** 페이지 동작 시간 등 성능 저하가 발생하는 지점을 찾아낼 수 있습니다.
*   **로깅의 필요성:** `System.out.println` 같은 방법으로 콘솔에 출력하는 방식은 성능 비용이 크거나, 배포 시 코드를 제거해야 하는 번거로움이 있습니다.
*   **로깅 시스템의 특징:**
    *   **로그 레벨(Log Level):** 가장 중요한 기능으로, 로그를 남길 때 레벨(예: INFO, DEBUG, ERROR)을 지정하여 설정 파일만 수정해도 원하는 수준의 정보만 출력할 수 있습니다.
    *   **표준화 (Slf4j):** 로깅 라이브러리는 개발자가 통일된 표준(예: SLF4J)을 따르도록 하는 것이 중요하며, 사용자는 이 표준만 기억하면 어떤 실제 구현체(예: Logback)를 사용하든 코드를 수정할 필요가 없습니다.
    *   **Spring Boot의 이점:** 스프링 부트는 설정 과정을 자동화(Auto-Configuration)하여, 추가적인 설정 없이도 로깅 기능을 바로 사용할 수 있게 해줍니다.

## 5. 웹 개발의 구조: MVC 패턴과 Spring MVC 동작 원리
*   **MVC 패턴의 등장 배경:** 초기 웹 개발은 서블릿(Servlet) 파일 하나가 요청 처리와 화면 구성(비즈니스 로직과 UI)을 모두 담당하여, 코드의 비대화와 수정의 어려움(특히 디자인 변경 시)을 초래했습니다.
*   **MVC (Model-View-Controller) 패턴:** 웹 애플리케이션의 구성 요소를 'Model(데이터)', 'View(화면)', 'Controller(요청 처리)' 세 부분으로 명확히 분리한 패턴입니다.
    *   **장점:** 각 부분이 독립적으로 개발되거나 수정될 수 있어 유지보수성이 극대화됩니다.
*   **Spring MVC 구조:**
    *   **Model 2 패턴 구현:** MVC는 기본적으로 Model 2 패턴(Model과 View를 분리)으로 구현되어 있습니다.
    *   **동작 원리:**
        1.  **DispatcherServlet:** 모든 클라이언트 요청은 먼저 `DispatcherServlet`이라는 단일 진입점 서블릿을 받습니다.
        2.  **Handler Mapping:** 요청된 URL을 분석하여 어떤 컨트롤러의 어떤 메서드가 처리해야 할지 매핑(연결)합니다.
        3.  **Controller 실행:** 해당 컨트롤러 메서드가 요청을 처리하고 데이터를 준비합니다.
        4.  **View Resolver:** 컨트롤러가 데이터를 넘기면, `ViewResolver`가 View 이름(템플릿 파일)을 찾아 실제 화면을 구성하여 응답합니다.
*   **REST Controller vs. Spring MVC:**
    *   **Spring MVC:** 일반적인 요청 처리 시 페이지(HTML) 형태로 응답합니다.
    *   **REST Controller:** 데이터를 주고받는 API 요청에 최적화되어 있으며, 응답을 페이지가 아닌 순수한 데이터(JSON 등) 형태로만 리턴할 때 사용합니다.

## 1. MVC 패턴의 이해 및 웹 애플리케이션 구조
*   **MVC 정의:** Model (데이터), View (화면), Controller (제어) 패턴에 기반하는 웹 애플리케이션 프레임워크이자 디자인 패턴이다.
*   **패턴의 배경:** 웹 애플리케이션 개발 과정에서 기능이 한 곳에 집중되어 발생하는 구조적인 문제점들을 효율적으로 분리하고 처리하기 위해 도입되었다.
*   **Spring MVC 구조:** 기본적으로 이 패턴 구조로 동작하며, 개발자는 주로 비즈니스 로직(Model)과 응답 뷰(View)를 구현하게 된다.

## 2. 웹 애플리케이션 동작 원리 및 요청/응답 객체
*   **클라이언트-서버 역할:**
    *   **클라이언트:** 정보를 *요청*하는 주체 (예: 웹 브라우저).
    *   **서버:** 정보를 *제공*하고 요청을 받는 주체 (예: 웹 애플리케이션 서버).
*   **서버 환경:**
    *   웹 애플리케이션 서버는 기본적으로 Tomcat과 같은 웹 컨테이너를 이용한다.
    *   Spring Boot는 이 내부의 웹 컨테이너(Tomcat)가 동작하는 구조를 사용하며, 개발자가 별도의 서버 설정 없이도 동작하도록 구조를 감싸준다.
*   **요청 처리 과정 (Servlet 기반):**
    *   모든 웹 요청은 웹 애플리케이션의 **입구**가 되는 서블릿(Servlet)을 통해 들어온다.
    *   **DispatcherServlet의 역할 (Front Controller):** 이 서블릿이 모든 요청을 받는 '프론트 컨트롤러' 역할을 수행하며, 모든 요청을 단일 진입점으로 받아 처리한다.
    *   **Servlet Filter / Handler Mapping / Handler Adapter:** DispatcherServlet은 이들 객체를 이용해 들어온 요청 URL을 분석하고, 해당 URL에 맞는 적절한 컨트롤러 메서드(Handler)를 찾아 호출한다.
*   **요청/응답의 추상화:**
    *   웹 요청이 들어올 때마다 `HttpServletRequest` 객체(요청이 추상화된 객체)와 `HttpServletResponse` 객체(응답이 추상화된 객체)가 자동으로 생성된다.
    *   **Request 객체:** 클라이언트가 보내준 모든 정보(폼 데이터, URL, 사용자 IP, 브라우저 언어 등)를 담고 있다.

## 3. 핵심 개념: 스코프(Scope)와 상태 관리
*   **HTTP 프로토콜의 특징 (Stateless):** HTTP 프로토콜은 본질적으로 **상태(State)가 유지되지 않는** 프로토콜이다. 즉, 요청과 응답이 한 번 끝나면 서버는 이전 요청자가 누구였는지 알지 못한다.
*   **스코프(Scope)의 필요성:** 사용자가 로그인이나 장바구니에 담은 정보처럼 '상태 정보'를 유지하기 위해 스코프 개념이 필요하며, 이는 요청과 응답 흐름을 따라 데이터를 저장하는 영역이다.
*   **주요 스코프 종류 및 생존 주기:**
    1.  **`ApplicationScope`:** 웹 애플리케이션이 처음 시작할 때 생성되어 서버가 꺼질 때까지 유지되는 공간 (모든 사용자가 공유).
    2.  **`SessionScope`:** 개별 사용자(세션)마다 생성되며, 사용자가 로그아웃하거나 세션을 삭제할 때까지 유지되는 공간 (개인화된 상태 유지에 필수).
    3.  **`RequestScope`:** 요청이 들어올 때 생성되어 응답이 나가는 순간 사라지는 가장 짧은 주기의 스코프.
    4.  **`PageScope`:** 여러 뷰(View)가 공유할 수 있는, 해당 페이지 로딩 시점까지만 유지되는 스코프.
*   **상태 유지 기술:** 상태 정보를 유지하기 위해서는 세션(Session) 또는 쿠키(Cookie)와 같은 추가 기술이 필수적으로 사용된다.

## 4. 데이터 흐름 제어: 모델(Model)과 프론트 컨트롤러의 역할
*   **뷰(View)로의 데이터 전달 (포워딩):** Controller에서 처리한 데이터를 최종적으로 화면(View)에 보여주기 위해 흐름을 View에게 넘겨주는 것을 **포워딩(Forwarding)**이라고 한다.
*   **데이터 저장소의 문제:** 서블릿 코드 레벨에서 직접 변수를 전달하는 것은 스코프 관리 문제로 인해 불가능하다.
*   **Model 객체의 사용 (권장 방식):**
    *   `Model` 객체는 데이터를 임시로 저장할 수 있는 역할을 하며, 프레임워크가 제공하는 추상화된 인터페이스이다.
    *   컨트롤러는 이 `Model` 객체에 데이터를 담아 View로 넘겨주며, View는 이 `Model` 객체를 통해 데이터를 읽어 화면을 구성한다.
*   **직접 접근 지양의 이유:**
    *   개발자가 HTTP Servlet 객체(`request.getAttribute()`)에 직접 접근하여 데이터를 다루는 것은 해당 라이브러리(API)에 강하게 종속(Dependency)되게 만든다.
    *   따라서 스프링 프레임워크가 제공하는 **Model 객체**를 사용하여 간접적으로 접근하는 것이 권장된다. (추상화와 유연성 확보)

## 1. Thymeleaf를 이용한 데이터 출력 및 속성 처리
*   **네임스페이스 선언의 필요성:** HTML 파일에 Thymeleaf 기능을 사용하려면 `<html xmlns:th="..."` 와 같은 형태로 네임스페이스(namespace)를 반드시 추가해야 합니다. (예: `xmlns:th`).
*   **실제 작동 방식:** Thymeleaf 태그(예: `th:text`)는 브라우저가 직접 동작시키는 것이 아닙니다. 서버 측(Java)에서 Thymeleaf 엔진이 값을 읽어와 HTML을 완성합니다.
*   **데이터 접근:** 템플릿에서 데이터를 출력할 때는 일반적으로 `th:text="${변수명}"` 형태를 사용합니다.
    *   데이터를 설정(Controller)할 때와 템플릿에서 가져올 때, **이름을 일치**시키는 것이 가장 중요합니다. (예: 설정할 때 `message`를 사용했다면, 가져올 때도 `message`를 사용해야 합니다.)
*   **파라미터 접근:** HTTP 요청을 통해 전달된 파라미터에 접근할 때는 `${param.파라미터명}` 형태로 사용할 수 있습니다.

## 2. Spring의 개발 철학: Request 대신 Model 객체 사용
*   **원칙:** Spring은 특정 API(Servlet API, Request 객체 등)에 강하게 종속되는 것을 지양합니다. 따라서 개발자가 `HttpServletRequest`를 직접 사용하여 데이터를 저장하거나 꺼내오는 방식(e.g., `request.setAttribute()`)은 권장되지 않습니다.
*   **권장 방식 (Model 사용):** 컨트롤러에서 데이터를 뷰(View)로 전달할 때는 `Model` 객체를 사용합니다.
    *   `model.addAttribute("키", 값)`을 사용하여 데이터를 모델에 저장하고, 템플릿에서는 `${키}`로 접근합니다.
    *   이는 개발자가 `Request` 객체를 직접 다루지 않아도 데이터를 안전하고 간결하게 전달할 수 있게 합니다.
*   **직접 Request 사용 시:** 필요하다면 요청 객체에 접근할 수 있지만, 가능하면 `Model`을 사용하는 것이 스프링의 철학에 부합합니다.

## 3. 데이터 처리 스코프 이해 (Scope Management)
*   **스코프의 정의:** 스코프(Scope)는 애플리케이션 내에서 데이터를 저장하고 접근하는 범위입니다. 같은 정보도 저장하는 위치(Scope)에 따라 생명 주기와 접근 범위가 달라집니다.
*   **4가지 주요 스코프:**
    *   **Page Scope:** 가장 좁은 범위. 현재 페이지에서만 사용.
    *   **Request Scope:** 가장 일반적. 단일 요청(Request) 처리 과정 동안에만 데이터가 존재하며, 요청이 완료되면 사라집니다. (대부분의 요청 데이터가 여기에 저장됨)
    *   **Session Scope:** 사용자가 로그인하거나 브라우저를 닫기 전까지(세션이 유지되는 동안) 데이터를 유지합니다. (로그인 정보 등 유지되어야 하는 정보 저장)
    *   **Application Scope:** 가장 넓은 범위. 애플리케이션이 살아있는 동안 영구적으로 유지됩니다. (전역 설정 정보 등)
*   **스코프 선택의 중요성:**
    *   요청이 끝나고 사라져야 하는 데이터를 세션 스코프에 저장하면 메모리가 누수(비대화)되어 심각한 성능 문제를 일으킬 수 있습니다.
    *   페이지 포워딩(Forwarding)이나 리디렉트(Redirecting) 같은 흐름 변화가 있을 때도 데이터가 유지되거나 사라지는 스코프의 차이를 정확히 이해해야 합니다.

## 4. Controller에서 요청 파라미터(Request Parameter) 처리하기
*   **`@RequestParam`의 역할:** URL의 쿼리 파라미터(Query Parameter)를 Java 메서드 매개변수(Parameter)로 받아오기 위해 `@RequestParam` 어노테이션을 사용합니다.
*   **필수성 및 기본값 설정:**
    *   **Required (필수값):** 만약 이 옵션을 생략하면 기본적으로 `Required=true`로 간주되어, 파라미터가 필수적으로 존재해야 합니다.
    *   **required=false:** 파라미터가 필수가 아닐 때 사용합니다.
    *   **defaultValue:** 파라미터가 전달되지 않았을 경우 사용할 기본값을 지정할 수 있습니다.
*   **다중 파라미터 처리:** 여러 개의 쿼리 파라미터를 받으려면, `@RequestParam` 어노테이션에 여러 개의 매개변수를 지정해야 합니다.

## 5. URL 매핑 및 시스템 동작 원리 정리
*   **URL Mapping의 중요성:** 애플리케이션의 구조(유저, 블로그, 댓글 등)가 커질수록 URL 규칙을 일관성 있게 관리하는 것이 중요합니다.
*   **클린한 매핑 설계:** 기능별로 주소를 분리하거나(예: `/user/list`, `/user/update`), 또는 핵심 기능 단위로 매핑하는 방식(예: `/user/list`만 사용) 등 일관성 있는 규칙을 적용하는 것이 가독성이 높습니다.
*   **구동 원리 이해:**
    *   Spring 애플리케이션은 단순히 코드가 동작하는 것이 아니라, WAS(Web Application Server)나 톰캣 등의 정해진 디렉터리 구조 내에 올라가서 동작합니다.
    *   코드를 수정하면 변경된 코드를 다시 컴파일하고 서버의 정해진 위치에 다시 올려주는 재배포 과정(배포/재시작)을 거쳐야 변경 사항이 반영됩니다.
*   **핵심 정리:** 웹 개발에서 가장 중요한 것은 각 컴포넌트(Controller, View, Model)와 데이터가 어떤 **범위(Scope)**에서, 어떤 **규칙(Convention)**에 따라 데이터를 주고받는지 그 **흐름(Flow)**을 파악하는 것입니다.

## 1. Spring MVC 아키텍처 이해: 동작 원리
- **필요한 기반 구조:** 웹 애플리케이션이 동작하려면 웹 어플리케이션 서버(WAS) 위에서 약속된 구조와 설정들이 필요합니다.
- **Spring Boot의 역할:** Spring Boot은 웹 애플리케이션 서버 자체를 포함하며, WAS가 가져야 하는 복잡한 설정이나 구조(설정 파일, 구조 등)를 자동으로 구성해주는 역할을 합니다.
- **핵심 구성 요소:**
    - **DispatcherServlet:** 모든 클라이언트의 요청(Request)을 받아 처리하는 단일 출입구 역할을 합니다. WAS가 요청을 받을 때 이 서블릿을 통해 통제 흐름을 시작합니다.
    - **요청 처리 과정:** 들어온 요청을 받으면, DispatcherServlet이 요청의 목적지(어떤 컨트롤러의 어떤 메서드가 처리할지)를 파악하고 적절하게 처리하도록 분배(Dispatch)합니다.
- **구조적 중요성:** 요청이 들어올 때 단일화된 진입점을 통해 처리하는 것이 중요하며, 이 과정을 Spring MVC 프레임워크가 효율적으로 구현하고 있습니다.

## 2. 요청 처리 및 매핑 설정
- **@RequestMapping의 역할:** 클라이언트의 요청이 들어왔을 때, 어떤 URL(경로)과 어떤 HTTP 메서드(GET, POST 등)를 사용하여 해당 컨트롤러의 특정 메서드가 실행되어야 하는지 매핑하는 규칙을 정의합니다.
- **매핑 어노테이션:**
    - `@RequestMapping`: 가장 포괄적인 매핑을 정의합니다.
    - `@GetMapping`, `@PostMapping`, `@PutMapping`, `@DeleteMapping`: 각각 GET, POST, PUT, DELETE와 같은 HTTP 메서드별 요청을 받아들이는 전용 어노테이션입니다. (이는 `@RequestMapping`에 메서드 타입을 지정하는 것과 동일하게 동작합니다.)
- **필수 원칙:** 요청을 처리하려면 해당 클래스에 `@Controller` 어노테이션을 붙여주어 Spring이 해당 클래스를 컨트롤러로 인식하게 해야 합니다.

## 3. 데이터 흐름 관리 및 상태 유지
- **HTTP 프로토콜의 특성:** HTTP는 본질적으로 상태를 유지하지 않는(Stateless) 프로토콜입니다. 즉, 클라이언트가 연속적인 요청을 보내도 서버는 사용자가 누구인지, 이전 요청에서 무엇을 했는지 알 수 없습니다.
- **상태 유지 기술 (State Management):** 사용자의 정보를 기억하고 연속적인 작업을 처리하기 위해 세션(Session)이나 쿠키(Cookie)와 같은 상태 유지 기술을 사용합니다.
- **Request와 Session의 범위:**
    - **`HttpServletRequest` 객체:** 요청이 들어올 때 생성되어 응답(Response)이 나갈 때 소멸되는 '요청 단위'의 객체입니다. 이 객체에 담긴 값은 해당 요청에만 유효합니다.
    - **`HttpSession` 객체 (세션):** 세션 개체가 생성되고 소멸될 때까지 지속되는 '사용자 단위'의 객체입니다. 이 객체에 저장된 값은 사용자의 요청이 바뀌어도 유지되므로, 사용자 정보를 저장하는 데 사용됩니다.
- **Model의 역할:**
    - **공동 사용 공간:** 뷰(View)와 컨트롤러 사이에서 데이터를 공유할 때, 단순한 `Request` 객체에 의존하는 것보다 `Model` 객체를 사용하는 것이 권장됩니다.
    - **구현 원리:** 모델을 사용하면 Spring 프레임워크가 내부적으로 이 모델을 생성하고 주입하여 관리해주기 때문에, 개발자가 데이터 공유를 위해 직접 `Request`를 다루지 않아도 됩니다.

## 4. 다양한 요청 처리 방식 (파라미터 및 매핑)
- **요청 값 받기 (Parameter Binding):** 컨트롤러 메서드가 요청 데이터를 받을 때 다양한 방식으로 값을 추출할 수 있습니다.
    - **`@RequestParam` (Query Parameter):** URL의 물음표(`?`) 뒤에 붙는 `key=value` 형태의 매개변수 값을 받아옵니다. (예: `?searchKey=apple`)
    - **`@PathVariable` (Path Variable):** URL 경로 자체에 포함된 변수 값을 받아옵니다. (예: `/user/{userId}`에서 `{userId}`의 값)
    - **Type Safety 및 필수 여부 설정:**
        - **`required` (필수 여부):** 매개변수가 필수로 와야 하는지 (`true` - 기본값), 아니면 오지 않아도 되는지 (`false`) 설정할 수 있습니다.
        - **`defaultValue`:** 값이 넘어오지 않아도 오류가 발생하지 않도록 기본값을 지정할 수 있습니다.
- **반환 타입 (Return Type):**
    - **`String`:** 단순히 뷰의 이름(View Name)만 리턴합니다.
    - **`Model` / `ModelAndView`:** 뷰 이름과 더불어 `Model` 객체를 함께 리턴하여, 뷰가 사용해야 할 데이터를 묶어서 한 번에 전달하는 것이 효율적입니다.
- **요청 요청의 구분 (GET vs. POST):**
    - **단일 URL, 두 가지 요청:** 회원가입과 같이 사용자 경험상 하나의 폼에서 시작하지만, 실제로는 요청 단계가 다릅니다.
        1. **첫 요청 (GET):** 폼을 보여달라는 요청 (`/user/join` GET 요청). -> 폼 화면 표시
        2. **두 번째 요청 (POST):** 실제 데이터를 전송하고 처리를 요청하는 데이터 전송 (`/user/join` POST 요청). -> 회원가입 로직 실행
    - **분리된 URL:** 이처럼 명확히 역할이 구분되는 경우, GET과 POST를 처리하는 URL 경로를 분리하여 사용하는 것이 구조적으로 가장 바람직합니다.

## 1. HTTP 요청 방식과 데이터 처리 이해 (GET vs POST)
*   **HTTP 메서드에 따른 데이터 전송 방식 차이:**
    *   **GET 방식:** 폼에서 전송된 값은 URL의 쿼리 파라미터(Query Parameter) 형태로 노출되어 전송된다.
    *   **POST 방식:** 폼에서 전송된 값은 URL에 노출되지 않고, 요청 본문(Body) 형태로 전달된다.
*   **메서드 인식의 중요성:** 웹 프레임워크는 URL이 같더라도, 실제 요청 메서드(GET 또는 POST)의 차이에 따라 다른 로직을 수행할 수 있다.

## 2. 요청 흐름 제어: 포워드(Forward)와 리다이렉트(Redirect)
*   **요청 흐름 설계의 원칙:** 하나의 클라이언트 요청(Request)은 하나의 명확한 목적(Action)을 처리하는 것이 가장 바람직하다.
    *   *예시:* 회원가입을 처리하는 요청이 '회원가입 완료 후, 웰컴 화면을 보여줘'라는 두 가지 일을 동시에 처리해서는 안 된다.
*   **Forward와 Redirect의 차이 (핵심):**
    *   **Forward (순방향):** 동일한 요청 객체를 유지하며 내부적으로 다른 뷰(View)나 리소스가 처리된다. URL은 보일지라도 실제 요청 흐름은 바뀌지 않는다.
    *   **Redirect (재지정):** 요청을 받은 서버가 응답으로 새로운 URL을 명시하여 클라이언트에게 알려준다. 클라이언트는 이 URL을 새로운 요청으로 재시도(Re-Request)하게 되며, **이 과정에서 요청 객체 자체가 완전히 교체**된다.
*   **사용 시점:** 회원가입이나 로그인처럼, 처리가 완료된 후 사용자에게 '다음 단계'의 경험을 제공해야 할 때 리다이렉트(Redirect)가 적합하다.

## 3. 객체 설계 및 데이터 바인딩 원칙 (DTO와 Lombok)
*   **복잡한 데이터 처리의 효율성:** 여러 개의 파라미터를 메서드 인자로 받는 것은 코드가 복잡해지기 쉽다.
*   **DTO(Data Transfer Object) 활용:** 요청으로 받은 여러 개의 데이터를 담기 위한 전용 객체(DTO, Value Object)를 정의하여 사용하는 것이 효율적이다.
*   **Lombok의 역할:** DTO를 사용할 때 필요한 게터(Getter), 세터(Setter), 생성자(Constructor), `toString()`과 같은 반복적이고 상용구적인 코드를 Lombok을 이용해 `@Data`, `@NoArgsConstructor`, `@AllArgsConstructor` 등의 애너테이션만으로 자동 생성하여 개발 편의성을 높인다.
*   **`@ModelAttribute` 사용:**
    *   `@ModelAttribute`를 DTO 파라미터에 사용하면, 스프링 프레임워크가 요청 파라미터(Request Parameter)의 데이터를 해당 DTO 객체에 **자동으로 바인딩(자동으로 채워줌)** 해준다.
    *   이 과정에서 프레임워크는 다음 세 가지 규칙을 따르므로, DTO는 적절한 구조(Getter/Setter)를 갖추어야 한다.
        1.  요청 파라미터의 필드명과 DTO 필드가 일치해야 한다.
        2.  필요한 속성에 대해 Getter와 Setter 메서드가 구현되어 있어야 한다.
        3.  (선택적이지만 권장) DTO 객체 생성을 위해 기본 생성자(No Args Constructor)가 필요하다.

## 4. 모델 어트리뷰트와 자동 바인딩 이해
*   **핵심 원리 (요청 객체의 변화):**
    *   `Request Parameter`를 사용할 때는 개발자가 직접 변수 이름을 지정해 값을 꺼내야 하지만,
    *   `@ModelAttribute`를 사용할 때는 스프링 프레임워크가 요청 파라미터의 규칙을 기반으로 DTO 객체를 **자동으로 생성하고 값을 채워준다.**
*   **실무 적용:** 상품 등록이나 회원가입 등 입력 정보가 많은 기능을 구현할 때, DTO와 `@ModelAttribute`를 활용하면 코드의 가독성과 안정성을 크게 높일 수 있다.
*   **결론:** 요청을 처리하는 모든 단계를 모듈화하고, 적절한 데이터를 담을 DTO 객체를 설계하는 것이 가장 깔끔하고 확장성이 높은 구조이다.

## 1. 개발 학습 태도 및 프로젝트 설계 개론
*   **실습의 중요성:** 이론 학습만으로는 실제 개발 역량을 갖출 수 없으며, 개념을 직접 반복적으로 구현하고 경험하는 것이 가장 효과적인 학습 방법이다.
*   **적극적인 질문:** 학습 중 이해가 안 되는 부분은 지체하지 말고 질문하며 해결해나가는 능동적인 자세가 필요하다.
*   **모듈화 및 구조화:** 프로젝트가 복잡해지면 관련된 기능들을 `아이템` 디렉토리, `유저` 디렉토리 등 기능 단위로 나누어(모듈화) 관리하는 것이 체계적이며 바람직하다.

## 2. Spring MVC와 컨트롤러 매핑 이해
*   **컨트롤러의 역할:** Spring MVC에서 특정 기능(예: 아이템 정보 처리)을 담당하는 로직을 컨트롤러 클래스 내에 구현해야 한다.
*   **필수 요소:** 클래스에 반드시 `@Controller`를 붙여야 Spring Framework가 이를 빈(Bean)으로 인식하고 기능을 수행할 수 있다.
*   **URL 매핑의 중요성:** `@RequestMapping`과 같은 어노테이션을 사용하여 해당 컨트롤러 메서드가 어떤 URL 요청(예: `/item`)에 반응할지 명확히 정의해야 한다.
*   **URL 설계 원칙:**
    *   `GET` 방식은 리소스의 조회(읽기) 요청에 사용하고, `POST` 방식은 데이터 생성(쓰기) 요청에 사용하도록 메서드와 URL을 분리하여 설계하는 것이 명확하다.
    *   (권장 방식) `item/add`와 같이 리소스명과 기능을 조합하여 URL을 일관성 있게 설계하는 것이 좋다.

## 3. 레스트(REST) 기반 API 설계 원칙
*   **개념:** RESTful은 클라이언트와 서버 간의 통신에 있어 **정해진 약속(규약)**을 가지고 정보를 제공하는 방식이다.
*   **의미 전달:** URL과 HTTP 메서드를 통해 요청의 의도가 명확히 전달되어야 한다.
    *   *예:* `/users` (리스트 조회), `/users/{id}` (특정 사용자 조회/수정), `POST /users` (사용자 생성).
*   **MVC 구현 흐름:**
    *   **GET 요청:** 리소스 조회 (폼 화면 로드 또는 리스트 보여주기).
    *   **POST 요청:** 데이터 제출 및 처리 (실제 데이터베이스에 정보 저장).
    *   **결과 처리:** 데이터가 성공적으로 저장된 후에는 일반적으로 요청을 받았던 페이지가 아닌 다른 화면(예: 성공 메시지 또는 리스트 페이지)으로 **리다이렉트**하여 보여주는 것이 좋다.

## 4. Thymeleaf 템플릿 엔진 활용 심화
*   **역할:** Thymeleaf는 서버에서 데이터를 받아 HTML을 동적으로 생성해 주는 템플릿 엔진이다. (브라우저에 값이 채워진 최종 HTML을 보내줌).
*   **데이터 전달 및 활용:**
    *   컨트롤러에서 처리한 객체(예: `List<Item>`)는 `Model` 객체를 사용하여 View (템플릿)에 전달해야 한다.
    *   템플릿 내부에서는 `${속성명}` 형태로 전달받은 변수에 접근하여 데이터를 출력할 수 있다.
*   **리스트 반복 처리 (`th:each`):**
    *   리스트 형태의 데이터를 페이지에 표시할 때는 반드시 `th:each` 반복문을 사용해야 한다.
    *   `th:each` 구문의 문법은 `th:each="변수명 : 컬렉션명"` 형태로 사용하며, 반복 시 현재 요소를 `변수명`으로 가져와 사용한다.
*   **표(Table) 구조화:** 리스트를 테이블로 출력할 때는 `<tr>` 태그를 `th:each`로 감싸서 반복시키고, `<td>` 태그 내부에 데이터를 출력하는 것이 일반적이다.
*   **설정의 이해 (Spring Boot):**
    *   Spring Boot은 개발자가 설정하지 않아도 `prefix` (접두사)와 `suffix` (접미사)를 기본적으로 설정해 주어 뷰를 찾는다. (예: `classpath:/templates/`)
    *   개발자가 직접 설정을 변경하여 뷰 파일을 다른 디렉토리에서 찾도록 지시할 수 있다.

## 5. 전체적인 데이터 처리 흐름 및 학습 방향
*   **요청-응답 흐름 이해:** 현재 학습의 핵심은 **요청(Request)과 응답(Response)의 흐름**을 이해하는 것이다. 클라이언트의 요청이 컨트롤러를 거쳐 데이터를 처리하고, 다시 뷰를 통해 화면으로 돌아오는 전체 과정에 대한 이해가 필수적이다.
*   **CRUD 구현 연습:** 아이템, 유저 등 여러 도메인에 대해 데이터를 생성(Create), 조회(Read), 수정(Update), 삭제(Delete)하는 **CRUD** 로직을 반복적으로 구현해보는 것이 가장 중요하다.
*   **지속적인 연습의 필요성:** 기술적 지식은 눈으로 보는 것만으로는 습득되지 않으므로, 본인이 직접 코드를 작성하고 오류를 해결해나가는 실습 과정을 반복해야 한다.
*   **심화 목표:** 궁극적으로는 서비스 레이어와 데이터베이스까지 연결하여 실제로 데이터를 영구적으로 저장하고 조회하는 과정까지 확장하여 학습하는 것이 목표이다.
